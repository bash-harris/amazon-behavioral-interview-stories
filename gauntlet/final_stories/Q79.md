# Q79 - tell me about a project where you did something exceptional
**LP:** Deliver Results (primary); Insist on the Highest Standards; Think Big.   **Story:** STORY 4/15 - shipping the whole PCB suite as one offline standalone HTML file; the *exceptional achievement* telling, distinct from Q8 (solo completion), Q29 (WASM blocker), Q31 (deadline build turnaround), Q49 (above-and-beyond), and the Q27/Q65 numbers (engine, classifier - separate ledgers).

## Core Answer

The project I'd call exceptional is the one where I deleted the server. My PCB inspection suite - a PCB is the green circuit board inside almost every electronic device - doing BOM (parts-list) reconciliation, board-layout comparison, image alignment, and defect classification, built solo - originally ran on a server (Flask: a small program that hosts the tool on one central computer). I rebuilt the whole thing as a single HTML file - one web file that opens in a browser - an engineer double-clicks, and shipped it onto factory-floor machines with no internet, no install rights, and barely any IT. The exceptional part wasn't a feature. It was the direction, and the bar I held it to.

The easy path was to keep polishing the server deployment. I argued myself out of it: a tool that can't run where the engineers work is a demo. So every dependency had to travel inside the file. The hard one was the computer-vision library - it loads its WebAssembly binary by fetching it (WebAssembly is a compact block of pre-compiled code a browser normally downloads before running), and offline there's nothing to fetch. I embedded the binary in the page and rewrote the loader to decode it at startup. The model weights - the numbers the AI learned during training - became a constant in the file, a fixed value baked into the code. Auto-save moved from the server's disk to the browser's own storage (saved on that one computer, not a server), with a quota check - the cap on how much a browser is allowed to save - so a full store drops the oldest inspection instead of losing the newest one. One file, tens of megabytes, opens in seconds. To put that in plain terms: "tens of megabytes" is roughly the size of a few phone photos, and "opens in seconds" means seconds from the double-click to a usable screen - how I remember it, not a benchmarked measurement.

What I refused to accept was "it opens" standing in for "it works." I ran the same known boards through both builds and compared the outputs - the reconciliation reports, the alignment, the model's verdicts - with a small automated diff to flag anything that didn't match (a simple script that compares the two outputs and points out every difference). The packaging step, which had been manual and broke often, became one deterministic command - one command that gives the identical result every time. Same suite, same answers, zero infrastructure.

Then the part that made it matter: it reached the people it was built for. About 15 manufacturing engineers across two sites, who told me it saved them roughly 20 hours a week. In plain terms: the 15 counts how many people used the suite, and the 20 hours is their own spoken estimate of the time it gave back - reported to me, never instrumented by me. I distributed it by email and USB; the handoff was two words - "double-click this." A full inspection suite in their hands with nothing behind it.

The honest learning is about order. I built server-first and retrofitted the server out of it, and the retrofit is what made the file big enough to bump email attachment caps - the maximum size an email inbox can receive. Standalone-first would have been the cleaner architecture. I'd still defend the direction; I wouldn't repeat the order.

## Memory Anchors
- Problem: a working CV+ML suite (image analysis + AI) lived behind a Flask server (a program running the tool on one central computer) its users couldn't run - factory-floor machines, no internet, no installs, minimal IT; polish was the default, delivery was the gap.
- Customer: manufacturing engineers on locked-down factory-floor machines across two sites (suite built solo).
- Insight: exceptional = the call to delete the running server and commit the whole suite to one self-contained file - plus refusing "it opens" as proof of "it works."
- Action (mine): embedded the WebAssembly binary (a compact block of pre-compiled code) as base64 (a way of dressing a binary file up as text so it can sit inside a text file) and rewrote the loader to decode at startup; model weights (the numbers the AI learned) baked into the file as a constant (a fixed value in the code); auto-save moved to browser storage (saved on that one computer, not a server) with quota handling (drop oldest, never lose newest); known boards re-run through both builds with a small automated diff (a script that points out output differences); packaging automated into one deterministic (identical every time) command; distributed by email and USB.
- Result: one double-click file, tens of megabytes, opens in seconds, full suite offline; ~15 engineers / two sites, ~20 hrs/week - engineer-reported (their words about their own time, not something I measured).
- Learning: I'd defend deleting the server forever, but should have designed standalone-first - the retrofit caused the size/distribution pain.

## Follow-Up Bank
1. What's "exceptional" about an HTML file? The output sounds mundane. - The output is mundane; the constraints weren't. A computer-vision and machine-learning inspection suite that normally wants a server and a Python install (a helper program that has to be installed on the machine), running fully offline from one double-clicked file on locked-down machines. Full capability where the environment allowed none. [SAFE]
2. How is this different from just packaging an app? - Packaging assumes a runtime. There was none to assume: the WASM loader (WebAssembly - the compact block of pre-compiled code a browser downloads and runs) had to be rewritten to decode an embedded binary, the model weights (the numbers the AI learned) had to become a constant in the page (a fixed value inside the file), persistence had to move into browser storage (saved on that one computer, not a server) with quota handling. Every dependency was a design problem, not a bundling step. [SAFE]
3. What did it cost? - Startup pays to decode the embedded libraries and model - the browser unpacks the embedded code and the AI before the tool appears; the server build opened faster; I kept the numbers deliberately soft because they're my recorded account, not a benchmark. The file got big enough to brush email caps (the maximum size an email inbox can receive). Cost was real and taken on purpose: a slower tool that runs beats a fast tool nobody can open. [SAFE - soft by design]
4. Why not fix the deployment instead - installer, Docker, IT ticket? - An installer or container (Docker: a packaged app that needs special software installed first) needs install rights the machines didn't have; IT was stretched too thin for tickets the team couldn't absorb. Separate bundled files break the one-file rule - move one and the tool dies, the exact failure I was removing. A service worker (a browser feature that lets a page work offline on its own) needs HTTPS (an encrypted web address) to register, which the floor didn't have configured. [SAFE]
5. How do you know the standalone matched the server version? - I ran the same known boards through both builds and compared the outputs - reconciliation reports, alignment, classifications - with a small automated diff flagging anything that didn't match (a simple script that compares two outputs and points out every difference). Known-board set, not a measured sample: I quote no parity percentage (no "X% of outputs matched" figure exists). [SAFE]
6. Where did 15 engineers / two sites / 20 hours come from? - Engineer-reported: distribution was by email and USB, and the users told me the reach and the savings. Their estimate of their own time, not instrumented - 15 is how many people used it, two sites is where, and ~20 hrs/week is what they said they saved, nothing I logged or measured - I'd defend the headcount, and I'd qualify the hours the second they're probed. [PARTIAL - engineer-reported]
7. Isn't build turnaround / the load failure your other story? - Same project, different moment. How the offline load failed and how I diagnosed it is one story; how the manual packaging threatened a deadline is another. Here the center of gravity is the bold call plus the quality bar plus the reach - those stories' numbers (timings, failure rates) don't appear in this one. [SAFE - separate ledgers]
8. Hardest part? - Not the code. Committing to delete a working server version I was proud of, against my own default that tools ship on servers - and then refusing to accept a demo that merely opened. [SAFE]
9. Did anyone disagree with you? - Solo project; I won't invent a scene. The disagreement was with my own default assumption, and the won/gave-up list is that argument written down. [GAP - no documented conflict, stated plainly]
10. Did it run on every machine? - It needed a WebAssembly-capable browser (a browser new enough to run that pre-compiled code block); machines without it got a clear startup error instead of a half-working tool. That environment-assumption miss is a separate story I tell for itself - one cross-reference, no retelling. [SAFE]
11. What happens at 10x - a hundred machines? - Per-user load is the whole point: fully client-side (everything runs on each user's own machine, nothing on a shared server), ten times the engineers breaks nothing I maintain. The ceilings are organizational: fixes require re-distributing the file, and nothing aggregates across machines. My read, not something I load-tested (I never ran a simulated multi-user test). [PARTIAL - qualitative reasoning]
12. Do differently? - Design standalone from day one instead of retrofitting it out of a server build; compress the embedded libraries (pack them smarter so the file shrinks) so the file clears email caps; add a checksum (a digital fingerprint that shows up when a copy is corrupted) and a between-builds diff so corruption is caught by the tool instead of by me. The direction I'd keep; the order I'd fix. [SAFE]
