# Q35 - a time when you worked on something outside your comfort zone

**LP:** Learn and Be Curious   **Story:** Tab Scroller (personal Chrome extension, Manifest V3 + LLM command layer) - distinct axis from Q21's vision-math learning

## Core Answer

The hardest part about building Tab Scroller wasn't any one feature. It was that I left the kind of program I actually knew. Everything I'd built before was a single self-contained page - one document, one context, deterministic in, deterministic out. This was a Chrome extension, Manifest V3, and it broke both assumptions at once: my program doesn't stay alive, and a language model sometimes decides what happens next.

I found the first problem the hard way. The feature was tab snoozing - close a tab now, it reopens at a time you pick. My first version set a timer inside the background script, which looked right in testing. Then I closed the browser and the snoozed tabs never came back. In MV3 the background script isn't a process you own; the browser tears it down whenever it likes, and my timer died with it. So the climb was learning to trust state I don't hold. I rebuilt it on chrome.alarms - a one-minute tick the browser owns - and moved the snoozed tabs into extension storage as url, title, and wake time, re-opening them as background tabs when the time comes. It survives restarts because nothing depends on my code being alive at the wrong moment.

Then came the AI command layer, which was its own discomfort. You type "close all my YouTube tabs" and the model maps words to a browser action. The output isn't a number on a screen - it's something that can erase your work, and a confident wrong answer is destructive. The local model I tested was flakier than I expected too; it sometimes wrapped its JSON in polite prose and my parser choked. Temperature zero and a fallback that digs the JSON out of the text fixed that, but it taught me not to give the model the whole blast radius. Simple commands are answered by local rules and never reach a model; what does reach it sees only a pre-filtered slice of relevant tabs.

What I can do now that I couldn't before: design for a program that might not be running when it's needed, and treat a model as one unreliable part inside a deterministic envelope instead of the brain of the thing. I also know where my line is now - destructive actions should have shipped with confirmation and undo. I designed that, didn't build it, and I say so plainly.

## Memory Anchors
- Problem: left my familiar world - single-page, deterministic tools - for a stateless MV3 extension with an LLM choosing browser actions
- Customer: me as the user; the real risk was the user's open work (tabs) destroyed by one confident wrong model call - no adoption claims, personal build
- Insight: two discomforts on different axes - (a) code that isn't continuously running, (b) a probabilistic model in a destructive control path; the fix for both is "don't hold it yourself, bound it"
- Action (mine): failed first with an in-worker timer for snoozing, rebuilt on chrome.alarms + storage ({url, title, wakeTime}, 1-min tick, restart-safe); routed simple commands to local rules; pre-filtered tab context; temp 0 + regex-JSON fallback for Ollama; cloud Gemini and local Ollama both supported
- Result: snooze survives browser restart; model sees only a reduced, relevant slice and is the last resort, not the first hop; guardrail design (confidence bands, undo, telemetry) exists on paper, not in the build
- Learning: when a model is in the control path, the work isn't prompt tuning - it's the deterministic envelope around it; and confirmation/undo are part of a destructive feature, not polish

## Follow-Up Bank
1. What exactly was unfamiliar? - Two things: the MV3 execution model (service worker torn down between events, message passing, no long-lived state) and putting a probabilistic model where a crash isn't the failure mode - closing the wrong tabs is. [SAFE]
2. Walk me through that first failure again. - I wrote snoozing the obvious way: schedule a wake-up from inside the background script. It worked while the browser stayed open and silently did nothing after a restart, because the worker and its timers were gone. That's my own build-process recollection, not a logged incident - but the shipped design is the evidence: alarms plus storage exist precisely because process-held state doesn't. [PARTIAL - personal observation, not instrumented]
3. Why alarms specifically? - It's the platform's own scheduler: the browser owns the wake-up, and storage is the only state that outlives the worker. The design question changed from "what's my state?" to "who wakes me up, and what's on disk before I stop running." Built in three iterations - alarm/storage engine, message handler, context-menu UI. [SAFE]
4. Why use an LLM at all instead of rules? - Useful requests are open-ended ("group my travel research"); hardcoding phrasings is linear effort against unbounded input. So rules are the default and the model handles only the residual. [SAFE]
5. What stops the model from doing something destructive? - In the build: routing (simple commands never call a model) and a pre-filter narrowing the tab set by domain category and keyword, plus parallel metadata extraction. Designed but NOT shipped: confidence gate (>=0.75 auto-execute, 0.4-0.74 confirm, <0.4 clarify), transactional undo for closes, telemetry. I state that gap rather than imply protection that isn't there. [PARTIAL - honest split between shipped and designed]
6. I see big perf numbers in your docs - measured? - No. The 50k->3k token reduction, 8s->3s and 5s->0.5s timings, and ~70% offline coverage are design targets from my implementation guide, not measurements. The measured behavior I can speak to is qualitative: rule path handles common commands with zero API calls. [SAFE - labeled as projected]
7. Who used this? How many users? - It's a personal build. I'm not claiming adoption numbers, internal or public. [SAFE]
8. Why carry both Gemini and Ollama? - To find the fallback boundary by testing, not assuming - provider availability and the user's tab data leaving the machine. Which one runs is a settings choice, not a rewrite. [SAFE]
9. What actually broke with the local model? - It sometimes emitted prose around its JSON, which failed strict parsing. Fix was temperature 0.0, a JSON response format, and a regex extraction fallback. Small thing, but it's where I learned to treat model output as untrusted input. [SAFE - fallback exists in the code]
10. Hardest part? - Unlearning the assumption that my code is always running. Every design decision after that followed from it. [SAFE]
11. Do differently? - Ship the guardrails with the action layer, not after it. The moment a model picks destructive actions, confirmation and undo are the feature. [SAFE]
