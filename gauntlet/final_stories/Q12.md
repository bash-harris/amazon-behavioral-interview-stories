# Q12 - tell me about how will you communicate if you think you will miss deadline

**LP:** Bias for Action (primary); Deliver Results; touches Earn Trust.   **Story:** The Flask-to-single-file rollout blocker named ~3 weeks before a committed line pilot (PREP STORY 4), contrasted with the copied-tool fork that "bought a deadline and cost six months" (BAR_RAISER_TECHNICAL_PREP).

## Core Answer

I flag the moment I can name a specific blocker and what it costs - not when the date passes. The message has five parts: the blocker in one sentence, what slips and by roughly how much, two or three options with their trade-offs, my recommendation, and the date I'll know more by. Then I commit to whatever gets decided.

Here's the case where it mattered. The inspection suite - my tools that photograph a finished circuit board and check it against the design - ran on a Flask server (Flask = a standard program that hosts the tool's logic on one central computer that everyone else connects to), and a pilot - a live trial on the actual production line - was locked in for the end of the project's eight-week arc. With about three weeks left - that's my own read of how far the risk was visible before the date, not a calendar record - I walked the deployment plan end to end and hit the blocker: every machine that wanted the tool needed a Python install, dependencies, and network configuration - Python is the programming runtime the server runs on, dependencies are the extra software pieces it needs, and network configuration is per-machine plumbing; and the factory-floor machines were locked down, no installs without a change request (a formal, scheduled IT approval ticket before anyone may alter one of those computers), thin IT support. I sent the sponsor and my manager the five-part note: blocker; impact - at the IT change-request cadence across the two sites, that's a slip of roughly a month, possibly more (a rough estimate from how long such tickets had taken before - order of magnitude, never a measured figure); options. One, run the pilot on the handful of machines IT could touch by the date - partial, but it keeps a demo honest. Two, I rebuild delivery as a single file an engineer opens in a browser - one file, double-clicked, that works like a web page with no server and no install at all, but it's my time with zero buffer. Three, slip the pilot a month and do the server installs properly. My recommendation was two, with option one wired in as a trip-wire (a pre-agreed trigger point: if a check fails by a set date, the fallback decision fires automatically instead of someone having to ask): if the single file couldn't run on a floor machine by the Friday before pilot week, I'd say so the same day and we'd switch. It ran with two days to spare. The pilot held its date, nothing went through IT, and the handoff became "double-click." The real costs, named up front and again after: every fix means re-sending the file, and it still pulls its libraries from the network - I don't pretend it was fully offline.

The flip side is what I learned on. For the second tool I needed it working that week, so I copied the first instead of having the options conversation. That shortcut bought a deadline and cost six months of divergence - two different anomaly formulas between the tools (an anomaly formula is the rule the software uses to decide when a board counts as faulty; two tools, two different rules, same job). Early flag or not, the debt always sends the invoice.

## Memory Anchors
- Problem: Committed line pilot at the end of the 8-week arc; deployment plan required per-machine Python/Flask installs on locked-down factory machines with thin IT.
- Customer: Manufacturing engineers on the floor; the sponsor in manufacturing engineering who asked for the BOM-vs-layout check (BOM = bill of materials, the parts list a board should carry; the check compares that list against the board's design drawing).
- Insight: A date is hostage to the deployment path, not the code - so a named blocker with a consequence, options, and a recommendation is what the stakeholder needs, while there's still a choice.
- Action (mine): Sent the five-part flag ~3 weeks out (blocker -> ~1-month impact -> 3 options -> recommend single-file rebuild with partial-pilot trip-wire -> know-by Friday); rebuilt delivery as one browser-openable file; shipped tool two by copying tool one without the conversation.
- Result: Pilot held its date; rollout needed zero IT tickets; handoff became "double-click." The fork cost six months of divergence, including two anomaly formulas.
- Learning: Price a shortcut before taking it, not after; every flag needs a trip-wire so the stakeholder knows when the fallback fires without asking.

So every rollout became a ticket queue the manufacturing team couldn't absorb, and the pilot date rode on it. [SAFE - documented in STORY 4's situation]

Content: one-sentence blocker; impact; three options with trade-offs; my recommendation; the date I'd know more; and the trip-wire - the pre-agreed trigger that says "if this check fails by this date, we switch to the fallback." It was email - the channel they'd answer on the floor. [PARTIAL - sponsor/manager roles are a reconstruction; the docs record the users and the event, not the recipient list or the message itself]

Change requests were handled in scheduled windows (fixed slots when IT was allowed to modify the locked machines) and the two sites couldn't be batched together; on the cadence I'd seen requests move at, site coverage plus training wouldn't land before the pilot and would clear in about the following month. Rough on purpose - the point of an early flag is the order of magnitude, not the decimal. [PARTIAL - defensible estimate; method stated, no instrumented figure exists]
4. Was "three weeks before the pilot" really when you flagged it? - It's the account that fits the arc: the deployment path was settled mid-project, the pilot sat at the end of the 8-week plan. Calendar dates weren't recorded, so I keep it relative - three weeks out - rather than invent a date. [PARTIAL - reconstructed timing, labeled]
5. Why not option one or three? - Option one (handful of machines) proved the tool but proved nothing about rollout - the whole point was zero-install delivery. Option three traded a month of the factory's time for an install path the machines were never going to allow cleanly. Option two spent only my risk, and I attached the trip-wire so it wasn't a blind bet. [SAFE - reasoning; options framing is prepared-practice detail on a documented event]
6. Did a date ever actually miss? - No. I can't show you a blown deadline; what I can show is the shortcut I took without pricing it: tool two copied from tool one to hit "working that week," and my notes record six months of divergence, two different anomaly formulas - two different rules for deciding what counts as a fault - before reconciliation. The flag I didn't send then is why I send it now. [SAFE for the fork (documented); GAP honestly stated on any blown date]
7. Another case of naming rework cost early? - My first model training run hit 99% training but 72% validation - meaning it scored high on the images it had studied and low on fresh images it had never seen, which is overfitting (memorizing the study examples instead of learning the pattern), not shippable. I rebuilt it with two-phase progressive unfreezing - a retraining schedule that thaws a pre-trained image model for further tuning stage by stage instead of all at once - and reached 94% on the ~300-image holdout (a held-out set = the ~300 example photos deliberately kept back from training so accuracy is scored on things the model never saw; that 94% is counted on those 300 fresh images), ~45 ms inference (about a 20th of a second for the model to judge one board image), retraining ~30 minutes (my laptop time per full retrain). The schedule move was naming the rework and its cost instead of absorbing it silently into the date. [PARTIAL - documented run figures from the story bank, validation on the holdout; the "named it early" framing is practice, not a transcript]
8. What was the biggest unknown on the 8-week plan? - CAD/Gerber parsing - reading the engineering design files a board is built from (CAD = the design drawing format; Gerber = the standard file format PCB factories actually machine from). I integrated an existing open-source parser - a free, community-built file-reader - instead of writing one; my notes record that as saving 2-3 weeks - an estimate of avoided build time, not a measurement. Avoiding that risk is a big reason there was slack to spend on the delivery rebuild. [PARTIAL - documented estimate]
9. How do you avoid crying wolf? - Flag on a named blocker and its consequence, not on a "maybe." Uncertainty without a consequence stays on my own list until I can pair it with an option and a recommendation. If the picture changes after I flag, I re-flag with a revised plan - silence after a flag is what burns the trust. [SAFE - the mechanism]
10. What if they'd kept option three - slipped the date - instead? - Then I commit and make it work, and I write the accepted trade-off down so it's a conscious choice, not a drift. The trip-wire still stands: it tells me when the agreed plan stops being viable. [SAFE]
11. Can you show me the single file? - Yes: one checked-in HTML file (a single web page you open by double-click), ~4.6 MB (the file's actual disk size - one countable, verifiable figure from the artifact itself), model embedded (the image-recognition model's pattern data is packed inside the file), no server, no install - but it loads its generic libraries from a CDN - a CDN is a shared internet service that hands out common code files, so the file still reaches out to the network when it opens - hence I don't claim a fully-offline build and don't quote the old ~25 MB embedded size or load-time figures my notes carried. Same rule as my standalone story: one verifiable number, no inherited ones. [PARTIAL - artifact-backed; conflicting figures dropped]
12. Hardest part / where'd you disagree with yourself? - Making the uncomfortable note when the news was mine: "the plan you liked is the one that slips." I also disagreed with my earlier self that a shipped copy is harmless - six months of divergence proved it's debt. [SAFE]
13. At larger scale? - Same message, shorter loop: five-part updates on a fixed cadence so an early flag is routine traffic, not a red alert, and a fork gets a merge-back deadline the day it's created - that deadline is the one thing my copy didn't have. [SAFE]
