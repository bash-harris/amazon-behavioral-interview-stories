# Q87 - describe a time when you optimized the performance of an application

**LP:** Dive Deep (primary - located the cost by stage before touching it); Invent & Simplify (deterministic shortcut in front of the model); Deliver Results (common case made cheap inside the extension's constraints).   **Story:** Tab Scroller - the AI command pipeline's latency breakdown and the staged fix (`IMPLEMENTATION_GUIDE.md` "Expected Performance Gains" + `background.js`). Same project as Q66, different spine: Q66 is the routing/simplification arc and owns the token-and-cost headline; this one is *where the seconds actually went*.

## Core Answer

The application was the AI command layer in Tab Scroller - the part that turns a typed instruction into an action - my Chrome extension (a small add-on that adds features to the Chrome browser), and the performance problem was that every typed command cost the same whether it was trivial or hard.

You'd type "group my coding tabs", and it read every open tab, pulled the full text of each page, and sent the whole pile to the model (the online AI service that reads the text and replies with what to do). On a window full of tabs that ran about eight seconds.

My instinct was that the model was slow. I looked instead at what happened before the model call, and the split wasn't close: roughly five of those eight seconds were just reading pages, one at a time - the software copying each page's text off the screen, not the AI taking that long to think. The model was being handed the body text of every page to answer a question that needed titles and URLs.

That reframed the job. The expensive work sat in front of the inference (before the AI was even asked), so I cut it in the order the stage breakdown suggested. Reading first: pull page data in concurrent batches - a handful of pages at the same time - instead of one page after another, which took five seconds down to about half a second. Then read less: a deterministic pre-filter - a fixed word-matching shortcut with no AI in it - scores tabs against a fixed category map and keywords before any extraction happens, so the model sees the relevant handful instead of everything. Then, for commands whose shape is predictable, a local rule layer - simple built-in shortcuts that run directly on the user's own computer - matches and runs them on the machine with no API call at all (no round-trip to an online service).

Those before-and-after figures are the projected gains written in my implementation guide - design targets I set before building, not a benchmark (a formally recorded timing test) I re-ran - and I keep saying it that way. What is real in code is the shape of the fix: extraction does batch, the pre-filter does run before extraction, and the rule path does make zero calls.

The trade-off I took was keeping the pre-filter dull. Keyword and category scoring will miss a fuzzy request; I accepted that instead of pulling in local embeddings - a small word-similarity AI running on the user's own machine - because a miss only means the filter keeps more tabs. It fails toward slower, never toward wrong. Embeddings are the next phase, once telemetry (the app's own timing logs) shows they earn their weight.

And that's what I'd change: I optimized before I could see. There's no per-stage timing or token logging, so every gain is designed rather than measured. Next time I instrument first, then tune.

## Memory Anchors
- Problem: one uniform path - a typed command cost the same whether it was "close YouTube tabs" or a fuzzy grouping request; slow, and dead without network.
- Customer: heavy tab user (me); the value was a command that answers fast enough to keep using.
- Insight: the model was not the bottleneck - most of the time was pre-inference work (sequential full-text extraction of tabs that didn't matter), so optimize stages in cost order, not the obvious suspect.
- Action (mine): traced the path stage by stage; concurrent batched extraction; deterministic keyword/category pre-filter ahead of extraction; local rule layer for pattern-shaped commands; compressed prompts behind that.
- Result: extraction projected 5s -> ~0.5s and the command off the model path entirely for predictable requests - the guide's "Expected Performance Gains", labeled projected; the shipped code is the real claim.
- Learning: measure before you optimize - no per-stage telemetry means my wins are designed, not proven; instrument first next time.

Typed command -> query all open tabs -> extract full page text per tab -> prompt to Gemini (Google's online AI service) or local Ollama (free software that runs an AI model on your own computer instead of online) -> action. The whole path is mine; solo build. [SAFE]
2. How did you find the real bottleneck? - By attributing cost to stages rather than timing the total: the before path queried every tab and extracted text sequentially (one tab after another), so a five-second read step sat in front of an inference (the AI's own answer step) that only needed titles and URLs. That reading of my own pipeline is the dive; the per-stage magnitudes come from the guide, and I don't upgrade that to instrumentation. [PARTIAL - state the method honestly]

The table's headline pairs - a busy-window command about 8 seconds down to about 3, and the page-reading step 5 seconds down to 0.5 - are those targets. The only concrete timing artifact in my notes is a batching check expected to finish ten tabs in around half a second against 5+ seconds sequential - an expectation printed by the test, not a recorded benchmark (a formal, logged timing run). Mechanisms are verified in code; magnitudes are projected. [SAFE - labeled]
4. What's the baseline built on? - Extraction: a per-tab text budget in the code (roughly 1,600 characters per page - a cap on how much text gets copied from each page) times every open tab, done one tab at a time. Token side (tokens = the units an AI service counts and bills text in, roughly word-fragments; kept out of the core so it doesn't collide with Q66): ~1,000 tokens of page text per tab across a fifty-tab window plus the prompt -> ~50,000 tokens before, ~3,000 after, ~$0.50 -> ~$0.03 per query (the price of one command, at the guide's assumed rates). All projected arithmetic on budgeted token counts, never billed traffic. [PARTIAL - estimate, say so]
5. Why batches of ten? - It's the concurrency cap in the code (the maximum number of pages read at once). Low enough not to thrash the browser's tab messaging and get throttled (the browser slowing or dropping the flood of requests), high enough that a filtered set resolves in one or two rounds. I'd tune it against telemetry, which is exactly what I didn't have. [SAFE]
6. How does the pre-filter work with no model? - Deterministic (same input always gives the same result - no AI guessing): a fixed category-to-domain map (coding, video, news, shopping, social, docs, work, learning) plus keyword scoring on titles and URLs; keeps the top ~30% with a floor of five and a ceiling of thirty (never fewer than five tabs, never more than thirty); if nothing scores, it falls back to the full tab set - the safety net is that when the shortcut finds nothing, the AI still sees everything. Runs before extraction, sub-millisecond (far faster than a blink - effectively instant), zero tokens. The guide's own example narrows fifty tabs to eight. [SAFE]
7. What if a rule doesn't match? - The rule set is deliberately narrow (group/close/bookmark/pin/mute by named site, duplicates, cluster by domain, inactive tabs). No match returns null (the code's way of saying "no answer") and the command falls through to the AI path. The failure mode is "slower," never "wrong." [SAFE]
8. Why not just use a faster model? - Because the request distribution isn't the cost driver; the pre-work is. A faster model still pays for fifty sequential page reads and a huge payload (bulk of text shipped over the internet to the AI service), still costs money, still needs the network, and still answers pattern questions with language understanding. [SAFE]
9. Alternatives rejected? - Embeddings in the pre-filter (Phase 2 - converting words into number-lists so the computer can judge how alike two things are in meaning; heavier than the problem, and it would run on the hot path - the step the user actually waits on - I was trying to shorten); batching alone with no routing (still calls the model for "close YouTube tabs"); dropping the AI path for speed (loses the fuzzy commands that genuinely need it). [SAFE]
10. How does it hold up at more tabs? - The expensive steps are bounded by the filtered set (capped five to thirty), not the total; extraction runs concurrently; prompts carry compressed subject-predicate-object triplets rather than page text - tiny "what-acts-on-what" summaries of each page instead of the whole text. That's design intent, exercised at my own window size - not a load test (a formal stress run at bigger scale). [SAFE - say "design intent"]
11. What went wrong, hardest part? - Ordering. I restructured the pipeline before I had any per-stage observability (the app's own logs of where each command's time goes), so I can describe the fix precisely but can't prove the saving. Hardest judgment call was what *not* to automate: keeping rules conservative so ambiguity falls through. [SAFE]
12. Who disagreed? - Nobody. Solo project; inventing a stakeholder fight would be a lie. The disagreement I handled was with my own first conclusion ("the model is slow"). [GAP - stated plainly]
13. Offline? - Routing the predictable commands locally means the common case works with the network off; the ~70% share is an estimate against my own command habits (roughly seven in ten of my typed commands are the predictable kind), no telemetry (timing/usage logs) exists, and Q66 carries that figure so I don't double-count it as a second result. [PARTIAL - estimate]
14. Can you show me the code? - Yes: the pre-filter, batched extraction, rule matcher and triplet compressor are defined and wired into the command handler (connected so the running code actually calls them) in the background worker, with console logging per stage (timing notes the code writes to a developer's debug log) - that logging is the seed of the telemetry I wish I'd built first. [SAFE]
15. What's next / do differently? - Per-stage token and latency telemetry (logging how much text each step sends and how long it takes), then replace keyword scoring with local embeddings only if the numbers justify it, plus progressive context disclosure (sending the AI only the information each decision needs, a little at a time) so even the AI path sends only what the decision needs. Instrument, then tune. [SAFE]
