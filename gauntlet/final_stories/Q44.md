# Q44 - tell me about a project where you had to learn a new skill and eventually excelled at it

**LP:** Learn and Be Curious (primary); Deliver Results (the excelling evidence).   **Story:** BGSW PCB Inspector Suite - the defect classifier I taught myself to train (PREP STORY 3, training arc from STORY 14; canonical ~300-holdout telling).

## Core Answer

Before this project I had ML theory (machine learning - software that learns a task from examples instead of hand-written rules) and zero shipped models. The PCB inspection suite needed a defect classifier - a cropped component photo sorted as good, wrong value, wrong orientation, or missing (in plain terms: software that looks at a photo of one circuit-board part and files it into a category). The bar was explicit, set by what the floor needed: high accuracy on held-out data - photos the model never studied during training, so the score is honest - fast enough to keep up with the line (the factory's production pace), and retrainable when new defect types appeared (able to learn a new fault later without rebuilding the system). I had to learn the whole discipline - data, architecture, training, deployment - to clear it (from preparing the photos, to picking the model design, to teaching it, to shipping it).

I learned in the order the problem demanded. I read across model families - ResNet, EfficientNet, vision transformers (named designs for image-recognition networks, like choosing between engine models) - and chose against my actual situation: a few thousand small images, no big compute (no bank of graphics cards). Transformers want far more data than I had. The smaller EfficientNet variant gave nearly the accuracy of the big one at a fraction of the training cost. Then the data: I built a small labeling tool with keyboard shortcuts, and normalized the wild factory lighting with contrast enhancement (evened out glare and shadows across the photos), so the model learned components instead of lamps.

Then the failure that taught me the most. My first fine-tune: 99% on training data, 72% on validation (fine-tune = re-training a ready-made model on my photos; validation = a check-only slice of my own photos, set aside for grading and never studied; the pair counts correct answers on the photos it had studied versus the ones it hadn't - one logged run, measured, just ugly). It was memorizing, not learning. My instinct said grab a bigger model - that would have just memorized faster. Instead I learned *why* it happened: the randomly initialized classifier head (the layer that makes the final call - good, wrong value, wrong orientation, missing - and the only part starting from scratch) fires huge noisy gradients early on (the error signals used to adjust every setting in the model) and overwrites the useful features - learned edges, textures, shapes - borrowed from ImageNet (the huge public photo library the base model was pre-trained on). The fix was a training strategy I'd never used - freeze the base (lock most of the network so it can't change), train the head alone, then gently unfreeze the top layers (release the outermost layers, gradually) at a much lower rate (tiny adjustments instead of big ones). And I logged every run, so how many layers to unfreeze was a measured choice, not a guess.

The result is where "excelled" stops being a claim. 94% on a roughly 300-image holdout I never trained on - above the bar - with the train-to-validation gap closed, so it was generalizing (genuinely recognizing new parts, not recalling studied ones). What that 94% counts: correctly sorted photos out of the ~300 unseen ones; it comes from my final logged run - solid as a measured score, but a single run, not several. The model ran inside the same single-file browser tool the engineers already used (browser ML: the trained model itself runs inside an ordinary web page - no server, no installs). I judged on per-class recall (for each defect type, what share of the real ones did it catch - checked type by type, because one overall score can hide a category the model keeps missing) - the honest metric, since good boards far outnumbered defects - and a retrain on new data stayed cheap (a short refresh, not a rebuild).

What stuck wasn't any framework. It was learning how to make a number trustworthy - name the set it's measured on - and how to find the next failure and close it.

## Memory Anchors
- Problem: Needed a production defect classifier; had ML theory but never shipped a model. Explicit bar: >90% held-out, <100 ms/image, retrainable for new defect types.
- Customer: Manufacturing engineers; the inspection tools were already live on the floor.
- Insight: The skill wasn't the API - it was the training dynamics. A 99%/72% split means memorizing, and the cause (random head overwriting pretrained features) dictates the fix.
- Action (mine): Chose the ~21M-param EfficientNet variant by matching model to data; built the labeling tool and fixed illumination myself; transfer learning + two-phase progressive unfreezing; logged every run; component-level 70/15/15 split; up-weighted rare defects and judged on per-class recall.
- Result: 94% on the ~300-image holdout vs the >90% bar; ~3-point train/val gap; ~45 ms CPU single-image benchmark vs <100 ms; >90% recall every defect category; ~30-minute retrain on one GPU; ran in-browser in the shipped tool.
- Learning: I learn by building the smallest real version, measuring honestly, and fixing the binding failure - and a number is only as good as the named set behind it.

## Follow-Up Bank
1. What exactly was new to you? - Everything past theory: dataset design, transfer learning (reusing a model already trained on generic photos as the starting point), training dynamics (how a network actually behaves while it learns), and exporting a model to run inside the browser tool (packing the trained model into a web page instead of a server). I built the whole suite solo, so there was no one to hand it to. [SAFE]
2. How did you learn it fast enough to ship? - In pipeline order, validating each piece before the next: labeling tool, then lighting normalization, then fine-tune a pretrained network (re-train a ready-made model on my photos), then the training strategy. Not study-until-ready - build the smallest real version and measure it. [SAFE]
3. Why transfer learning instead of training from scratch? - ImageNet already encodes the edges, textures, and shapes a component crop needs. A few thousand images can't train a network from zero (from zero means re-learning even edges and shapes, and a few thousand photos isn't enough) - that was a simple-vs-complex call made deliberately. [SAFE]
4. Why that model size - did you consider bigger? - ResNet, EfficientNet, and vision transformers researched. Transformers want more data and compute than existed. Within EfficientNet, the ~21M-param variant (parameters = the tunable knobs inside the model) trailed the big one under two points on my data (less than two percentage points of accuracy) at roughly a third of the training cost (about a third of the time and compute to teach it) - right point on the curve, not a compromise. [SAFE]
5. Walk me through the failure. - First run: 99% train, 72% validation (the memorized-versus-check pair from my logged first run). I thought "more model" - what actually happened was the random head's early gradients scrambling the borrowed features. Changed to two-phase unfreezing: head alone first, then the top layers at a tenth the rate (the rate = how large each adjustment to the model is). Learned that the gap is the signal and the training number is vanity (the train-versus-check gap tells the truth; the studied-photos score just flatters). [SAFE]
6. How do you know 94% is real, not a lucky split? - Held-out ~300 images, above the explicit >90% bar, split by component so the same part never appears twice. What the 94% counts: correctly sorted photos out of those ~300 never-studied ones; it's from my final logged run - solid as one measured score, but not yet repeated. ~3-point train/val gap; per-class recall instead of one aggregate a majority class could inflate (one blended score can look great just by coasting on the abundant good boards). Honest caveat: single final run, no repeated seeds (re-running the whole training several times to see how much the score wobbles). [PARTIAL]
7. Where did the ~2,000 labeled images come from? - A labeling tool I wrote myself - keyboard shortcuts, CSV out (plain spreadsheet export) - fast enough that the whole set was an afternoon's work, not a week. The labeling speed-up numbers belong to another story; the point here is the data supply was part of the skill I learned. [SAFE]
8. Why per-class recall above accuracy? - Good parts outnumbered defects about 5:1, so an always-good model would score around 83% (with 5 good parts for every 1 defect, a lazy program stamping "good" on everything would look 83% accurate while catching nothing). Weighted defects 5x (told the training to count each missed defect five times as costly) and tuned on precision-recall (precision = how many of its "defect" alarms were real; recall = how many real defects it caught); every defect class came back above 90% recall (caught more than 90% of each defect type). [SAFE]
9. The 45 ms - measured how? - Single-image benchmark on CPU against the <100 ms bar (the time for one photo through the model on an ordinary computer processor, versus the under-100-milliseconds-per-photo requirement); hardware not recorded, and the deployed path ran in-browser, so I call it a benchmark, not a production floor. The ~30-minute retrain is what made it maintainable (the cost of teaching the model a new fault type later). [PARTIAL]
10. Hardest single thing to learn? - That unfreezing *more* of a pretrained network can make things worse on a small dataset - too few layers underfit, too many overfit (underfit = too little learned to do the job; overfit = memorizing the study photos); the middle was found from logged runs, not intuition. [SAFE]
11. Biggest trade-off? - Speed versus trust: I could have shipped the flattering 99% headline into a tool people already used (the studied-photos score, which looks great only because the model had already memorized them). Chose to block my own ship on the ugly validation number and root-cause it. [SAFE]
12. Any disagreement? - No person-vs-person dispute - solo build. The disagreement was with my own first instincts: bigger model, raw accuracy, unfreeze everything. All three were wrong and the measurements said so. [PARTIAL]
13. What would you do differently? - Collect far more than ~2,000 images; use a learning-rate schedule instead of a fixed rate in phase two (easing the size of the adjustments over time instead of holding them constant); assert input shape at inference so a train/serve preprocessing mismatch fails loudly (inference = the model running for real, not in training; the check is that incoming photos are preprocessed exactly as during training, so a mismatch crashes visibly instead of silently mis-sorting). [SAFE]
14. Can you show me the code? - Partly. The repo's checked-in training script is a later hardened variant for a different binary task (a two-outcome yes/no job); the 4-class pipeline behind the 94% isn't in the repo - it's the documented run from my records. And a separate note says "500-image test set," which doesn't reconcile with ~300 of ~2,000 at a 15% split (15% of ~2,000 photos is about 300, not 500 - the records conflict) - so I keep the canonical ~300 number and don't blend the two. [GAP - own it first]
