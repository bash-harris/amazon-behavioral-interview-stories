# Q32 - tell me about a time you had to earn the trust of a skeptical colleague

**LP:** Earn Trust.   **Story:** BGSW PCB Inspector Suite - the manufacturing engineers who didn't trust the BOM tool's verdicts, and the debug-view transparency layer that changed that (PREP STORY 11, with the reliability half from STORY 1).

## Core Answer

The people I had to win over were the manufacturing engineers who used my BOM reconciliation tool. (A BOM - "bill of materials" - is the parts list for a circuit board; "reconciliation" means cross-checking that list against the board's design.) I built the inspection suite solo, so their skepticism came from the floor, and they had good reason. The tool compared a bill of materials against the layout - the design drawing that shows where each part goes - and printed a verdict, a pass-or-fail call, but it showed the conclusion and hid the reasoning. When it flagged a part as a mismatch, the engineer couldn't see why. So for anything that mattered they re-checked by hand - exactly the work the tool was supposed to replace. A verdict you can't check is a verdict nobody trusts.

The naive parser - the first, plain version of the program that reads the parts list - handled maybe 70% of real BOMs: roughly seven of ten actual files it read correctly, and that's my rough sense from early use, not a counted study. It then broke in production one edge case at a time - an oddball input the code hadn't met: process-code prefixes glued onto references (manufacturing codes stuck in front of a part's label, like a code bolted before "R1"), cells exported as hyperlinks (list items that arrived as clickable links instead of readable text), variants like `R1||R2` (one spot on the board that can hold either of two interchangeable parts - the double-pipe is the list's way of writing "this or that"), DNP positions left empty on purpose (DNP = "Do Not Place": a part listed but deliberately not fitted on some board versions). I fixed each at the root, backed every change with a fifteen-BOM regression suite - a fixed set of fifteen real parts-list files that every future change has to pass, so nothing that worked before can silently break - and got to zero false positives and false negatives on those files: on that set, no good part wrongly flagged and no bad part missed. Necessary - but it didn't touch the real complaint. They still couldn't see why a flag was a flag.

So I built them the view. In debug mode - a hidden diagnostic screen that shows the tool's working, not just its answer - it showed, per component, the raw BOM text (the parts-list line before any processing), what the parser extracted after each cleanup step, which layout entry it matched, and the exact rules that fired - which specific checks caused the flag - plus a decision tree: reference valid? matching layout entry? pin count acceptable (does the part have the right number of electrical connection legs)? type correct? My rule was simple: if an engineer asks why the tool flagged something, the view has to answer completely. If a step were missing, they'd just have to ask me instead - and a tool you fact-check with me isn't trusted.

That changed behavior, not words. In the first week they used the debug view to find two real edge cases - unusual component naming the parser handled wrongly - and I fixed both. Then the hand-verifying stopped being universal: they relied on the tool for production verification - the checks on boards actually being manufactured, not trials. They used my tool to find where my tool was wrong, and trusted me to fix it.

What I'd do differently: their skepticism was predictable, and I treated transparency as an afterthought. Trust came from making decisions auditable, then making good on the fixes they surfaced. The next automation I build makes its reasoning checkable from the first commit - the very first saved version of the code.

## Memory Anchors
- Problem: The BOM tool printed verdicts (pass/fail calls) but hid its reasoning; engineers re-checked everything by hand and wouldn't rely on it for critical decisions.
- Customer: The manufacturing engineers on the floor who used the tool - I built the suite solo, so this was my daily trust relationship.
- Insight: Accuracy alone doesn't buy trust - verifiability does; a verdict you can't check is a verdict nobody relies on.
- Action (mine): Root-cause parser fixes behind a 15-BOM regression suite (fifteen fixed test files every change must pass) - zero FP/FN (no false alarms, no missed defects) on that suite; per-component debug view (hidden diagnostic screen) exposing raw text -> each parse step -> matched layout entry -> rules fired -> decision tree (a chain of yes/no checks); rule: the view must fully answer "why" without me.
- Result: Two naming edge cases (unusual part-name formats) surfaced by them via the debug view in week one, both fixed; they shifted from hand-verifying everything to relying on the tool for production verification (checks on real manufactured boards).
- Learning: Build the transparency layer day one, not after the skepticism; trust = auditable decisions plus making good on the fixes they find.

11. Hardest part / any disagreement? - Not getting defensive. The verdicts were often right and still got second-guessed; the fix wasn't arguing, it was handing them the means to check. Framing is mine; the record documents the skepticism and the outcome, not a blow-by-blow (no step-by-step record of who said what). [PARTIAL]
