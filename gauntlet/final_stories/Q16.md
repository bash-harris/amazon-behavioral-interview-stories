# Q16 - when have you gone beyond surface-level analysis?

**LP:** Dive Deep (primary); touches Insist on the Highest Standards.   **Story:** BGSW PCB Inspector Suite - BOM parser edge-case analysis (PREP STORY 1, "The BOM Parser That Refused to Break"); a different deep-dive from Q11's classifier training.

## Core Answer

I built a tool that reconciles a Bill of Materials - the parts list for a circuit board - exported from SAP (Bosch's production-management software) against the PCB layout, the design file showing where every part goes, and flags components that are missing, extra, or mismatched. The reading part of the tool - the "parser," the code that opens and interprets the file - looked like the easy part, until real production files arrived. It handled many real BOMs, then broke, and every time it broke the first explanation was wrong.

The first break was total: every component reported missing. The surface read was "the file didn't parse." But the file opened fine and the layout matched clean - a dead parser doesn't fail that one-sided. I logged the raw cell values: every reference came back as "MP_R1" instead of "R1." A reference is the short code marking where a part sits on the board - R for resistor, C for capacitor. A manufacturing process code was glued on the front. The lazy fix - strip anything before an underscore - would have eaten legitimate test-point prefixes; a test point is a bare pad the factory probes with equipment, and its code can contain underscores honestly. So I audited the pattern across thousands of entries: the prefix was always two or three letters followed by a standard reference. I keyed the rule on that suffix, not on the underscore.

Second break: cells that looked empty. They showed fine in Excel - the data was there, my reader just couldn't see it. They were SAP hyperlink cells: the cell was a clickable link, not plain text, and the library hands you a link object where you expected a word. My test data had none, so I stopped trusting my own fixtures (the saved test files I'd built on) and wrote a recursive extractor - code that peels a cell's layers off one at a time until it finds text: a string if it is one, else the value field, else the link's display text.

Third: references like `R1||R2`. I'd been dropping them as invalid - but the layout always had a position at that spot, and garbage text doesn't get that consistent. So I asked the manufacturing engineer what the line meant: one position on the board, two possible parts depending on which version of the board is built - that's what the "variant notation" `R1||R2` spells. Each side became a valid match target; I split both separators and tested the whole matrix of combinations, malformed forms included.

Fourth, the subtlest: `DNP_R3` flagged as missing. Technically true, semantically wrong - DNP means "do-not-populate," i.e. the position is meant to be *empty* on purpose. False "missing" alerts - flagging something as wrong when it's actually fine - kill trust in an inspection tool.

What turned four patches into an actual dive was the audit around them: a regression suite - a kept set of real files the tool must pass after every single change, like re-taking the same exam - of 15 real production BOMs, grown every time production surfaced a new case, re-run after every change. That suite ran zero false positives and zero false negatives - on those files, nothing fine got flagged, and nothing actually wrong got missed - and in week one the tool caught three real mismatches manual review had missed.

What I took from it: surface analysis tells you what broke, not why. The references weren't the data; the conventions underneath them were.

## Memory Anchors
- Problem: Parser worked on ~70% of real BOMs, then broke on production files - and each break's symptom hid a different root cause.
- Customer: The BOM-vs-layout reconciliation users - replacing a 20-30-minute-per-board manual cross-check (engineer-reported).
- Insight: The reference designators weren't the data; the manufacturing conventions underneath them were (MP_ prefix, hyperlink cells, variant separators, DNP semantics) - the unwritten factory rules hiding inside the files.
- Action (mine): Raw-cell logging; suffix-keyed prefix strip after auditing thousands of entries; recursive cell extractor after distrusting my own test fixtures; asked the manufacturing engineer what `||` meant, then built the splitter and test matrix; DNP detection; 15-BOM regression suite re-run on every change.
- Result: Zero false positives (nothing fine flagged) and zero false negatives (nothing wrong missed) across the 15-BOM suite; three real mismatches caught in week one.
- Learning: "Never normalize without understanding the semantics"; discovery was reactive - next time collect sample BOMs from the floor before writing code.

## Follow-Up Bank
1. How did you find the MP_ issue? - First real BOM run showed every component missing; I thought the file wasn't parsing at all. But a broken parser doesn't fail only on the BOM side - a file that truly wouldn't open would kill both sides of the comparison, not just one - so I logged raw cell values and saw "MP_R1" vs the layout's "R1." A naming convention, not a parsing failure - symptom vs cause. [SAFE]
2. What made you distrust each surface explanation? - Pattern: the output was too clean to be a crash. Total-but-one-sided misses -> data problem, not file problem. Cells visible in Excel but empty to the parser -> reader problem, not data problem. "Invalid" references that always had a real layout position -> my definition of valid was wrong, not the file. [SAFE]
3. Why regex and not positional/structured parsing? - A "regex" (regular expression) is a compact pattern describing text to look for, like "letters followed by digits." The BOM is semi-structured: references move between columns across exports. The text pattern (letters + digits) is the only reliable signal; a per-export column mapping - telling the tool which column holds what, each time - needs configuration, which defeats automation. [SAFE]
4. Walk through the recursive extractor. - "Recursive" means the code handles one layer of the cell, then hands the leftover to itself until it runs out of layers. String -> return it; else if it has a `v` value -> recurse into `v`; else if it has an `l` hyperlink -> take the link's display text. Priority-order property checks handled nested shapes I hadn't anticipated. [SAFE]
5. Why was DNP a false positive, not a real miss? - DNP = do-not-populate: the factory deliberately leaves that position empty. "Missing: DNP_R3" is technically true but semantically wrong - DNP means the position should be empty. Detected it case-insensitively (DNP, dnp, Dnp all caught), marked the position intentionally empty. False "missing" alerts - saying there's a problem when the emptiness is by design - erode trust in an inspection tool. [SAFE]
6. How did you know the strip wouldn't damage legitimate prefixes? - Audited instead of assumed: MP_ was consistently a 2-3-letter process code followed by a standard reference; "TP" test points - bare pads probed by testing equipment, with their own honest code style - have a different suffix pattern. Rule: unknown convention -> leave alone and flag, never guess. [SAFE]
7. Where did the `||` semantics come from? - From the manufacturing engineer, not the file. I had it filed as invalid; he explained it's one position, two candidate parts by board variant - the same board sold in versions, this spot gets part R1 on one version, R2 on the other. Both `||` and `/` split into valid match targets; matrix covered `R1||R2`, `R1/R2`, `R1||R2||R3`, and malformed `||R1` / `R1/`. [SAFE]
8. How solid is the 70%? - What it counts: roughly how many real files my early parser handled correctly. Where it came from: my own early trials against real files. How solid: a rough sense, not a measured corpus figure. It's there to size the gap, not as a statistic. [PARTIAL]
9. What does zero FP / zero FN actually cover? - Plain words first: a false positive is flagging something as wrong when it's actually fine; a false negative is a real problem the tool fails to report. What the zeros count: no fine things flagged and no real problems missed, across the 15 suite BOMs - that's the honest scope. I can't claim no edge cases exist in the wild; that's exactly why the suite grew with each new production find and re-ran on every change. [SAFE]
10. What's the manual baseline the tool replaced? - What it counts: an engineer eyeballing the parts list against the layout by hand, time per board. Where it came from and how solid: engineer-reported - cross-checking BOM against layout took 20-30 minutes per board; the report produces the same check in seconds. The 20-30 min figure is a team recollection, not instrumented. The three week-one catches are a story-bank record, not an audited count. [PARTIAL]
11. Performance? - What it counts: how long the tool takes to read a big parts list. A 2,000-component BOM parsed under 200 ms - a fifth of a second - against a sub-second success bar for 500-2,000 components; the scaling is linear O(n+m) - work grows in step with the size of both lists, so twice the parts is about twice the time, never a blow-up; unknown formats degrade gracefully rather than crash - they get flagged instead of taking the tool down. Where it came from and how solid: recorded figures, single-run - one measured timing, not a benchmark study. [PARTIAL]
12. Hardest part / what would you do differently? - Hardest: re-questioning my own test data after the hyperlink miss - the saved example files I'd trusted were the problem (my assumption failed, not the library). Differently: I found every case reactively via production failure - I'd collect sample BOMs from the manufacturing floor first. Accepted trade-off: the parser is tightly coupled to SAP export formats - it assumes Bosch's software lays files out a certain way. Surprise: DNP x variant interaction needed manufacturing intent, not text matching. [SAFE]

## Risk Check

2. 70% and the 200 ms figure - 70% is my feel from early trials, 200 ms is one recorded run; story-bank-recorded, estimate/single-run provenance, not surveyed or benchmarked. Label them that way under probing rather than defending precision. [PARTIAL]
3. "Three mismatches manual review missed" and the 20-30 min/board baseline - week-one story-bank record and engineer-reported recollection, not audited or instrumented; don't elaborate on how review missed them beyond what the record says. [PARTIAL]
4. "Garbage text doesn't get that consistent" distrust beat - a reasoning step, not a measured statistic; safe to say as my thinking, not as data. [SAFE]
