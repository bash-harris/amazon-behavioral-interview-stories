# Q75 - tell me about a time you made a mistake in a data pipeline / a data quality issue and how you resolved it

**LP:** Earn Trust (primary); Dive Deep; Deliver Results.   **Story:** BGSW PCB Inspector Suite - the BOM parser silently dropping variant references (AMAZON_INTERVIEW_PREPARATION.md STORY 1). Distinct from Q28 (person consulted), Q16 (edge-case tour), Q73 (feature walkthrough).

## Core Answer

One caveat first, so I don't oversell: this wasn't a streaming ETL job - ETL is software that continuously extracts, cleans, and shuttles large volumes of data between systems. It was a reconciliation pipeline - a program whose whole job is to cross-check two lists against each other: it read a SAP-exported bill of materials (SAP = the software the business uses to track parts; a bill of materials is the official list of every component that should be on a board), pulled out every component reference (each component's label, like R1 or C20), and matched them against the board layout (the design file showing where each part sits). But the mistake was a data-quality one, and it was mine.

I built the first version on a strict reference pattern - the label had to be letters then digits - and I made anything that didn't match get silently skipped. Silently skipped means thrown away without an error or a warning, so nothing told anyone data had been dropped. That default was the mistake.

Here's what it cost. Some boards use variant notation: `R1||R2` means two possible components share one physical position - the board gets built with one or the other, and the list records that choice. My parser - the part of the code that reads the list - saw that string as garbage and dropped it. A position that should have been checked simply wasn't in the report. That's the nastiest class of data bug: a report only lists what it parsed, so missing data never announces itself. The output looked clean, and the tool said "no problem" where the truth was "I never looked at this." A manufacturing engineer found it. Not me. That's the part I own.

I didn't blame the data. The BOM wasn't malformed and the notation wasn't wrong - my parser was, and the silent-skip default was the root cause. So I fixed both the feature and the proof. I built a variant splitter that normalizes both separators, extracts each reference, and treats each as a valid match target for that position. Then I wrote a test matrix of clean and malformed variants and folded it into a regression suite of 15 real production BOMs - an automated checklist of 15 actual parts lists copied from production, rerun after every change so fixing one format couldn't break another.

The result: all fifteen passed - the fifteen real files in the checklist, none flagged with a false alarm (a mismatch reported that isn't there) and none losing a missed part (a real mismatch the report didn't show). The report came back in seconds against the twenty-to-thirty minutes the engineers said they spent per board by hand - that baseline is their own memory of the old manual process, not a timed study. And in the first week of production use, it caught three real mismatches that manual review had missed - a count reported to me afterwards, with no confirmation log behind each one.

The rule I kept from it: never let a pipeline quietly discard an input it doesn't understand - surface it. An incomplete result that looks complete is more dangerous than a failure that announces itself. And I'd fix this upstream of the code next time: collect real files from the floor before writing the parser, so the first strange format is a test case, not an incident.

## Memory Anchors
- Problem: my BOM reconciliation parser silently dropped valid variant references (`R1||R2`, `R1/R2`) - data loss hiding behind a clean-looking report.
- Customer: Bosch manufacturing engineers - the user caught my mistake, not me; their reported manual baseline was 20-30 min/board.
- Insight: the failure class of every data pipeline - an unhandled input silently discarded, producing a complete-looking wrong result; a report only lists what it parsed.
- Action (mine): owned the silent-skip default as my error; built the variant splitter normalizing both separators; wrote the variant + malformed test matrix; grew the 15-BOM regression suite and reran it after every change.
- Result: 15/15 BOMs with no false alarms and no missed parts; report in seconds vs reported 20-30 min; three real mismatches caught in week one.
- Learning: never let a pipeline silently discard input it doesn't understand - surface it; collect real files before writing parsers, not after production failures.

## Follow-Up Bank
1. Is this really a "data pipeline" mistake? - Honest answer: not in the streaming/warehouse sense. It's a structured-document reconciliation pipeline - SAP Excel plus Altium layout (Altium = the design tool that produces the board layout file) - not an ETL job over event streams (a never-ending flow of data arriving in real time). Same failure class though: unhandled input silently dropped, complete-looking wrong output. Same fix: fail loud (stop with a visible error instead of moving on quietly), test the formats, regression-lock them. That's why I answer with it instead of inventing a warehouse incident. [SAFE]
2. Why did the parser skip instead of failing? - I designed for graceful degradation (the tool keeps running even on input it doesn't recognize): users are manufacturing engineers, not developers, and I didn't want an unknown format to crash the tool. Right instinct, wrong granularity - skipping an unparseable cell is acceptable; silently dropping a component reference is data loss. Correct behavior is to report what it couldn't parse. [SAFE]
3. Walk me through the fix. - Normalize both separators (`||` and `/`), split, extract each reference, treat each as a valid match target for that position - so `R1||R2` matches either part instead of vanishing. Locked down with a matrix: `R1||R2`, `R1/R2`, `R1||R2||R3`, `R1/R2/R3`, malformed `||R1` and `R1/`. [SAFE]
4. How did you keep this class of bug from coming back? - The regression suite (the automated re-checklist described above) grew to 15 representative production BOMs - 15 actual parts lists copied from production, chosen to cover how the files really arrive - each new production failure becoming a new case. It runs in about two seconds, so there was no friction to rerun constantly. Plus the new rule: surface unknown formats, never skip them. [SAFE]
5. How do you know there aren't more silent drops? - I don't claim completeness. I stopped when false positives and false negatives both hit zero across the 15-BOM suite (a false positive = a false alarm, flagging something fine; a false negative = a real problem missed), and the server build added a `?debug=true` view showing the raw BOM text and every parsing step (a switch you add to the tool's web address that reveals exactly what the program read and did, so an engineer can see what the parser did and flag a format I haven't seen). [PARTIAL - suite-scoped, not production-wide]
6. How was "no false alarms and no missed parts" measured? - Against the 15-BOM regression suite: representative production files across board variants and SAP export configurations, checked for correct per-reference extraction (every component label in each file individually found and matched). Zero FP/FN means *on that suite* - the 15 files, not all production traffic. [PARTIAL - suite-based]
7. Performance / scale? - A 2,000-component BOM parses in under 200 milliseconds (a parts list of 2,000 entries processed in less than a fifth of a second) - a recorded single-run figure against my sub-second bar, not a benchmark distribution. [PARTIAL]
8. How reliable are the headline numbers? - The 20-30 minute baseline is engineer-reported recollection, no timing protocol (told to me from memory, no one timed it); the three week-one catches are real but I can't produce a confirmation log for each. Reported, not instrumented (no system recorded either figure). [GAP - no instrumentation exists]
9. What was the baseline before the fixes? - The bare reference pattern handled roughly 70% of real BOMs in my early trials - about 7 in 10 real files parsed with no change needed; a sense from usage, never a shipped target; the rest arrived as production failures, one edge case at a time. [PARTIAL]
10. Where did the variant semantics come from? - From an engineer. I could see the string; I couldn't see the intent. He explained: one physical position, either part valid depending on board variant. I changed the code on his correction. [SAFE]
11. General principles you carry? - Two: never normalize an input without understanding its semantics - I don't strip dots because a dot can mean a sub-component; and never let an understood-less input disappear. [SAFE]
12. Who owned this? - Solo. I wrote the parser, the silent-skip default that caused the bug, the splitter, and the suite. The engineer contributed the semantics and the catch, not code. [SAFE]
13. What would you do differently? - Upstream of the code: collect representative files from the floor before writing the parser, so the first variant notation is a test case on day one, not a production incident. [SAFE]
