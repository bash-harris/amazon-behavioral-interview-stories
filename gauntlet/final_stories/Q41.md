## Core Answer

I'll be blunt: I don't have a story where I took a task past my job description, and the reason is structural. On my main project I was the sole builder and architect - the only person who both designed the software and wrote it. The role was defined by an outcome, not a narrow task list, so almost everything I did sat inside the charter (the job's official scope). I won't relabel assigned work as a bold step over a line that never existed.

The closest true thing I can show you is this. Nobody assigned me the browser-computer-vision question - "computer vision" is software that looks at photos and checks them, and "browser" means it runs inside an ordinary web browser, like the one you read email in, instead of a program someone installs. But it sat between me and the outcome. The inspection suite - the photo-comparison tools the factory used - had to run on factory machines with no server and no installs, meaning the locked-down shop-floor computers couldn't connect to a central machine and wouldn't accept new software, and I didn't know if that was even possible in a browser. So I ran a one-day spike - a spike is a short, deliberately throwaway experiment built to answer one question - the smallest prototype that could work: load two images, run one operation. That made an unknown that could have cost me weeks cost a day, and the architecture call got made on evidence instead of guessing - the decision about how to build the whole tool, settled by what the experiment showed rather than a hunch. Plainly, about those two numbers: the day is real time the experiment took; the weeks are my own estimate of finding the same answer the hard way - a judgment, not a measured figure.

Two adjacent things show the same instinct, and I'll keep their bounds honest. The defect model - the part of the tool that names what kind of flaw a board has - needed labeled images, which are example photos a person has marked up to show what each one contains and what's wrong with it, and they didn't exist, so I built the labeling tool rather than report a blocker - but my own notes record that as my responsibility. Engineers didn't trust the reconciliation verdicts - the yes/no answers the tool produced when it cross-checked a board's parts list against its design file - so I built a debug view exposing the reasoning, a screen that shows how the tool reached each answer so a person can check it, but it shipped inside the tool I was assigned. Both are owning an unowned dependency - something the work needed that was nobody's job - not taking a task outside the job.

The pattern I can defend: when something blocks the outcome, nobody owns it, the cost of trying is bounded (small and capped, so a wrong attempt is cheap to undo), and I'm closest to it - I pick it up, and I say out loud what I'm taking and why.

The gap, openly: **[GAP]** - I have no documented moment where a clear line existed and I stepped over it. A real example belongs to team experience, with somebody else's duty or an orphaned one in it, and I'd bring that prepared instead of stretching this record.
