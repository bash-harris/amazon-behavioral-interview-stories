# Q81 - tell me about a time when your project deadline was very near, but you still took time to verify or test the data/code before submission

**LP:** Insist on the Highest Standards (primary - a full cost pass over the shipped loop before submission); Dive Deep (traced the cost to a function signature); Deliver Results (the fix reused a pattern already proven in my own repo)   **Story:** the pre-submission cost audit of the deployed comparison tool - a full-image decode hidden inside the per-component crop loop (~1,000 decodes, ~48 GB churn, computed from recorded dimensions), and the pre-read-Mat pattern that already existed in the sibling tool and had never been back-ported (BAR_RAISER_TECHNICAL_PREP.md Finding 1, :112-132); distinct from Q38 (the O(NxM) lookup scan in the same file) and Q46 (the reported-bugs verification rule)

## Core Answer

The verification that paid off was one I almost skipped because the build already worked: a stage-by-stage read-through of what a full board run actually does, before submitting the deployed version of my board-comparison tool - it inspects a photo of a finished circuit board against a golden reference. The factory machines it runs on are slower than my laptop, and it's one offline file with no server to offload to - "opens fine in front of me" was never the bar.

Reading the loop, I found heavy disk-shaped work hiding in the hottest place I had. The function that crops a single component out of a board photo took the whole photo as its input, and each call allocated a full-size canvas, drew the entire image, decoded it into browser memory, then cut out its one small region. It runs twice per component - reference board and test board - so a typical board pays about 1,000 full-image decodes: tens of gigabytes of memory made and thrown away for maybe 30 megabytes of crops. That's arithmetic on dimensions I knew, from reading code - not a profiler's trace, and I won't quote a speedup I didn't measure.

Two things made it a verification story, not a found typo. First, the call site looked innocent - "crop this component" - because the decode hid behind the parameter type: hand it an image and it must decode. The loop advertised no cost. Second, I didn't invent the fix: the repo already contained the right pattern - the sibling tool's analysis worker takes a pre-decoded buffer and slices regions out of it - and nobody had back-ported it between the two tools that grew apart from a copy. The fix was hoisting the decode out of the loop - pay once per image, then slice - and changing the signature so the cost is visible where it's paid.

What I kept: expensive operations go in the signature, not behind it - a parameter that says "image" is announcing "I will decode you a thousand times." And a deadline-adjacent read of the hot path is the cheapest bug find that exists: hours of reading, versus a crawl discovered on a factory floor with no network, no tools, and no IT to ask. - Customer: engineers on slow, offline, locked-down factory machines where the single file runs; the decode storm is invisible on a dev laptop and brutal on the floor
- Insight: an I/O-shaped cost can hide behind a parameter type - the call site looked cheap because the function accepted a whole image; and the correct pattern already existed in my own repo, never back-ported between copied tools
- Action (mine): the read-the-loop verification before submission; arithmetic on shipped counts (~2 decodes x ~500 components; 4000x3000 RGBA ~48 MB per decode; ~48 GB churn); fix by hoisting the decode - O(1) decodes + O(N) region slices - via the sibling tool's pre-read-buffer worker, and changing the signature so cost is visible at the call site
- Result: a named, bounded corrective (back-port + signature change); no claimed seconds saved - found by reading, profiling still owed before any speedup number [PARTIAL]
- Learning: "works for me" isn't verification on a fleet I can't see; put expensive operations in the signature, not behind it; deadline near = read the hot path, not less
