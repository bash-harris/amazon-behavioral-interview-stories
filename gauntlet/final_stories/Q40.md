# Q40 - Tell me about a time you made an unorthodox decision.

**LP:** Are Right, A Lot (primary); Invent and Simplify; Bias for Action.   **Story:** BGSW PCB Inspector Suite - GPT-4o VLM as the inspection engine instead of the purpose-built classifier (AMAZON_INTERVIEW_PREPARATION.md STORY 8; decision-framed telling of the same event Q1/Q3 used).

## Core Answer

The unorthodox call: I used a general-purpose cloud vision model as the inspection engine - that means an AI that can look at a photo and answer questions about it, running on someone else's computers over the internet and paid for per use - instead of the trained classifier machine-vision inspection says to build: a custom image model you train yourself on labelled photos of your own defects.

I was the only engineer on a PCB inspection suite for manufacturing engineers. A PCB is the green circuit board inside every electronic device. The comparison could tell you *where* a board didn't match its design - it drew a red region - but not what the region *meant*. Wrong part? Rotated? Just a reflection? An engineer read every flag by eye, about thirty seconds a pop - their own estimate of one zoom-and-decide, not a timed study. Interpretation was the bottleneck.

The orthodox fix was a bespoke classifier - a custom image-recognition model you train yourself: label photos of each defect type, train a model on them - it runs offline, cheap, and it's yours. I did the opposite: cropped each flagged region from both the layout and the photo, sent both to GPT-4o with a structured prompt - an instruction that demands the answer in a fixed fill-in-the-blank form the software can read mechanically - and got back a verdict: component type, mismatch type, and a confidence (the AI's own score for how sure it is).

That was odd here, and each oddity was a real risk. One: a cloud dependency - the tool leaning on someone else's paid internet service - in a tool built for factory machines with restricted networks. Two: the "intelligence" was a black box (a system you can't open up and inspect inside) I didn't train or own, and wrong verdicts on a production tool are expensive. Three: I inverted the job - building the pipeline (the automated steps around the AI: cut the images, send them, read the answer back) and the prompt around someone else's model, not my own model. That looks like less engineering until you've done it.

I treated it as a bet, measured first. I hand-compared candidate models on the real task: speed, small-part accuracy, hardware fit - my own side-by-side trials, not a formal benchmark. Then I bounded each risk. Only flagged regions went to the model, so cost scaled with mismatches, not components - the price follows how many red marks a board has, not how many parts sit on it. The cloud path lived only in the server build - the suite existed in two versions: the server build, which ran through our own server and could reach the internet, and a self-contained offline file running straight on the factory machines; "server-build only" means the AI lived in the first version alone, and the offline factory-floor tool never touched it. The output was labeled "AI Analysis" - a suggestion with a confidence the engineer confirmed or overrode, plus a correct/incorrect feedback loop (a right/wrong button on every answer). If the API - the point where software plugs into a paid online service - died, the tool kept working.

It worked out. The thirty-second eye-read became a five-second answer - API time, the computer's reply, not a stopwatch saving for the human; the engineer went from interpreting to confirming and, by their own word, saved most of their ~30 seconds per flag. It read component and mismatch type right about eighty-five percent of the time - my rough check against the engineers' right/wrong clicks, not a measured rate from a formal test. The misses were images too poor or parts too small.

What I got wrong: I thought it could read values off small surface-mount parts - the tiny components soldered directly onto the board. It can't - context, not OCR (reading printed letters off a photo, the way a scanner does). And I'd start with the simple prompt, not the clever one. The call was right because I bounded the risk before I took it, not because I trusted the model.

## Memory Anchors
- Problem: comparison flagged *where*, not *what*; every red region cost the engineer a ~30-second eye-read (engineer-estimated, not timed). Interpretation was the bottleneck.
- Customer: the manufacturing engineers using the suite on the factory floor.
- Insight: a general vision model (cloud AI that reads photos and answers in words) already had the "expert eye" I'd otherwise spend months training - my work was crop, prompt, parse.
- Action (mine): solo; hand-compared model candidates on the real task; built the dual-crop structured-JSON pipeline (cut-out images + fixed fill-in-the-blank reply form + parsing); server-build-only (AI on the server build; the offline floor file runs none) and optional; confidence display + correct/incorrect feedback + graceful degradation (tool still works with the AI absent); rewrote the failing first prompt to a fixed schema.
- Result: ~30 s eye-read (engineer-reported) -> ~5 s answer (AI reply time - computer time, not measured human time); ~85% on component/mismatch type by rough self-assessment (no formal test behind it); engineers triaged dense boards with the labels; offline build untouched by the VLM (vision-language model - the image-reading cloud AI).
- Learning: reach for the general model where a bespoke one would be maintained forever; bound risk before betting; don't trust a VLM for OCR on tiny text; start with the simple prompt.

## Follow-Up Bank
1. Why wasn't a red box enough? - Every flag was a manual judgment call: wrong value, wrong orientation, or a lighting artifact (a reflection or shadow that only looks like a defect). About thirty seconds a region by the engineers' own estimate - not a stopwatch study; a dense board typically threw five to twenty of them - a reported typical, not an instrumented count. Detection was solved; interpretation wasn't. [SAFE]
2. A trained classifier is offline, cheap, and yours. Why not that? - Because it's a labeling-and-retraining project that restarts for every new defect type, and I was a solo engineer already carrying three tools. Reusing an existing "expert eye" pointed my effort at preprocessing and the prompt. It also wasn't either/or: the deterministic comparison stayed the core (the fixed-rule red-marking math - same input, same answer, no AI judgment); the VLM was an escalation for flagged regions only. I'd build the custom model if cost or privacy ever became the binding constraint. [SAFE]
3. Why GPT-4o specifically? - Hand-tested side by side on the real task (my own observations on real flagged regions, not a formal benchmark): GPT-4V ran about eight seconds per request versus about three for 4o - that's the wait for the answer; Claude 3 saw well but its API was less mature then; Gemini Pro Vision was weaker on small-object detection, which is exactly what SMD parts need (SMD = surface-mount devices, the tiny components soldered straight onto the board). A local LLaVA-style model (a free model you run on your own hardware instead of paying a service) was the self-host option but wanted at least 8 GB of VRAM the factory machines didn't have - VRAM is the memory on a graphics card - so it was rejected on hardware, not preference. [SAFE]
4. How reliable is that 85%? - As a rate, not very. It was my rough check against the correct/incorrect marks on flagged-region reads - no held-out set, no n, no confusion matrix. In plain words: a "held-out set" is a batch of fresh, hand-checked examples deliberately kept from the model so it's tested on things it has never seen; "n" is how many examples a rate actually rests on; a "confusion matrix" is a table showing which mistake got called which. It was acceptable because the model's output was a first-pass suggestion, never the decision. If you want a validated number, I'd build the labeled eval set first - that's a real gap. And note: 85% in my alignment story measures something else entirely - different tool, different loop; I never mix them. [GAP - no measured accuracy exists; lead with the label]
5. Was 30 s -> 5 s an instrumented saving? - No. The 30 s is engineer-reported - their own guess at one eye-read's duration; the 5 s is the API's response time - the computer's wait for the AI's answer - and the confirm step was never costed. The honest claim: the engineer saved most of their thirty seconds per region. Not a timed study. [PARTIAL]
6. Was putting board photos into a cloud API even allowed? - I put it through the security team before shipping the cloud path; they approved because the images contain no trade secrets. And the offline build runs no VLM at all, so the network constraint on the floor never became a failure mode. [SAFE]
7. What when the API is down or slow? - The VLM is an enhancement, not a dependency. Comparison and red highlights still render, the UI says AI analysis is unavailable, and the engineer inspects as before. Typical 4o response was about three seconds, inside the under-five-second design budget. (The "design budget" is the reply-time ceiling the tool was specified to stay under; the ~3 s is my hand-observed average in use, not a measured distribution.) [SAFE]
8. What does it cost, and where would you NOT use the model? - Roughly a cent an analysis, so a ten-mismatch board is about a dime. (The cent = the provider's published price per request times a typical call - an estimate from the price list, not a billed-and-audited figure.) Never on every component - hundreds of components across thousands of boards a day wrecks cost, latency (how long each call takes to answer), and auditability, since you can't reproduce a hosted model's verdict months later. Never offline. A cost-aware cascade - a two-stage funnel where cheap fixed-rule image code screens every flagged region and only the unsure ones escalate to the paid AI - is a design target - designed, not built. [SAFE; cascade PARTIAL - target only]
9. What went wrong while building it? - Two things. The first prompt was verbose natural language and returned junk I couldn't parse reliably; I rewrote it to a fixed JSON schema with examples (JSON = the rigid fill-in-the-blank answer form software reads mechanically). And I overestimated the model: it couldn't read value text on small surface-mount parts - context, not OCR. [SAFE]
10. Did anyone push back on the idea? - I was the only engineer, so the argument was with my own default - the domain reflex says build the bespoke model. I settled it with a bounded-risk checklist rather than a debate. I won't claim external opposition I didn't have. [PARTIAL - no recorded external disagreement]
11. Hardest part? - Not the code. Committing to an engine I couldn't audit line-by-line, and designing the human loop so that *not* being able to audit it was okay. [SAFE]
12. Bigger scale / do differently? - Build the labeled eval set before shipping - a kept-back batch of hand-checked examples to score on, so accuracy is measured, not judged. Start with the simple structured prompt instead of the clever one. And keep the rule: general model for judgment, deterministic core for detection. [SAFE]

## Risk Check
1. The ~85% has no held-out set behind it - defensible only in the labeled form used ("my own rough check, not a measured rate"); pressed for audited accuracy, it's a GAP, and follow-up 4 owns that.
2. "30 s -> 5 s" could be heard as a measured human-time saving - it's engineer-reported baseline + API turnaround; defensible with the labels in follow-up 5.
3. "A cloud model on a factory-floor tool is disqualifying" - defensible: server build only, optional, deterministic core always works, security-team-reviewed, offline build runs no VLM.
4. "Calling an API isn't unorthodox" - defensible as judgment: the domain default was a bespoke classifier; the unorthodox parts were inverting build ownership and accepting a cloud dependency in a restricted environment - each bounded, not ignored.
