# Q31 - tell me about a time when you had to finish a project quickly to meet a deadline

**LP:** Bias for Action (primary - removed the schedule-threatening manual step fast, small right tool over a perfect one); Deliver Results (secondary - final milestone landed inside the eight-week window).   **Story:** STORY 15 "Compiling a Full Stack into a Single File" (build turnaround under deadline), artifact facts from STORY 4; distinct from Q26 (eight-week scope) and the five-day prototype (Q13/Q18/Q19).

## Core Answer

The deadline was the last milestone of an eight-week solo project: ship my PCB inspection suite as one standalone HTML file - no server, no network - that factory machines could just open. Weeks seven and eight. (A PCB is the green circuit board inside electronic devices; the suite is my browser-based tool that checks a made board against its design files. "HTML file" is the ordinary format a web browser opens, and "standalone" means everything the tool needs - code, styling, the trained model - is packed inside that one file, so opening it is enough. Weeks seven and eight.)

The threat to the date wasn't code. It was packaging. The tool normally lives as many separate source files, and turning them into that one file was manual: I concatenated the files by hand (pasted them end to end), inlined the CSS and JavaScript (pasted the styling rules and the program logic directly into the file instead of linking to them from elsewhere), base64-encoded the libraries (converted the non-text parts into plain text so they fit inside a text file), checked the result. Each run of this was a "build" - one pass that produces the finished file. About 30 minutes a build, and it broke roughly one time in five - I'd inline a file in the wrong order or miss one, and the failure only showed up when a manufacturing engineer opened the file. And I rebuilt again and again as I fixed things across the suite. So 30 minutes at a one-in-five failure rate was eating the calendar and shipping defects into the deliverable itself. (What those numbers count and how solid they are: 30 minutes is my typical working time per build and one-in-five is the share of hand-builds that broke - both my own recollection from the weeks of doing it, not logged or measured data; the basis is in the follow-ups.)

So I stopped packaging by hand and wrote the compiler - here just a small program that does the packaging automatically: source files in, finished file out, not a language compiler in the C++ sense. About 200 lines of Python (a plain, readable programming language), three stages: collect every HTML, CSS, JS, and library file; process each by type - CSS into style tags, JS into script tags in dependency order (each piece placed before the code that calls it), binaries base64-encoded (text-converted so they fit); assemble the document. Two details mattered. Ordering: the build reads a manifest - a simple checklist file stating exactly what goes in and in what sequence: CSS before the HTML that uses it, utility scripts before the business logic that calls them - instead of trusting the filesystem's order (the arbitrary sequence the computer happens to list files in), which is what had been biting me. And traceability: it stamps the git commit hash - a version fingerprint from the tool that tracks my code history - into the HTML title, so I could tell which build any file in the field came from.

The result: a build in about 8 seconds that stopped failing on ordering. Before, about 30 minutes and one failure in five; after, 8 seconds and zero. (What this counts and how solid it is: the 8 seconds is my stopwatch average over release builds, and "zero" means zero of that one wrong-order-or-missing-file failure class since the checklist took over - small samples, stated as estimates, not logged metrics; method in the follow-ups.) The artifact itself - the shipped file - is unchanged: the same roughly 25MB single file, that is, one file in the tens of megabytes: big for a web page file, nothing a factory PC can't store and open, and it runs the whole suite offline.

The call I'd defend: a 30-minute manual step that repeats under a deadline is a schedule problem, and it was worth an hour of tooling - the compiler paid for itself by the second build. And I kept it simple: string manipulation (the program just pastes text into a template), not a Webpack setup (Webpack being the heavyweight industry-standard packaging tool for large web projects). What I'd add now is a checksum on the output (a content fingerprint, so accidental corruption becomes obvious) and a diff mode between builds (an automatic side-by-side comparison of two finished files), so a corrupted file gets caught by the tool instead of by me.

## Memory Anchors
- Problem: the weeks-7-8 standalone milestone was gated by a ~30-min manual packaging step that failed ~1 in 5 builds (my recollection, not logged) - eating calendar and leaking order/missing-file defects (a part inlined in the wrong sequence or skipped entirely) into the artifact (the shipped file)
- Customer: manufacturing engineers opening one file on locked-down factory machines (machines where users cannot install anything) - no server, no network, no installs
- Insight: under a deadline, a repeated error-prone manual step is a schedule problem, not a chore to absorb - an hour of automation is cheaper than one missed date or one bad field build
- Action (mine): wrote `compile_tool.py` (~200-line Python): collect -> process-by-type -> assemble; manifest-driven inline ordering - the manifest being the ordered checklist of what goes into the file (CSS before HTML, utilities before business logic); OpenCV.js WASM loader patched to decode at runtime (WASM = WebAssembly, the fast binary format browsers execute; its loader was changed to decode the copy stored inside the file instead of fetching a separate one); git commit hash - a version fingerprint - stamped into the HTML title for build traceability (knowing which build a field file came from)
- Result: ~30 min and ~1-in-5 failures -> ~8 s and zero of that failure class (stopwatch-timed, small samples, scoped to the ordering class); artifact unchanged (~25 MB single file - tens of megabytes, large for a web file but routine for a PC - full suite offline)
- Learning: automation pays back immediately when the manual step repeats; get correctness controls (ordering, stamp) first, name the assurance (checksum, diff mode) as deferred debt

## Follow-Up Bank
1. Was there a real deadline, or did you decide it was urgent? - The eight-week delivery window is documented and the standalone compilation (building the one-file, no-server version) was the weeks-seven-and-eight milestone. 2. Why not Webpack or a real build tool? - The logic is string manipulation - no module bundling (automatically weaving many code modules together), minification (squeezing code smaller), or source maps (lookup tables that map squeezed code back to the original for debugging). The script is about 200 lines and does exactly what the artifact requires; Webpack adds config, plugins, and a learning curve for a step that runs once before each release. [SAFE]
3. Where do 30 minutes and one-in-five come from? - Honest labels: both are my personal recollection from the weeks of hand-builds, roughly 15-20 of them before I wrote the compiler, with three or four order/missing-file breaks - a file pasted into the wrong sequence or skipped - that surfaced when a file was opened in the field (on an engineer's machine). One-in-five is that remembered fraction - no logs, no instrumented rate (nothing automatically counted it; I'm estimating from what I lived through). The 30 minutes is the typical wall time I worked to. [PARTIAL - recalled, small sample]
4. And the 8 seconds and zero? - Timed by hand with a stopwatch across release builds: ~8 s average, ~12 s worst case on a slow disk; the bottleneck is reading and base64-encoding (text-converting) OpenCV.js - the biggest embedded library, the image-processing "eyes" of the comparison - at about 8 MB. Zero means zero order/missing-file failures since the manifest drove the build - small n (only a handful of builds watched), and it's a failure class removed by construction - the fix's design makes that mistake impossible, not merely unlikely - not a universal defect guarantee. [PARTIAL - stopwatch-timed, scoped claim]
5. How do you know the compiled artifact is correct and not just fast? - The ordering control removes the exact failure mode by construction, and I checked builds the way I always had - the by-hand check: I ran the same known sample boards (real boards whose correct inspection results I already knew) through both the server build and the standalone build and compared the outputs, confirming the one-file version behaved exactly like the online version; a small automated diff - a simple script that lines the two outputs up and flags any mismatch, instead of me eyeballing everything - flagged anything that didn't match. [SAFE - consistent across answers, no parity percentage quoted]
6. Walk me through what the build actually does. - Three stages: collect source files; process each by type (CSS - the styling - into `<style>`, JS - the logic - into `<script>` in dependency order, binaries base64-encoded, the OpenCV.js WASM loader modified to decode at runtime: instead of fetching its fast binary format - WebAssembly - from a separate file at startup, it decodes the text-encoded copy carried inside the file itself); assemble the final HTML. It reads the order from a manifest (an ordered checklist of what goes in), not the filesystem - that's what removed the ordering failures - and stamps the git commit hash (a version fingerprint from my code-history tool) into the title. [SAFE]
7. What's inside the 25 MB file? - About 12.5 MB of embedded libraries: OpenCV.js ~8 MB (image processing - the visual comparison), TensorFlow.js ~3 MB (runs the trained defect-classifier model in the browser), PDF.js ~1 MB (opens the design sheets, which are PDFs), XLSX.js ~0.5 MB (opens Excel parts lists). The rest of the file is the model weights (the trained classifier's learned data) plus the app itself - embedding the browser libraries together with the weights and the app is what pushes the single file into the tens of megabytes; the ~25 MB is one soft overall figure, not a sum to be multiplied. It loads in roughly five seconds on a factory machine against about two on the server version, and runs the full suite - BOM reconciliation (matching the board's actual parts against its bill of materials, the official parts list), layout comparison, alignment, ML inference (the trained model judging a photo), auto-save - with no network. [SAFE - canonical STORY 4 artifact account]
8. Hardest part? - Not the compiler. The diagnosis. Under deadline pressure every instinct says write more code, not spend an hour of calendar on tooling. I had to treat the packaging step itself as the deliverable's risk (the thing most likely to make me miss the date was the packaging, not the product). [SAFE]
9. Any disagreement with stakeholders? - Solo project; I won't invent a scene. The argument I actually had was with my own default - absorbing a 30-minute manual step because "we're almost done." [GAP - no documented conflict, stated plainly]
10. Main trade-offs? - An hour of automation against immediate progress (paid back by the second build); a 200-line script against a bundler toolchain (a heavyweight packaging system); correctness controls done now (ordering, version stamp) against assurance deferred (checksums - content fingerprints that catch corruption - and diff mode - automatic file-vs-file comparison) and named as debt. [SAFE]
11. Would this scale to a team or a pipeline? - The compiler is plain Python with a manifest - it drops straight into CI (continuous integration: a team's system that automatically rebuilds and checks the software on every code change), and the ordering and commit-stamp are exactly what a release process would enforce. My read, not something I built or load-tested. [PARTIAL - qualitative]
12. Do differently? - Ship the checksum and the two-build diff mode with the compiler, so a corrupted or silently changed build is caught by the tool instead of by me - and build the parity harness (an automated checker that runs both versions side by side and proves the outputs match) before the deadline, not after.
