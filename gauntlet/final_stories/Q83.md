# Q83 - tell me about a time you had to make a difficult decision

**LP:** Are Right, A Lot (primary - good call under ambiguity, held it against the wrong-looking evidence); Bias for Action; Invent & Simplify (smallest model that clears the bar).   **Story:** BGSW PCB Inspector Suite - the defect-classifier **model-selection decision** (`AMAZON_INTERVIEW_PREPARATION.md` STORY 3). Distinct from Q19/Q58 (prototype scope cut) and Q74 (standalone-vs-server); the training-*fix* retelling belongs to Q11 - here the spine is the *selection*: options, criteria, rejected alternatives, and holding the call when the first run "said" it was wrong.

## Core Answer

The hardest decision I made building the PCB inspection suite - a PCB is the green circuit board inside nearly every electronic device - was which model to bet the defect classifier on, the part of the tool that sorts a component photo by what kind of mistake it shows. And I had to make it before I had a labeled dataset - example photos with the right answers written down by a human - or had ever trained a production model.

Some context. I built the suite alone: browser tools manufacturing engineers use on the factory floor. The classifier's job sounds small: sort a component photo as good, wrong value, wrong orientation, or missing. But it ran in a browser on plain factory PCs - no GPU, no server, meaning no special graphics hardware and no central computer behind it - and the tools were live, so the model had to keep their trust. My bar: clearly accurate on a small dataset I'd label myself, fast enough for a browser, and retrainable the week a new defect type showed up.

Three options. Train a convolutional network from scratch - the classic recipe for image-recognition models, well-understood, but it eats data and compute (it needs far more example photos and computer time than I had), and I had neither. A Vision Transformer - a newer, heavier design, strongest on paper, hungriest on data. Or transfer learning - borrow the visual building blocks a ready-made model already learned from millions of natural images, and fine-tune on my crops (gently adjust those settings for my parts).

I scored them on accuracy with small data, training cost, and speed, and picked transfer learning at the efficient end of one family: about 21 million parameters - parameters are the learned internal settings of a model, think of them as dials training turns, and more dials means a bigger file and slower training. That figure is the published spec of the model variant I chose, so it's a design-sheet fact, not one of my measurements. Component inspection is local features - edges, printed text, shapes - not scene understanding, so bigger variants cost several times the training for an accuracy difference I couldn't see. I chose the smallest model that cleared the bar, not the strongest one available.

Then my first run failed. Training scores looked excellent; validation didn't - validation being the score on photos I kept back that the model never studied while learning. The tempting lesson - "too small a model, go bigger" - would have reversed the decision for the wrong reason. The mechanism said otherwise: my randomly initialized head - the final decision-making layer, starting from random settings - was shouting over the borrowed features. So I kept the model and fixed how it trained - the two-phase unfreeze: first train only the new head with the borrowed layers locked in place, then carefully unlock them.

The bet held: 94 percent on a holdout set I'd never trained on - that's the share of exam photos it sorted correctly, from one measured run on my own labeled exam set, so it's solid but a single run; around 45 milliseconds per image on plain CPU - the time to judge one photo on an ordinary computer chip, from one benchmark I ran myself, so I call it a benchmark, not a guarantee; every defect type caught at a rate the engineers trusted.

What I'd decide differently isn't the model - I started with too few labeled images. The transfer-learned features are what carried the small-data bet; better data would have removed the need. The selection itself I'd make again.

## Memory Anchors
- Problem: pick the model for the defect classifier before the dataset was labeled and with zero production-ML experience - while tools were already live on the floor.
- Customer: manufacturing engineers; the classifier ran in a browser on plain factory PCs (no GPU, no server) and had to keep their trust.
- Insight: component inspection is a local-feature task, not scene understanding - pretrained features transfer (the visual building blocks a ready-made model already learned carry over), extra capacity doesn't; so bet the smallest model that clears the bar and judge the bet by criteria, not vibes.
- Action (mine): scored three families (from-scratch CNN - convolutional neural network, ViT - Vision Transformer, transfer-learned EfficientNetV2 - built on a ready-made pretrained model) on small-data accuracy / training cost / inference speed (how fast it judges one photo); chose the ~21M-parameter variant over the larger ones; paired it with two-phase unfreezing (lock the borrowed layers while the new decision layer learns, then unlock); held the selection when the failed first run pointed at "go bigger."
- Result: 94% on the holdout I never trained on (one measured run on the ~300-image exam set), ~45 ms per image on CPU (one benchmark), every defect type clearing the recall bar the engineers trusted (recall = the share of that defect type actually caught), retrain in about half an hour.
- Learning: separate a bad selection from bad execution before reacting to a failure - and the data underneath a decision is the one input you can't shortcut.

## Follow-Up Bank
1. What exactly was the bar? - Set before I built: above 90% on held-out data (photos kept back that the model never studies), under 100 ms per inference (inference = the act of judging one photo), retrainable as new defect types appeared. 94% cleared the accuracy bar; 45 ms CPU cleared the speed bar with room; a retrain (training the model afresh on current data) took about 30 minutes on one GPU (specialized graphics hardware), so the retrainable clause held. [SAFE - retrain time is one observation, not instrumented]
2. Why not train from scratch? - ~2,000 labeled images (photos with the right answers written by a human) after real effort; from scratch would overfit - memorize the training photos instead of learning general rules - or demand far more labels and compute. ImageNet pre-training (a model already trained on the huge public ImageNet photo collection) already carries edges, textures, shapes - knowing which problem I actually had *was* the decision. [SAFE]
3. Why not a Vision Transformer? - Attention (the heavy everything-compares-to-everything mechanism that design runs on) pays off on large datasets; mine was small and my compute matched the efficient families. On paper the ViT was the strongest option and the worst fit. [SAFE]
4. Why the 21M variant over the bigger ones? - 21M vs 54M vs 119M parameters - three sizes of the same model family, counting the learned internal settings; bigger means a larger file and slower training. The accuracy gap on my data was under two percent; the big one trained roughly three times slower; and the model had to live inside one offline HTML file the factory machines open in seconds, so every megabyte mattered. [SAFE - deployment line consistent with the standalone telling]
5. What did the first run actually show? - 99% training against 72% validation - it scored 99% on the photos it studied but only 72% on the unseen exam photos, the signature of memorizing instead of learning. My dive-deep answer retells that fix in full; here it's the pressure test on the decision. The failure's obvious lesson was "bigger model"; the mechanism's lesson was "stabilize the borrowed features first." I kept the selection and changed the strategy. [SAFE - cross-ref, no retell]
6. What was the two-phase strategy? - Freeze the base (lock the borrowed pretrained layers so they can't change), train the head alone for 10 epochs (an epoch = one full pass through the training photos); then unfreeze the last 30 of roughly 100 layers and run 20 more epochs at a tenth the learning rate (learning rate = how big a correction step the model takes each round; a tenth = much gentler nudges). A random head fires big, noisy gradients early (large, erratic correction signals shot back into the locked layers); open the base from the start and they rewrite the pre-trained features the whole bet relies on. [SAFE]
7. How was the 94% measured? - Validation on the ~300-image holdout of a component-level 70/15/15 split of ~2,000 images (every image sorted into train/check/exam piles per component, so two photos of the same part never landed in two sets). Plain terms: 94% = the share of those ~300 exam photos it sorted correctly. Single final run, no repeated seeds; the train-to-validation gap (the drop from the studied-photo score to the unseen-photo score) closed to about three points. [PARTIAL - labeled]
8. Per-class numbers? - Recall above 90% for every defect type - recall = of all the real instances of one defect type, the share actually caught rather than passed. I won't quote exact decimals per class: each defect class is only a couple dozen images, so one sample moves a point. [PARTIAL - same demotion as the dive-deep telling]
9. Is 45 ms real? - A single-image CPU benchmark (the time to judge one photo on an ordinary computer chip, no graphics hardware); hardware unrecorded, and the shipped path was TensorFlow.js in the browser (the model running through the browser's own machine-learning library). I call it a benchmark, not a floor - not a guaranteed speed for every machine. [PARTIAL - same label as the dive-deep telling]
10. How did you compare runs without fooling yourself? - Every config logged in Weights & Biases (an experiment-tracking service - a searchable lab notebook that records every training run and its scores); I compared logged runs objectively instead of trusting memory of which one felt better. [SAFE]
11. Who disagreed with the choice? - Nobody. Solo project, and inventing a stakeholder fight would be a lie. The real disagreement was with the failure's obvious advice, and the logged comparison was how I argued with it. [GAP - stated plainly]
12. When should a decision like this be slowed down? - When it's irreversible, or when the missing information is cheap to get. Swapping backbones (the core model architecture underneath) cost me a ~30-minute retrain, so committing early was rational. The input I shouldn't have rushed was the dataset - it's the ground truth (the reference answers everything is scored against) the whole decision sits on. [SAFE]
13. Can you show me the model? - Not as an artifact. The four-class pipeline isn't a checked-in file - the code and steps that produced those runs were never committed to the repo; these are documented runs from my records - the same disclosure I lead with in the dive-deep telling. [GAP - own it first]
14. What would you do differently? - Collect more labels *before* selecting, and control the capture lighting on the floor instead of assuming preprocessing (CLAHE - a standard photo filter that evens out local contrast and brightness) would normalize the extremes - it didn't cover all of them. [SAFE]
