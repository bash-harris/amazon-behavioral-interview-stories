# Q90 - a time when you optimized the performance of an application

**LP:** Dive Deep (primary - tied parameter count to latency and checked the result against a hard budget); Invent & Simplify (sized the model to the constraint, avoided the biggest model); Deliver Results (shipped inside the budget without losing accuracy).   **Story:** BGSW PCB Inspector Suite - the defect classifier's **inference-latency engineering** (`AMAZON_INTERVIEW_PREPARATION.md` STORY 3/14). Deliberately NOT the Q87/Q66 Tab Scroller telling: same question kind, different application, different mechanism, and none of the tab-scroller projected figures.

## Core Answer

The application was my PCB inspection tool - a PCB is the green circuit board inside every electronic device. Built solo, browser-based, running on factory-floor machines with no server. One part of it was a classifier - a model whose only job is sorting a photo into a fixed list of buckets - and it judged a photo of a component: good, wrong value, wrong orientation, or missing. That part had a hard budget. "Budget" here means a fixed time limit the tool had to fit inside, not a wish: under 100 milliseconds per image - one-tenth of a second, roughly how fast a computer reply has to be before it stops feeling instant. Not because anyone liked round numbers. If a crop - a small square cut out of the photo around one component - didn't classify inside what a person will wait for, the tool stopped feeling interactive and the workflow on the line broke.

So I optimized against the budget instead of against accuracy for its own sake. I evaluated ResNet, Vision Transformers, and the EfficientNet family - three families of neural-network designs, more like engine models you choose between than one piece of software. The performance decision was sizing. I picked the small EfficientNetV2 variant, about 21 million parameters. A "parameter" is one of the internal settings the model learns from training examples - think millions of tiny dials; more dials usually means a bigger, slower, more capable model, and 21 million of them is what this one carried, where the biggest one I tested was several times that. The reasoning was what the task actually is: a small crop of a single component carries color, shape, printed text - local features, not scene understanding. Across the sizes the accuracy gap on my data was smaller than anything I could justify paying latency and memory for. I took the accuracy I could stand behind and refused to buy the rest.

The cost of inference here is the convolutions - "inference" means the model judging one new image, as opposed to training, which is teaching it in the first place; "convolutions" are the heavy pattern-scanning math this kind of model runs, so they dominate the time. And on a plain factory CPU - the computer's ordinary main chip, no special graphics hardware - that lands at about 45 milliseconds per image: what my own timing test measured, less than half the 100 ms budget. Budget met with room, and I didn't buy the speed with accuracy - the headline number matched the bigger models, and recall on every defect type stayed above the bar I'd set (recall = of the real defects of a given kind, how many the tool caught - the "missed one" error is the expensive one here). The faster hardware paths are documented characteristics, not something I benchmarked, so I don't quote them.

The wrong part was what I thought I was optimizing. The model wasn't the dominant cost of the application - the OpenCV library's cold load, before any compute, was where the time actually went (OpenCV is the image-processing software that reads and crops the photo, and "cold load" is the startup delay the first time it fires up). The classifier's remaining seconds were outside the classifier. Lesson: profile the whole path before picking an enemy. My next optimization plan wasn't a smaller model. It was the load path.

## Memory Anchors
- Problem: browser-only, server-less defect classifier on plain factory PCs had to return per-image inference inside a human-patience budget (<100 ms - a tenth of a second per image) or the interactive workflow died.
- Customer: manufacturing engineers using the inspection tool on the floor; latency was their usability constraint, not a benchmark trophy.
- Insight: the budget is the spec - size the architecture to it, don't maximize accuracy; component crops are a local-feature task, so extra capacity buys latency, not correctness.
- Action (mine): evaluated ResNet / ViT / EfficientNet; chose the ~21M small variant (M = millions of learned "parameters," the model's internal dials) over the 54M/119M ones on a measured accuracy gap; kept input small (224x224 pixels - a thumbnail, not full resolution); verified the CPU result against the budget; held per-class recall above the set bar.
- Result: ~45 ms per image on CPU vs the <100 ms budget (target and achieved number, never blended); accuracy matched the larger models within an unpayable margin; then found the real remaining cost was OpenCV.js cold load, not the model.
- Learning: profile the whole path before picking an enemy; the biggest win was outside the component I optimized; label documented hardware figures as documented.

## Follow-Up Bank
1. What was the application and who set the bar? - One self-contained HTML inspection suite, solo build; the classifier sorts a crop as good / wrong value / wrong orientation / missing; the <100 ms per image was a documented design criterion in my plan so the tool stayed interactive (a "budget" = the time limit the design had to meet; 100 ms = a tenth of a second, the point below which a reply feels instant). [SAFE]
2. Did you actually optimize, or just pick a smaller model? - The optimization was against a hard budget and the delivered result was the measured 45 ms; the sizing decision is what produced it - ~21M parameters vs ~54M/~119M, with under a 2% accuracy difference on my data, so the larger models spent latency for a gain I couldn't justify. ("Parameters" = the learned internal dials inside the model; the big models carried 2.5-5.5x as many but were wrong on under 2 more answers per 100 test photos - not worth the extra time and memory.) [SAFE]
3. How do you hold the 45 ms number? - Single-image CPU benchmark, hardware not recorded in my notes; the shipped path ran TensorFlow.js in the browser (TensorFlow.js = the AI runtime running inside the web page). It's a benchmark - a timing test I ran myself, on one photo at a time on the ordinary main chip - not a floor. The 100 ms is the target, 45 ms is what was achieved - I never present the target as a measurement. [PARTIAL - labeled]
4. Why not the large EfficientNet for the extra accuracy? - Gap under 2% on my holdout (a "holdout" = examples deliberately kept back from training that the model never saw, so the score is honest); roughly 6x the parameters; ~3x slower to train; and the weights live embedded inside one offline file the factory machines open in seconds - "weights" are the parameter numbers themselves, so every megabyte mattered. [SAFE]
5. What's the compute story? - About 8 GFLOPs per forward pass at 224x224, dominated by convolutions. (A "forward pass" = one run of the model on one image; 224x224 pixels is a small square thumbnail; "GFLOPs" = billions of arithmetic operations - so ~8 billion math steps per image.) GPU is documented at under 5 ms and WebGL sits near it (GPU = the special graphics chip; WebGL = the browser's way of using it) - those are the runtime's documented characteristics, not benchmarks I ran, which is why I only quote the CPU figure. [PARTIAL - only 45 ms is mine]
6. Did the speed cost you accuracy? - 94% on the ~300-image holdout (measured: the model was right on 94 of every 100 photos in a set of about 300 it had never seen), and the small-vs-large difference stayed under the margin I'd pay for; per-class recall held above the >90% bar (recall = of each defect type's real cases, how many got caught; every type cleared 90). I won't quote exact per-class decimals - each defect class is a couple dozen images, one sample moves a point. [PARTIAL]
7. The OpenCV.js bottleneck - measured or noticed? - Stage attribution from my documented pipeline analysis (multi-MB WASM cold load before inference - WASM is a fast binary format that lets heavy code run in the browser; several megabytes of it has to arrive and start up once, the "cold load", before the first answer), not an instrumented profile. That's exactly why the stated next step is per-stage instrumentation. [PARTIAL]
8. What breaks at 10x? - Resolution, not count: fixed 224x224 input means more components is throughput, while higher-res or tiling means more forward passes per item. (Throughput = how many images per second the tool gets through; "tiling" = splitting a bigger image into several 224x224 squares so the model runs once per square.) Both answers point at the same thing - instrument the full browser path. [SAFE]
9. Alternatives rejected? - ViT (needs labeled data and compute I didn't have), from-scratch CNN (data-hungry on ~2,000 images) (CNN = convolutional neural network, the standard image-model design; "from scratch" = with no head start from pretraining on outside photos), keeping the large model and blowing the budget, and any server-side inference (running the model on a distant computer instead of the machine in front of the user - the tool was one embedded file with no server). [SAFE]
10. What went wrong / hardest part? - My assumption that the model was the app's cost center. I optimized what was easy to reason about instead of profiling what the user actually waited through. [SAFE]
11. Who disagreed? - Nobody; solo build, and inventing a stakeholder fight would be a lie. The real argument was with my own "bigger model" instinct and the "the model is the bottleneck" assumption. [GAP - stated plainly]
12. What's next / do differently? - Instrument per-stage latency first, then fix the cold load (defer/parallelize the WASM fetch; a Web-Worker parallelization of the independent comparison signals is projected at ~3.5x - projected, not measured) (a "Web Worker" = a background task inside the browser; ~3.5x = the estimated speedup from running the independent checks side by side). Retraining took about 30 minutes on one GPU, so new defect types never stalled the floor. (Retraining = re-teaching the model when a new defect type is added; ~30 minutes on a single graphics chip, from my notes.) [PARTIAL - labeled projections]
