# Q26 - a time when you had to finish a project quickly to meet a deadline

**LP:** Bias for Action (primary); Deliver Results.   **Story:** STORY 12 (AMAZON_INTERVIEW_PREP.md) - three tools in production, the eight-week solo delivery.

## Core Answer

The deadline I'd point to is eight weeks to deliver the whole PCB inspection suite - three tools - on my own. (PCB = the green circuit board inside electronic devices; the "suite" = three programs that check a board for build mistakes; "eight weeks" = the calendar window from start to all three running.)

The factory needed three checks covered. Schematic vs EBOM: does the bill of materials match the schematic - the schematic is the design drawing of the circuit, and the bill of materials (BOM for short) is the list of parts the board is built from; this check asks whether the list and the drawing agree. PCB vs Layout: does the physical board match its design file - the blueprint of its physical structure. Good Board vs New Board: does a fresh board match a known-good reference - a board already confirmed perfect. Different inputs, different algorithms (step-by-step calculation rules), different failure modes (the ways each check typically goes wrong) - and I went in with incomplete information. I'd never parsed a Gerber file (Gerber = the standard manufacturing file that tells factory machines where the copper and parts go), and I hadn't used OpenCV.js or TensorFlow.js (a ready-made image-processing library and a ready-made AI-model library, both running inside a web browser).

So I sequenced by dependency and impact instead of designing one perfect unified engine - dependency meaning what has to exist before something else can work, impact meaning how much pain each tool removes. The BOM check went first - biggest pain point, no dependencies - with its parser (the program that reads and translates that file format), a debug endpoint (a small test address that shows what the parser read, so mistakes are visible), and a reconciliation dashboard (a screen listing what matches and what doesn't) out in the first two weeks. PCB vs Layout second, because that's where the hard unknown lived: reading the Gerber files and alignment (shifting a board's photo onto the design picture so matching points line up). Board-vs-board last, because it could stand on the plumbing the first two had already paid for - the shared code, like reading files and lining up images, that later tools reuse for free. Each shipped as a complete, usable slice: one tool engineers could actually use, not three unfinished ones. A half-built unified engine would have delivered nothing at week eight.

The risk I attacked early was Gerber parsing. The spec - the format's rulebook - runs 200-plus pages (counted in the published Gerber specification; a fact about the format, not my estimate), so instead of writing my own parser I found an open-source one - free, community-owned code anyone can use - and integrated it. That bought back weeks of calendar time (my estimate of what hand-writing it would have cost - the math is in follow-up 4) - the Bias for Action call I'd defend hardest, because I didn't need to prove I could write a parser; I needed the tools shipped.

I kept the UX identical across all three - UX meaning what the tool looks like and how you drive it: same drag-and-drop (you pull files into the window), same colors, same export (saving results as a file) - so engineers learned the workflow once and I didn't rebuild the interaction layer - the parts of the software a person touches and clicks - three times. The final two weeks went to the training pipeline (running sessions that taught the engineers to use the tools) and a single-file offline build (one self-contained file that opens in a browser with nothing installed), so the tools ran on factory machines with no network.

All three landed inside the eight weeks. Fifteen engineers across two sites use them - that count comes from who attended my training and got user accounts, remembered, not from a usage dashboard - and they tell me it saves the team around twenty hours a week: total working hours the engineers believed they saved across all three tools, their reported number, not something I instrumented (never measured by the software itself).

What I'd change: get the real Gerber files and sample BOMs (real-world parts lists) in front of me before I estimate. My first risk read was guesswork until I saw the actual formats.

## Memory Anchors
- Problem: eight-week deadline (calendar window, stated in the story) for the full three-tool PCB inspection suite (three board-checking programs), solo, with incomplete information (no Gerber experience - the board manufacturing file format; new to OpenCV.js/TensorFlow.js - the browser image-processing and AI libraries).
- Customer: manufacturing engineers at two sites doing schematic/layout/board verification (checking the parts list, the design drawing, and built boards).
- Insight: ship ordered, complete slices by dependency + impact (what must exist first, and what hurts most); kill the biggest unknown early by reuse instead of building it.
- Action (mine): sequenced EBOM -> PCB vs Layout -> board-vs-board; integrated `gerber-parser` rather than writing one; identical UX across tools; training pipeline + standalone offline build last.
- Result: all three tools delivered inside eight weeks; 15 engineers / 2 sites using them (counted from training attendance and accounts, from memory); ~20 hrs/week savings (the engineers' own estimate of team time saved, engineer-reported, not measured).
- Learning: real artifacts before estimates; under deadline, reused beats proven.

## Follow-Up Bank
1. Was eight weeks aggressive or padded? - Aggressive against the unknown: new file format (Gerber), two new libraries (OpenCV.js, TensorFlow.js). It landed only because of the sequencing plus reusing the Gerber parser - the original plan assumed I'd write it, which is what made the timeline look impossible. [SAFE]
2. How did you pick the order? - Dependency and impact - what must exist before the next thing works, and which check removes the most pain. BOM check: top pain, standalone. Layout check: steepest learning curve, so second while there was slack. Board-vs-board: heaviest algorithmically (the most calculation involved), but it rode the first two's infrastructure (their shared code). [SAFE]
3. What would you cut if you were going to miss? - PCB vs Layout: most complex, least used. Shipping the other two would have delivered most of the value in roughly half the time, and I'd have phased the third (delivered it later as its own round). "Most of the value in half the time" is my rough estimate, not a measurement. [PARTIAL - self-assessed 80/50-style split from STORY 12]
4. How sure are you about the parser saving weeks? - Estimate, and a counterfactual one - a guess about a road not taken, so no data could ever exist for it: a self-written parser against a 200-plus-page spec versus an existing one I integrated in days ("days" = my recollection of that integration's effort). I'd call it two to three weeks of the eight, but I can't prove the alternative. [PARTIAL - estimate]
5. Where does "twenty hours a week" come from? - Engineers' own recollection in training and follow-ups: per-board BOM cross-checks that took them 20-30 minutes now come back in seconds. To spell it out: the 20-30 minutes is their own estimate of one manual parts-list cross-check per board, and the "seconds" is how fast the tool produces its report; the ~20 hrs/week is their total across all three tools. I never built telemetry on time saved (the software never collected usage or timing data automatically), so I say "they tell me." [PARTIAL - engineer-reported, not instrumented]
6. How do you know 15 engineers at 2 sites? - Headcount from the training sessions I ran and the accounts I provisioned (the user logins I set up for people). It's recollection, not a dashboard. [PARTIAL - qualitative]
7. How did you know each tool was done, not demo-ready? - It passed real boards before hand-off. The BOM reconciler ran a 15-BOM regression suite - fifteen parts lists with known right/wrong answers, re-run to check the tool didn't misbehave - with zero false positives or negatives on first week's real usage (it cried wolf zero times and missed zero real differences across those fifteen), catching three genuine mismatches (real mistakes the tool found on live boards, not test cases); parse of a 2,000-component BOM came in under 200 ms - reading a very long parts list in a fifth of a second. Plain-provenance note: those figures come from my own test suite and first-week use - measured, but self-measured, not audited externally. Adoption is the harder evidence - a demo nobody uses isn't delivery. [SAFE - matches canonical BOM anchors]
8. Did the AI bits work in the offline build? - No. The GPT-4o component analysis (the AI model that can see images and explain a flagged spot) ran only in the server build (the version hosted on a company computer with network access); the standalone file works with the comparison pipeline alone (the engine that marks differences in red, without AI explanations). I treated the VLM (vision-language model - AI that looks at a picture and describes it in words) as optional so the deadline never depended on network or a third party. [SAFE - canonical STORY 8 anchor]
9. Hardest moment? - Gerber parsing was the risk from day one. If I'd discovered at week six that I couldn't read the format, the deadline was dead. Attacking it in week one with reuse is what I'd repeat. [SAFE]
10. Any disagreement with stakeholders on scope? - Not in my account; the eight weeks and the three checks were fixed by me at the time. I won't invent a fight. [GAP - no documented conflict]
11. Main trade-offs? - Three slices vs one unified engine (took the slices); reuse vs write-my-own parser (reuse); identical UX vs per-tool polish (reused shell - one shared look-and-click layer for all three); shipping vs proving (getting it working in time vs proving it thoroughly correct). [SAFE]
12. Would this scale to more sites/tools? - The shared parser, alignment, and comparison modules (the reading, image-lining-up, and difference-finding parts) were reused as-is, so a fourth check starts from infrastructure, not zero. That's my read, not a load test (I never stress-tested it at many more users or boards). [PARTIAL - qualitative]
13. Do differently? - Get real artifacts before estimating, and bound risk explicitly in week one (name upfront the piece most likely to blow up) rather than by instinct. [SAFE]
