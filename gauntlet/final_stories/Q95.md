# Q95 - a time when you took a big risk and it failed

**LP:** Bias for Action (primary - the calculated single-file bet); Earn Trust (ownership of the unchecked assumption); Learn and Be Curious (the channel-verification rule)   **Story:** STORY 4 standalone build - the base64 single-file bet that broke the ~20 MB email-attachment limit. Distinct from Q14 (risk that *succeeded* - the alignment bet) and Q7 (browser-capability/IE11 failure - deliberately not retold or merged).

## Core Answer

The big risk that failed: I bet that one file could carry the whole delivery of my tool through email - and the file didn't fit the email.

The setup. I'd built a PCB inspection suite - BOM (bill of materials: the parts list every board should match) reconciliation, defect classification - running on a Flask server (a small web program: one central computer the users' machines would call over the network). The users' factory-floor machines had no internet, no installs, minimal IT. The server plan was dead. So I made the bet: one self-contained HTML file - the single-file design: the whole tool inside one double-click file, nothing kept outside it - everything embedded (packed inside), the browser libraries (ready-made code from others the tool borrows), the trained model (the AI's learned numbers), the app - with base64 encoding (a way of rewriting non-text pieces as plain-text characters so they can sit inside a text file) so nothing is fetched at runtime (the file downloads nothing when opened). No CDN (pieces hosted online for the file to pull at open time), no companion files, double-click to run. A zip would have reintroduced the failure where someone moves the HTML without its parts, so I accepted a size hit - a bigger file - on purpose. The upside was real, and I moved fast because it unblocked people.

The artifact (the thing I built - the file itself) worked. One file, roughly 25 megabytes - the size as I remember the shipped file; my account, not an instrumented measurement - opened in seconds, and the analysis matched the server build (the version that needed the central computer) on the known boards I checked. Embedding everything plus the base64 overhead - it inflates binaries by about a third (a fixed property of that text encoding: the rewritten parts come out roughly a third bigger than the originals they wrap) on top of the libraries and model weights (the learned numbers inside the AI) - is what made it that size.

The failure was the channel - the delivery route, not the tool. I distributed by email, and some mail systems cap attachments at 20 megabytes (an attachment limit: the biggest file a mail system lets ride along with a message; the 20 MB figure is the mail systems' own rule - a constraint of the pipe, not my estimate). The file was over. The one-file design that made delivery easy was the thing that couldn't fit the pipe I chose. I'd verified the file; I never verified the channel. That's on me. The cost was real: that path closed, and the file went out on USB drives (plug-in memory sticks) instead - slower, clunkier, especially for the engineers at the other site.

What I did after was bounded. USB stayed as a distribution route. The size fix - compressing (shrinking) the embedded parts more aggressively, likely bringing the file to about 15 megabytes, under the cap - I designed in reflection and never built (the 15 MB is my estimate of what that unbuilt fix would have produced: a plan, not a measurement). I'm not going to call a projection a result.

What I learned: a calculated risk includes the delivery constraint, not just the artifact. Now I check the pipe like I check the target - attachment limits, quotas, the actual channel - before I build around it. The bet itself was right; it's what got the tool onto locked-down machines. The unchecked assumption is what failed.

## Memory Anchors

- Problem: factory-floor machines were locked down (no internet, no installs, minimal IT) - the server build couldn't reach the users; delivery, not code, was the blocker
- Customer: manufacturing engineers on the floor and at the other site, receiving the tool remotely
- Insight (the bet): one embedded HTML file kills the server, the installs, and the broken-dependency failure mode - high upside, accepted size cost
- Action (mine): took the single-file architecture call solo; base64-embedded the browser libraries (OpenCV.js, TF.js, PDF.js, XLSX.js), model, and app into one double-click file (base64 = rewriting the non-text parts as text so they fit inside one file); distributed by email; after the cap failure carried distribution on USB; designed (did not build) an aggressive-compression fix projected at ~15 MB
- Result: artifact worked - ~25 MB, opens in seconds, matched the server build on known boards - but exceeded 20 MB email caps; real cost: email path closed, USB fallback carried the rollout
- Learning: risk math includes the pipe - verify delivery constraints (attachment limits, quotas) before building around them; never present an unimplemented fix as a result

## Follow-Up Bank

1. Was this really a failure, or just a trade-off? - A partial failure of a specific bet. The bet was that one embedded file (all the tool's parts inside a single double-click file) would be an easy distribution channel; the file worked, but at ~25 MB it broke the 20 MB attachment caps some email systems use (an attachment cap = the largest file size a mail system accepts on a message - a fixed rule of the mail systems, not of my file). The tool succeeded; the distribution assumption didn't, and the fallback cost - USB drives - was real. [SAFE]
2. Why was the file so big? - Embedding the browser libraries plus the model weights and the app itself pushed the single file into the tens of megabytes - I say about 25 (what it counts: the size of the delivered file; where it came from: my memory of the shipped build, not an instrumented measurement; how solid: deliberately soft, my account). On top of that, base64, the encoding that squeezes binaries into an HTML text file (it rewrites the non-text pieces as plain-text characters), adds roughly a third over what it wraps (a fixed property of the encoding - solid arithmetic; the softness is only in the parts it starts from). I'm not deriving the total from the library sizes; ~25 MB is my account of the shipped file. [SAFE - canonical phrasing, no size-chain math]
3. Why not a CDN or separate files? - A CDN (pieces hosted online for the page to download when it opens) needs internet; the floor machines don't have it. Separate files or a zip reintroduce the failure where someone moves the HTML without its dependencies and the tool breaks. The single file eliminated that - I took the size hit deliberately. I just didn't check the size against the delivery channel. [SAFE]
4. You said a fix to ~15 MB - why didn't you ship it? - Because I identified it in reflection, after distribution, and "about 15 MB" is a projection, not a measured build (what it counts: my estimate of the file's size after compressing - shrinking - the embedded parts harder; where it came from: planning on paper, never built; how solid: the weakest kind - an untested guess). The mitigations I actually implemented were USB distribution alongside email. The compression is what I'd do next, and I label it that way. [SAFE - honest boundary is the credibility of the story]
5. How is this different from the browser-compatibility failure on the same build, or a risk that worked? - Different assumption each time. That one was a capability assumption - that the fleet ran modern browsers with WebAssembly (WebAssembly = the way a browser runs compiled code quickly, which the tool's imaging libraries need; owned in a separate story, not blended here). My successful-risk story is the alignment bet - it paid. Here the bet paid on the artifact and failed on the channel. All three trace to checking the thing I built instead of the environment or pipe it ships through - which is why the lesson generalizes. [SAFE]
6. How do you know the file itself was fine? - I ran the same known boards through both builds (both builds = the single file and the server version) and compared the outputs - by hand, plus a small automated diff (a simple script that lines up the two results and flags any difference). No parity percentage; the known-board set wasn't a measured sample. [SAFE]
7. What was the actual cost - how many bounces, how much time? - None measured. The email path closed and USB drives carried distribution; it was slower and clunkier, especially for the other site. I never counted failures or lost hours, and I won't invent a number now. [GAP - concede]
8. Hardest part? Disagreement? - Hardest was admitting the failure was a half-checked assumption while the tool itself worked - it's tempting to file 25 MB under "packaging nit." No documented pushback from others: solo project, and I'd be inventing a scene to claim one. The argument was with my own default that if the artifact works, delivery works. [GAP if demanded as conflict story - stated plainly]
9. Larger scale? Do differently? - One tool, one rollout; no larger-scale instance of the new habit is documented, so I don't claim one. Differently: check delivery constraints - attachment limits, quotas, throughput (how much can move through the route at once) - before choosing the packaging, and test the compressed build early so size is a measured input to the architecture, not an after-the-fact finding.
