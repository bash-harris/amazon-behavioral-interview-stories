# Q8 - tell me about time where you completed a project on your own

**LP:** Ownership (primary - solo, start to shipped artifact); Invent and Simplify (strong - 80-line script over a toolchain, complexity deliberately avoided); Think Big (narrow but defensible - deleting the server against the default); Deliver Results (touch)   **Story:** STORY 4/15 "The Standalone HTML That Replaced a Server," told only from the artifact-backed account on disk

## Core Answer

The project I finished solo was turning my PCB inspection suite into one file you double-click - no Python, no server, nothing to install. (PCB = printed circuit board, the flat board with electronic parts soldered onto it that is inside most electronics. Python = a programming language the old version had to have installed on the machine to run at all.) I built the suite solo: browser tools - programs that run in an ordinary web browser - where manufacturing engineers reconcile a BOM (bill of materials: the parts list for a board) against the board layout (the design drawing of where every part goes) and classify defects (sort the faults into kinds); a Flask backend (a small server program written in Python) parsed BOMs and served the trained model - the AI part that had learned to judge a board. Users were the problem: factory-floor machines, restricted network, no installs, minimal IT - no tech-support staff to call. Every rollout meant installing Python and configuring the server - an IT ticket (a formal install request to the IT department) the team couldn't absorb. The blocker between a working tool and a used tool was delivery, not code. I was the only engineer; the call was mine: kill the running server, ship one file they already know how to open.

I started by auditing what the browser couldn't fetch at runtime (while the file was actually being opened and used). The app code was already client-side - it already ran on the user's own machine inside the browser. The only thing living on the server was the trained model - a TensorFlow.js topology file (the blueprint of how the model is wired together; TensorFlow.js is a standard format for running AI models in a browser) plus roughly 3.4 megabytes of binary weight shards. Plain words: the "weights" are the numbers the model learned during training, stored as raw non-text data in chunks ("shards"); the ~3.4 MB is the on-disk size of that chunk - I looked at the file and read it off the computer's own file properties, so it's a measured file size, not an estimate. That had to travel inside the file.

So I wrote compile_tool.py - a small helper program (the .py means it's Python) - 80 lines of code, which is just the line count of the file I wrote and counted, checked in with the source (stored alongside the rest of the code). It reads the model manifest (a list file naming the model's parts and their correct order), concatenates the shards in manifest order - joining the chunks one after another like re-gluing pages of a book; the order the files happen to sit in on a computer breaks a multi-shard model - base64-encodes and injects topology and weights into the HTML as JavaScript constants. Base64 is a standard trick that rewrites raw binary data as safe plain-text characters so it can be pasted into a web page file; the constants are fixed values the page's program reads. The loader decodes them at startup and builds the model from memory - the page's startup code undoes the text-rewrite and assembles the model fresh in the computer's working memory each time it opens, so no extra files are needed. Then I embedded the browser libraries - OpenCV.js, TF.js, PDF.js, XLSX.js - the same way, so the file fetched nothing at runtime. Those are ready-made code packages other people wrote that my tool relied on: OpenCV.js looks at images, TF.js runs the AI model, PDF.js reads PDF documents, XLSX.js reads Excel files. What shipped was a single self-contained HTML - one web page file with everything inside it - that ran on the factory machines with no server and no installs: one file, a few tens of megabytes, opens in seconds. That size and speed are a rough feel, deliberately an order of magnitude rather than a benchmark.

State was the other server dependency - the data the tool has to remember between uses. The tool keeps per-board training labels - good, bad, ignore (the engineer's judgement calls on what the tool flagged, which also feed back as the model's training examples) - and the standalone build keeps them in localStorage, surviving restarts with nothing behind them. localStorage is the browser's built-in notepad: data saved on that one computer, not on a server. Packaging went from a by-hand, order-dependent assembly to one deterministic command - one command that produces the exact same file every time it's run.

What this won: zero installs on locked-down machines, trade-secret board layouts that never leave the laptop, a reproducible build (the shipped file can be rebuilt identically from the source). What it gave up: no update channel - a way to push new versions to users automatically - so every fix means re-sending the file; no aggregation across machines - nobody's results get pooled into one central place; and startup pays to decode the embedded model and libraries - opening takes a few seconds longer because the page has to undo the text-rewrite and reassemble the model and the code packages every time it opens.

The lesson was about verification, not engineering. I proved the standalone matched the server by running the same known boards through both builds and comparing the outputs - by hand, with a small automated diff (a throwaway comparison script that prints the two builds' results side by side and shows where they differ). My rule now: never quote a measurement I didn't take. And design standalone from day one - retrofitting delivery (adding it afterwards) is harder than designing it in.

[SAFE]
2. The floor has no internet - how does it run with no network at all? - Everything travels inside the file. The app code was already client-side; I embedded the model, and the browser libraries the page used to fetch at runtime - OpenCV.js, TF.js, PDF.js, XLSX.js - went in the same base64 way as the weights. No server, no CDN, no installs. (A CDN is a rented file-hosting service that normally delivers code libraries to browsers over the internet - with the libraries baked into the file, there's nothing left to download.) [SAFE]
3. Why one file instead of a zip or an installer? - A zip adds a failure mode: the files must stay together, and moving just the HTML breaks the tool. An installer is precisely what IT wouldn't approve on those machines. Base64 costs ~33% overhead on what it wraps - the weights and the libraries - meaning the text-safe rewrite makes the embedded parts about a third larger than the originals, which is part of why the single file lands in the tens of megabytes; single-artifact delivery is worth it. [SAFE]
4. Hardest part? - Making the model travel correctly. TF.js stores weights as manifest-referenced shards (the learned-numbers data split into chunks that a list file says how to reassemble); concatenating in filesystem order is wrong, so the script merges in weightsManifest order, and the page loader had to build from decoded constants (rebuild the model at open-time from the text-rewritten numbers pasted inside the file). The guard matters too: if the embedded block is missing, the loader refuses rather than half-works - it fails loudly instead of limping along on a broken model. [SAFE]
5. Why Python instead of Webpack or a JS bundler? - (Webpack is the standard toolchain for stitching many JavaScript files into one.) The job is reading two files, concatenating bytes, base64-encoding, and replacing one string - no module graph, no minification, no source maps (none of that machinery's jobs: tracking which code files import which, shrinking the code, or keeping a map back from shrunk code to the human-readable original). It's 80 lines - the line count of the file itself, counted from the code. (My notes said "about 200" - the notes were wrong; I checked the file.) A bundler's config surface isn't justified for a step that runs once per release. [SAFE]
6. How did you know the standalone matched the server version? - I ran the same known boards through both builds and compared the outputs: by hand on the results, plus a small automated diff that dumped each item's scores from both builds so mismatches stood out (a comparison script printing each check's numbers from both versions side by side). No parity percentage - a single "how identical" figure - the known-board set wasn't a measured sample, so I quote none. [SAFE]
7. What about build time, before vs after? - Qualitative only: hand-assembled and order-dependent, tens of minutes, broke periodically -> one deterministic command finishing in seconds, timed with a hand stopwatch. No instrumentation exists, so no decimal timings. In plain terms: both figures are my own rough feel - the stopwatch was mine, nothing was logged - and that's exactly why this answer is only partial rather than a hard before/after number. [PARTIAL]
8. What happens at 10x - 100 machines, 100 boards a day? - (The 10x and 100s are a what-if, not a result I achieved.) Per-user load is the frugality win: fully client-side, so 10x users breaks nothing I maintain - each machine does all its own work, so more users costs me nothing to run. The ceilings are organizational: fixes require re-distributing files, and labels/calibration can't aggregate across machines - no fleet learning (nobody's lessons pool to make everyone's tool better). A service worker was the middle path I considered - cache the libraries, keep the small file - but workers need HTTPS to register, which the floor machines didn't have configured. (A service worker is a browser background helper that can store the big files once on the machine so a smaller tool still works offline; the browser only allows it on encrypted HTTPS pages.) [SAFE - reasoning, no claims of scale achieved]
9. How did versioning work across builds? - Badly, and honestly: I edited the title string by hand - that's the "v26 (Hardcoded Model)" in the file, a version number I typed into the page title myself, bumped by hand each release. A git-hash stamp was planned, never built (an automatic code-version identifier burned into each build). With no update channel, a wrong-version file in someone's hands is undetectable - that's the architecture's real cost, not trivia. [SAFE]
10. Did anyone disagree with deleting the server? - No documented pushback; it was a solo project and I'd be inventing a scene to claim one. The disagreement that did exist was with my own default assumption that tools ship on servers - the won/gave-up list is the argument I had with myself, written down. [GAP - stated plainly, not papered]
