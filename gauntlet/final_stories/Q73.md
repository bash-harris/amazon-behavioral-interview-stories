# Q73 - walk me through a feature you developed

**LP:** Invent and Simplify (primary); touches Deliver Results and Customer Obsession.   **Story:** BGSW PCB Inspector Suite - the BOM reconciliation feature (AMAZON_INTERVIEW_PREPARATION.md STORY 1).

## Core Answer

I'll walk through the BOM reconciliation feature, because the best part of the design didn't come from me. (A "feature" is one tool inside the bigger software suite; "BOM" is short for bill of materials - the list of every part that goes on a circuit board. "Reconciliation" just means checking that list against reality and reporting where they disagree.)

The problem: the manufacturing engineers verified every board by hand - cross-referencing the SAP-exported bill of materials against the Altium layout PDF, entry by entry. (SAP = the software the factory uses to manage production; it exports the parts list. Altium = the design tool the board is drawn in; its layout PDF is the drawing showing where each part belongs. Cross-referencing = checking the two lists line by line.) They told me that ran 20 to 30 minutes a board - what it counts is human minutes on one board, where it came from is the engineers' own estimate of their routine, and how solid is: remembered, not a stopwatch study. I was the only engineer building the replacement: upload two files, get a report of missing, extra, or mismatched parts - for users who are engineers on a floor, not developers.

Design first. I didn't hand-roll parsers - a "parser" is code that reads a file and pulls out the useful content; instead of writing that from scratch, XLSX.js read the Excel and PDF.js read the layout, ready-made browser components. And I made one call early - match components by the shape of the reference text, not by column position. (Every part has a label on the board, like R1 for resistor one; matching by "shape" means recognizing the label by what it looks like, wherever it sits.) Columns move between exports, so position lies; the reference pattern is the only consistent signal. I considered a config file of column mappings and rejected it: a settings file spelling out "column A is the part number, column B is the quantity," which someone would have to edit every time an export changed - asking those users to maintain mappings is a worse experience than a parser that just works.

Then production data broke the baseline one edge case at a time. Each break became one small, isolated normalization stage - a separate cleaning step that rewrites messy text into one standard form before the comparison: strip the `MP_` process prefix (stray characters the export system sticks in front of some part numbers); unwrap SAP's hyperlink cells, which come back as objects, not strings (a cell formatted as a clickable link arrives as a bundle of data, not plain text); detect DNP - "do not fit," a spot the design leaves empty on purpose - so an intentionally-empty position isn't flagged missing.

The decision that mattered most came from a customer. My parser saw `R1||R2` and dropped it as garbage - it treated the entry as unreadable junk and ignored it. An engineer explained what it actually means: one physical position, either part, depending on board variant - "variant" being a version of the same board - so it should match either reference, not vanish. I could read the string; I couldn't see the manufacturing intent. That correction reshaped the feature: I built a variant splitter handling both separators - code that splits the combined label into each acceptable part, recognizing both the `||` and `/` dividers.

The build stayed simple on purpose. Isolated stages, so a new case couldn't regress an old one (a "regression" is an old case breaking when a new one is added), backed by a regression suite of 15 production BOMs covering every edge case I'd found. What that counts: 15 real parts lists from different board versions and export setups, saved as an automated re-test checklist - where it came from: production files; how solid: it's my own test set, so every claim from it is scoped to those 15. I ran it after every change - it was fast enough that there was no excuse to skip.

Outcome: all 15 reconciled with every match correct - on all 15 test files the tool's answer matched a human's, entry for entry - and the report came back in seconds against their 20-to-30-minute baseline (seconds being machine runtime, minutes being human time). In the first week of use it caught three real mismatches that manual review had missed - what it counts: genuine problems found in week one; source: engineer reports; solidity: real, but I have no confirmation log for each - reported, not instrumented.

What I'd change: interview the engineers and collect sample BOMs *before* writing the parser. The variant semantics came from a person - I should have gone to the person first.

## Memory Anchors
- Problem: hand cross-reference of SAP BOM vs Altium layout PDF, entry by entry; user-reported 20-30 min/board.
- Customer: Bosch manufacturing engineers - non-developer users of the report.
- Insight: reference-pattern matching beats positional parsing; the floor semantics (`R1||R2` = either part at one position) can't be inferred from data.
- Action (mine): solo built the pipeline - XLSX.js/PDF.js over hand-rolled parsers; isolated normalization stages (MP_ strip, recursive hyperlink-cell unwrap, DNP detection); variant splitter from the engineer's correction; 15-BOM regression suite run after every change.
- Result: 15/15 BOMs with every match correct; report in seconds vs. their reported baseline; 3 real mismatches caught week one.
- Learning: get real customer artifacts and the domain person in front of me before coding, not after each production failure.

## Follow-Up Bank
1. What was the baseline parser's hit rate before the fixes? - "Hit rate" meaning how often the very first version read a real file correctly with no changes. The bare reference pattern handled roughly 70% of real BOMs; the rest arrived as production failures, one edge case at a time - so the 70% is the mirror of the failures I saw crossing my desk, a remembered tally, not a logged rate. 70% was never a shipped target - I kept going until the 15-BOM suite was clean. [SAFE]
2. Why pattern matching over positional parsing - isn't regex fragile? - ("Regex," short for regular expression, is a compact text pattern used to recognize strings by their shape.) Positional parsing - trusting the part label always sits in the same spreadsheet column - is the fragile one: references sit in column A in some exports and column C in others. Pattern matching - spotting the label by what it looks like, wherever it appears - is the robust one. The only consistent signal is the text shape. Config-file column mappings were the rejected alternative - a settings file listing which column means what - the users can't maintain mappings. [SAFE]
3. How did you know the variant behavior was right, not just convenient? - The engineer was the floor authority - the person on the production line who knows how boards are actually built; he explained the semantics and I changed the code. Then proved it mechanically: `R1||R2`, `R1/R2` (the two divider styles for "either of two parts at one spot"), three-way variants (one spot accepting any of three parts), and malformed `||R1` / `R1/` (half-written notations that must not be mistaken for valid pairs) - each checked for correct per-reference extraction: that the splitter pulled out exactly the right individual part labels and rejected the broken ones. [SAFE]
4. How was it measured? - The 15 BOMs - 15 real parts lists - are representative production files across board variants (versions of the same board) and SAP export configurations; the suite runs in about two seconds (machine time for the whole checklist, which is why it gated every change). Zero false positives and zero false negatives - nothing wrongly flagged (crying wolf) and nothing wrongly passed over (a real mismatch missed) - means *on that suite*, my own 15-file test set - I'm not claiming every format that will ever exist. [PARTIAL - suite-based, not a production-wide measurement]
5. How fast, and does it scale? - A 2,000-component BOM - the biggest real file I handled, counting its part rows - parsed in under 200 milliseconds: less than a blink of machine time, not a human wait. Main loop is O(n) over BOM entries, layout O(m), reconciliation a set intersection (finding the labels the two lists share) - "O(n)" is programmer shorthand for work that grows in step with the input: double the parts, roughly double the time, no explosive growth - linear overall, so size isn't a design limit. [SAFE]
6. How reliable are the headline numbers? - All engineer-reported or story-recorded: the 20-30 minute baseline has no timing protocol or sample count - nobody timed it and no record says how many boards that average came from; the three week-one mismatches were real but I can't produce a confirmation log for each - known through engineer reports, not a tracked system. I label them reported, not measured. [GAP - no instrumentation exists]
7. What happens on a format you've never seen? - Graceful degradation: plain terms, if it sees something unrecognizable it moves on instead of crashing - anything off the reference pattern is skipped, not crashed - but a silent skip is data loss, a line vanishing from the report unnoticed, so the server build (the version running against the company server) added a debug view exposing the raw entry and each parsing step - a screen showing the original text and what the program tried with it - so an engineer can flag a new format instead of having it vanish. [SAFE]
8. Hardest part / what went wrong? - Going wrong was mine: I dropped valid variant references because I'd assumed the notation was garbage. A customer caught my mistake. The hardest part was reactive discovery - learning each tricky format only after it broke on a real file: each edge case arrived as a production failure. [SAFE]
9. Who owned this? - Solo. I built the parser, the normalization stages (the cleaning steps), the splitter (the either-part code), and the suite. The engineer contributed the semantics - how boards actually work - not code. [SAFE]
10. Trade-off you'd defend again? - Correctness over breadth. I prioritized zero false results on the cases I'd seen - no crying-wolf flags and no missed mismatches (the two ways a report can be wrong, per follow-up 4) - over claiming support for everything, and kept every fix an isolated stage instead of one clever parser - one big do-everything program. [SAFE]
11. What would you do differently? - Collect representative BOMs - real parts lists covering the formats users actually export - and interview the users before writing code - the first variant notation should have been a test case, a saved check in my suite, not an incident, a live production failure. [SAFE]
