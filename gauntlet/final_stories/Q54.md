# Q54 - tell me about a time you saw a problem and implemented a solution
**LP:** Invent and Simplify (primary); Ownership; Customer Obsession   **Story:** STORY 9 "Building the Training Data Collector" (observed problem + the solution I designed and built)

## Core Answer
The problem was sitting right in front of me: my defect classifier had no training data, and the only way to get it was slow and error-prone. A defect classifier is a program that looks at a photo of a circuit-board part and sorts it by what's wrong with it. Training data is the pile of example photos, each with its correct answer written down, that the model learns from.

I was building the ML piece (machine learning - the part of the software that learns from examples) of the PCB inspection suite (the set of tools that check factory circuit boards for defects; a PCB is the green circuit board inside every electronic device) - take a cropped image of a component (a photo of a single part, cut out of the whole-board picture) and call it good, wrong value, wrong orientation, or missing. The model is only as good as its labels (the recorded correct answer for each picture, like the answer key for a test), and the images I had were unlabeled boards, no link between a picture and its answer. The obvious fix was a spreadsheet: open an image, look at it, type a label, repeat. Across the roughly 2,000 images I wanted - that number is the planned size of the training set, my own target count, not something instrumented - at maybe 30 seconds each (my own estimate of how long spreadsheet labeling takes by hand, not a timed study), that's a full day of clicking - and one fat-fingered label poisons the set the engineers would trust (a mistyped answer gets baked in and quietly teaches the model the wrong thing).

So I stopped looking at the labels and looked at the bottleneck. It wasn't the judgment, it was the interface. I built a tiny desktop tool - a small program with its own window running on one computer, not a website. One image at a time, keyboard shortcuts - G for good, number keys for the defects - next image loads itself. I kept it deliberately bare: any extra chrome (fancy buttons, colors, or decoration) just slows down the labeler. Python's built-in Tkinter for the window (Tkinter is the basic window-making toolkit that comes free with Python, the programming language), Pillow to show the picture (a standard free add-on that displays images), pandas to write the file (a common tool for saving spreadsheet-style tables).

The invention was mostly in what I chose *not* to build. I thought about a web labeler (the same job as a tool running in the browser) and rejected it - a local server, file serving, browser quirks, all to buy nothing for a single-machine tool (that's the plumbing of a background program on my laptop serving the images to the browser, plus every browser behaving a little differently). Tkinter ships with Python; the only extra was Pillow. I shaped the output from two directions: a flat CSV, because that's the sheet the engineers already live in (a CSV is a simple rows-and-columns file that opens straight into Excel), and columns matched exactly to what the training pipeline already read (the automated steps that feed the labeled images into the model), so no conversion step. The schema is the interface (the schema being the file's exact column layout), so the next dataset reuses the workflow untouched.

Two things I added because the data mattered more than the demo: a skip key for blurry or ambiguous images, sent to a separate file instead of forcing a guessed label into the set, and a resumable session (close the tool and it picks up exactly where you left off), because 2,000 images won't fit in one sitting.

The result: per-image time went from about 30 seconds to about 3, and the output landed already in the format the pipeline consumed. What that counts is the time to look at one picture and record its answer; both figures are my own estimates from doing each method by hand, not instrumented - solid as "roughly an order of magnitude faster," soft as exact seconds. That set trained the classifier the engineers got.

What I'd do differently: batch-label near-identical crops (give a whole group of almost-the-same part photos one shared answer instead of clicking through each). Many were the same component at a slightly different angle, and a "label all these" action would've shaved the remaining time.

## Memory Anchors
- Problem: classifier had no labeled data; manual spreadsheet labeling ~a day for 2,000 images and error-prone.
- Customer: manufacturing engineers who'd rely on the defect classifier; the labeler (me) needed to be fast and correct.
- Insight: the bottleneck was the labeling *interface*, not the labeling judgment.
- Action (mine): built a bare keyboard-first Tkinter tool (Pillow display, pandas CSV), skip key + resumable session, CSV schema matched to the pipeline.
- Result: ~30s -> ~3s per image; pipeline-ready output; dataset trained the classifier.
- Learning: batch-label near-identical crops next time.

## Follow-Up Bank
1. Who's the customer - did you build this just for yourself? - End customers were the manufacturing engineers who needed the classifier; the labeling step was the bottleneck between them and a model they could trust. I designed around the person labeling because a sloppy dataset makes a shaky model for the floor. [SAFE]
2. Why Tkinter and not a web tool? - Simplest thing that met the need. Web meant a local server, file serving, browser-compat work; Tkinter ships with Python, needed only Pillow, runs anywhere Python runs (Tkinter = the window toolkit included free with Python; Pillow = the standard image-display add-on - neither needs anything installed on the factory machines beyond Python itself). Trade-off is a plainer UI, which was fine for an internal tool. [SAFE]
3. Where did the design ideas come from? - Two sides. Externally I weighed the approaches (web labeler vs built-in Tkinter/Pillow/pandas) and picked on the constraint. Internally I shaped the CSV around the engineers' Excel familiarity and matched the columns to the pipeline so there'd be no conversion step. [SAFE]
4. How did you handle an image that's both wrong-value and wrong-orientation? - One label per image forces a primary-defect call, which is what training needs (the model learns best when every picture has exactly one right answer to practice against). Genuinely ambiguous ones I skipped to the separate file rather than coin-flipping a label in. [SAFE]
5. Why CSV and not JSON? - Simpler to generate, opens in Excel the team already used, and the labels are flat (filename, label, timestamp), so nested JSON adds structure with no benefit (JSON = a common way of saving data as nested, indented text - built for complex records, not a simple list). [SAFE]
6. What complexity did you deliberately avoid? - No web stack/server, no label-format conversion, and I kept it single-label; multi-label would've changed the pipeline's output layer and loss (the model's final decision step and the error signal it trains against), so the simple boundary was the right call for now. [SAFE]
7. How confident are the time numbers? - 30s and 3s are my own estimates from doing both by hand, not instrumented; the "full day" for 2,000 is the 30s figure scaled. What they count is the time to give one picture its correct answer, start to finish. The real point was order-of-magnitude faster, in the right format. [PARTIAL - estimates, label honestly]
8. Hardest part? - Resisting the urge to make the tool "nice." The discipline was keeping it bare so the labeling stayed fast. [SAFE]
9. What would you do differently? - Batch-label near-identical crops; grouping them would've cut remaining time and shown how much of the set was duplicate content. [SAFE]
