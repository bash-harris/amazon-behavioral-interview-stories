# Q66 - describe a time you simplified a complex process

**LP:** Invent and Simplify   **Story:** Tab Scroller - the token-saving AI command pipeline (rule engine -> pre-filter -> batched extraction -> triplet compression)

## Core Answer

The process I simplified was how my Chrome extension, Tab Scroller, answered typed commands - you type something like "close all my YouTube tabs" and the extension carries it out. The first design had one path for everything. Every command - even "close all my YouTube tabs" - ran the same way: grab every open tab, extract the full text of each page one at a time ("extraction" simply means pulling the readable text out of a web page), and ship the whole pile to Gemini or a local model - an online AI service like ChatGPT, or an AI program running free on the user's own computer. Cost and delay were set by the hardest case and paid by every case, and with the network down, nothing worked at all. That was complexity in the worst sense: the process couldn't tell a trivial request from a hard one.

My insight was that most commands don't need a model. So I replaced the one path with a four-stage pipeline - a fixed sequence of steps like an assembly line, where most commands never reach the paid station.

Stage one is a local rule engine - a built-in list of set phrases the extension recognizes and carries out on the user's own computer. "Close all YouTube tabs", "find duplicates", "group by domain", "mute this site" - those are patterns, not language understanding. They match and execute on the machine, zero API calls - zero trips to the paid AI service. Stage two is a pre-filter that runs before any extraction - like pulling only the possibly-relevant files out of a stack of folders before reading a single word: it scores tabs against a fixed category map and keywords and keeps only the handful that could matter. Stage three pulls page data in parallel batches instead of one at a time - reading ten pages at once instead of one after another. Stage four compresses each page into subject-predicate-object triplets - tiny sentence-shaped facts like "this page - is about - a guitar amp", boiling a page down to a pile of sticky notes instead of shipping the whole text - so the prompt the model finally sees is small. Throughout, "token" is the unit AI services charge by and take time to process - roughly three-quarters of a word - so fewer tokens means less money and less waiting.

The after picture is design targets written in my implementation guide, and I say it that way: a fifty-tab command goes from about 50,000 tokens to roughly 3,000 - that's the amount of text shipped to the paid AI, about seventeen times less; from about eight seconds to three - that's how long the user waits for the command to finish; and the rule path serves around 70% of commands with the network off - seven in ten commands handled with no internet at all. None of these were measured on a running system; they're goals the design sets itself.

The complexity I avoided was treating the model as the default - a bigger model isn't what closes a tab. And I didn't rip out the expensive path either: the rules stay deliberately conservative, and anything ambiguous falls through to the full pipeline. The simplification was routing, not deleting - deciding which station of the assembly line each command actually needs. What I learned: before reaching for a smarter model, check how many of your requests were never hard to begin with.

## Memory Anchors
- Problem: every command, trivial or hard, paid the same all-extraction-all-API path - slow, costly, dead offline (read every page, paid AI for everything)
- Customer: heavy tab user (me); speed, cost, and working without network
- Insight: most commands are pattern-matching, not language understanding - don't pay the model for them
- Action (mine): staged pipeline - local rule engine (on-device set phrases) -> keyword/category pre-filter (relevance shortlist before reading pages) -> parallel batched extraction (read pages in groups of ten) -> triplet-compressed prompts (boil each page to sentence fragments so the AI sees tiny text)
- Result: projected 50k->~3k tokens (text sent to the paid AI), ~8s->~3s (user wait time), rule path serves ~70% of commands offline (no internet) - design targets from the guide, not measurements
- Learning: simplify by routing around complexity, not deleting it; check how many requests were never hard before scaling the model

## Follow-Up Bank
1. What exactly was complex before, and what made it simpler? - One uniform path: query all tabs, sequential full-text extraction, send everything to the model. Now: rules handle common shapes with no API call, a pre-filter shrinks the tab set first, extraction runs in parallel, prompts carry compressed triplets. Same outcomes, far less work per command. In plain terms: common requests are answered free on the user's own computer, only plausibly-relevant pages get read, they're read in groups, and only the boiled-down facts ever reach the paid AI. [SAFE]
2. Are those numbers measured? - No. They come from my implementation guide's "Expected Performance Gains" table, and I present them as design targets. In plain words the targets say: about seventeen times less text sent to the AI, wait time on a fifty-tab command projected from ~8 to ~3 seconds, and ~7 in 10 commands projected to work with the internet off - expectations set at design time, not results read off a stopwatch. What is real in code: the rule engine makes zero API calls, the pre-filter runs before extraction, and extraction batches ten tabs at a time. [SAFE - labeled projected]
3. Where does the 50,000-token baseline come from? - Rough engineering math: ~1,000 tokens of page text per tab across a fifty-tab window, plus the prompt. A token is roughly three-quarters of a word, so ~1,000 tokens is about one dense page of text. A per-tab text budget, not instrumented traffic. [PARTIAL - estimate, stated as such]
4. What drives the 8s->3s? - Sequential extraction dominated the before time (reading ten pages one after another was the slow part; my guide's own batching test expectation: ~5s -> under 1s - one-at-a-time reading of a tab group projected to drop below a second when the ten are read at once); the rest is model latency - the AI service's own think-time before answering - on a much smaller payload. A component-level estimate, not an end-to-end benchmark. [PARTIAL - estimate]
5. What's the basis for "~70% offline"? - The share of my own command habits that fit the rule set (group/close/bookmark/pin/mute by site, duplicates, domain clusters, inactive tabs). "Offline" here means the command is answered entirely on the user's computer with no internet at all. A design estimate - telemetry was never shipped, so I don't state it as measured usage. [PARTIAL - own the no-telemetry gap]
6. Cost per query? - Before path  $0.50/query at ~50k token payloads; the compressed, routed design projects  $0.03. Pricing arithmetic on projected token counts, not billed results. In plain words: fifty cents versus three cents per command, and only if the text-shrinking targets actually hold. [PARTIAL - projected]
7. How does the pre-filter decide relevance without the model? - Deterministically - by fixed rules, not judgment: a domain-category map (coding, dev, docs, video, social, shopping, news, work, learning) plus keyword scoring on titles and URLs; keeps the top ~30%, between five and thirty tabs, and fails back to the full set if nothing scores. Sub-millisecond, zero tokens - it runs faster than a stopwatch can catch and sends nothing to the AI service. [SAFE]
8. What alternatives did you reject? - A bigger model for everything (pays latency, money, and privacy for pattern matches); embeddings from day one (numeric summaries of text that let you find related items by math instead of keywords - heavier than the problem warranted; deferred to Phase 2); batching alone without routing (still calls the model on every command). [SAFE]
9. What if a rule doesn't match? - Rules are intentionally narrow. No match returns null and the command falls through to the full AI path. The failure mode is "slower," never "wrong." [SAFE]
10. Hardest judgment call? - Deciding what didn't need the model. Dumping everything into an LLM is easy; I had to sort commands into pattern-versus-understanding and keep the rules conservative so nothing risky shortcuts. [SAFE]
11. How does this scale with more tabs? - The expensive steps are bounded by the filtered set (capped at five to thirty tabs), not the total; extraction runs concurrently in tens; triplet payloads are small. Design intent, tested at my fifty-tab window. [SAFE - say "design intent"]
12. What's next? - The guide's Phase 2: local embeddings to replace keyword pre-filtering, a client-side WebLLM for offline semantic work (an AI model that runs inside the browser itself, no internet), progressive context disclosure so even the AI path sends only what the decision needs. [SAFE]
13. Do differently? - Instrument first: rule-hit rate and tokens-per-command telemetry before Phase 2, so the gains stop being projections. [SAFE]
