# Q47 - tell me about a time you had to make a design trade-off that prioritized the customer experience over technical convenience

**LP:** Customer Obsession (primary - the tool meets the user's camera, not the other way around); Invent & Simplify (touch - one import-step conversion, no user-facing pipeline change); Deliver Results (touch - the file kept shipping whole)   **Story:** the iPhone .heic photo problem in the PCB Analyst tool - users' photos were unopenable by any browser, and I paid the cost inside the tool with a runtime conversion at pick time instead of handing users a homework assignment (file_io.js:87, index.html:14); distinct from Q8/Q74/Q79 (same project, other spines)

## Core Answer

The trade-off was about a file format. Users of my PCB analyst tool photograph circuit boards with whatever is in their pocket, and a chunk of those pockets are iPhones - which save .heic, Apple's compressed photo format ordinary browsers can't open. My tool was refusing exactly the files my customers brought it.

The technically convenient answer was one line in a guide: "convert your iPhone photo to JPEG first." It costs me nothing - no new code, no new weight on an offline tool that carries every library inside itself as one double-clickable HTML file. And I knew what that line would do: some users wouldn't find a converter, couldn't install one on a locked-down factory machine anyway, and the tool would quietly stop existing for them. My documented friction was their wall.

The customer-first answer was to convert on their behalf, inside the tool, at the moment they pick the file. That's what I shipped: the import step looks at the chosen file, and if it's a .heic, a small converter library rewrites it to an ordinary JPEG right there in the browser, at a quality I set deliberately - 0.7 on the converter's scale: small enough for slow machines, good enough for comparison input, not for prints. The rest of the pipeline never learns the difference; the person at the bench picks their photo and it works like any other file.

I paid for that convenience twice. The bundle grew by a third-party library - code I didn't write - inside a single file already carrying everything it needs to run offline. And conversion runs on the user's machine at pick time, so choosing an iPhone photo is a beat slower than choosing a JPEG. [PARTIAL - neither the library's weight nor the conversion time is measured in the record; I keep both qualitative]

The judgment I'd defend: "supported formats" is a customer-experience decision, not a file-extension one. The format in the room was iPhone, so iPhone became a supported format - and the cost of that sat on my side of the wall, where I could absorb it once, instead of on theirs, where everyone would pay it every day.

One limit I own: the check looks at the file's extension, not its actual contents - a .heic renamed to .jpg slips past and fails downstream. I documented it rather than pretending the path was closed.

## Memory Anchors
- Problem: factory users bring iPhone photos (.heic - Apple's compressed photo format browsers can't open); the tool refused the exact input its customers produced
- Customer: the engineers/inspectors photographing boards; locked-down machines can't install converters
- Insight: a documented workaround is a wall for the user; the pipeline should absorb format reality at the boundary
- Action (mine): import-step runtime conversion - detect .heic, convert to JPEG via heic2any at quality 0.7, swap the converted image into the pipeline (file_io.js:87-92); shipped the converter inside the tool (index.html:14)
- Result: users pick iPhone photos like any file; costs accepted knowingly - one extra bundled library, a slower pick for .heic (both unmeasured [GAP]); known limit: extension-based detection, renamed files slip through
- Learning: choose where pain lands - absorb it once in the build, or distribute it daily to users; pick the first, and measure the second only honestly

## Follow-Up Bank
1. Where's the code? - The file-input handler checks the chosen name for .heic, calls heic2any with the raw file as a blob, converts to image/jpeg at quality 0.7, and replaces the image URL with the converted one (file_io.js:87-92). The converter library loads with the page (index.html:14). [SAFE]
2. What is heic2any? - An open-source browser library that decodes HEIC - High Efficiency Image Container, Apple's photo format - into common formats like JPEG, so no server or install step is needed. [SAFE]
3. Why quality 0.7 and not lossless? - The converted photo feeds image comparison, not archival; a mild lossy setting trades invisible-for-the-job fidelity for a smaller working image on slow machines. The value is recorded in the code; the reasoning is mine, and it's a tunable constant. [PARTIAL - rationale not recorded]
4. What if the library isn't loaded or conversion fails? - The guard only converts when the library is present; otherwise the raw .heic URL flows on and the browser fails to display it - a visible dead end, not silent corruption. Honest weak point; no user-facing error message was built. [SAFE - from code]
5. What did it cost in size/speed? - Bundling one more library into an offline single-file tool, plus one conversion per iPhone photo at pick time. No measurement in the record - I won't put numbers on it. [GAP]
6. Why not convert server-side or pre-process? - There is no server: the whole point of the build is one offline file on machines with no network and no installs - the conversion had to live inside the browser or not at all. [SAFE - consistent with the canonical standalone account]
7. Did users ask for this? - No request is recorded and I won't invent a quote. My account is that iPhone-shot boards were the live failure the import guard answers; volume untracked. [GAP - reporter/volume unknown]
8. Alternatives rejected? - User-side conversion instructions (the trap this story is about), a desktop helper app (installs - ruled out by the environment), and extension-only support lists (same wall, differently worded). [SAFE - reasoning]
9. What would you do differently? - Detect by file contents, not name, and time the conversion on factory-class hardware so the "beat slower" gets an honest number instead of a hedge. [SAFE]
