# Q47 - tell me about a time you had to make a design trade-off that prioritized the customer experience over technical convenience

**LP:** Customer Obsession (primary - works backwards from the engineers' constraint); Invent & Simplify (touch - simpler store chosen for dependability); Earn Trust (touch - same tool, verified, kept its promise)   **Story:** STORY 4 "The Standalone HTML That Replaced a Server" - the trade-off decision itself; a different moment from Q8 (solo completion), Q29 (the WASM blocker), Q30 (scope beyond responsibility).

## Core Answer

The biggest design trade-off I made was throwing away the architecture I'd already built and liked, because the people I built it for couldn't run it.

My PCB inspection suite first ran as a Flask server. (In plain words: a PCB is the green circuit board inside every electronic device; a "server" means a second computer that stays switched on and runs the program, and every user's machine has to reach it over the network; Flask is just the software I used to run it.) Technically, the server was the easy choice - it started fast, libraries came from disk ("libraries" = pre-built code parts the tool borrows instead of writing itself), and I'd already written it. But the users were manufacturing engineers on factory-floor machines: no internet, no software installs, barely any IT support. The server meant installing Python, managing dependencies, configuring networking - none of which they could do or should have to. The better architecture was unusable where they worked.

So I shipped the whole suite as a single standalone HTML file - one self-contained file, about 25 megabytes, that opens with a double-click and needs no server. ("Standalone/offline" here means everything the tool needs lives inside that one file and runs in the browser on the engineer's own machine - no network and nothing to install. The 25-megabyte figure counts how heavy that single file is - the tens of megabytes range, roughly a short phone-video download - and it's the account of what the file weighed, not a benchmarked measurement.) The cost landed on me. I embedded every browser library (packed all the pre-built code parts into the one file), packed the computer-vision library's binary into the file as base64 (a "binary" is the finished, machine-ready form of the code that runs fast; "base64" is a way of rewriting it as plain text so it can hide inside a text file), and changed its loader to decode it at startup (the "loader" = the part that reads that code in when the tool opens). On a factory machine it takes about five seconds to open; the server version took two. (Both times are from double-click to a working tool - what I saw on those machines with a stopwatch, not benchmark precision.) I took the slower one - five seconds they could use beat two seconds they'd never get to start.

I applied the same lens to the parts they'd feel. Auto-save had to be dependable, so I used synchronous local storage with a quota check (local storage = the data is saved on the engineer's own one machine, not on a server; synchronous = the save finishes before the tool moves on, slower but never half-done; quota check = a check against the fixed size limit the browser allows). When it fills, the tool warns and drops the oldest results instead of silently eating an inspection. The technically stronger database was asynchronous (the tool moves on while the save finishes in the background), which complicates exactly the moment that has to be dependable.

What that bought: the engineer's job went from install-and-configure to double-click. I checked the tool itself hadn't changed by running the same known boards through both builds (the server version and the single-file version) and diffing the outputs (comparing the results line by line for any difference), then handed it out by email and USB. What I got wrong: the file was big enough to brush email attachment caps - compressing the embedded libraries was a fix I should have taken from day one.

The lesson: "technical convenience" is really a question - convenient for whom? I stopped grading architecture by its elegance and started grading it by whether the customer can run it alone.

## Memory Anchors

- Problem: the already-built, faster Flask-server version was unusable by its customers - factory-floor machines with no internet, no installs, minimal IT support (a server needs a second always-on computer every user's machine must reach, which the floor couldn't provide)
- Customer: manufacturing engineers on restricted factory-floor machines; the block was delivery, not code
- Insight: judge the architecture by whether the customer can operate it alone; the technically better artifact failed the one constraint that mattered, so I made the "worse" one
- Action (mine): rebuilt delivery as one self-contained HTML file - embedded the browser libraries, base64'd the WASM binary (WebAssembly: the browser's fast, machine-ready format for heavy image-processing code) and modified its loader to decode at startup; chose synchronous localStorage (the browser's small, simple on-machine store) over asynchronous IndexedDB (the bigger but more complicated browser store) for auto-save; verified parity by re-running known boards through both builds; distributed by email and USB
- Result: ~25 MB double-click file (the weight of the one file - a few tens of megabytes), no Python / no config / no IT ticket; ~5 s startup accepted knowingly vs the server's ~2 s (double-click-to-working times, stopwatch-observed); known-board both-builds outputs matched
- Learning: "convenient for whom?" is the first question in a design trade-off; underestimated distribution - should have compressed the embedded libraries (20 MB email caps - the biggest file the email systems would carry) from day one

## Follow-Up Bank

1. Wasn't the server version just better technically? - By its own metrics, yes: about two seconds to load versus five, and none of the embedding gymnastics (the extra work of squeezing all the code files into the one file). That was exactly the trade-off - better on my side of the wall, unusable on theirs. I chose the one that met them where they worked. [SAFE]
2. What did the standalone build cost you, concretely? - Embedding the browser libraries plus the model weights (the trained model's stored numbers, which ship as a big data file inside the tool) plus the app itself pushed the single file into the tens of megabytes - around 25 MB. Runtime decode of the WebAssembly binary (turning that machine-ready code from its text form back into runnable form when the tool opens) added about two seconds to startup. These figures count one thing each: how heavy the single file is, and how long the tool takes to open - and they're the recorded account of what I saw, not instrumented benchmarks. [SAFE - label on probing]
3. Why one file instead of a zip, sidecar files, or a service worker? - A zip or sidecar files (extra files that must travel next to the tool) reintroduce the failure I was deleting: move one piece and the tool dies. A service worker (a browser feature that lets a web page keep its own files cached so it works offline) needs HTTPS to register (HTTPS = the encrypted web address browsers require for this feature), which the floor machines didn't have configured. Base64 costs size and buys zero external dependencies (nothing the tool must fetch from anywhere else). [SAFE]
4. Why localStorage - the weaker store? - IndexedDB has a bigger quota (storage size limit) and structured data, but it's asynchronous (the tool moves on while the save finishes in the background), and auto-save is a few KB per inspection (the size of each saved record) against localStorage's 5 MB budget (the size limit the browser allows on that machine). Sync storage let me keep the save path dead simple: a try-catch on every write (code that catches the storage failure the moment it happens); on a quota error it warns the engineer and garbage-collects the oldest results (automatically deletes the oldest saved inspections) instead of failing silently. The behavior they depended on stayed dependable. [SAFE]
5. How did you know the trade-off was worth it? - Adoption on their terms: double-click worked where the install ticket (a formal request to the IT queue) never cleared. And I checked the tool itself was unchanged - same known boards through both builds, outputs compared by hand plus a small automated diff (a small script that compares the two versions' results and flags any difference). The board set wasn't a measured sample, so I quote no parity percentage. [SAFE]
6. How did you actually distribute a 25 MB file with no network? - Email where the system allowed it; some mail systems cap attachments around 20 MB (the largest file email will carry), so a USB stick (a small plug-in storage drive) covered those cases. Gzipping the embedded libraries (standard file compression - shrinking the file) would have brought the file near 15 MB and made email reliable - the fix I flag for next time. [SAFE]
7. Didn't you consider just asking IT to install Python? - Yes - that's the technical-convenience answer, and it pushes the cost onto the least-supported party. Every new machine becomes a ticket in a queue with no SLA the factory respects (SLA = "service-level agreement," a promised turnaround time - there wasn't one). The tool would have stayed undeployed. [SAFE]
8. What if the constraint changes? - If the floor gets reliable network, serve the libraries from a CDN (content-delivery network - remote computers that deliver the code files the tool needs over the internet instead of carrying them inside the file) and the file shrinks dramatically; I'd switch without hesitation. The single file was designed for the constraint that actually existed, not a hoped-for future. [SAFE - reasoning, no achieved-scale claims]
9. Did anyone push back on dropping the server? - No documented disagreement - I was the only engineer on the suite; inventing a debate would be fiction. The real pushback was against my own default assumption that tools ship on servers. [GAP - stated plainly, not papered]
10. How many engineers used it, and what did it save them? - About 15 engineers across 2 sites (how many people used the suite, and across how many locations), and they told me it saved roughly 20 hours a week (their own estimate of team-hours the suite gave back per week). Engineer-reported, not instrumented - I present it as their number. What's concrete on my side: install-and-configure became double-click. [SAFE - engineer-reported, label it]
11. Do differently? - Compress the embedded libraries from day one (the email-cap problem - the file being bigger than email would carry - I accepted too quietly), and treat delivery format as a design input, not a retrofit - designing standalone first is easier than unbundling a server later. [SAFE]

## Risk Check

1. "Five seconds versus two - measured how?" - Defensible with label: typical observed startup on the factory machines (double-click to a working tool, roughly what I saw with a stopwatch), stopwatch-grade, not a distribution (no full record of every startup's speed). State it once as "about," never upgrade to benchmark precision. Same numbers as the sibling stories, deliberately consistent.
2. "How do you know the offline build did the same job as the server?" - Defensible: same known boards run through both builds, outputs compared by hand plus a small automated diff (a script that compares the two versions' results and flags differences); no parity percentage exists and none is quoted. Never confess the check was informal beyond that.
3. "Impact - how many users, how much time saved?" - Defensible with the label on it: about 15 engineers across 2 sites (number of users and locations), saving roughly 20 hours a week (their own estimate of team-hours per week) - engineer-reported recollection, not instrumented. Say it that way before they ask; the handoff change (install-and-configure -> double-click) is the concrete claim underneath.
4. "You chose a slower, uglier artifact - isn't that just sloppiness aimed at a sympathetic constraint?" - Defensible: every cost was quantified before choosing (size of the single file, startup time, build complexity), the functionality was proven equivalent (same boards, same results from both versions), and the alternative failed the hard constraint outright. Judgment, not taste.
