# Q3 - tell me about a time you used genai to solve a business problem and what measurable result it delivered

**LP:** Invent and Simplify (primary; source story's own header), with Deliver Results via the separately documented suite delivery (STORY 12)   **Story:** BGSW PCB Inspector Suite - GPT-4o VLM inspection engine (AMAZON_INTERVIEW_PREPARATION.md STORY 8)

## Core Answer

The business problem was on the manufacturing floor. I built Bosch's PCB inspection suite - a PCB is the green circuit board inside every electronic device. The tools compare a board photo against its CAD layout - the board's engineering drawing - and highlight every mismatch in red. But the tool could only say *where*. It couldn't say what it *meant*. Every red region became a manual task: zoom in and decide - wrong-value part, rotated component, or a reflection off a solder joint, the shiny metal dot where a part is joined to the board. That took about thirty seconds per mismatch, and a typical board flags five to twenty - a per-mark time estimate and a typical mark-count, not a timed study. That interpretation was the verification bottleneck: the last slow step before a board gets signed off. I was the only developer on the suite, and my job was to delete that step.

I added a vision-language model - an AI that looks at a picture and answers in words - as the inspection engine: it reads the flagged region, identifies the component, classifies the mismatch - wrong value, wrong orientation, missing, extra, or false alarm - and returns a confidence, a how-sure-am-I score. The business constraint was under five seconds per analysis - a time budget the job had to meet, a requirement rather than a result.

I chose GPT-4o. GPT-4V ran about eight seconds per request versus three - the wait for one answer, roughly timed while I lined the candidate models up side by side. Claude 3's API - the hookup software uses to call an online AI service - was less mature at the time; Gemini Pro Vision was weak on small SMD parts, the tiny components soldered straight onto the board. I rejected a custom classifier - training my own image-recognition model - because that's a labeling-and-retraining project per defect type. My engineering went into the pipeline: crop the flagged region from layout and photo, send both with a structured prompt - an instruction with strict, fixed rules - and parse a fixed JSON reply, a machine-readable form with named fields, like a fill-in-the-blanks answer sheet.

My first prompt failed. "Describe what you see and compare it to the expected layout" returned verbose, inconsistent answers. I rewrote it to force a fixed JSON schema, added examples for the common mismatch types - then it became reliable.

The result, stated carefully. The documented figures: manual interpretation from about thirty seconds per mismatch to about five - human reading time replaced by AI answer time - at roughly 85% correct on component and mismatch type. Those are estimates logged from validation use - the AI's answers checked against what the engineers' own inspection found - not an instrumented study: no labeled eval set, meaning no fixed batch of examples with human-checked correct answers kept aside to score the AI like a final exam it has never seen, and no sample size. Scope honestly: the VLM ran only in the server build - the version hosted on a company machine with the live AI hookup; the offline tool the factory floor used - the single file the machines opened on their own, no server - does not run the VLM, and I never instrumented the AI feature's usage: no counter existed, so I cannot say how often it was used. What I can stand behind: server-build per-mismatch estimates, and engineers reporting the AI helped them prioritize on dense boards - boards crowded with red marks.

What I learned: I was wrong that the model could read values - the printed part codes - off small surface-mount parts; the text is too small; it's much better at type and orientation. First thing I'd build: a labeled eval set and usage telemetry - built-in usage counters - so the next version of this number is measured, not logged.

## Memory Anchors

- Problem: manual mismatch interpretation was the verification bottleneck - ~30s per red region (a logged estimate, not a timed study), 5-20 regions per board (typical count), solo developer on the suite
- Customer: verification engineers (the staff who formally sign off that a board is correct) on the Bosch (BGSW) manufacturing floor
- Insight: the deterministic comparison (the step-by-step image math that produces the same red marks every run) already knew *where*; a VLM pointed only at the flagged crops could say *what it means* - no custom model needed
- Action (mine): evaluated 4 VLMs (image-reading AI models), picked GPT-4o; built crop -> structured prompt -> JSON pipeline; rewrote the failing first prompt to a fixed schema + examples; kept human verification and a correct/incorrect feedback loop
- Result: documented server-build estimates ~30s->~5s per mismatch, ~85% on type, ~3s typical response, ~$0.01 per analysis - all logged estimates from validation use, none instrumented; floor standalone (the no-server single-file version) did NOT run the VLM; AI usage not instrumented; suite (not the AI) adopted by 15 engineers, two sites, in 8 weeks
- Learning: VLMs can't OCR (read printed text out of a photo) values off small SMD parts; without an eval set and telemetry there is no measured number - build those first

## Follow-Up Bank

1. Why is this a business problem, not a cool demo? - The cost was operator time on a required verification step (staff hours spent reading red marks); manual interpretation was the documented bottleneck. The board math (~5 min -> under 1 min per ten-mismatch board, ~$0.10 per board - the five minutes is ten marks at the ~30-second manual estimate; under a minute is ten at the ~5-second AI estimate; ten cents is ten analyses at ~$0.01 each; all multiplied-out estimates, never timed or invoiced) shows the shape of the win - but I'll scope it: server build only, no instrumented usage, so I call it a documented estimate, not a measured ROI (return on investment - money back versus money spent). [PARTIAL]
2. How was the 85% measured? - Measured is too strong. The ~85% and the 30s->~5s were logged from validation use - analyses checked against what the engineers' own inspection found - with no defined eval set, no n, no confusion matrix. In plain words: no fixed scoring set of examples, no stated sample size ("n" = how many cases a number rests on), and no table breaking errors down by defect type. What the 85% counts: AI labels matching the engineer's finding on the marks checked; where it came from: everyday validation use, not a controlled test; how solid: a logged estimate. If you want n and a labeled protocol, that's a gap, and building the labeled set is exactly what I'd do first. Why 85% was still acceptable: the model is a first-pass suggestion, not the decision - labeled "AI Analysis" with a confidence, engineer always verifies, correct/incorrect feedback button surfaces systematic errors (the engineer stays the final judge - a "human in the loop"). Typical API response was about three seconds - the usual wait for one AI reply - inside the five-second budget. [GAP, by design of the human-in-loop]
3. What does it cost at scale, and where would you NOT use the model? - Only regions the comparison already flagged go to the model, so cost and latency (latency = the wait per check) scale with mismatches (5-20 per board - the typical red-mark count, not a measured distribution), not component count. About $0.01 per analysis - roughly one cent for each red mark the AI reads - ~$0.10 for a ten-mismatch board (ten analyses at that cent). I would not put a VLM on every component - 500 components across 1,000 boards a day wrecks cost, latency, and auditability (the ability to re-check a past call), since you can't reproduce a verdict from a hosted model version months later - the provider can change the model without notice. That 500-by-1,000 is a deliberately-chosen what-if, not a measured workload. A cost-aware cascade - a cheap first screen that forwards only the hard cases to the paid AI - is a design target - designed, not built, so its savings are plans, not results. [SAFE]
4. Why GPT-4o over a purpose-built or self-hosted model? - GPT-4V ran ~8s per request vs ~3s for 4o (the wait before an answer comes back; rough timings from lining the models up in my evaluation, not an instrumented study); Claude 3's API was less mature then; Gemini Pro Vision was weaker on small-object detection, which matters for SMD parts - the tiny components soldered straight onto the board. A custom classifier meant labeling and retraining per defect type - hand-tagging example photos and re-teaching the model for each new defect kind - ongoing work for a task an existing general model could handle after preprocessing. LLaVA-style self-hosting - running an open AI model on my own computer instead of a paid online service - is the alternative I'd weigh if cost or privacy became binding - future option only, needs >=8GB VRAM (video memory on a graphics card) the floor machines don't have; I didn't evaluate or run it. [SAFE]
5. You've said the standalone had a BYOK key panel and also no VLM - which is it? - Both are in my record and they reconcile on key handling. I built a standalone configuration panel where a key - a password-like code that lets software use a paid online AI service (BYOK = "bring your own key") - stays in localStorage (saved on that one computer, not a server) and goes straight to the API (the online AI service); with no key configured, the VLM analysis is gracefully disabled. The standalone as deployed to the floor shipped with no key, so the feature was off. The documented result is the server build, full stop. [SAFE]
6. Where did the ideas come from, inside and outside? - Outside: the model landscape (4o, 4V, Claude 3, Gemini Pro Vision) and the browser-CV stack already powering the tools (OpenCV.js, TensorFlow.js - free image-processing and AI libraries that run inside a web browser). Inside: I sat in on three of the engineers' screen-sharing sessions before writing the first comparison tool - those shaped how mismatches get presented (visual highlighting), and the AI analysis was built on top of that established workflow, not on fresh observation. I walked the data question through the security team, who approved sending board photos because they contain no trade secrets. [PARTIAL]
7. What happens when the API is down? - The VLM is an enhancement, not a dependency. Comparison still runs, highlights still show, the UI says "AI analysis unavailable - check API connection" - plain words for "the online AI service can't be reached right now" - and the engineer falls back to the manual check. That fallback describes the server experience; the offline file never used the VLM at all. [SAFE]
8. What went wrong? - Two things. The first prompt: free-form - letting the AI answer in open-ended prose - "describe and compare" gave verbose, inconsistent answers until I forced the fixed JSON schema with examples (the fill-in-the-blanks answer-sheet format). And my wrong assumption: I thought the model could read component values off small SMD parts - text is too small; it's much better at type and orientation. The 15% failures - the flip side of the ~85%, the marks the AI got wrong or couldn't read, from the same validation-use log - were images too poor or components too small to read. [SAFE]
9. Hardest part / disagreement? - The hardest call was how much to trust the model - I kept it as a labeled suggestion with confidence and a feedback button instead of letting it replace the engineer's verdict. Closest to a disagreement was the security data-privacy question, which I resolved up front with the security team. No documented fight over the approach itself. [PARTIAL]
10. Adoption and scale of this? - Precisely: all three comparison tools shipped within eight weeks and the *suite* - not the AI specifically - was adopted by 15 engineers across two sites. What that counts: people using the three tools together; where it came from: the rollout as I reported it; how solid: not a measured usage counter - and it says nothing about the AI feature itself. I never instrumented feature-level usage of the AI analysis; that telemetry is the first thing I'd add. [PARTIAL]
11. Do differently? - Start with the simple structured prompt instead of the clever one; don't assume a VLM reads values off SMD parts; and before scaling any business claim, build the labeled eval set and feature-level usage telemetry I skipped. [SAFE]
12. What exactly did the model output? - A fixed JSON schema: `component_type`, `mismatch_type`, `confidence`, `description` - structured output, not prose (a fill-in-the-blanks form with named fields the software can act on, not a paragraph), parsed and shown as the labeled "AI Analysis". Forcing that schema is what made the prompt reliable. [SAFE]
