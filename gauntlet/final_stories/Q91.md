# Q91 - a time where you received critical feedback, how did you implement it?

## Core Answer

The most useful critical feedback I ever got came from a manufacturing engineer using the BOM reconciliation tool I built, and it was specific - down to a single string (one exact piece of text in that file). BOM = "bill of materials," the list of every part that goes into a product; "reconciliation" means cross-checking that list against the board's design.

Context in one line: the tool reads a SAP-exported parts list and matches component references against the board layout. (SAP is the inventory-and-production software most big factories run; a "component reference" is the code naming where one part belongs on the board, like R1; the "board layout" is the drawing showing where every part should sit.) Before it, the engineer cross-checked by hand, and he said that cost twenty to thirty minutes a board. What that number counts: one board's list-versus-drawing check done by eye; where it came from: the engineer's own words; how solid: a self-estimate, never timed. The tool returns a report in seconds - which is why a wrong report costs something. ("Seconds" counts the machine doing that same comparison and producing the report; it's his experience of the wait, not stopwatch data.)

The feedback: some references are variant references - `R1||R2` or `R1/R2` - one physical position that accepts either part, depending on the board variant. In plain terms: every spot on the board carries a label like R1; this notation is two labels written together, marking a single spot that may hold either of two parts because the board is built in slightly different versions ("variants") for different products. My parser (the part of the program that reads the file and works out what each line means) didn't recognize the notation, judged it invalid, and dropped it. Silently - no error, no warning, the reference just never reached the report. He caught it and told me plainly: if the BOM lists `R1||R2` and the layout shows one position, the system should treat that as a valid match for either reference. That was critical, not cosmetic - a dropped reference could mean a real placement went unchecked, and every false mismatch (the tool wrongly claiming a difference where there is none) sent him back to the manual check the tool existed to kill.

How I implemented it mattered more than the acknowledgment. First, I didn't patch the one string I was shown. I built a variant splitter (a small piece of code that cuts a combined label back into its parts) that normalizes both separators (the `||` and `/` symbols written between the labels), extracts the individual references, and treats each as a valid match target for the position. Second, I made sure the fix stayed fixed: a test matrix (a checklist of inputs to try) - the clean forms, three-part variants, and malformed shapes (deliberately broken labels) like a leading `||` or a trailing `/` - checked against the case most likely to false-mismatch: only one of the pair present in the layout. That matrix went into my regression suite of fifteen real production BOMs (a "regression" is an old feature breaking because of a new code change; a "regression suite" is a saved set of test cases re-run after every change to catch that - here, 15 actual parts lists taken from production), which I ran after every parser change, so fixing one edge couldn't quietly break another. Third, the tool's debug view (a screen that shows how the tool interpreted the data at each step) shows the parsed reference after each step, including the variant split - so he could verify the fix on his own data instead of taking my word for it.

What I took from it: the dangerous failure isn't the one that crashes - a crash announces itself. It's the silent data loss, where a clean-looking report hides that the tool never looked at that line. And implementing feedback properly means generalizing past the example you were shown, then pinning it with a test.

## Memory Anchors

- Problem: user-reported semantic bug (the code ran fine and simply meant the wrong thing) - the parser treated variant references (`R1||R2`, `R1/R2`) as invalid and silently dropped them; a clean report hid unchecked positions
- Customer: the manufacturing engineer running the reconciliation - false mismatches returned his manual ~20-30 min/board check (his report, not measured by me); dropped references could miss real placements
- Insight: the correction had two parts - the semantics (one position, either part by variant) and the failure class (silent drop). Implementing feedback means fixing both, not just the reported string
- Action (mine): variant splitter normalizing both separators; test matrix of clean / multi-part / malformed forms; folded into the 15-BOM regression suite run after every parser change; verification shown through the debug view on his own data
- Result: variants now match either reference; the whole notation class pinned against regression; zero false positives/negatives (false positive = a false alarm; false negative = a missed real problem) on that suite (suite-scoped claim - it covers only those 15 test files, nothing beyond)
- Learning: silent data loss is more dangerous than a crash; a proper implementation generalizes past the example and gets pinned with a test

## Follow-Up Bank

1. How is this different from the prototype feedback you've told me about? - Different event, different shape. That one was a team review listing three rough edges of a five-day demo - alignment, lighting, export. This was one user correcting the semantics of one notation in my code. Different feedback, different fix set, different lesson: that one taught me what counts as working; this one taught me how to implement a correction so it can't regress (so no later change can quietly break it again). [SAFE]
2. Was that really "critical" feedback? - Yes by consequence, not by tone. He wasn't angry - he was right. A dropped reference could hide a real placement, and the false mismatches gave back the manual check the tool removed. I took it as a code-level defect report and treated it that way. [SAFE]
3. Why did the parser drop the reference instead of erroring? - My reference pattern (the rule the parser uses to decide what counts as a valid label) only accepted the standard form, and the default skipped anything unmatched - a deliberate degradation (an intentional keep-running fallback) so unknown formats don't crash the tool on the floor. The flaw: "skip the unknown" and "lose a real part" look identical to the user. That's what his feedback exposed. [SAFE]
4. What exactly changed in the code? - The variant splitter: normalize both `||` and `/`, extract the individual references, treat each as a valid match target for the position - so `R1||R2` against one layout position matches either part. Malformed shapes like `||R1` or `R1/` were made safe at the same time, so they can't produce bogus references. [SAFE]
5. How did you verify, and how do you know nothing else broke? - A test matrix: `R1||R2`, `R1/R2`, `R1||R2||R3`, `R1/R2/R3`, plus the malformed `||R1` and `R1/`, each checked for correct extraction and for matching when only one variant is in the layout. Then it joined the 15-BOM regression suite - representative production files, run after every parser change. Zero false positives and zero false negatives - in plain words, across those 15 files the tool raised no wrong alarms and missed no planted problem - but that claim is scoped to that suite - my own harness (the testing setup I built myself), deliberately small and boring, not CI (the team-wide automated system that re-runs tests on shared infrastructure with every code change). [PARTIAL - suite-scoped, self-built]
6. Where does the 20-30 minutes number come from? - The engineer's own report of his hand cross-check before the tool. I never timed it, so I say "he said," and the "report in seconds" is his experience too, not stopwatch data. [PARTIAL - engineer-reported]
7. Did you accept it immediately? - Near enough, and I won't dress it up. My first instinct was that my rule was defensible - dropping the odd strings kept comparisons simple. His explanation of the intent ended the instinct: he had the manufacturing reality, I had a guess about it. I adopted his semantics completely and rewrote that part without keeping a piece of my old logic out of pride. [SAFE]
8. What alternatives did you reject? - Patching just the reported string (leaves the whole class open), and flagging every variant position for manual review, which would push work back onto the queue the tool existed to clear. "Either reference matches" arrived as a stated requirement from him. Honest gap: no formal trade-off record. [PARTIAL]
9. Did he give you the exact words? - No quote is on record; I paraphrase his instruction - BOM lists `R1||R2`, layout shows one position, either reference counts as a match. I won't reconstruct dialogue. [PARTIAL - premise labeled]
10. What's the general lesson for how you handle feedback? - Two. Treat a single reported example as a sample of a class: fix the class. And don't call it done until the correction is verifiable by the person who reported it - the debug view shows the parsed reference after each preprocessing step (the reading and cleaning the tool does before comparing the documents), including the split, so he can check the tool on his own data and flag a new format instead of losing it quietly. [SAFE]
11. Larger scale - did the discipline pay off elsewhere? - The suite kept growing: each new production failure became a permanent case in it. And in the tool's first week of use it caught three real mismatches the manual review had missed - three genuine part-placement errors the human check let through - same reconciliation work, engineer-reported week-one result. [SAFE - canonical, labeled]
12. What would you do differently? - Collect representative BOMs from the floor before writing the parser, so the first variant notation is a test case on day one instead of something a user has to catch in production. [SAFE]
13. Can you show me the splitter? - Partly. The repo snapshot (a saved copy of the project's code folder) doesn't contain the splitter or the silent-skip default (the drop-anything-unrecognized fallback) - that's narrative. What I can walk through is the semantics, the matrix, and how the debug view exposes each preprocessing step. Never offer "here's the code." [GAP - own it first]
