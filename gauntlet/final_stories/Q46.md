# Q46 - a time when your project deadline was very near, but you still took time to verify or test the data/code before submission

**LP:** Insist on the Highest Standards (primary); Deliver Results.   **Story:** BGSW PCB Inspector Suite - the regression harness for the standalone single-file build (PREPARATION.md STORY 4/15).

## Core Answer

The deadline I keep coming back to was the last milestone of my PCB inspection suite (a PCB is a printed circuit board - the green board inside every electronic device): the standalone build that ran offline on factory-floor machines - one HTML file (a web page that opens in an ordinary browser), no server, no installs. It was the final stretch of the delivery window, and that file was the last thing standing between the manufacturing engineers and a tool they could actually use.

The tempting cut was to ship the build that opens. Compiling (the step that bundles all the code, images, and software libraries into that one file) was fast, I double-clicked it (checked it by hand - just opened it and looked at it), the page looked right. "It opened" felt like proof. And with the date close, every minute on testing felt like a minute not spent finishing.

I kept the rule: no build goes out unless it passes the regression harness (an automatic re-check that reruns the same fixed set of known test cases every time - a "regression" is when a new version accidentally breaks something that used to work), and the harness runs after every compile, not just the last one. It pushed the same 15 bill-of-materials files and 10 board images through both the server version and the fresh standalone - a bill of materials is the parts list for one board design, saying which components belong on it; the board images are photographs of real boards; the server version is the full program running on office computers; and those 15 files and 10 images are the exact, named inputs in the test script, not estimates - and checked three things. Reports had to match exactly (the reports are the cross-checks that compare the parts list against what the board photo actually shows). Alignment within 1 pixel (alignment = how precisely the design drawing lines up over the photo; a pixel is the tiniest dot on a screen, so "within 1" means lined up essentially perfectly - and that one-dot gate was a tolerance I chose, not a measured fact). Machine classifications identical (the labels the built-in image-recognition model gives to each flagged spot came out the same in both versions). Defining what "same product" meant was the judgment call - leave it vague and you're back to vibes.

The reason I didn't skip it: compile bugs are silent (something breaks and no error message ever appears). A library inlined out of order (a library = a prebuilt block of software copied directly into the single file), a path not resolved (the file's internal pointers still looking for pieces at their old locations) - the page still opens on my machine. On the factory floor there's no internet, no tools, no IT to ask. And once I'd emailed a broken build, it was out there. The tests paid for themselves once: a recompile failed the classification check - the ML library had been inlined after the code that called it (ML = machine learning, the software doing the pattern-spotting). It opened. It just didn't classify. That build got rejected before it left my desk.

The file I shipped ran the full suite offline - parsing, comparison, alignment, inference (running the AI that spots and names defects), auto-save. The engineers double-clicked it. No Python (no programs to install), no network setup.

What I'd do differently: make the checking itself robust. A checksum on the output (a short fingerprint generated from a file's contents - if anything silently changes, the fingerprint no longer matches) and a diff mode between two compilations (a comparison that lists exactly where two files or outputs differ), so the tool catches a corrupted build instead of me remembering to test under deadline pressure. The deadline being close was the reason to verify more, not less.

## Memory Anchors
- Problem: last milestone - standalone offline single-file build - with the delivery date close and every recompile looking "fine" because it opened.
- Customer: manufacturing engineers on factory-floor machines; no network, no installs, no IT support; distribution by email/USB (USB = small plug-in storage stick) meant a bad build spreads.
- Insight: "opens in my browser" is not the bar; the bar is "same product as the tested server version," defined as three named comparisons.
- Action (mine): built solo; wrote the harness (the automatic re-check - 15 BOMs (parts lists) + 10 images (board photos) through both builds); ran it after every compile; rejected failing compilations; refused a one-time end-of-project check.
- Result: shipped one self-contained file, tens of MB, opens in seconds, full suite offline; one silent classification failure caught before distribution; no bad build reached an engineer.
- Learning: verification is cheapest before submission - add checksum + diff mode so the tool, not my discipline under pressure, is the guarantee. Deadline near = verify more, not less.

## Follow-Up Bank
1. What exactly did the harness compare? - Same 15 BOM files and 10 board images through the server build and the standalone build. Three checks: reconciliation reports byte-for-byte identical (byte-for-byte = the same down to every single character in the file), alignment within 1 pixel (the design drawing lined up over the photo to within one screen dot), ML classifications identical (the AI's defect labels the same in both versions). Pass/fail, nothing to argue about. [SAFE]
2. Where did the 1-pixel tolerance come from? - The comparison pipeline (the step that decides whether two views of the same spot differ) runs on a 10-pixel mismatch threshold (it calls a spot a mismatch only when the difference covers more than about ten screen dots), so even a pixel or two of alignment drift between builds could flip mismatch output and make reports non-comparable. Reports had to be exact and classifications identical; alignment was the one check with a tiny numeric tolerance, set at 1 pixel. [SAFE]
3. How can a compilation fail silently enough to need this? - The compiler concatenates HTML/CSS/JS (glues together the page's structure, its styling, and its code), inlines and base64-encodes libraries (copies the prebuilt software blocks straight into the single file, converted into plain-text form so they fit inside it), and resolves relative paths (rewrites the internal file pointers so they find everything inside the new one-file layout). Wrong ordering - a library after the code that calls it - or a missed path breaks one feature while the page still opens. It only surfaces when that feature is exercised, e.g. on a factory machine, not on my dev box (my own laptop, which has all the supporting software installed anyway). [SAFE]
4. Did the tests actually catch anything? - Once: a recompile failed the classification check because the ML library was inlined after the code that called it. The page opened fine; it just didn't classify. The harness exercised the whole tool, not the landing page (it actually ran every feature on the test inputs, not just launched the file), so it caught what double-clicking wouldn't. [PARTIAL - rejection-after-failure is the documented rule; this specific catch is a consistent recollection of the documented failure mode, state it as one build I remember being rejected]
5. Why after every compile, not once at the end? - The artifact was rebuilt repeatedly while the rest of the suite changed (the artifact = the finished file that gets shipped), and each rebuild could shuffle the inlining or a path. One end-of-project run would pile up regressions with no clean point to bisect (regressions = new builds breaking what used to work; bisect = the binary-search-style sweep through past builds to find which one introduced a fault). A few minutes per run was cheap against a bad offline artifact. [SAFE]
6. Wasn't that slowing you down at the deadline? - Small cost: the compile took seconds and the harness a few minutes. The downside was much worse - an engineer with a broken offline build has no internet, no install tools, restricted IT, and I distributed by email and USB, so one bad file could spread. [SAFE]
7. How big/slow was the shipped file? - About 25 MB, roughly 12.5 MB of it embedded libraries (MB = megabytes, a measure of file size; the embedded libraries are ready-made software blocks that let one browser file do all the work without installing anything - OpenCV.js ~8 MB for comparing images, TensorFlow.js ~3 MB for running the AI model, PDF.js ~1 MB for reading design documents, XLSX.js ~0.5 MB for reading the parts-list spreadsheets). Loaded in about 5 seconds on a factory machine versus ~2 on the server. Stopwatch checks on ordinary machines, my own numbers. [SAFE - canonical account]
8. Was email enough for a 25 MB file? - No - many mail servers cap attachments around 20 MB (most companies' email systems refuse files sent along with a message above that size), so some copies went by USB stick instead. That's also why an untested build worried me: once copied, it travels. [SAFE]
9. How did you verify on actual factory machines? - I ran the same known boards through both builds and compared outputs; a small automated diff between the two builds' outputs was part of it (a scripted comparison that lists exactly where the two builds' answers differ, instead of a person checking each report by hand). The harness was the gate; the floor double-click was the acceptance (an engineer opening it on their own machine was the final real-world check). [SAFE]
10. Disagreement/pressure? - I built the suite solo, so the pressure was self-imposed against my own schedule, not a stakeholder pushing to skip tests. The trade-off was real either way: visible progress (another compile) vs invisible insurance (one more harness run). [SAFE - honest solo scope]
11. Alternatives rejected? - Ship-the-build-that-opens (rejected: silent failures - broken behavior that shows no error), and test-once-at-the-end (rejected: no bisect point across rebuilds - if the one end-of-project run found a fault, there'd be no way to search back for which rebuild caused it). Kept it simple: one harness, every build, three checks. [SAFE]
12. How reliable are the numbers? - 15 BOMs and 10 images are exact - they were named files in my test script, a personal regression set (my own fixed collection of known test cases that I rerun with every build). The 1-pixel tolerance was my choice, derived from the pipeline's 10-pixel threshold. The catch is my recollection, framed as such. [PARTIAL]
13. What would you do differently? - Checksum on the compiled output (a fingerprint of the file's contents that catches any hidden change) and a diff mode between two compilations (a line-by-line comparison showing exactly what differs), so a corrupted or silently changed build is caught by the tool. Both were in my notes from that week; I didn't build them. [SAFE]
