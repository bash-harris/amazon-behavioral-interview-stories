# Q28 - a time when you had a complex problem where you needed to understand the details, who did you talk to for useful information, and how did you use it?

**LP:** Dive Deep (primary); Learn and Be Curious.   **Story:** BGSW PCB Inspector Suite - BOM reconciliation parser, the manufacturing-engineer conversation (PREP STORY 1); spine here is the person consulted and how their input changed the design (Q5 told the trust angle, Q16 the edge-case tour).

## Core Answer

The complex problem was the BOM reconciliation parser in the PCB inspection suite. (PCB = the green circuit board inside every electronic device. Its BOM - Bill of Materials - is the shopping list of every part that belongs on it. The "parser" is the software that reads that list from the file, and "reconciliation" means checking the list against the board's design file.) The detail I couldn't reach on my own wasn't in the data - it was in a person's head on the manufacturing floor.

The tool I built reconciles a Bill of Materials exported from SAP (the business software factories use to run purchasing and production) against the PCB layout (the design file showing where each part sits) and flags components missing, extra, or mismatched - marks them as problems for a human to look at. It worked on most real BOMs I tried, then production files arrived and it broke. Some of the failures were pattern problems - a process-code prefix glued onto references (every part carries a label like R1 for "resistor number 1" - the designator; some files had an internal process code stuck in front of it instead of the bare label), or spreadsheet cells exported as hyperlinks (a cell that came out as a clickable link object instead of plain text, so the software read the wrong thing) - things I could diagnose from raw-cell logs (a dump of exactly what the program saw in each cell) and data audits.

The one I couldn't crack was `R1||R2`. And `R1/R2`. (Variant notation: two part labels joined by double-bars or a slash.) My parser treated them as invalid and silently dropped them - skipped them without any warning. I could see the text; I couldn't see the intent, and no amount of reading the file harder would tell me whether dropping them was right. So I went to the person who knew: a manufacturing engineer who used the tool and had done the cross-checking by hand before it existed.

He explained it plainly. One physical position, either part valid, depending on which board variant you're building (a variant = a version of the same board built with slightly different parts for different products or regions). So `R1||R2` in the BOM against a single layout position is not a mismatch and not malformed - it's a manufacturing instruction. What my parser called garbage was a legitimate assembly rule.

That rewrote that part of the design. I built a variant splitter that normalizes both separators, extracts the individual references, and treats each as a valid match target for the position. (The splitter is a small piece of code that breaks that either-or notation apart: it reads `||` and `/` as the same "either one" mark, pulls out each part label - R1 and R2 - and lets the checker accept either label for that position.) To make sure the fix matched what he actually told me - not what I half-remembered - I made a test matrix (a grid of deliberate cases to check, both valid and broken): `R1||R2`, `R1/R2`, `R1||R2||R3`, plus malformed shapes like `||R1` and `R1/`, checked against a regression suite of fifteen real production BOMs (a standing set of 15 real parts lists re-run after every code change, to catch anything a fix broke). That suite ran with zero false positives and zero false negatives - on that set, it flagged nothing that wasn't a real mismatch and missed no real mismatch - and the tool returned in seconds a report the engineers said took twenty-to-thirty minutes per board by hand (their estimate of their own old manual cross-check, not something I timed). In the first week it caught three real mismatches manual review had missed.

The lesson stuck: diving deep isn't only reading the artifact (the file itself) harder - some detail lives in the person who holds the intent, and one narrow question beats guessing. What I'd change: I found this reactively, after my wrong assumption had already dropped valid parts in production. Next time I sit with the engineers and collect real files before writing the parser.

## Memory Anchors
- Problem: BOM-vs-layout (parts list vs design file) parser broke on production files; the hardest failure was semantic - about meaning - not a pattern bug.
- Customer: manufacturing engineers - the people the tool replaced (20-30 min/board manual cross-check, their reported figure - what they told me, not timed).
- Insight: `R1||R2` / `R1/R2` = variant notation meaning one physical position, either part valid by board variant - intent a file cannot show.
- Action (mine): went and asked the engineer; built the variant splitter (breaks either-or notation into the individual part labels, both separators treated alike) normalizing both separators; wrote the variant + malformed test matrix; ran it against the 15-BOM regression suite (the standing real-file test set re-run after every change).
- Result: zero false positives / zero false negatives on the 15-BOM suite (no false alarms, no missed real problems - on that set); report in seconds vs reported 20-30 min; three real mismatches caught week one.
- Learning: some detail lives in the person who holds the intent - ask narrow questions early; my discovery was reactive, next time collect real BOMs upfront.

## Follow-Up Bank
1. Who exactly did you talk to, and why him? - A manufacturing engineer who used the BOM tool and had done the board cross-referencing by hand before it existed. He actually knew how variants (the different versions of the same board) get built, so he held the intent behind notation I could only see as text. [SAFE]
2. Why couldn't you work it out from the data alone? - The file gave me the string `R1||R2`, not its meaning. "One position accepts either part depending on variant" is a manufacturing convention - not inferable by pattern matching (checking text shapes against known formats), which is exactly why I needed a person. [SAFE]
3. How did you verify the fix matched what he said? - Test matrix (a deliberate grid of valid and broken cases): `R1||R2`, `R1/R2`, `R1||R2||R3`, and malformed `||R1` / `R1/`, each checked for extracting the right references (part labels) as valid match targets (labels the position is allowed to accept); re-run against the 15-BOM regression suite (the standing set of real parts lists re-checked after every code change) after every change. [SAFE]
4. How did you decide what to solve yourself versus ask about? - Deliberate split (a conscious dividing line between what I could fix from data and what needed a person): pattern problems (`MP_` prefix - a process code stuck in front of a part label; hyperlink cell objects - spreadsheet cells holding a clickable link instead of plain text) I could audit in the data and fix; semantic intent (variant references, what DNP means on the line - "Do Not Populate", the factory's way of marking a position left empty on this version of the board) only the engineers could tell me. [SAFE]
5. Why "either reference matches" instead of flagging variant positions for review? - Either-matches (accepting any of the listed parts as valid for the position) arrived as a stated requirement from the engineer; flagging every variant position would push work back onto the manual queue the tool existed to clear (the backlog of boards a person had to check by hand). Honest gap: my record doesn't show a formal comparison of that alternative. [PARTIAL]
6. What if no engineer had been available? - Default behavior skips anything not matching the standard reference pattern (the plain part-label format the software expects, a letter plus a number like R1), so it degrades instead of crashing - keeps running but quietly skips the odd entries - but that means silently dropping valid components, a worse failure than an error (a silent miss lets a wrong board pass; an error at least gets looked at). Part of why I'd interview users before writing the parser next time. [SAFE]
7. How solid is "worked on most real BOMs"? - Roughly 70% from my early trials against real files - that number counts the share of real parts lists I first tried that processed correctly, and it came from my own early usage, not a survey of a defined file set; a sense from usage, not a surveyed corpus figure. [PARTIAL]
8. How reliable are the result numbers? - All reported or recorded, none instrumented by me (nothing counted by a measuring system I built): the 20-30 min baseline is the engineers' recollection; the three week-one catches are a story-bank record, not an audited count; zero FP/FN is scoped to the 15-BOM suite, not a universal claim - on that one test set there were no false alarms and no missed real mismatches, nothing more. [PARTIAL]
9. Performance? - A 2,000-component BOM parsed in under 200 ms - a parts list for a board with 2,000 parts read and checked by the software in less than a fifth of a second; a recorded single-run figure against my sub-second bar (my own target of under one second), not a benchmark distribution (not a series of many timed runs with averages and worst cases). [PARTIAL]
10. What went wrong? - My own assumption: I'd filed `R1||R2` as garbage (invalid text) and the parser silently dropped valid parts in production (skipped them with no warning, so nobody looked at them). A customer correction caught my mistake - I would not have found it from the data alone. [SAFE]
11. Hardest part? - Admitting the file couldn't answer the question and going to ask, after I'd already shipped the wrong behavior. Also distrusting my own fixtures (the sample files I'd written my tests against) - my test data had no hyperlink cells. [SAFE]
12. Scale / do differently? - One team, one plant, one week of numbers - I won't pretend wider. Differently: collect sample BOMs from the floor and interview users before writing code, not after it breaks. [SAFE]
