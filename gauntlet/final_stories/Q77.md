# Q77 - tell me about a situation where you pushed back on a customer request

**LP:** Customer Obsession (primary); Have Backbone; Disagree and Commit (primary). **Story:** BGSW PCB Inspector Suite - data-first pushback on the pin-count measurement rule (STORY 10, expanded by STORY 11's transparency/override).

## Core Answer

The customer I pushed back on was internal - the manufacturing engineer who used my BOM reconciliation tool. (A BOM, or "bill of materials", is the parts list for a circuit board - every component with its specs. The tool cross-checks that list against the board's design file and flags anything that doesn't line up.) The request, as it reached me, was: make the pin-count false alarms stop. A pin is a component's metal leg; the tool counted them and compared literally - if the parts list said one number and the spot on the board offered another, any difference at all set off an alarm, even when it was harmless. A "false alarm" meant the tool crying wolf on a board that was actually fine. The easy fix was to drop pin count from the comparison. I pushed back, because it traded his short-term pain for a worse long-term failure. Pin count is what catches a genuinely wrong part: if the BOM calls for more pins than the footprint has pads, that part physically can't fit, and without the check it sails through. (The "footprint" is the patch on the board where a component sits; "pads" are the solder points in that patch.)

Straight answer: no external customer, no recorded quote in my notes. The request arrived as pain and a workaround - he had started re-checking every mismatch by hand, which defeated the point of the automation.

I didn't push back with an opinion. I pulled 20 BOMs with pin-count mismatches - twenty real parts lists where the tool had flagged a pin problem, a set I sorted myself - and sorted each by footprint larger than the part, smaller, or exact. The pattern was clean. A larger footprint is almost always a legitimate package variation - extra pads for variants or no-connects (pads that sit on the board but are wired to nothing). A smaller one is a real mismatch, because the part can't fit. Exact is fine. So instead of deleting the signal, I proposed keeping it and making it discriminate: more pads, flag for review; fewer pads, definite mismatch.

That opened a new hole - a larger footprint on the wrong component type - so I pushed a second time for a component-type check with a configurable ratio threshold, defaulted from the data at 2:1. (The threshold is the tolerance for how many more pads than pins is still okay - up to twice as many passes; more than that alarms. "Configurable" means it's a setting the engineer can change, not hardcoded.) False alarms dropped from about 12% to under 2% on boards with mixed component types - that's the share of the tool's total flags that were cries of wolf, before versus after - and the manual re-checking stopped. I ran the full regression suite to confirm no previously-correct match had changed - a regression suite is a saved set of test boards with known-right answers, re-run after every change, so a fix that breaks good cases isn't a fix.

I also kept the residual risk honest: the heuristic can still miss a mismatch that happens to satisfy the type and ratio rules. (A "heuristic" is a practical rule of thumb, not a perfect test; the miss it can still make is a "false negative" - a real problem the rules let through.) Rather than hide it, I documented it and put the threshold and an override in the engineer's hands through a debug view, so judgment stayed with the person accountable for the board. (A "debug view" is a settings-and-internals screen; the "override" lets the engineer see why the tool decided what it did and manually change its call on any item.)

So I didn't refuse the request - I refused the shortcut it implied. He got what he actually needed: a report he could trust. And once the rule was set and the risk documented, I committed to it fully and stopped pushing.

## Memory Anchors
- Problem: Pin-count compared literally (any difference between the parts list and the board, even a harmless one, set off an alarm), so legitimate larger footprints (extra pads for variants/no-connects - pads wired to nothing) flagged as mismatches; engineer manually re-verifying every flag.
- Customer: Internal manufacturing engineer using the tool - honestly, no external customer, no verbatim request; the ask was "make the false alarms stop."
- Insight: The implied shortcut (delete the signal) trades short-term noise for a long-term escape of physically wrong parts; the data shows the error is directional - larger footprints are benign, smaller are genuine.
- Action (mine): Pulled 20 mismatched BOMs (real parts lists the tool had flagged), bucketed by footprint-vs-part size; proposed discriminating rule (more pads -> flag for review, fewer -> mismatch); pushed a second time for component-type check with configurable 2:1 default (pads may be up to double the pins before it alarms); documented residual false-negative risk (a real mismatch the rules miss); exposed threshold + override in debug view (an internals-and-settings screen for the engineer); regression-checked (re-ran the saved known-answer test boards).
- Result: False positives ~12% -> under 2% on mixed-component boards (cried-wolf flags as a share of all the tool's flags); manual re-verification stopped; no previously-correct matches changed.
- Learning: Push back with a finding, not a preference; refuse the shortcut, not the customer; once the decision is made and the risk documented, commit fully and stop re-arguing.
