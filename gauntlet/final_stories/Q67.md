# Q67 - tell me about a time when you had to implement a direction you didn't agree with

**LP:** Have Backbone; Disagree and Commit (primary; touches Are Right, A Lot, Earn Trust) - *the superior-issued-and-overruled scene is a GAP; no such event exists in the record*   **Story:** STORY 10 ("The Pin Count Mismatch Problem") - the documented pin-count requirement I had reservations about and implemented at full strength; this file's spine is the commitment half, not the argument (Q17 owns that ground)

## Core Answer

The direction was the pin-count rule in my BOM reconciliation tool. Plain words first: a BOM is the parts list for a circuit board - every component with how many electrical pins it has; the tool checked the board by comparing each part's pin count against the number of solder pads the board's design allotted for it (pads are the little metal spots a part sits on). The rule matched parts this way, and the requirement I worked to was to kill the false alarms - reports crying "mismatch" on boards that were actually fine - without removing that comparison.

I didn't agree with pin count as the signal. Here's why, in plain terms: a "footprint" is the pad pattern on the board for a given part slot, and footprints are designed for whole families of parts, so a larger footprint legitimately hosts a smaller part - the extra pads just go unused. Literal equality therefore calls normal, correct hardware an error. My view was that the part's label on the board (its reference designator, like "R1") plus the footprint name is the better signal.

One thing up front: that direction was a documented requirement and the tool's existing rule - not a manager handing me an approach and overruling me. I built the suite solo, so there's no boss scene in my record, and I won't manufacture one. **[GAP]**

What is real is how I executed. I made the disagreement once, with data: twenty BOMs with pin-count differences, sorted into three buckets - footprint larger than the part, footprint smaller, and exact match. Then I committed to the requirement completely - no watered-down version. Pin count stayed in. Larger footprint flags for review; smaller is a definite mismatch (a part can't fit pads that aren't there). That leaves a hole - wrong component type, bigger footprint, slips through, meaning a real error the tool would now miss - so I added a component-type check, a configurable 2:1 ratio threshold from that twenty-BOM set (the allowable footprint-to-part size gap, adjustable rather than baked in), and a debug view showing the raw values behind each call so an engineer can see and override any decision. I wrote the residual false-negative risk - the errors that could still slip past - down instead of burying it. On mixed-type boards (boards carrying many different kinds of parts) the false alarms went from about 12% to under 2%.

For a genuine overrule - labeled as framework, not memory: counter once, privately, with the data; if the call stands, build it as if it were mine; if execution turns up a fact nobody saw, raise that once, then respect the call. Dragging my feet to prove I was right would have been worse than the disagreement itself.

## Memory Anchors

- Customer: manufacturing engineers who stopped trusting reports full of false mismatches
- Insight: half-committing is worse than disagreeing - the honest move is full implementation plus an owned, documented risk
- Action (mine): 20-BOM three-case analysis; kept pin count, made it discriminating (larger -> review, smaller -> mismatch); component-type check; configurable 2:1 threshold; debug view with engineer override; residual risk documented
