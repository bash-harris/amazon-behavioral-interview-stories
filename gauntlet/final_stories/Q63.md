# Q63 - describe a time you used data to make a recommendation, which requires you to explain your financial reasoning without necessarily building a valuation model on the spot

**LP:** Are Right, A Lot (primary); Dive Deep; Customer Obsession.   **Story:** BGSW PCB Inspector Suite - make-vs-buy call between my custom classifier and a hosted GPT-4o VLM (STORY 8 + STORY 3, same project).

## Core Answer

The inspection tool flagged board mismatches - places where a finished circuit board didn't match its design drawing - but couldn't say what they meant. So an engineer zoomed in and read each flagged spot by hand - about thirty seconds a flag, and there were several per board. (That ~30 seconds counts one human check of one flagged spot; the source is what the engineers told me plus my own watching, so it's an estimate, never timed.) That was the bottleneck I wanted to remove.

There were two realistic ways to automate the interpretation: extend the classifier I'd already trained myself (a program taught with example photos to recognize defect types from pictures), or call a hosted vision-language model - an AI service that looks at an image and answers questions about it, rented per-use from someone else's servers (GPT-4o). One thing up front - this is engineering, not finance. I'm not going to fake you a valuation model (a formal money calculation of what something is worth). But it's the same discipline the question is really asking for: cost of each option, what it buys back, and which one wins for the shape of the job. So I costed it out.

On the custom route the numbers were unfriendly. My classifier was accurate on the defect types I'd already labeled (had example photos of, with the right answer marked by people), but every new type meant a new labeled dataset and a retrain (teaching the program again on a fresh batch). Interpreting mismatch types I hadn't anticipated was a project, not a function call (a single command).

On the hosted route I gathered actual data. I ran real flagged boards through GPT-4o: it got the component and mismatch type right about 85 percent of the time - with zero training data - for about a cent per analysis. (The 85% counts times the AI named the right part and the right kind of mistake; its source is my rough tally over those real flagged boards, and its solidity is self-assessment, not a formal test. The cent - $0.01 - is the provider's published price for a request of typical size, so that side is plain arithmetic, not a guess.) So a whole board cost pennies. Before settling I'd also checked the alternatives - GPT-4V was noticeably slower (longer wait per answer), Claude 3's API - the connection that lets software call an online service - was still immature back then, and Gemini did worse on the tiny surface-mount parts (the small components soldered directly onto the board).

The recommendation: use the VLM for the interpretation step only, and keep my deterministic comparison engine (the rule-following picture-check that always gives the same answer to the same input, no AI guessing) as the verdict. The argument was that pennies-per-board against engineer-minutes, plus skipping a labeling project that might never have finished. And I said the flip out loud: at higher volume, or under cost or privacy pressure, the math reverses and I'd retrain the classifier instead.

What I learned - the recommendation was never "which model is better." It was which model fits the shape of the job, and the numbers are what make that a recommendation instead of a preference.

## Memory Anchors
- Problem: Tool flagged mismatches but couldn't interpret them; engineer read each flag by hand (~30 s each).
- Customer: Manufacturing/test engineers running the inspector on the floor.
- Insight: The decision is a cost-benefit - operator time and per-call cost vs a labeling-and-retrain project; fit the tool to the job shape.
- Action (mine): Ran real flagged boards through GPT-4o; compared accuracy/latency/cost/maintenance vs my own classifier; benchmarked GPT-4V, Claude 3, Gemini first; recommended VLM-for-interpretation-only, deterministic engine as the verdict.
- Result: Interpretation shipped as a confidence-labeled suggestion the engineer verifies; pennies per board vs minutes of time; tool fully works without the API.
- Learning: "Which model is better" is the wrong question; "which fits the job, at what cost" is right - and state the flip conditions with the recommendation.

## Follow-Up Bank
1. Why is this a fair answer to a finance-framed question? - I'm an engineer; the domain is QA cost-benefit, not a valuation model. Same discipline: gather the numbers, compare options on cost and benefit, make the call, and say what would change it. I'd rather own that than fake a DCF (a discounted-cash-flow model - the classic finance calculation of what future money is worth today). [SAFE]
2. The financial reasoning in one line - about a cent per analysis (pennies per board) against ~30 seconds of engineer time per mismatch (one human eyeball check; the engineers' own estimate, not a stopwatch study) and the avoided labeling-and-training cost (paying to mark up example photos and retrain the program); the recommendation goes to whichever side of that ratio is cheaper for the task shape. [SAFE]
3. Your classifier beat the VLM on accuracy, didn't it? - Different jobs. My EfficientNetV2S (the image-recognition model I trained myself) was 94% on a ~300-image holdout - a holdout is examples deliberately kept back so the model never trained on them, which is what makes the score honest; the ~2,000 labeled photos were split 70/15/15 into training/tuning/testing - so that 94% is measured and solid, unlike the VLM's self-assessed 85% - ~45 ms per image on CPU (about 45 thousandths of a second per photo on an ordinary processor, no special hardware), ~30-minute retrain (one full teaching run) - and it owned the hot-path per-component verdict (the routine up-or-down check on every part on the line). But interpreting mismatch *types* with no labeled set per type was a retraining project; there, ~85% as a human-verified first pass for a cent beat building data. [SAFE]
4. How reliable is that 85%? - Honest answer: rough self-assessment on real flagged boards, no held-out set (no formal test on fresh examples the model never saw). That's exactly why the output is labeled a suggestion with a confidence (the AI's own "how sure am I" score) and the engineer verifies - I never let the soft number carry a hard decision. [PARTIAL]
5. Where did "thirty seconds per mismatch" come from? - Engineer-reported, plus watching their workflow on the floor. Estimate, not instrumented - nobody timed it. [PARTIAL]
6. Was the cent-per-analysis measured? - From the API's per-token pricing on typical prompt sizes (the provider bills by "tokens" - chunks of the text sent and returned - so the price follows published rates, not my guess); consistent across calls. Scope note: the VLM ran only in the server build (the version that used the factory network); the single-file offline build (one self-contained file that runs with no network at all) called no model at all. [SAFE]
7. Why not put the VLM on every component? - Cost and latency (the wait for each answer) scale linearly at board volume - twice the boards, twice the calls, twice the bill - and QA audits need to reproduce a verdict months later from image bytes plus model version (a quality audit must be able to re-run an old decision and get the same answer; "model version" = which release of the AI produced it) - a hosted model behind someone else's version doesn't give you that. Deterministic comparison stays the core; the VLM stays on the uncertain, low-volume step. [SAFE]
8. What data would flip the recommendation? - A labeled set per defect class (enough human-marked examples for each defect type), higher volume, tighter cost pressure, or stricter privacy requirements all push toward retraining the classifier. The call is a function of those inputs, not a preference - I said so when I made it. [SAFE]
9. What went wrong / error mode? - The ~15% miss: poor image quality or parts too small for the model to read. The feedback loop (correct/incorrect flags from engineers) exists to surface systematic errors (mistakes that repeat the same way), and the tool degrades to "AI analysis unavailable" rather than guessing when the API is down. [SAFE]
10. Hardest part; any disagreement? - Hardest was recommending against my own model on the step where it lost. No external fight to report - the engineers were receptive - so I won't invent pushback; the tension was internal, and I surfaced the flip conditions early so anyone could object. [GAP on external disagreement]
11. Do differently? - I'd have scored GPT-4o against a small labeled set first (a handful of examples with known right answers), so the 85% was measured, not self-assessed. The decision wouldn't have changed - the cost gap was wide - but the evidence would have been harder. [PARTIAL]
