# Q74 - describe a time you had to make a decision with incomplete information

**LP:** Bias for Action (primary - moved without fleet/browser certainty because the constraint was real); Are Right, A Lot (good calls under ambiguity + naming the un-verifiable unknown)   **Story:** STORY 4 "The Standalone HTML That Replaced a Server" - the standalone-vs-server decision itself. Distinct from Q58 (five-day prototype scope bet, STORY 8) and from Q7 (IE11 miss) and Q29 (WASM blocker) in the same project.

## Core Answer

The decision I'd point to: I killed my own running server and shipped the whole PCB inspection suite as one offline HTML file - and I committed before I could check the ground.

Some context. I built the suite solo: browser tools - programs that run inside a normal web browser with nothing extra installed - manufacturing engineers use to reconcile a board's parts list (the "bill of materials": the list of components that should sit on a board) against the board's layout drawing, and to sort defects into types. It had to run on factory-floor machines - no internet, no installs, minimal IT support. The old design leaned on a Flask backend (Flask being a small helper program that runs on a separate machine - a "server"); it needed Python and network setup that team couldn't absorb. I could see that part. What I couldn't see: whether a browser alone could carry the whole stack - image processing, the trained model (the part of the tool that learned to spot defects from example photos), the PDF and spreadsheet readers - and behave identically; whether a file tens of megabytes big would load acceptably on those machines (a megabyte is a unit of file size - a page of text is a fraction of one, so a single file in the tens is a big file); and whether the floor's browsers could run it at all. I had no list of which machines and browsers were actually on the floor - "the fleet" - and I had no lab that matched it.

Three options. Keep the server and push installs onto IT - the status quo, and exactly what made the tools unusable. A lighter local server - still an install, still mine to support. Or one self-contained file, double-clicked open, no network. I chose standalone - but I turned the leap into a checkable bet. The same source built both versions - one set of code, packaged two ways; one flag (a single on/off setting) swapped only the storage layer, meaning where the tool keeps its data; the server build stayed alive as a fallback; and I ran the same known boards - boards whose correct answers were already on record - through both builds and compared the outputs by hand plus a small automated diff (a program that flags any difference between two results). Being wrong cost me a test day, not the product. My rule: commit under uncertainty when being wrong is cheap, quick to find out, and recoverable. This one qualified.

The call held. A single file, around 25 megabytes - big enough that you'd carry it on a memory stick - opening in about 5 seconds on a factory machine against 2 on the server. In plain terms: the ~25 MB is the recorded size of that one file, and the seconds are the wait from double-click to a usable tool, timed by my own stopwatch over a handful of boards - an estimate, not an instrumented benchmark. Every feature identical. The engineers got a double-click: no Python, no IT ticket. I distributed it by email and USB.

What I couldn't see came out later: some machines' browsers couldn't run the WebAssembly inside the build (WebAssembly being the compact format that lets heavy image and AI code run fast inside a browser). I added a startup capability check - the tool asks the machine whether it has what it needs and says so plainly instead of half-working. I'd rather name that limit than claim the call was perfect.

## Memory Anchors
- Problem: factory-floor machines had no internet, no installs, minimal IT - the Flask backend (a small server helper program) made every rollout an IT ticket the team couldn't absorb
- Customer: the manufacturing engineers using the suite on the floor; they were blocked by delivery, not by code
- Insight: the three unknowns (browser can carry the stack / big file loads acceptably / fleet browsers support it) were not gettable by asking - so the decision had to be made checkable instead of informed
- Action (mine): chose standalone over server / lighter-server; made the same source build both versions; one flag swapped only the storage layer (the server's disk vs browser localStorage - data saved on that one computer, not a server); kept the server as fallback; verified by running the same known boards through both builds and diffing outputs (comparing the two results for any difference - by hand plus a small automated diff)
- Result: one ~25 MB double-click file (~25 MB is large for a single file - a page of text is a fraction of a megabyte), ~5 s load on a factory machine vs ~2 s on the server (the wait from double-click to usable tool; a stopwatch estimate, not instrumented), full functionality identical; distributed by email and USB; no installs, no tickets
- Learning: commit under uncertainty when being wrong is cheap, quick to find out, and recoverable - and whatever residual unknown you can't test, ship a check for it (the capability check), don't pretend it away

## Follow-Up Bank
1. What exactly was the incomplete information? - Three unknowns: whether a browser-only file could carry the full stack and behave identically; whether a very large single file would load acceptably on factory machines; whether the fleet's browsers could run it at all. I couldn't inventory the fleet and had no matching lab. ("The fleet" = every machine on the floor; "inventorying" it means having a list of which browsers and versions were installed - I couldn't get one.) [SAFE]
2. What was in the file, size-wise? - OpenCV.js around 8 MB - a WebAssembly module (WebAssembly = the compact format that lets heavy code run inside a browser; OpenCV.js = the image-processing library) - plus TensorFlow.js around 3 MB (the AI library), PDF.js around 1 MB (opens PDF documents), XLSX.js around half a meg (opens Excel spreadsheets). Embedding the browser libraries plus the model weights and the app itself pushed the single file into the tens of megabytes - around 25 MB. What these numbers count: the rough size of each piece packed into the one file. Recorded account, not a benchmark sheet. [SAFE - label on probing]
3. Why not just wait and survey the fleet? - Waiting was also a decision, and it left the engineers stuck while I asked permission for information I could partly generate myself. I couldn't get the fleet list, so I built the parity check instead - a test that runs the same boards through both versions and requires their answers to match - that produced the data I could get, and bounded the part I couldn't. [SAFE]
4. Why not keep the server and escalate to IT? - The constraint was the users' environment, and escalating stalls them on a dependency I could remove inside my own build. When the path is mine and I can test it, waiting for someone else is the slower choice, not the safer one. A "lighter" local server (a smaller helper program running on the user's own machine) still meant an install and still meant me supporting it remotely on locked-down machines (machines where users can't add or change software). [SAFE]
5. What made the bet checkable? - compile_tool.py (my build script) builds the standalone from the same source as the server, so the two can't drift - one code base, two packages, so they can't quietly end up different; a standalone-mode flag swaps only the storage layer - browser localStorage (data saved on that one computer, not a server) versus the server filesystem (the server's own disk). Then I ran the same known boards through both builds - 15 BOM files (parts lists) and 10 board images - and compared, by hand with a small automated diff to catch anything I missed: reconciliation reports identical, alignment within about a pixel (the two versions matched their board pictures to within one dot on the screen), classifications identical. Run after every compile. [SAFE]
6. Was a slower load really acceptable? - Yes, deliberately: about 5 seconds on a factory machine against about 2 for the server, my own stopwatch over a handful of boards, not an instrumented distribution. In plain terms, the 5 seconds counts the wait from double-click to a usable tool; nobody measured it during real use, so it stands as a labeled estimate. A slower start on a tool that runs offline beat a fast tool that doesn't run there at all. [PARTIAL - labeled estimate]
7. What did you get wrong? - I assumed every floor machine ran a modern browser. Some didn't, and the WebAssembly-dependent build (the version carrying its heavy code in the fast browser format) failed entirely on those. A real fix was a rewrite, so I added a startup capability check that names the missing requirement instead of a mystery failure. That full failure story is a separate answer - here it's the residual unknown my test couldn't cover. [SAFE - cross-reference, no retell]
8. How do you decide a bet is safe enough to make? - Bound the downside and make it checkable: same source for both builds, a test I can run myself after every compile, a live fallback (the server version stayed working alongside). Being wrong meant losing a day, not the product. If being wrong were expensive or invisible, I'd slow down and buy information first. [SAFE]
9. Who disagreed with killing the server? - Nobody on record; it was a solo project and inventing a scene would be a lie. The real disagreement was with my own default assumption that tools ship on servers - the fallback I kept was that argument made concrete. [GAP - stated plainly, not papered]
10. Who actually used it? - About 15 engineers across 2 sites; they told me it saved roughly 20 hours a week. Engineer-reported, not instrumented - meaning there is no usage counter; the hours are what they recalled in conversation, not something I measured. For this build specifically, the impact I can state directly: the handoff became "double-click" - no Python, no network setup, no ticket; distribution was email and USB. [PARTIAL - canonical reporting stance]
11. Known ceilings of the decision? - A ~25 MB file bumps into 20 MB email caps (most company email systems refuse attachments larger than 20 MB), so some copies went by USB stick; gzip on the embedded libraries (standard file compression) could have brought it near 15 MB - the optimization I deferred, consciously. And no update channel: every fix means re-sending the file. [SAFE]
12. Do differently? - Put the browser capability check in from day one instead of after the surprise, and design standalone from the start - retrofitting delivery is harder than designing it in. [SAFE]
