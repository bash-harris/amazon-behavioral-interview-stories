# Q21 - tell me about a time when you went out of your comfort zone

**LP:** Learn and Be Curious (primary); Invent and Simplify + Deliver Results (touch)   **Story:** BGSW PCB Inspector Suite - rebuilding CV into the browser with never-used tools after the known stack was locked out (PREP.md STORY 5, one telling only)

## Core Answer

The biggest move out of my comfort zone was rebuilding my inspection tool to run computer vision - a program that understands a photo well enough to spot problems in it - inside a browser, with tools I'd never opened, because everything I already knew how to build had just been ruled out.

I built the PCB inspection tools alone. A PCB is the green circuit board inside every electronic device. The manufacturing engineers who used them sat on locked-down factory machines - no software installs. My stack was Python behind a small server; none of it could cross to that floor (Python being the language, and the server one shared computer on the network that each user's machine had to reach - which the locked machines couldn't do). If the tool didn't run in the browser, it didn't exist for them. So: image processing and a trained model - software that learned from example photos what a fault looks like - in JavaScript, on OpenCV.js and TensorFlow.js, neither of which I'd used. JavaScript is the language every browser runs, and those two are free browser libraries for image work and machine learning. And it wasn't a toy - the tool had to line up a photographed board that was physically bent against a flat reference (the board's flat design drawing), and run the defect model.

Before committing, I capped the risk: one day to prove the browser could do one real operation - load two images, find the edges (the outlines of the parts in each photo), show the difference (light up where the two don't match). It could. That day paid for the two weeks after it.

The first failure was mine and it was embarrassing. The model output was garbage, and I blamed the model for hours. What I'd actually done was feed it the image with the pixel array in the wrong order - to a model, a photo is just a stack of number-grids, and I stacked them in an order it didn't expect (the technical name is a wrong tensor shape) - no error thrown, just silently wrong output. Three hours to find what one line of checking would have caught in seconds. I now write the shape check before the inference code - "inference" meaning the moment the model actually makes its prediction.

The real climb was the bending. Straightening a warped photo needs a warping algorithm - digitally bending the photo so a curved board matches a flat drawing - and no JavaScript implementation of one existed to lean on. So I read the paper that defined it - Bookstein, 1989, the academic article that first laid out the maths for this kind of bend - and coded it step by step, checking my output against the worked examples in the paper. Reading a thirty-year-old paper to ship a feature you're building this week is the least comfortable I've been at work.

My rule the whole time: learn just enough to build the next feature, then build it.

What it left me able to do: ship to the factory floor with zero IT involvement, fast enough to feel interactive - about forty milliseconds per comparison once you click through boards. In plain terms: a millisecond is a thousandth of a second, so forty is a blink; that figure counts the time one photo comparison takes to finish, I read it off the developer tools built into the browser, and it's my own observation while working, not a formal benchmark. And I learned the pattern works, because I repeated it later with a vision-language API (an AI service that can look at pictures and answer in words, called from code): same unfamiliar ground, same method - list the real options, let the constraints I actually had pick.

## Memory Anchors

- Problem: known stack (Python + Flask server - Flask being a simple tool for serving a Python program over a network) blocked from factory floor by install lockdown; the job required CV in a browser on two never-used libraries
- Customer: manufacturing engineers on locked-down factory machines - no installs, no IT bandwidth (no spare time from the IT department to help)
- Insight: bound the unknown cheaply - a one-day feasibility spike (a deliberately time-limited trial just to prove something can work) before committing; then learn just enough to build the next feature
- Action (mine): one-day minimal prototype (two images -> edges -> difference); ported the pipeline to OpenCV.js/TF.js; found and fixed the tensor-order bug (the wrong-order-of-numbers mistake from the core); implemented thin-plate-spline warping from the Bookstein 1989 paper (the specific 1989 bending maths), validated against its examples
- Result: browser-only tools, no IT approval, instant adoption; ~40 ms per comparison (console-timed personal observation, comparison step only - "console" being the timing tools built into every browser); alignment later canonically 15-20 px far-edge -> 2-3 px (px = dots on screen; how far the matched photo still sat off from the drawing at the board's far corners, 15-20 px before the fix, 2-3 px after); pattern repeated with the GPT-4o vision integration
- Learning: write the cheap invariant check (tensor shapes) before the code it protects - a one-line check that the numbers arrive in the order the model expects; when the literature already derived it, write the derivation down before coding, not after

## Follow-Up Bank

1. How did you actually learn the libraries? - Docs first for the API surface (the full list of commands the library offers), then the one-day minimal prototype, then incremental build: roughly two days on docs plus prototype, two weeks iterating the pipeline - my own recollection of how the learning time split, not logged hours. OpenCV.js mirrors the C++ API (C++ = the older compiled language the original OpenCV was written in), so general OpenCV knowledge transferred, but most docs and examples were C++ - I translated as I went. [SAFE]
2. What exactly was the tensor bug? - TF.js expects NHWC layout; I passed the CHW shape `[1, 3, 224, 224]` where the model wanted `[1, 224, 224, 3]`. In plain words: a tensor is the grid of numbers a photo turns into for the model, and those four numbers say how the grid is stacked - NHWC means one image, then height, then width, then the three red/green/blue channels last; CHW puts the colour channels before height and width. Both stackings hold the same picture - only the order differs - which is exactly why nothing crashed. No exception - just wrong scores. Three hours to isolate by printing shapes at each pipeline step (a pipeline = the chain of steps the image flows through; I had the code print the number-order it received at each step; that three hours is my recollection of the session, not a logged figure); now a shape assertion goes in before any inference code. [SAFE]
3. How did you validate a from-scratch warper with no reference implementation? - Two checks: the worked examples in the Bookstein paper itself, and my own small marked-grid test images (I drew grids with points at known positions, so I could predict exactly where each point should land) where I knew what the bend should look like - the warp had to pull each marked point onto its target. What it counts: whether my hand-written maths reproduced answers I could check by hand. Slow, boring verification, but it made the output trustworthy feature by feature. [PARTIAL - paper-examples validation is sourced; grid tests are my own ordinary harness, not instrumented]
4. Why that warping method over the alternatives? - The boards bent unevenly, so a flat perspective fix wasn't enough (a perspective fix = the simple correction for a photo taken at an angle, which assumes a flat surface); non-rigid was the actual requirement. I compared the standard non-rigid options (thin-plate spline, elastic, B-spline - three textbook ways of digitally bending an image) and the spline method needed only the marked control points the pipeline already produced (control points = spots, like component corners, that the matching step had already located on both images). [SAFE]
5. What if the one-day spike had failed? - Honest gap: no recorded fallback. The server option the network rules excluded would have been the only one left, so realistically I'd have had to reopen the IT conversation. The move wasn't "I had a plan B" - it was "I bounded the unknown before building on it." [GAP - stated plainly, not papered]
6. Where did the 40 ms come from, and does it clash with your "~45 ms CPU" figure? - Forty milliseconds is the image-comparison step in the browser (align + diff), timed in the browser console against routine board pairs on a factory-class laptop while developing - personal observation, not a benchmark suite. Plain line: it counts how long one photo-vs-design comparison takes to finish in the shipped tool; the source is timings I read off the developer tools built into every browser; the solidity is my own observation on ordinary boards, not a measured study. The ~45 ms figure is the classifier's inference on CPU in the server build (the classifier = the trained defect-spotting model; inference = one pass of it making a prediction; CPU = an ordinary processor rather than a graphics card). Different steps, different builds; I don't quote a browser inference time. [PARTIAL - honestly framed]
7. Was the unfamiliarity the language or the domain? - I already wrote the app's JavaScript; the discomfort was computer vision in a browser - a rendering-adjacent runtime doing numeric work I'd always done server-side in Python (a browser is built to draw pages, not to crunch numbers the way a server is). [SAFE]
8. The vision-LLM repeat - what did that involve? - Same comfort-zone shape: GPT-4o for reading mismatch reports, after weighing GPT-4V (slower, ~8 s vs ~3 s - seconds before each answer arrives), Claude 3 (less mature API - fewer tools for wiring software to call it), Gemini Pro Vision (weaker on small objects), and a local LLaVA (an open AI model I could run on my own hardware instead of online; needed >=8 GB VRAM the machines didn't have - VRAM is a graphics card's own memory). Picked on documented constraints, not my own bake-off. Reading a mismatch went from ~30 s manually to ~5 s (the human's zoom-and-decide time before, the AI's answer time after - not a stopwatch study), correct about 85% of the time by my own rough check - no held-out set (no batch of test examples the model had never seen, which is the fair way to score accuracy), and it ran only in the server build.
