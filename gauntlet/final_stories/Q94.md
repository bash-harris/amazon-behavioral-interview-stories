# Q94 - tell me about a project you recently worked on and what the... (truncated; read as "...what the impact/outcome was")

**LP:** Deliver Results; Think Big; Invent and Simplify.   **Story:** Tab Scroller - one clean STAR arc (personal project; perf figures = design targets); PCB suite appears only as a number-free one-line breadth nod.

## Core Answer

The project I'd point to is Tab Scroller, a Chrome extension - a small add-on program that runs inside the Chrome browser - I built around a problem I was living with. I keep a few hundred tabs open between work, interview prep, and paper reading, and the browser stops being usable - nothing is findable, and a research session can't be picked up a day later. Chrome won't let an extension touch the native tab bar, so everything had to live as an injected overlay - a panel the add-on draws on top of web pages, since it can't become a built-in browser part. That constraint set the architecture.

I scoped it deliberately bigger than a tab manager: an AI research workspace - you type what you want in ordinary English (an "AI command," like "snooze these tabs until tomorrow") and the tool carries it out, then turns a messy session into something reusable.

The real decision was where the model sits. My first instinct, send every command to an LLM - a large language model, the kind of AI behind chatbots - is wasteful: "close all the YouTube tabs" doesn't need a model. So I built rule-first routing - a lookup table of plain-text patterns matched on the user's own computer. Simple commands match local rules and never touch the network; the model is the last hop, not the first. For hard commands, a pre-filter narrows the tab set before any extraction - before the tool reads the pages' text - and page text gets compressed into subject-predicate-object triplets - tiny "thing -> does -> thing" summaries, far shorter than the pages - before the model sees it. I kept the UI framework-free - plain browser code (JavaScript and CSS), no third-party interface library - because a heavy framework in an injected bar is response delay that users actually feel. And I supported two backends - interchangeable AI engines - on purpose: cloud Gemini (Google's online AI service) for quality, local Ollama (software that runs open AI models on the user's own computer) so privacy-sensitive users keep everything on-machine.

Snoozing - like the alarm button on a phone: a tab is set aside and returns at a chosen time - was the reliability problem worth solving: a dismissed tab has to return even after a browser restart. So the state (which tab, when to return) lives in chrome.storage.local - the browser's own saved data on that one computer, not a server - and chrome.alarms - the browser's built-in timer service - re-arms across restarts. The timer has to be the browser's because the add-on's own background program, Chrome's so-called service worker, isn't running while the browser is closed. I wrote it against a PRD - a written product spec - and shipped in three iterations - alarm engine, message handler (the code that routes commands between the page and the AI), context-menu UI - verifying each one before moving on.

Honest status: it works, and it's a personal project - the only daily user is me. The speed numbers are design targets - figures the plan aimed for, not stopwatch readings; the documented target is simple commands back locally in under 10 milliseconds (thousandths of a second) with no API calls - no requests to any online service at all. Before it I shipped the Bosch PCB inspection suite solo, and the habit I keep reusing is the same: start from the hardest constraint and let it pick the architecture.

The miss I'd own: I shipped the AI action layer - the part that actually carries out commands - without guardrails. A wrong model call can close your tabs. A confidence gate - acting automatically only when the AI's certainty score is high enough - and transactional undo - reverting an action completely or not at all - are written in my upgrade plan but not in the build; that's the first thing I'd do next.

## Memory Anchors
- Problem: a few hundred open tabs (personal observation); Chrome can't be modified at the native tab bar -> injected-overlay constraint.
- Customer: me - this is a personal tool; no adoption claimed.
- Insight: the model should be the last hop, not the first; the hardest constraint (browser + privacy) picks the architecture.
- Action (mine): solo build vs a PRD (product spec) in three verified iterations - rule-first token-saving pipeline (pre-filter -> parallel extraction -> triplet compression), two backends (Gemini = cloud AI / Ollama = AI on the user's own machine), framework-free vanilla JS/CSS, restart-safe snooze via chrome.alarms (browser timer) + storage (saved on that computer).
- Result: working extension in my daily use; <10 ms local-match is a design target, never instrumented; memory layer turns a session into a Markdown (plain-text notes format) research brief.
- Learning: shipped the AI action layer before its guardrails - confidence gate + undo designed, not built; that's step one next time.

## Follow-Up Bank
1. What was the hardest technical decision? - Making the model the last hop instead of the first. Costs more local logic to maintain; buys latency (response speed), cost, and privacy, and it's why simple commands run offline - in plain terms, most commands never leave the computer, so they're fast, free, and private. [SAFE]
2. Why two backends instead of one? - Different users: Gemini reasons better on hard commands; Ollama lets someone who won't send tab data to a cloud still use the feature. The backend is a setting, not a rewrite. [SAFE]
3. How does snoozing survive a restart? - State lives in chrome.storage.local - the browser's own saved data on that one computer, not a server - chrome.alarms re-arms when the browser returns so the one-minute tick resumes; the tab is removed only after the storage write is confirmed. Why the browser's timer is essential: the add-on's background program - Chrome's "service worker" - stops entirely when the browser closes, so only the browser itself can promise the future wake-up. [SAFE]
4. How did you measure performance? - I didn't instrument. The figures in the implementation guide's "Expected Performance Gains" are design targets, not measurements: rule-path commands 2s -> <10 ms with zero API calls, complex 50-tab commands 8s -> 3s with 50k -> 3k tokens, extraction 5s -> 0.5s, and ~70% of commands served offline. In plain terms: 2s -> <10 ms is the time from issuing a command to it happening, for commands matched by local rules (a millisecond is a thousandth of a second); 50k -> 3k tokens is the amount of text handed to the AI (tokens  word-chunks, what AI services measure and bill by); 8s -> 3s and 5s -> 0.5s are the planned response times for complex commands and for reading page text; ~70% offline is the share of commands needing no internet. All are goals written in the design doc before building; none was timed. In my own use the rules path feels instant; that's personal observation, not telemetry. [PARTIAL - projected, not measured]
5. What does the memory layer do? - Condenses a session into a Markdown research brief - a notes file in a plain-text format - with source-referenced cross-tab Q&A (answers that cite which tab each fact came from) and evidence capture, stored in chrome.storage.local (the browser's saved data on that computer). [SAFE]
6. Biggest weakness in the build? - The action layer has no guardrails. The design exists - deterministic confidence, auto-execute above 0.75, confirm 0.4-0.74, clarify below 0.4, plus transactional undo and telemetry - but it's in the upgrade plan, not the code. In plain terms: a fixed score for how sure the AI is would decide auto-run vs. ask-the-user vs. ask-for-clarity; "transactional undo" means the action reverses completely or not at all; "telemetry" means built-in usage and error logging. None of that exists in the shipped build. [SAFE - disclosed]
7. Who else uses it? - Nobody, and I won't pretend otherwise. It started as my own workflow tool; I've made no rollout or store-listing claims. [SAFE - honest status]
8. Why no UI framework? - The bar is injected into every page; a framework tax is paid on each tab. Vanilla JS and CSS kept it light; the model call is the only heavyweight path by design. Plain terms: a third-party interface library would load extra code into every web page the user opens, slowing each one down. [SAFE]
9. Any external inputs? - Two model ecosystems (Gemini, Ollama), and watching the tab-utility category shift toward AI workspaces - that range of inputs is what set the scope. [SAFE]
10. What would you do differently? - Build the guardrails before the action layer, and instrument intent latency/failure rates from day one so "is it fast?" has a real denominator. Start from the constraint, not the feature list. In plain terms: "instrument" means build in timing and error logging so answers come from data, not feel; "intent latency" is how long a plain-English command takes to carry out. [SAFE]
