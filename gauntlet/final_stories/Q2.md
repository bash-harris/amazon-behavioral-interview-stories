# Q2 - tell me about a time you used genai to automate or streamline a workflow
**LP:** Invent and Simplify (primary); touches Deliver Results, Frugality, and Learn and Be Curious.   **Story:** BGSW PCB Inspector Suite, told as one inspection workflow with two tools - deterministic BOM reconciliation (a rules-based parts-list check, no AI), plus the GPT-4o VLM - an AI model that can look at images - living only in the photo-vs-layout comparison tool (STORY 1/8/10/11).

## Core Answer

I built the PCB inspection suite at Bosch, solo. A PCB is the green circuit board inside nearly every electronic device, and a "populated" board is one with all its components soldered on. Verifying a populated board had two manual steps inside one workflow. The first: an engineer cross-referenced the SAP-exported BOM spreadsheet - SAP is the factory's production-management software, and a BOM (bill of materials) is the parts list naming every component and where it goes - against the Altium layout, the engineering drawing of the board, part by part; the engineers reported 20 to 30 minutes a board (their own estimate, not a timed study), and it was easy to miss things. The second: every region the photo-vs-layout comparison tool - it puts a photograph of the real board against the drawing - flagged in red (circled as suspect) still took a person about 30 seconds at the component to decide whether it was a wrong value (the wrong spec of part), a wrong orientation (installed backwards), or just a lighting artifact (light glinting off the board that only looks like a difference). I deleted the first step with deterministic parsing - plain rules-based software: same input, same output, no AI anywhere - and the second with GenAI (generative AI; here, an AI model that looks at a picture and interprets it), and I deliberately kept the two apart.

The split matters because the artifacts differ. The reconciliation is document versus document - a BOM Excel (the parts list as a spreadsheet) against a layout PDF (the drawing as a document), no photo, no model anywhere in that code. The comparison tool puts a photograph of the real board against the layout. That is the one place a model earns its keep. When it flags a region, I crop it from both the layout and the photo and send both to GPT-4o - an AI model that can look at images - with a structured prompt (an instruction written to demand one fixed answer shape): identify the component, classify the mismatch - wrong value, orientation, missing, extra, false alarm (a flag on something that's actually fine) - and return JSON I can parse (a machine-readable answer format the software can read directly). Before choosing it I baked off GPT-4V, Claude 3, and Gemini Pro Vision - I ran the same test spots through each model and compared the answers; a local model (one run on the factory computer itself instead of online) would have needed VRAM - graphics-card memory - the factory machines didn't have.

The GenAI result: interpreting a flagged mismatch went from a reported ~30 seconds (the engineers' own estimate of their look-and-decide time) to a ~5-second suggestion that the engineer verifies (that ~5 seconds is how long the AI takes to answer - computer time; the engineer's confirming step still takes a moment and was never timed). The output is labeled "AI Analysis" with a confidence figure (how sure the model says it is) - a suggestion, never a diagnosis - and when the API - the connection to the online AI service - is unreachable the tool still works: the visual highlights show, it says AI analysis unavailable, and the engineer inspects as before. The AI part is an enhancement, not a dependency.

The learning came from the other tool. My regression suite - a fixed set of known test files I re-run on every change - reported zero false positives (it cried wolf on nothing *in those files*), then production (real boards on the factory floor) surfaced a class it had never seen: footprints - the mounting outlines where components sit - legitimately carrying more pads (solder points) than the BOM listed. I fixed it, but the lesson stuck: a test suite you size yourself only tests your imagination. GenAI belongs where interpretation is the bottleneck; rules should own everything else.

## Memory Anchors
- Problem: One inspection workflow, two manual steps - a 20-30-minute (engineer-reported) part-by-part BOM-vs-layout cross-reference (parts list against the board drawing), plus a ~30-second human look at every visually flagged mismatch.
- Customer: Manufacturing/test engineers on the factory floor - non-developer users, restricted-network machines (locked-down computers with limited internet), one developer (me).
- Insight: Only the visual interpretation is a model job. The reconciliation is document-vs-document with no photo; the VLM (the image-capable AI model) belongs solely in the photo-vs-layout comparison tool.
- Action (mine): Solo-built the deterministic BOM reconciliation (regression suite - a fixed set of known test files I re-run every change - built from production failures; a `?debug=true` decision-tree view: a web-address switch that displays the tool's step-by-step reasoning); in the comparison tool, GPT-4o on crops from layout + photo with a structured JSON prompt after a bake-off (same test spots through several models, compared); suggestion-not-diagnosis UI with confidence and feedback marks; graceful degradation with no API (the tool keeps working when the AI service is unreachable).
- Result: Reconciliation returns in seconds what engineers reported taking 20-30 minutes; per-mismatch interpretation ~30s -> ~5s verified suggestion; suite-clean (no false alarms on my own test files), then one real false-positive class escaped and was root-caused (traced to its underlying cause) and fixed.
- Learning: A suite you size yourself only tests your imagination - collect real BOMs first; the VLM reads component type and orientation, not tiny SMD values (SMD = surface-mount device: the tiny parts soldered straight onto the board, whose printed markings are hardest to read); rules own everything a model doesn't need.

## Follow-Up Bank
1. How do the two tools relate - does the reconciliation feed the model? - It doesn't, and I won't pretend it does. Reconciliation compares a BOM Excel to a layout PDF - structured data, no photo, no model call in `bom_server.py` / `bom-verification.js` (the two named files that make up that tool). The VLM (the image-capable AI) lives in the comparison tool (`vlm_scanner.js`), where a flagged region has images on both sides. The workflow is automated because both manual steps are gone, not because one pipeline calls the model. [SAFE]
2. Why not just send everything to the model? - A parser (rules-based code that reads the two lists item against item) is cheaper, faster, and explainable for symbol-to-symbol matching - comparing each part reference in the list to the drawing one by one, with a showable reason behind every decision; sending 2,000 components to a VLM would be slower and costlier for no gain. I send only the 5-20 regions per board the comparison already flagged (the typical number of red marks on a busy board, from the tool's everyday output) at roughly a cent an analysis (about what the AI service charged per call then - a cost estimate, not a billing study). [SAFE]
3. How did you measure the improvement? - With honesty about what's instrumented: the 20-30-minute and ~30-second baselines were engineer-reported, not a timed study - people's own estimates of what their old manual step took. Reconciliation stats are regression runs on 15 production BOMs (15 real parts lists taken from production as my fixed test set): zero FP/FN there - zero false alarms (FP: crying wolf on something fine) and zero missed real errors (FN) on *those 15 files*, not on every board ever; a 2,000-component BOM parsing under 200 ms (my biggest test file, timed on the parse step itself); three real mismatches caught in week one (actual discrepancies flagged on live boards, counted from the tool's production reports). The ~5 seconds is the comparison tool's API response time - computer time answering, not the engineer's total time. The pin-count fix's ~12%->under 2% came from analyzing 20 failure BOMs before and after - the share of flags that were false alarms, counted over those 20 real failure files; a small, self-run tally. No stopwatch study - a gap I'd own. [PARTIAL - baselines reported, not measured]
4. What happens when the model is wrong, or the API is down? - Output is a suggestion labeled "AI Analysis" with a confidence figure (how sure the model says it is); the engineer verifies it. Correct/incorrect feedback marks (buttons to say the AI was right or wrong) exist so systematic prompt errors - a wording flaw repeating the same mistake - can surface; design intent, not a found bug. No API or key (a key is the "password" that lets software use the paid AI service): highlights still show, UI says AI analysis unavailable, inspection continues; reconciliation never needed the API at all. [SAFE]
5. Walk me through the messy BOM data. - A naive regex - a compact text pattern-matching rule; mine said "a part reference is letters followed by digits," written `/^[A-Z]+\d+$/` - worked on about 70% of real BOMs (the share of the first real parts lists I tried it on that passed - a rough tally of my own files, not a formal study), then production broke it four ways: an `MP_` manufacturing-process prefix (a code stuck on the front of the name by the production system); SAP hyperlink cells (spreadsheet cells that are clickable links - you must follow each to its display text, not the URL behind it); variant refs `R1||R2` / `R1/R2` (one entry standing for several board positions - a manufacturing engineer taught me their matching semantics); and DNP positions ("do not populate" - slots intentionally left empty, not missing parts). Each was a production failure first, then a permanent case in the 15-BOM regression suite. [SAFE]
6. Did anything escape your suite? - Yes: a pin-count false-positive class - footprints legitimately with more pads (solder points) than the BOM listed, from no-connects (pads wired to nothing by design) and package variants (the same part in a different physical housing). I categorized 20 failure BOMs (real parts lists that had produced wrong flags, grouped by cause), added a component-type check with a configurable 2:1 pad ratio (a part may have up to twice as many solder points as listed - the multiplier adjustable without code changes), and false alarms on mixed-type boards (boards carrying many different component families) dropped from ~12% to under 2% - measured over those 20 files before and after the fix, a small self-run count. The debug view shows the raw per-component comparison so the engineer can override - the human keeps the final call. [SAFE]
7. Tell me about one of the three mismatches caught in week one. - I know the count and the categories - missing, extra, mismatched - but I can't walk through each from memory; they're in the tool's production reports, not my notes. What I analyzed component-by-component, and can speak to concretely, is the pin-count false-positive fix. [GAP - don't dress up the headline]
8. Why GPT-4o over the alternatives? - Bake-off (the same test spots run through each model, answers compared): GPT-4V ran ~8 seconds per request versus ~3 - seconds = the wait for the AI's answer to one question, observed in my own bake-off; Claude 3's API was less mature at the time (the tooling to plug it into an app was rougher); Gemini Pro Vision was weaker on small parts; a local LLaVA (an open AI model I could run on the factory computer instead of online) would have needed 8 GB of VRAM (graphics-card memory) the factory machines didn't have. [SAFE]
9. Where did the design ideas come from? - Externally: the model bake-off and a browser CV stack (OpenCV.js, TensorFlow.js - ready-made image-analysis and machine-learning libraries that run inside a normal web browser; not my code). Internally: the manufacturing engineer on variant semantics (what `R1||R2`-style entries mean when matching); the engineers' use of the debug view, which surfaced two naming edge cases in week one; and the security team, who approved sending board photos because they contain no trade secrets (no confidential company information) - a discussion, no written artifact. [PARTIAL - security approval verbal, no artifact]
10. Hardest part? - Trust, not code. Non-developers on restricted factory-floor machines (locked-down computers) don't accept black boxes - tools whose reasoning you can't see - so I made my judgment calls visible: raw BOM text, every preprocessing step, the layout match, and the exact decision tree behind `?debug=true` (a web-address switch that walks through, for each part, what the code saw, did, and decided), plus an aggregate dashboard (a summary page of overall results). Engineers used it to teach me two edge cases in week one. [SAFE]
11. What would you do differently? - Collect representative BOMs (real parts lists that cover the world's edge cases) and pin-count semantics from the floor before writing code - every edge case arrived as a production failure. Build the debug view from day one. Never let a "zero false positives" claim outrun a suite you sized yourself. And design the UI around the VLM's ceiling (what the image-capable AI is and isn't good at): strong on component type and orientation, unreliable on tiny SMD values. [SAFE]
