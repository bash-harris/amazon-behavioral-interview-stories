# Q84 - tell me about a time you did something that was not your task (like go above and beyond)

**LP:** Ownership (primary); Customer Obsession (touch).   **Story:** BGSW PCB Inspector Suite - BOM reconciliation transparency layer (`AMAZON_INTERVIEW_PREPARATION.md` STORY 11). Honest spine: the debug mode was assigned; the beyond-brief acts are the dashboard, the self-imposed completeness bar, and owning adoption. One telling only - STORY 11.

## Core Answer

The honest version of this story starts with a confession: the debug mode was my assigned task - the work my role told me to do, not something I volunteered for. I'd built the BOM reconciliation tool - a BOM is a Bill of Materials, the list of parts that go on a board, and the tool checks that parts list against the board layout, the drawing of where every part sits - and my job was to add a debug view (a screen that shows how the tool reached its conclusion) so a manufacturing engineer, the person who runs board assembly on the factory floor, could see why it called a component a mismatch - why it said a part didn't match the design. I built that. The above-and-beyond is everything after it, and that's where I'd point.

Because the real problem under the task wasn't visibility. It was trust. The engineers used the tool, but when it flagged a mismatch the report showed the verdict and hid the reasoning. So on anything that mattered they cross-checked by hand anyway - twenty to thirty minutes a board. That figure counts how long one engineer said it took to verify a single board by hand against their files; it's a recollection they gave me, never timed or logged, so it's their number, not mine. And a debug view answers a question about one part. It doesn't tell you the whole board is safe.

So I built a second thing nobody asked for: a reconciliation dashboard over the same data. A live table with totals, matches, mismatches, and needs-review; the component-type mix; color-coded status chips - small colored labels showing each part's state at a glance; severity ranking so missing parts sort to the top. Click a row and you jump to that component in the debug view. Verify the whole board first, then drill into one part.

I also set a bar that wasn't in the brief - wasn't in the list of work I was given: if an engineer asks "why did you call this a mismatch?", the view answers completely - the raw entry text, what it parsed to (what the software decided those words meant), what it matched in the layout, which rule fired. Any missing step just sends them back to me, which kills the point of building transparency at all.

Then I owned what the transparency exposed. In the first week, an engineer used the view to catch two cases where my matching heuristic was wrong - a heuristic is a rule of thumb the software follows, here for deciding which part on the list is which part on the drawing. Both cases were parts named in an unusual way, so the rule paired them up wrongly. That was my tool being wrong, so I fixed it instead of defending the logic.

The outcome wasn't the feature. It was the behavior. Once they could see the reasoning and check it against their own files, they stopped re-checking by hand and started relying on the tool for production verification - using its output to decide whether real boards coming off the line were acceptable.

What I learned: I built all this as an afterthought. Had I started with the transparency, it would have caught those errors sooner. Going above and beyond for a customer usually isn't a longer feature list. It's removing the reason they don't trust the result.

## Memory Anchors

- Problem: the reconciliation tool's reports showed verdicts (its decision) without reasoning, so engineers re-checked by hand - an adoption/trust gap hiding under an assigned "debug mode" task.
- Customer: manufacturing engineers using the BOM tool on the floor; they needed to verify a decision without routing through me.
- Insight: the literal ask (per-part visibility) missed the real constraint (whole-board trust); transparency only counts if it answers "why" completely.
- Action (mine): built the assigned debug view; self-initiated the reconciliation dashboard (live totals, type mix, status chips, severity sort, click-to-drill); set the completeness bar; fixed the two bugs in my rules-of-thumb matching logic that the view exposed instead of defending them.
- Result: two naming-convention errors surfaced and fixed in week one; engineers stopped hand-re-checking and relied on results for production verification.
- Learning: build the transparency first-class from the start; above-and-beyond = removing the distrust, not padding the feature list.

Same data, arranged so a human can audit the decision - no new exposure. [SAFE]
8. If the debug view itself were wrong, wouldn't it give false confidence? - It displays the raw pipeline output (the tool's unedited step-by-step result) consistently, so an engineer can compare it against the actual BOM file and see where the parse - the software's reading of the text - diverged - exactly how the two naming bugs were found. Hiding the intermediate data is what creates false confidence. [SAFE]
9. What did you consider and reject? - Shipping just the specced debug endpoint (the debug page exactly as the brief specified - answers one part, leaves the board-level trust gap); flagging every uncertain position for manual review (pushes back the work the tool exists to remove); cramming diagnostics into the main report (noise - the view stays separate). [SAFE]
10. Hardest part? - Letting the tool's own mistakes be seen. The completeness bar meant users could prove I was wrong, and twice they did, in week one. Defending the logic would have been the easier move and the wrong one. [SAFE]
11. Who did this work - you or a team? - I built the suite solo. The dashboard is my code, documented in the reconciliation module's dashboard rendering. [SAFE]
12. Do it differently? - Build the transparency from the start, not as an afterthought - it would have surfaced the edge cases weeks earlier. For an automated system, explainability - being able to show how a decision was reached - is what makes the result usable at all. [SAFE]
