# Q29 - a time when you had a blocker in your work and how did you resolve that blocker?

**LP:** Bias for Action (primary); Deliver Results   **Story:** STORY 4 "The Standalone HTML That Replaced a Server" - the OpenCV.js / WebAssembly load blocker only; a different moment from Q7 (IE11 miss) and Q8 (solo ship) in the same project.

## Core Answer

The clearest blocker I hit was OpenCV.js refusing to boot inside my PCB inspection suite's single-file offline build. (OpenCV.js is the browser image library - a professional image-processing tool that runs inside the web browser instead of being installed on the computer - and "offline" meant the file had to work with no internet at all.) Without it, alignment and comparison - the actual product - never started.

The setup: manufacturing engineers needed the tool on factory-floor machines - no internet, no installs, minimal IT support. The original ran on a Flask server (a small program that hosts the tool on one machine while everyone else opens it over the network), and Python installs (Python being the programming language that server needs) were beyond what the team could do. So I was compiling everything into one HTML file they could double-click. The file built, the UI opened, and the pipeline just sat there dead.

The trouble was how WebAssembly loads. (WebAssembly is a way for a browser to run code written in older, compiled languages at near desktop-program speed - but first it has to receive a binary: a block of compiled machine code.) OpenCV.js is JavaScript plus a binary module, and the loader normally fetches that binary as a separate file - like any web page downloading its pieces from a dedicated file server while it opens, which is what a CDN is. A single offline file has nothing to fetch from. So I separated the two steps: the JavaScript loaded fine, instantiation failed - instantiation meaning the browser turning that block of code into a running module - and reading the loader showed me the fetch. The transport was the blocker, not the library. Shipping a folder of files was off the table - a second file that gets accidentally moved was the exact failure I was eliminating.

The fix removed the fetch. I embedded the binary inside the HTML as a base64-encoded copy - base64 is a way of rewriting any file as plain text so it can live inside a text file - then changed the loader to decode it at runtime into raw bytes and hand them straight to the WebAssembly engine. No network, no extra files: "embedded" meant everything ships inside the one file. Same trick for the machine-learning library - also a browser image/learning library - : inline the bundle, make the weights (the learned numbers inside a model) a constant instead of a sidecar file (a helper file that has to sit beside the main one).

The cost was real and taken deliberately: about 5 seconds to load on a factory machine, versus 2 for the server version. What those count: double-click to a working tool; where they come from: my typical observed startup noted on real machines - stopwatch-grade, not a formal benchmark. A slower cold start on a tool that works offline beats a fast tool that doesn't. And "it runs" wasn't the bar - I ran the same boards I knew through both builds and compared the outputs, by hand plus a small automated diff. By hand means I read the two result sets side by side; the small automated diff was a simple script I wrote to flag any place the two outputs disagreed. They matched, alignment within about a pixel - about one dot on screen - on what I checked.

The result was one file, about 25 megabytes - into the tens of megabytes, because every image and learning part now lives inside it. Engineers double-clicked it - no Python, no server, no IT ticket (no help-desk request) - distributed by email and USB.

The lesson: when a deliverable is blocked, question the delivery mechanism - mine was a transport assumption, not code. And one limitation I accepted too quietly: the file was big enough to hit email attachment caps; compressing the embedded libraries (shrinking the files with standard compression) would have fixed that.

## Follow-Up Bank

1. What exactly was the blocker? - OpenCV.js is a WebAssembly module: its binary loads separately, normally fetched at runtime (the browser downloads the block of compiled machine code when the tool starts, from a file server - the CDN-style fetch a normal web page also relies on). In the single offline file there was nothing to fetch from, so instantiation failed and the alignment/comparison pipeline couldn't start. [SAFE]
2. How did you diagnose it? - Separated the JavaScript load from the WASM instantiation: JS succeeded, instantiation failed. Reading the loader showed it requesting the `.wasm` file over the network. That moved the problem from "broken library" to "missing transport" - from "the tool is broken" to "the tool is fine, it just had no way to receive one of its parts." [SAFE]
3. Why base64 instead of sidecar files or a service worker? - Sidecar files (helper files that must stay next to the main one) break the one-file rule - move one file and the tool dies, the exact failure I was removing. A service worker (a small background program a web page can install in the browser to serve files locally) needs HTTPS (encrypted web traffic) to register and adds compatibility risk on the floor machines. Base64 costs ~33% size overhead (the text version of a binary is bigger than the original) but removes every external dependency. [SAFE]
4. What did the fix cost, exactly? - ~2 seconds of runtime base64 decode on startup (re-translating the text-embedded code back into machine code each time the tool opens); ~12.5 MB of embedded libraries inflating to the ~25 MB file (OpenCV.js alone ~8 MB) - the rest is the machine-learning libraries, the model weights, and the app itself, which together push the single file into the tens of megabytes; recompile takes ~10 seconds (my build script re-assembling the file after a change), mostly the OpenCV file. Recorded figures, not benchmarks - my own notes while building, not instrumented measurements. [SAFE - label on probing]
5. How did you verify the standalone matched the server build? - By hand: I ran the same known boards through both builds and compared the outputs, reading the two result sets side by side, with a small automated diff flagging score mismatches - a simple script I wrote pointing out every place the two outputs disagreed; alignment within about a pixel - roughly one dot on screen - on what I checked. The known-board set wasn't a measured sample, so I quote no parity percentage. [SAFE]
6. Why not escalate to IT for network access? - The blocker sat in my own build pipeline; the offline constraint was the product requirement, not a ticket. Escalating would have added delay without changing the constraint. [SAFE]
7. Can you show me the offline file? - Honest line: it's built from source by my compile script, and the size/load figures are my recorded account of the offline build - my own notes from real use, not instrumented measurements - so I don't offer to open it on the spot. [PARTIAL - artifact can't be produced in the room]
8. Did it run on every machine? - It needed a WebAssembly-capable browser - one new enough to support the browser's fast compiled-code feature - and machines without it got a clear startup error instead of a half-working tool. The environment-assumption miss there is a separate failure story - one cross-reference, no retelling. [SAFE]
9. Hardest part / what almost went wrong? - Resisting the urge to swap libraries. The failure read like an OpenCV bug; the fix was nearly the wrong rewrite. Patience to isolate load vs instantiate - asking "can the browser read the file?" and "can it start the compiled code?" as two separate questions - found the real cause. [SAFE]
10. Do differently? - Compress the embedded libraries from the start: at ~25 MB the file ran into 20 MB email attachment caps (most email services refuse bigger files); gzip on the embedded libs (a standard file-compression method) could have brought it near 15 MB - a distribution problem I accepted when I didn't have to. [SAFE]
