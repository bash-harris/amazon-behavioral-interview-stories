# Q7 - tell me about a time you failed

**LP:** Earn Trust (primary); Learn and Be Curious; touches Deliver Results   **Story:** BGSW PCB Inspector Suite - the IE11/WebAssembly browser-compatibility miss in the standalone single-file deployment (AMAZON_INTERVIEW_PREPARATION.md STORY 4)

## Core Answer

I failed a subset of the users I built something for. The PCB inspection suite - a PCB is the green circuit board inside every electronic device; my software photographs a finished board and flags its defects - ran on a Flask server, a small web program running on one central computer that everyone else opens through their browser, but the manufacturing engineers needed it on factory-floor machines: restricted network, no software installs, minimal IT support. So I built a standalone version - one HTML file, a single self-contained web-page file engineers could open in a browser, no server - using the analysis libraries: OpenCV.js (the image-comparison engine), which is a WebAssembly module - WebAssembly is the low-level format that lets heavy image code run in a browser - plus TensorFlow.js (the AI model that recognizes defects), PDF.js (reads the board's design documents), and a spreadsheet reader (opens the parts-list files). I wrote the compile script that assembled it - a small build program that packs all those pieces into the one file.

My assumption was simple and untested: that the factory-floor machines ran modern browsers - current, still-supported versions, not old ones. Some ran IE11 - Internet Explorer 11, Microsoft's old browser that it has since retired. IE11 has no WebAssembly support - the browser simply cannot run that engine format - and OpenCV.js is a WebAssembly module - so on those machines the tool just didn't work. Those were exactly the machines the standalone existed to serve. And I'll be honest about the size of that failure: I never took a fleet count - I never went through the plant and counted how many machines were actually affected. I don't know today whether it was one cell's machine or half the floor. That missing number was itself part of the failure - I never went and looked at the environment I was shipping into.

Here's what I own: it wasn't a tricky bug that slipped through a test. It was an assumption about the deployment environment I never verified. I tested on modern browsers - the environment I had, not the environment I was shipping to. I could point at machine age or the IT setup, but the honest root cause is that I designed for "browser" in the abstract instead of the actual machines in front of me.

I couldn't fully fix it. Making it run on IE11 meant replacing the WebAssembly-dependent image pipeline - the chain of image steps that only runs through that engine format - with JavaScript fallbacks, meaning re-implementing those steps in the browser's standard scripting language - effectively a rewrite for an end-of-life browser, one its maker no longer updates or supports. My estimate on the spot was that it wasn't worth the cost; if a still-supported browser on the fleet had shown the same gap, I'd have paid it. So I did the honest thing within reach: I added a startup browser-compatibility check - when the file opens, it first tests whether this browser can actually run the tool - that displays a clear error message when the browser can't run the tool, so the engineer got an explicit "this won't run here" instead of a mystery.

The lasting change is the habit. I now verify the target environment before I build for it - the actual OS and browser on the actual machines, not the assumed one. It's the same lesson the BOM parser - the tool that reads a board's bill of materials, its complete parts list - taught me about data: don't trust your assumptions about the environment you're deploying into; go look. Being curious about *why* IE11 failed - the WebAssembly capability gap, meaning exactly which built-in feature the browser lacks, not "old browser, shrug" - is what turned a dead end into a guardrail.

## Memory Anchors

- Problem: the standalone build didn't run on the factory-floor machines that ran IE11 - no WebAssembly there, and OpenCV.js is a WebAssembly module
- Customer: the manufacturing engineers on restricted-network machines with no installs and minimal IT support
- Insight: the failure was an unverified environment assumption, not a bug - I tested the environment I had, not the one I was shipping into; and I never measured how many machines it hit
- Action (mine): built the standalone single-file version with my compile script; after the miss, added a startup browser-compatibility check showing a clear error message; judged the IE11 rewrite not worth it (labeled on-the-spot estimate)
- Result: modern-browser machines could use the file as designed; IE11 machines got an explicit error instead of a mystery; impact never quantified - owned, not inflated
- Learning: verify the real target environment before building; root-cause capability gaps instead of shrugging; same "go look" lesson as the BOM parser
