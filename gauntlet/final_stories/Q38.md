# Q38 - tell me about a project where you chose the UI/middle layer/database/etc

**LP:** Are Right, A Lot (primary - three layered calls under an environment constraint); Invent and Simplify (single-file delivery, complexity deliberately avoided)   **Story:** STORY 4 "The Standalone HTML That Replaced a Server" - the stack-choice moment; distinct from Q21 (learning the stack), Q29 (the WASM blocker), Q7 (the IE11 miss, touched once here)

## Core Answer

The PCB inspection suite (a PCB is the green circuit board inside every electronic device) was one architecture decision with three layers: where the compute runs - which computer actually does the processing work; how the tool ships - what form the software arrives in; and where the data lives - which machine keeps the saved records. I was the only engineer on it, so these calls were mine.

The users settled the shape: manufacturing engineers on factory-floor machines - no internet, no installs, minimal IT support.

Layer one, the middle layer - the engine of the app, the part between the screen the user touches and the work that gets done. My default, and where I started, was a Flask backend with a web front end: a small always-running server program (Flask is a tool for building one) that the engineers' browsers talk to, with Python code doing BOM parsing (a BOM is the bill of materials - the parts list for a board) and image processing. A desktop app was the other candidate - a program installed directly on each machine. But a server meant Python, dependencies, and network config on machines the engineers don't administer, and a desktop app meant an install IT wouldn't approve. So I moved the compute into the browser itself: OpenCV.js for alignment (image-processing code that matches the design file to the photo of the board) and TensorFlow.js for defect inference (it runs the trained model that decides whether something is a defect). The axis that decided it: runs on the machine with no install and no network.

Layer two, packaging. I could load the libraries from a CDN and keep the file small (a CDN delivers the code files from the internet each time the tool opens, instead of them traveling inside it) - but that needs the internet the floor doesn't have. Separate sidecar files broke too (extra companion files that must sit next to the HTML): move the HTML without its companions and the tool dies. So I base64-embedded everything into one HTML file - base64 means converting each code file into plain text stored inside the one file, so opening a single file delivers the whole tool - the OpenCV binary included as a data URL (a file spelled out as text inside the page rather than fetched separately). That carries real size overhead, which I accepted - one file removes the failure mode.

Layer three, the database. Auto-save needed persistence - the tool had to remember records after closing - and the realistic options were localStorage and IndexedDB, the two kinds of storage built into every browser; both keep data on that one computer, not on a server. I picked localStorage: the save path is synchronous and simple (writes happen immediately, in step-by-step order - no "the answer comes later" code), an inspection is a few KB (small text records), and the 5 MB quota (the fixed space the browser allows per site - a documented limit, not my estimate) covers that easily. IndexedDB buys capacity I didn't need yet at the cost of async complexity (the code must juggle callbacks and promises - patterns for waiting on results that arrive later). I added a quota guard that drops the oldest entries, and a commitment to move to IndexedDB if the data grew.

The result: one file, about 25 megabytes (the file's size on disk, per my recorded account of the build - a "round" figure, not a measured measurement), double-click to run (open it straight in the browser, no install), full functionality - loading in about 5 seconds on a factory machine versus 2 on the old server build (time from double-click to a working tool; my own stopwatch observations, not instrumented tracking). A slower start on a tool that works, taken on purpose.

I was right about the stack and wrong about one assumption: I figured every machine had a modern browser, and a few had IE11 (a very old version of Internet Explorer), which can't run WebAssembly (the fast, machine-code format the browser libraries depend on). I added a real compatibility check instead of pretending. The honest costs: no central audit log (a record on a server of who did what), no shared calibration across machines (settings that keep measurements consistent from machine to machine). Do it again, I'd compress the embedded libraries.

## Follow-Up Bank

1. Why not just run a local server on each machine? - That's the deployment problem, not a solution: a server is a background program someone has to start, configure, and keep alive - Python, dependencies, and network config on machines the engineers don't administer. The browser was already there; I built on it. [SAFE]
2. You chose browser compute - what does the browser middle layer actually run? - OpenCV.js (~8 MB) for alignment and comparison, TensorFlow.js (~3 MB) for the trained defect model, PDF.js (~1 MB) and XLSX.js (~0.5 MB) for documents (reading design files in PDF form and spreadsheets). The MB figures are each library's file size, from my recorded build notes - round approximations, not precise measurements. The server's only jobs - parsing and inference - moved into the page. [SAFE]
3. Why base64 embedding instead of CDN, sidecar files, or a service worker? - CDN needs internet the floor machines don't have; sidecar files break when someone moves just the HTML (the exact failure I was removing); a service worker - a browser-stored background script that lets a site work offline - needs HTTPS (the encrypted web-address protocol) to register and adds compatibility risk. Base64 inflates everything it encodes by roughly a third - the ~12.5 MB of libraries plus the app code and the embedded model weights together land the ~25 MB file - accepted for single-artifact delivery: one file to email, copy, and open. [SAFE]
4. localStorage versus IndexedDB - defend it fully. - In plain terms: I chose the simple shelf with a small fixed space over the big filing cabinet that takes more code to operate. Data is a few KB per inspection; the 5 MB quota (the browser's published allowance per site) covers a station's history comfortably. localStorage is synchronous - the save finishes immediately, no callback or promise (code patterns for "the answer arrives later") in the auto-save path. IndexedDB gives large quota and structured queries but async complexity I didn't need yet. Mitigation shipped: quota check plus a GC pass (automatic cleanup of old records) dropping oldest entries past ~4 MB - that 4 MB trigger was my own chosen warning line, set below the 5 MB limit; explicit trigger - switch to IndexedDB if volume grows. [SAFE]
5. How did you verify the standalone behaved like the server build? - A test harness (a small comparison script I wrote myself, feeding the same inputs through both versions and diffing the outputs) ran the same 15 BOM files and 10 board images - that's my self-built regression set, the counts from my recorded notes - and compared outputs: identical reconciliation reports, alignment within about a pixel (one picture dot - visually indistinguishable), identical classifications. [SAFE]
6. What did the browser-only choice cost you? - No central audit log, no shared calibration corpus across machines, an 8 MB WASM cold start (the WebAssembly binary loading from zero the first time the file opens), a single-machine performance ceiling (one machine's speed is the cap), and no way to push a fix except re-distributing the file. Named, not hidden. [SAFE]
7. How solid are the 25 MB / 5 s numbers? - What they count: 25 MB is the single file's size on disk; 5 s versus 2 s is the time from double-click to a working tool on a factory machine versus the old server build. My recorded account of the offline build: typical observed startup versus the server build, stopwatch-grade, not an instrumented distribution. [PARTIAL - labeled, held once as "about"]
8. Did it run on every machine? - It needed a WebAssembly-capable browser - one able to run the fast machine-code format the libraries use; IE11 machines didn't have one and couldn't be made to without a rewrite. That wrong assumption is my biggest-mistake story in full - here it's one line: I added a clear startup compatibility check. [SAFE - cross-reference, not a retell]
9. How many engineers used it? - Distributed by email and USB; the handoff became "double-click" - the old way would have been an IT setup ticket. Adoption was never tracked, so I won't quote a headcount. [GAP - stated plainly]
10. What happens at 10x - a hundred machines? - Per-user load is the frugality win: everything is client-side - all the work happens on each user's own machine - so more users break nothing I maintain. The ceilings are organizational: fixes require re-distribution and data can't aggregate across machines. [SAFE - reasoning, no claimed scale]
11. Did anyone disagree with killing the Flask server? - No documented pushback; solo project, and I'd be inventing a scene to claim one. The real argument was with my own default that tools ship on servers. [GAP - stated plainly]
12. Do differently? - Compress the embedded libraries from day one - gzip (standard file compression) pulls ~25 MB toward ~15 MB, the expected after-compression size from the same recorded notes - which also clears 20 MB email attachment caps - and add the browser-compatibility check at the start instead of after the IE11 surprise. [SAFE]
