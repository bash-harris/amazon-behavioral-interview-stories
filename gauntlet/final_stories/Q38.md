# Q38 - tell me about a project where you chose the UI/middle layer/database/etc

**LP:** Are Right, A Lot (primary - the data-structure call under a hard environment constraint, and naming where it breaks); Invent and Simplify (chose the boring structure that solves the measured bottleneck; complexity deliberately avoided)   **Story:** the per-component scan over the whole CAD drawing - O(NxM), ~25M distance checks per board - and the uniform spatial hash I chose as the middle layer to replace it (BAR_RAISER_TECHNICAL_PREP.md Finding 2, :134-152); distinct from Q81 (the sibling hot-loop decode finding in the same audit) and Q21 (learning the browser stack)

## Core Answer

The layer I chose was a data structure - the part of the tool that answers "what's near this point" - and in a browser tool that effectively is the middle layer: the structure of the data between the screen and the computation. In my PCB inspection suite, every component detected on a board photo had to find its matching shape in the CAD drawing - the engineer's design file - to get the right crop size. The first version answered with a scan: for each component, loop over every layer and every shape in the drawing and measure the distance. That's a choice nobody makes on purpose; it writes itself.

A board carries a few hundred components. The drawing carries roughly 50,000 shapes. Multiply: about 25 million distance checks per board - and it was nested inside another loop that was already doing too much work, so the costs compounded. It worked; it just slowed with board complexity, and the factory boards are the complex kind.

The options were: keep scanning, buy a faster machine, or change the data structure. A faster machine isn't an option when the tool has to run as one offline file on locked-down factory computers. So the choice was the structure. I picked a uniform spatial hash: bucket every shape once into grid cells sized to the typical shape, then ask only about the 9 cells around a component instead of the whole drawing. Build once per load, proportional to shape count; each query touches only local density. The multiplication becomes an addition.

The call I'd defend isn't "I knew about spatial hashes" - it's naming where my choice breaks before someone else finds it for me. A uniform grid degrades when shape sizes vary wildly, because a board's outline polygon spans every cell. The known mitigations are size-bucketed grids, or an R-tree - a balanced tree over 2D space - if the size distribution is genuinely heavy-tailed. I took the simple structure that fixed the real bottleneck and documented its failure mode, rather than picking the sophisticated one to look careful.

One honest flag: I found this by reading the code and multiplying recorded counts, not by a profiler's trace. Before I'd quote a speedup in seconds, I'd want the profile - the 25-million figure is arithmetic about the shipped loop, which is itself the point: the loop was visible, and it was wrong.

## Memory Anchors
- Problem: every component's crop-size lookup scanned every layer x every shape of the CAD drawing - O(NxM), ~25M distance checks per board, nested inside an already-expensive loop
- Customer: manufacturing engineers on slow, offline, locked-down factory machines - "buy a faster computer" was not a deliverable option
- Insight: the middle layer choice is the data-structure choice; the bottleneck was a range query over 2D points that had been answered with a linear scan
- Action (mine): chose a uniform spatial hash - one-time bucketing of ~50k shapes into grid cells sized to the median shape, queries narrowed to the 9 surrounding cells; kept the simpler structure over an R-tree and documented its size-variance failure mode + mitigations
- Result: per-component full-drawing scan replaced by local-cell queries; preprocessing once per load [PARTIAL - no committed benchmark numbers; found by reading, not profiling]
- Learning: name where your chosen structure fails before the interviewer does; the boring structure that fits the access pattern beats the clever one that fits your resume

## Follow-Up Bank
1. Where do 50,000 shapes and 25M checks come from? - The shipped loop iterates layers x shapes per component; the audit records ~500 components x ~50,000 CAD shapes = ~25M distance checks per board. Arithmetic on recorded typical counts, not a measured distribution. [PARTIAL - computed, labeled]
2. Did you profile it? - No. I found it by reading the code; the audit's own standard is to get the profile before claiming a speedup number, and I hold that line. If pressed: the trace plan is Chrome DevTools' performance panel, looking for the distance-check loop dominating. [SAFE - honest label]
3. Why not a real database - SQLite or the like? - The whole tool ships as one offline HTML file inside a browser (no server, no installs); the "database layer" had to be plain in-memory JavaScript structures. The spatial hash is the database choice under that constraint. [SAFE]
4. Why a hash grid and not an R-tree or kd-tree? - Access pattern is static (bucket once after load, query many), queries are small-radius, and a grid is dozens of lines that I can debug on a factory machine. An R-tree buys balance the static workload doesn't need at the cost of code complexity; kd-tree degrades with the heavy-tailed size mix. Reasoning about structure fit, not a benchmark bake-off. [PARTIAL - reasoning]
5. How did you size the cells? - Side ~ median shape size: too small and a query spans many cells; too large and the cells degenerate back toward scanning everything. The grid constant is a tuning knob, and the size-variance failure is the knob's known limit. [SAFE]
6. What was it nested inside? - A second, separate inefficiency in the same loop (a full-image decode per component) - that one is its own story (Q81); here it's one line: fixing the lookup without fixing the decode would still have crawled, because the costs compounded. [SAFE - cross-reference, not a retell]
7. Who felt the slowness? - The suite went to about 15 engineers across 2 sites; they told me it saved roughly 20 hours a week - engineer-reported recollection, not instrumented, and the same account I give everywhere. No per-feature timing claims. [SAFE - canonical, labeled]
8. What would you do differently? - Instrument before rewriting (the profile I skipped), and make the index a shared module across the two comparison tools - they had diverged from a copy, so a fix in one didn't reach the other. [PARTIAL - reasoning + documented fork divergence]
