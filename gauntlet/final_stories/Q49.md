# Q49 - Tell me about a time you went above and beyond for a customer.
**LP:** Customer Obsession (primary); Deliver Results.   **Story:** PCB inspector suite - 5-day prototype + install-free standalone build for the manufacturing engineers (STORY 1/8/12 + PREP STORY 4).

## Core Answer

The customer was the manufacturing engineers on the factory floor, and the ask was a tool to compare circuit boards automatically - a tool that looks at two pictures of a board and points out where they differ. Going past the ask, for me, was not stopping where the comparison logic worked - it was staying until they could actually double-click it on their machines and share it with each other.

First I went to them. Before I wrote any code I sat in on a few of their screen-sharing sessions. They flipped between two photos and circled the problem areas with Zoom's annotation tool. They didn't need a similarity score - a single number grading how much alike two boards are; they needed to see where the difference was. So the tool was built around color-coded highlighting that matched the workflow they already had.

Then I built a working prototype fast and put it in front of the team instead of polishing in private. The request had sat in a backlog for months as "too complex to scope," and the prototype surfaced the real problems inside an hour: it broke under lighting changes, it couldn't handle boards photographed at an angle, it couldn't export results. I fixed them in the order that mattered to them - alignment first, illumination second, export third. In plain words: line the two pictures up correctly even when the board was shot at an angle; keep working as the factory lights change; and let them get the results out as a file.

Then the environment. Their machines sat on the factory floor: no internet, no permission to install anything, IT stretched thin. The easy delivery was a Flask server (the tool running on one central computer everyone connects to), but it needed Python and configuration the team couldn't manage - deliver that and it ran nowhere. So I took on work nobody had asked for: I compiled the whole suite into one self-contained HTML file - a single web-page-style file that opens in the browser with a double-click and carries everything it needs inside itself. That meant rewriting the OpenCV.js loader (the ready-made image-analysis code that does the comparing) to decode its WebAssembly binary (its fast math engine) from an embedded data URL (packed inside the file itself instead of downloaded over the internet) at runtime, and moving auto-save into localStorage (the browser's own saving space on that one computer) with quota handling (respecting its fixed size limit). It opens in seconds on their machines. All of it so the engineer's job became a double click: no install, no network, no IT ticket.

I handed the file out by email and USB (a small drive you carry between machines), and it spread to fifteen engineers across two sites, who reported saving roughly twenty hours a week together. That last part is in their own words - what they told me, not something the tool ever counted.

What I'd do differently: treat the locked-down environment as the design driver from day one instead of after I'd built the server version. And I'd compress the embedded libraries (the code packed inside the file) harder - the twenty-five-megabyte file ran into a twenty-megabyte email cap: the file held about 25 MB of data, and the company's email refuses attachments over 20 MB.

## Memory Anchors
- Problem: board-comparison request sat unscoped in a backlog (a queue of pending work) for months; "too complex."
- Customer: manufacturing engineers - factory-floor machines, no internet, no install rights, thin IT.
- Insight: they need to see *where* the difference is (their Zoom-circling workflow), and a tool they can't run isn't delivered.
- Action (mine): observed their sessions before coding; 5-day prototype (working version in five days); fixed their issues in their order; embedded the browser libs into one HTML file; rewrote OpenCV.js WASM loader off a data URL (the image code's math engine boots from inside the file instead of the internet); localStorage autosave with quota handling (the browser's on-computer saving space, within its fixed size limit); distributed by email/USB (carry-between drive).
- Result: before -> manual toggle + circling; after -> color-coded diff from a double-clicked file; ~15 engineers, 2 sites, ~20 hrs/wk engineer-reported (their words, not tool-counted).
- Learning: deployment environment is a day-one design driver; "above and beyond" must name a customer cost or it's gold-plating (polish the customer never asked to pay for).

## Follow-Up Bank
1. What did they ask for vs what you delivered? - The ask was automated comparison. I delivered one they could run on locked-down machines and share - a comparison tool that needs Python on the factory floor (needs that programming system installed on their machines) is a tool nobody uses. [SAFE]
2. How did you know highlighting, not a score? - Watched their screen-shares first: toggling between images, circling concerns in Zoom. The output had to show *where*, in a form they could point at. [SAFE]
3. Why ship a rough prototype? - It replaced my guessing with their words. The prototype took me five days, and lighting, angle, export came from them in the first hour; six months of scoping had produced nothing. I fixed in their priority order: alignment, illumination, export - lining tilted pictures up correctly, handling lighting changes, getting results out as a file. [SAFE]
4. Was export an unrequested delight? - No, be honest: the team explicitly flagged missing export at the demo. It was their ask, answered fast - above-and-beyond was the packaging (how it was delivered, not what it does), not the features. [SAFE]
5. Why not just the Flask server? - Server (the central-computer version) was less work for me but zero workability for them. Trade-off: I absorbed the build pain (embedding, loader rewrite, quota handling - stuffing the code into the file, reworking how it starts up, and respecting the browser's size limit) so their side became one double click. [SAFE]
6. What's actually in the single file / how big / how fast? - One self-contained HTML: embedding the browser libraries (ready-made image-analysis and document-reading code that runs inside the browser) plus the model weights (the trained numbers a defect-detection model carries with it) and the app itself pushed the file into the tens of megabytes - around 25 MB. Base64 WASM decode at startup adds ~2 s (unpacking the image code's fast math engine from the text form it's stored in inside the file); ~5 s to open on a factory machine vs ~2 s on the server build - that's the time from double-click to a usable screen. Verification: same known boards through both builds, outputs matched (I ran identical test boards through both versions and compared - same results). The load times are my own stopwatch over a handful of boards - rough, not instrumented (the software never measured it itself). [PARTIAL]
7. Why touch localStorage? - Server filesystem auto-save doesn't exist in a single HTML file; moved it to localStorage (the browser's own saving space on that one computer) with the 5 MB quota handled (the fixed 5 MB size limit - warn the user, then clear old entries). [SAFE]
8. Where do 15 engineers / 2 sites / 20 hrs/wk come from? - Engineer-reported recollection: they told me their comparison time dropped, based on how often they'd run boards. In plain terms: 15 = how many people used it, 2 = how many factories, ~20 hrs/wk = time they believed the group saved together. Not instrumented - "instrumented" means the software counted it, and it never did - I'd present it as "their reported savings," nothing stronger. [PARTIAL]
9. How do you avoid gold-plating? - Anchor extra work to a named customer cost. Offline packaging had one: machines with no installs, no network, no tickets. I left formal versioning/CI out on purpose (numbered releases with automated release checks) - no engineer's experience changed if it was in. [SAFE]
10. Hardest part? - Getting OpenCV.js to boot with no network: it wants to fetch its WASM from a URL (the image-analysis code tries to download its fast math engine from the internet when it starts). Had to embed the binary as a data URL (pack it inside the file itself) and patch the loader to decode it at runtime, debugging on a locked-down machine with no dev tooling (no debugger or developer tools installed). [SAFE]
11. Disagreement? - No conflict - the server default was the easy path and *I* rejected it against my own convenience. If pressed, that's the pushback: I pushed back on myself, not a stakeholder. [SAFE]
12. Larger scale / do differently? - Distributing a 25 MB file by email bumped a 20 MB cap (the company's email server refuses attachments over 20 MB, and this file was bigger than that); gzip (standard file compression that shrinks a file before sending) would have brought it near 15 MB. And I'd have treated the locked-down environment as the design driver before building the server version at all. [SAFE]
