# Q78 - tell me about a time you utilized customer feedback to drive improvement

**LP:** Customer Obsession (primary); Earn Trust; Learn and Be Curious.   **Story:** BGSW PCB Inspector Suite - three documented feedback loops: transparency/trust (STORY 11), the variant-semantics correction (STORY 1), the prototype export ask (AMAZON_INTERVIEW_PREP STORY 8).

## Core Answer

The most useful feedback I ever got wasn't a feature request. It was that the engineers didn't always trust the tool, and were hesitant to rely on it.

Context: I built the BOM reconciliation tool solo. A BOM - bill of materials - is the list of every part that goes on a circuit board, and "reconciliation" just means checking that list against the layout PDF, the engineering drawing of where each part sits. It replaced engineers hand-checking the parts list against the layout PDF, entry by entry. It worked. But when it flagged a mismatch - when it said the list and the drawing didn't agree - the report showed the verdict and hid the reasoning - so on anything that mattered they were hesitant to rely on it. That stung because it was about credibility, not a missing feature.

I didn't ask for trust. I made the tool auditable - able to show its work so they could check it themselves. In the server build I put a debug view behind a separate route - a developer's page living at its own web address: for one component reference - the printed label of a single part, like "R1" - it showed the raw BOM text, how it parsed (how the software read that text), what it matched in the layout, and which rule decided the result. Above that, a stats dashboard - a summary panel with component count, matches, problems flagged - so they could size up a run before opening any single verdict. My rule: if an engineer asks "why is this a mismatch?", the view has to answer completely - any step I left out just sent them back to me.

That flipped the loop. In week one the engineers used the view to surface two cases where my matching heuristic - the rule of thumb the software uses instead of a perfect test - was wrong, both odd component naming, and with the intermediate data on screen, they were quick to fix. (That "two" is the number of matching mistakes the engineers themselves turned up through the new view that week; it comes from the story record, not from any tracking system.) Then trust moved: seeing how decisions were made, they reported being more willing to rely on the results for production verification - for checking boards that would actually ship. Trust, not accuracy, was the binding constraint - the thing that was actually holding the tool back.

The second loop was face-to-face. I'd treated notations like `R1||R2` and `R1/R2` - shorthand written into the parts list - as garbage and silently dropped them. A manufacturing engineer explained what they actually mean: one physical position, either part, depending on board variant - the same design built in slightly different versions. I rewrote the parser, the code that reads the parts list, to match either reference and locked the behavior with a regression suite of real production boards - a saved set of test files that re-runs after every code change so old fixes can't quietly break. In the first production week it caught three mismatches manual review had missed. (That "three" is the count of real errors the fixed tool found in its first live week that a human check had passed over; story-recorded, not counted by software.)

The third loop came earlier. Users of my first working prototype found real gaps within the first hour, including that they couldn't save results - so export, a way to write the report out to a file, went on the roadmap and shipped. I fixed things in order of impact, not order of complaint.

What I learned: the feedback is the spec. And if I'd shipped the auditable view from day one, I wouldn't have had to earn their trust twice.

## Memory Anchors

- Problem: the reconciliation tool gave verdicts without reasoning, so engineers were hesitant to rely on it - an accuracy-success, adoption-failure gap (right answers it couldn't prove, so nobody leaned on them).
- Customer: manufacturing engineers using the BOM tool (plus the prototype team earlier); corrections came from people, not data.
- Insight: trust is the binding constraint, and the users hold domain semantics (variant notation) no log can reveal; the audit view doubles as a feedback channel.
- Action (mine): solo built the debug view (per-reference evidence) + stats dashboard on a separate server route; rewrote the parser per the engineer's variant correction and locked it with a 15-BOM regression suite (15 real parts lists, re-tested after every change); shipped export from prototype feedback, prioritized by impact.
- Result: two heuristic edge cases surfaced and fixed in week one (two matching mistakes the engineers found via the view; story-recorded); engineers reported more willingness to rely on results for production verification; 3 real mismatches caught week one (errors the tool caught in its first live week; story-recorded, not instrumented); export shipped.
- Learning: treat feedback as the specification; build transparency from day one.

## Follow-Up Bank

1. What baseline did the tool replace? - The engineers reported manual cross-checks of roughly 20-30 minutes per board - that figure counts one engineer's estimated hand-check time for a single board, from their own recollection; the report came back in seconds. Their recollection, not something I instrumented. [PARTIAL - reported, not measured]
2. Which feedback mattered most? - The trust feedback, because it was about adoption, not features. A perfectly accurate verdict still fails if nobody relies on it. Making reasoning auditable moved them from hesitant to rely to more willing to rely on the results for production verification. [SAFE]
3. What did the debug view actually show - can you demo it? - What the shipped build backs: a server debug route - a developer page at its own web address - returning raw per-reference evidence: which layout pages the reference appears on, matched text spans with position and color classification, nearby hyperlinks and DNP keywords ("DNP" marks a part listed on the bill of materials but deliberately left off this board) - plus the run-level stats dashboard. I describe it; I never promise a live demo. [PARTIAL - richer step-by-step trace page is story-bank prose]
4. How did you know the improvement worked, not just that you shipped it? - Two signals: a concrete one (two naming-convention edge cases surfaced through the view in week one, quick to diagnose - "two" being the matching mistakes the engineers themselves found using the new view, per the story record), and a behavioral one (they reported being more willing to rely on the results for production verification). The behavioral one is their self-report, not measured adoption. [PARTIAL]
5. How was the parser fix verified? - The fifteen BOMs are representative production files - "fifteen" counts the real parts lists saved as standing tests; the suite covered both separators (the `||` and `/` shorthand marks), three-way variants (one position that can hold any of three parts), and malformed forms like `||R1` and `R1/` (broken shorthand that must not crash it), and ran after every change. After the variant work it passed with zero false positives and zero false negatives - on those fifteen files it raised no wrong alarms and missed nothing; a 2,000-component BOM parsed in under 200 ms - a 2,000-part list read in a fifth of a second. These are my own test runs, so they're solid within the suite; Suite-scoped - not a claim about every format that will ever exist. [SAFE - scoped wording required]
6. How reliable are the headline numbers? - The two edge cases (matching mistakes the engineers surfaced), the three week-one mismatches (real errors the tool caught in its first live week), and the 15-BOM suite (the number of saved test files) are story-recorded; the 20-30 min baseline is engineer-reported. None was instrumented - no tracking system ever counted any of them; they are what the story records and the engineers recalled. [GAP - no instrumentation exists]
7. Alternatives rejected? - Flagging every variant position for manual review (pushed work back into the queue the tool existed to clear); keeping diagnostics in the main view (noise - separate route instead); and the implicit alternative of just asking them to trust the verdict. I chose auditable rules over a black box - answers with no visible working. [SAFE]
8. What went wrong - your own mistake? - My parser silently dropped valid variant references - quietly discarded legitimate shorthand instead of flagging it - because I assumed notation I didn't recognize was bad data. A customer caught my bug; a silent skip is data loss - valid information vanishing with no record of it. That's the same event told as a mistake in Q75; here it's the feedback loop. [SAFE]
9. What about feedback you couldn't act on immediately? - The prototype surfaced alignment (the photo not lining up with the drawing), illumination (uneven lighting on the board), and no-export (nowhere to save the results) in the first hour. I fixed them in impact order - alignment, illumination, export last as the nice-to-have. Being explicit about order is using feedback honestly instead of pretending everything is urgent. [SAFE]
10. How did you keep gathering feedback after launch? - The debug view became the channel: engineers used it to flag cases the heuristic got wrong. Same pattern later on the AI feature - engineers could mark analyses correct or incorrect, which surfaced systematic prompt errors - repeating mistakes in the wording I sent the AI - I could fix. Feedback counts only if there's a path from user back into the code. [SAFE]
11. Any disagreement with the feedback? - Not with the users - I took both corrections without defending the original design. The pushback was my own prior assumption that unfamiliar notation meant bad data. [PARTIAL - no documented user conflict]
12. Scale of it? - Solo-built; one team at one plant for these loops. Across the full suite it was about 15 engineers across 2 sites; they told me it saved roughly 20 hours a week - engineer-reported, not instrumented. Those three figures count the people using the whole suite, the factory locations, and the hours they believed they saved each week across all three tools - what they told me from memory, not a usage counter. [PARTIAL - reported]
13. What would you do differently? - Ship the transparency layer from the beginning, and collect representative BOMs (real parts lists) and interview the engineers before writing the parser. One lesson: get the customer's real artifacts and the domain person in front of me earlier. [SAFE]
