# Q93 - tell me about a time when you worked on something outside your comfort zone

**LP:** Learn and Be Curious (primary)   **Story:** BGSW PCB Inspector Suite - the GPT-4o vision-language interpretation step (PREPARATION.md STORY 8; single telling, canonical ~85% / ~30s->~5s). Distinct discomfort axis from Q21 (unfamiliar-but-inspectable browser CV tools), Q35 (my local model in my personal tool's destructive control path), Q44 (learning the ML discipline), Q71 (unfamiliar domain semantics): here my own debugging loop was removed - an external, non-reproducible model inside a correctness-critical workflow, and the stretch was managing what I could not debug. Not Q63/Q1/Q3 (same facts, recommendation/productivity frames).

## Core Answer

The real stretch for me wasn't a new library. It was putting an AI model inside a tool people depend on - a model I couldn't open, couldn't debug, couldn't rerun to the same answer.

The tool was my PCB inspector. A PCB is the green circuit board inside almost every electronic device. The inspector could flag where a photographed board didn't match its design, but not say what the difference meant. So an engineer zoomed in on every flagged spot and read it by hand - about thirty seconds a spot, and a dense board has a handful. That "thirty seconds" is the engineers' own estimate of a typical read, not a stopwatch study. I wanted to hand that reading step to a hosted vision-language model, GPT-4o - an off-the-shelf AI that looks at a picture and answers in words, "hosted" meaning it runs on the provider's computers and I pay per call.

That was the discomfort. I've never built anything I couldn't debug. No source to read, no stack trace - the error trail normal software leaves so you can find what broke - and the same crop could give different answers on different calls. And a wrong answer wouldn't crash the tool - it would just look right and mislead an inspector. It also cost money per call on a service I don't run.

So I managed it instead of trusting it. First I tried the main hosted options - GPT-4o, GPT-4V, Claude 3, Gemini - on real flagged boards; GPT-4o was fastest and best on the small parts. Prompting itself was a new skill: my first loose "describe what you see" gave chatty, inconsistent answers, so I learned structured prompts - make the AI answer in a fixed, machine-readable form (JSON) with named fields and examples - and rehearsed them on crops whose answers I knew by hand, until the format stopped surprising me. Then the leashes: only flagged regions go to the model, the answer is labelled a suggestion with a confidence - the AI's own "how sure am I" score - an engineer confirms it, and the tool still works when the online service is down. Before any board image went out, security confirmed it held no trade secrets.

The honest part: by my own rough count it read the right component and mismatch type about 85% of the time - my self-assessment from normal use, not a formal test on a separate batch of examples the AI had never seen - and the misses were images too blurry or parts too small. I also dropped a wrong assumption: it could read the value printed on a tiny part. Good at type and orientation, useless at text that small. What made it worth shipping wasn't the 85%. It was the human check: a thirty-second read became a five-second first pass someone confirms - the five seconds is the AI's reply time, not the whole human step, which still ends with the engineer's yes.

I'd never built anything whose correctness leaned on a model I don't control. What I kept: benchmark before betting - try it on real cases first - shrink what the model sees, label its uncertainty, keep a person verifying, keep a working fallback.

## Memory Anchors

- Problem: inspector said *where* a board mismatched but not *what it meant*; wanted to automate the interpretation step with a hosted VLM (vision-language model - an online AI that reads an image and answers in words) despite having no training data and no guarantee of correctness
- Customer: manufacturing/test engineers whose QA decision the tool feeds - a confident wrong reading misleads them
- Insight: the discomfort was losing my debugging loop - no source, no stack trace, no reproducible rerun; the response is to manage rather than debug
- Action (mine): hand-tested the hosted options on real flagged boards before committing; taught myself structured prompt authoring (loose prose -> fixed JSON with named fields + examples) and format-checked it on a small set of crops with hand-verified answers; cropped the model's job to flagged regions; output labelled a suggestion with confidence + correct/incorrect feedback loop; works normally when the online service (API) is down; security sign-off before any image went out
- Result: ~85% on component/mismatch type by my own rough count (no held-out set - no batch of fresh examples kept back to score fairly); manual read ~30 s -> ~5 s confirmed first pass (the 5 s is the AI's answer time; the engineers' 30 s baseline is their own estimate); feature optional - core tool never depends on the API
- Learning: when you can't debug a system, verify around it - benchmark before betting, constrain the context, label the uncertainty, keep a human verdict and a working fallback

## Follow-Up Bank

1. Why is this outside your comfort zone rather than "just another API call"? - Because my core skill stopped working. When deterministic code - ordinary software that does the same thing every time, so you can retrace it - is wrong I read it, trace it, reproduce it. Here there's no source, no stack trace, and the same input can give different outputs - I couldn't chase a failure to a cause, only build guards so a failure can't reach a verdict. [SAFE]
2. How did you pick GPT-4o? - Hand-tested the main hosted options side by side on real flagged boards: GPT-4o around 3 seconds a call versus around 8 for GPT-4V - that's the wait between sending the picture and getting the answer; Claude 3's API (the online doorway software uses to reach the service) was less mature then; Gemini Pro Vision was weaker on small surface-mount parts (the tiny components soldered straight onto the board, the hardest to read). Speed and small-part accuracy decided it. [SAFE]
3. What new skill did you actually build? - Prompt authoring. My first loose "describe what you see" prompt produced verbose, inconsistent answers, so I learned structured prompting: fixed JSON output (a strict, machine-readable answer form), named fields (component type, mismatch type, confidence), examples in the prompt. Before relying on it I ran a couple dozen crops whose answers I'd verified by hand until every reply parsed consistently - that checked the format, not the accuracy. [SAFE - format rehearsal labeled honestly]
4. How solid is the 85%? - Honest answer: rough self-assessment on real flagged boards - what it counts is my tally of right vs wrong readings during normal use - no held-out set (no separate batch of fresh examples reserved for a fair test), single pass. That uncertainty is exactly why the output is a labelled suggestion the engineer confirms - I never let the soft number carry a hard decision. [PARTIAL - labeled, not instrumented]
5. Where did 30 s -> 5 s come from? - The engineers' own report plus watching their workflow on the floor; typical-case estimate, not instrumented. What it counts: the human's per-spot read before (~30 s) versus the AI's first-pass answer time after (~5 s) - the engineer still spends a moment confirming. A dense board flagged five to twenty regions. [PARTIAL - engineer-reported]
6. What were the risks and how were they bounded? - Latency (how long one answer takes - under ~5 s per analysis, a target rather than an instrumented measurement), cost (about a cent per analysis - what it counts: the provider's charge for each picture the AI reads - so pennies per board), availability (falls back to "AI analysis unavailable" - no guessing), privacy (security team cleared the flow before any image went out; board images carry no trade secrets). [SAFE]
7. Where did you go wrong? - Twice: the loose first prompt, and a wrong assumption that the model could read component values printed on small SMD parts - surface-mount components, the tiny parts soldered directly onto the board - the text is too small or blurry; it's reliable on type and orientation, weak on exact value. [SAFE]
8. Why not extend your own classifier instead? - Different job. My classifier - a model I trained to sort defect photos into fixed categories - was 94% on a ~300-image holdout (300 pictures it had never been trained on, held back for a fair score) for the defect classes I'd labeled, but interpreting unforeseen mismatch *types* meant a new labeling-and-retraining project per type. The VLM covered interpretation with zero training data. [SAFE]
9. Did the offline standalone build have the AI feature? - No. The vision-language step ran only in the server build - the version served from my server; the single-file offline tool - the version that opens as one file on a factory machine with no server - called no model at all. The AI part is an enhancement, never a dependency - that's deliberate. [SAFE]
10. Any disagreement? - No person-vs-person dispute to report - solo project, inventing dissent would be the only false thing here. The real tension was internal: betting a step on something I couldn't verify myself. [GAP - stated, not papered]
11. What breaks at 10x the volume? - Cost and latency (answer time) scale linearly, and auditability gets harder - the ability to retrace a decision later - a hosted model behind someone else's version can't reproduce a verdict months later. At that point the math flips toward a self-hosted or trained model; I keep the deterministic comparison - the rule-based photo-vs-design check, same answer every time - as the verdict precisely so the VLM stays optional. [SAFE - reasoning]
12. Do differently? - Score the model against a small labeled set first, so the accuracy number was measured rather than self-assessed - the ship decision wouldn't have changed, the evidence would be harder. And re-evaluate a local LLaVA-class VLM - an open model you run on your own hardware instead of paying online - when hardware allows; floor machines lacked the ~8 GB VRAM (graphics-card memory), so the API was right at the time. [SAFE]

## Risk Check

1. "85% with no held-out set - is that a measured number?" - Defensible only as stated: rough self-assessment - a tally from use, not a formal test - and the product design (suggestion + confidence + human verify) carries the correctness. Never upgrade the word "rough" under pressure.
2. "30 s -> 5 s measured?" - Engineer-reported typical case plus my observation; label it as an estimate, never instrumented. The 5 s is the AI's reply time; the confirm step was never costed. [PARTIAL]
3. "Isn't this the same 'bounding a probabilistic model' story as your Chrome extension?" - Needs the distinction held: Q35 is a *local* model in *my own* personal tool where the fear was destructive blast radius on the user's tabs and the skill was the deterministic envelope; this is a *hosted* model in *their* correctness-critical QA tool where the fear was an un-debuggable wrong answer and the skill was manage-don't-debug (benchmark, bound context, label uncertainty, human verdict). Different project, model, failure mode, and lesson - don't borrow Q35's "envelope" phrasing here.
4. "You shipped something you couldn't verify into a QA workflow?" - Defensible: it never owns the verdict - the deterministic comparison (the rule-based check that gives the same answer every time) is the verdict, a human confirms every reading, and the tool is fully functional with the API down.
