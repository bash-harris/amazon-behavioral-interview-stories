# Q71 - tell me about a time when you went out of your comfort zone

**LP:** Learn and Be Curious (primary); Customer Obsession (touch)   **Story:** BGSW PCB Inspector Suite - the manufacturing/CAD (computer-aided design - drawing how a product is built) domain ramp behind the PCB-vs-layout and BOM tools (PREP.md STORY 12 + PREPARATION.md STORYs 1/4/5/8/11). Distinct axis from Q21 (vision libs/math - the image-software itself), Q35 (MV3 - the modern browser-extension rulebook - + LLM - large language model, a big AI text/image model - control path), Q44 (ML - machine-learning - training arc): here the unfamiliar thing is the problem domain itself.

## Core Answer

The comfort zone I left wasn't a language or a library - a programming language or a software toolkit. It was a problem domain I had no claim to: electronics manufacturing.

Before that, I'd built web tools around documents and data. Then I took on the PCB-vs-layout comparison tool. A PCB is the green circuit board inside every electronic device; its "layout" is the design file - the blueprint saying where every part goes. The tool checks a photograph of a real board against that design file. It sits on a world I didn't know: Gerber files - the industry-standard set of instructions that tells the factory how to physically build the board; footprints and pads - the spots and the small metal dots where a part sits and solders down; package variants - the same electrically-identical part in a different physical shape; reference designators - short labels like "R1" naming which part goes in which spot. I'd never parsed a Gerber file - "parsing" means reading a file like that and turning it into data the software can use - and the format spec runs 200-plus pages. That page count is the length of the official published document itself: a fact, not my estimate. It was the steepest learning curve of the three tools I built. The risk wasn't "can I write the code" - it was "will I understand what the data means well enough to be right."

So I made the unknown cheaper before betting on it. Instead of reimplementing the format, I found an open-source Gerber parser - a free, community-built piece of code that reads that file format, which I could drop into my program - and integrated it. That saved an estimated two to three weeks - the count is coding time I'd have spent hand-writing that format reader; the source is my own back-of-envelope; how solid: an estimate, not a measurement. My learning went to the domain instead of the plumbing. I checked its output against real boards.

Then I learned the domain from the people who live in it. A manufacturing engineer corrected one of my assumptions: "R1||R2" in a BOM - the bill of materials, the parts-shopping-list for a board - means one position that accepts either part. ("R1" names a resistor spot; the "||" is workshop shorthand for "either listed part fits here.") No spec teaches you that - it's floor knowledge. I changed my parser to match reality instead of my model of reality. In an unfamiliar domain, a practitioner's shorthand is the actual spec.

Because I was new to the domain, I couldn't lean on my own confidence, so I built the checking in. A debug view - a diagnostic screen built into the tool - shows the raw entry, the parsed reference after each step, the match found, and the rule applied, so an engineer can verify any decision and override it. The first week it caught real mistakes my heuristics - my own best-guess rules - made on unusual naming conventions, the ways engineers' part-naming didn't follow my assumptions; fixes I'd never have found by re-reading my own code. Those week-one catches are a small count the engineers reported from actual use, not numbers from an instrumented tally.

The environment came with rules. The machines had no internet and no installs, so everything shipped as one file that runs offline - no server, no secrets in it, meaning no passwords or account keys hidden inside the file. Before board images went to a vision API - an AI image service outside the company, called over the internet - the security team confirmed those images contained no trade secrets. That security review is the company's own experts checking whether it's allowed for factory data to go to an outside service.

What stuck: domain knowledge compounds. Understanding the workflow made all three tools better. The correctness net was a regression suite: a fixed set of test files every new version must pass, so fixing one thing can't quietly break another. Mine held 15 production BOMs covering every convention I'd been taught - the count is real parts-lists taken from actual production, genuine files rather than made-up tests - and every change had to pass it before it reached the floor.

## Memory Anchors
- Problem: build PCB-vs-layout comparison (photo vs design file) and BOM reconciliation (checking the parts-list against the design) with zero prior manufacturing/fabrication background; Gerber spec 200+ pages (official document length, a fact); correctness required, not just function
- Customer: manufacturing engineers on restricted factory machines who had to trust and verify every result
- Insight: the discomfort was domain semantics, not code - make the unknown cheap (reuse the parser), learn from practitioners, and build verification in when you can't trust your own confidence
- Action (mine): integrated the open-source gerber-parser and checked its output against real boards; changed the parser after the engineer's "R1||R2" correction; built the debug view (raw -> parsed -> match -> rule) with engineer override; shipped one offline file with no secrets; took the vision-API images through the security team
- Result: est. 2-3 weeks saved on parser work (my estimate, not measured); week-one heuristic errors caught via debug view (engineer-reported); 15-BOM regression suite (real production files) gated every change; ramp carried across all three tools
- Learning: in an unfamiliar domain the practitioner's shorthand is the spec; when you can't trust your own certainty, make verification part of the product
