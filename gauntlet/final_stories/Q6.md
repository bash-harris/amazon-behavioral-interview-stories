# Q6 - a time when you needed to influence a peer who had a differing opinion about a shared goal

**LP:** Have Backbone; Disagree and Commit - only the *commit* half and standing up for what's best for the customer, which makes Customer Obsession + Earn Trust the true center of gravity; the "disagrees with peers and supervisors using data" half is an acknowledged GAP   **Story:** BGSW PCB Inspector Suite - BOM reconciliation debug view + `R1||R2` variant semantics (AMAZON_INTERVIEW_PREPARATION.md STORY 11 + STORY 1)

## Core Answer

I'll be straight about the shape of this one. I built the PCB inspection suite solo - I was the only engineer on it - so there was no teammate across the table. (A PCB is the green circuit board inside every electronic device.) The people whose opinions mattered were the customers: the manufacturing engineers. So this is a stakeholder-influence and commit story, and I won't dress it up as anything else.

We shared one goal: boards verified correctly. The pushback came on two documented points - two, because these are two concrete items actually recorded from what they raised with me, not a general sense of grumbling.

The first was a design call where I was simply wrong. In a board's design file, every part has a position name, and a *variant reference* like `R1||R2` is a notation where one position is listed as able to carry either of two parts. I had decided those references were invalid, and my parser - the code that reads the design file and turns it into the list of positions to check - dropped them silently, with no warning or error message. Each dropped position broke the tool in production, meaning in real use on the factory floor, not in a test. A manufacturing engineer explained that one physical position can accept either part. He had the domain intent; I had a bad assumption. I didn't litigate it. I adopted his meaning for the notation and rewrote the splitter - the piece of code that breaks a combined reference like that into the parts it stands for - to normalize both `||` and `/`, i.e. treat the two ways of writing "either part here" as the same thing. That's the commit half - dropping my own design completely once the better call was clear.

The second was their distrust of the BOM reconciliation tool - the check that cross-compares a board's BOM (Bill of Materials: the parts list for that board) against the design layout and flags where the two don't match. When it flagged a mismatch, they couldn't see the reasoning behind it, and they were hesitant to rely on it for critical decisions. The move in my hands wasn't an argument - it was making the decision path inspectable. I shipped a debug view, turned on by typing `?debug=true` into the web address, that exposes the tool's internal reasoning for every flagged item: the raw BOM text (the parts list exactly as it was entered), the parsed reference after each preprocessing step (the position name after each cleanup step, so you can see where and how it changed), the matched layout entry (the item in the design layout the tool paired it with), the comparison result (match or mismatch), and the rule that fired (which check produced the flag) - plus a per-component decision tree (a step-by-step diagram of the logic behind each individual part's verdict) and an aggregate dashboard (summary counts across all the parts). I deliberately made it a URL parameter - something you type into the web address - instead of a UI toggle (a visible button or switch on the screen), because debug is for technical users and shouldn't clutter the production view, and localhost-only - openable only on the machine running the tool itself - because it echoes the engineer's own data back to them and nothing more.

That shifted their stance. In the first week they used the view to find two edge cases - problems that live at the awkward margins of real data, here parts named in unusual conventions the tool hadn't handled - and I fixed both. Those two are concrete issues the engineers themselves found and reported by checking the tool's reasoning, not estimates; what keeps them soft is simply how small the sample is. Once they could verify the calls themselves, they were more willing to rely on the results for production verification - judging real boards on the manufacturing line, not a trial run.

Two things I won't oversell. Nobody argued against the debug view, so "influence" here meant shipping what they'd asked for, not holding a line - and I'm not asking anyone to trust a black box, a tool whose inside nobody can see. And I'd change one thing: build the debug view from day one. The trust gap was predictable, and I treated transparency as an afterthought.

## Memory Anchors

- Problem: the inspection tool was distrusted because the reasoning behind a flagged mismatch was invisible; my own variant handling was also wrong (`R1||R2` references - one position listed as accepting either of two parts - silently dropped, i.e. skipped with no warning)
- Customer: the manufacturing engineers - a stakeholder group, not a peer; solo project, no teammate existed
- Insight: the gap wasn't accuracy, it was verifiability - and on the variant call, the right move was to concede fast and commit fully to the engineer's domain intent
- Action (mine): adopted the engineer's `R1||R2` semantics (rewrote the splitter - the code that breaks a combined reference into its parts - to normalize `||` and `/`, treating both notations as the same thing); shipped the `?debug=true` view - raw BOM text (the parts list as entered), parsed reference per step, matched layout entry, comparison result, fired rule, per-component decision tree, aggregate dashboard; chose URL parameter over UI toggle; localhost-only exposure (viewable only on the machine running the tool)
- Result: engineers found two naming edge cases in week one, both fixed; became *more willing* to rely on results for production verification
- Learning: build transparency from the start - the trust gap was predictable; and commit completely when a domain expert is right
