# Q4 - tell me about a time you failed

**LP:** Earn Trust (primary - owned the wrong assumption, no blame to formats or users) + Dive Deep (root-caused through the size math).   **Story:** BGSW PCB Inspector Suite - the .jpg photo vs .png layout-export size mismatch that poisoned the overlay scaling (reconstructed from code evidence; see Source).

## Core Answer

I was the only engineer on a PCB inspection suite. Its headline feature laid a circuit board's design map over a photo of the real board and flagged every place they disagreed. Two inputs: the photo, taken on the line - usually a .jpg, a camera format - and the design export - a .png, a screenshot-like format. My assumption was simple: it's all just images; once the browser loads one I can ask its size and get pixels. The file extension is a name, not a behavior.

I was wrong, and it failed quietly. My code asked the browser how big the image *displayed*, not how many pixels it actually held. A camera .jpg can carry its own rotation note, so those two numbers can disagree; a .png export never disagrees. When someone loaded a portrait photo against a landscape export, width and height were swapped for one input but not the other - and every scale number after that was poisoned. The design map landed at the wrong size and off-center; the comparison lit up half the board as "wrong" - nonsense - the overlay visibly misaligned. A tool that cries wolf gets ignored, and I'd built the wolf.

I owned it as my assumption, not the formats' fault, then went to the numbers. The pipeline already had a step comparing the two inputs' aspect ratio - width divided by height - so I read its log: far past the code's five-percent mismatch warning. Then I traced back every place that had asked an image "what size do you display as?"

The fix had three layers. Read the image's real decoded pixel size, whatever format it came in, and make a decoded canvas - not the display size - the single source of truth for all later math. Re-encode both inputs to one normalized format at load, so no downstream step sees jpg-versus-png again. And guard the scaling step: zero or nonsense dimensions now clamp and warn instead of flowing through. Comparisons also letterbox - gray padding instead of squashing - so differently-shaped inputs meet at one size.

The mixed-format pairs that had flagged whole boards came out clean, and the five-percent check stayed in as a permanent tripwire. Lesson, applied everywhere now: never assume input shape. I test with mixed formats - camera photo, design export, phone file - before trusting any number from a user's file.

## Memory Anchors
- Problem: .jpg board photo vs .png layout export; code sized everything off the image element's *displayed* size, which one format can report differently from its true pixels -> swapped W/H -> wrong overlay scale, nonsense mismatch flags.
- Customer: factory-floor manufacturing engineers who were about to learn not to trust the report.
- Insight: file format is a behavior boundary - "how big does it display" != "how many pixels are there," and the two only diverge across formats.
- Action (mine): logged the image-vs-CAD aspect check to prove the swap; made the decoded canvas the single source of truth; read real pixel dimensions (`naturalWidth`-style) regardless of format; normalized every input to one re-encoded format at load; clamped zero/non-finite scale; letterboxed comparison crops to one size.
- Result: mixed-format pairs aligned; the >5% mismatch warning kept as a permanent tripwire; no instrumented before/after rate - honestly qualitative.
- Learning: don't assume input shape; normalize at the boundary; keep mixed-format (jpg/png/heic) fixtures as day-one regression tests.
