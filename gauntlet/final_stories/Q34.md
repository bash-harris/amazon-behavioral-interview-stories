# Q34 - tell me about a time where you introduced a new process and why was it not already in place at your company ?

**LP:** Invent and Simplify (primary - made testing structurally possible before mandating it; complexity deliberately avoided); Ownership (strong - solo project, the gap was mine to notice and close).   **Story:** the audit finding that my codebase was untestable by construction - zero tests, 67 blocking browser popups, files that touch the live page at load - and the headless-core + known-input regression + escape-everything process I introduced as the response (BAR_RAISER_TECHNICAL_PREP.md Finding 6, :231-241); distinct from Q85 (the same audit's scoring-metric finding) and Q46 (the verification-checklist rule).

## Core Answer

The process I introduced was a regression harness - a fixed set of inputs with known-correct answers, re-run on every change - plus the step that made it possible at all. Why it wasn't in place: the codebase could not have had tests. Not skipped. Could not.

I built the PCB inspection suite alone - the tools that compare a photo of a circuit board against its design. After a while I audited the repo and counted what was there: no package file, no test file, zero tests. My first read was that I'd been undisciplined. The second read was harsher and more useful: testing had been architecturally impossible. There were 67 alert() calls - blocking popups that freeze the page until a human clicks OK, so no automation gets past the first. The analysis functions read the page directly - grabbing live elements, writing results into a shared global. And the module holding shared state queries the page at load, registers listeners, even implements a magnifier - import it outside a browser and it dies on line one.

The real cost of no tests showed up when I traced a scoring bug: the similarity scorer was padding images to equal size, and the padding quietly poisoned its numbers on letterboxed boards. The bug had survived because nobody - me included - could write a test for a scoring function without a browser. The scorers themselves were already pure functions: images in, number out. They were just trapped in files that touched the page at import time.

So the process had two parts, in that order. Make testing possible first: pull the pure scoring functions into a headless core - code that runs with no browser open - a mechanical change, not a rewrite. Then lock behavior down: the known-input regression set, run on every change, so fixing one format can't silently break another. One more rule came out of the same audit: one line puts a part label parsed from a customer design file straight into live page markup - untrusted text executed as page content, an injection risk - so the process requires every string from a parsed file to be escaped before it touches the page.

What I stopped doing: treating "add tests" as a willpower goal. It's an architecture question. When nobody can test something, find the thing that makes testing impossible, fix that, then write the test.

## Memory Anchors
- Problem: solo-built browser tool with zero tests, 67 blocking popups, DOM (live page) touched at import - regression testing impossible by construction; a padding bug in a scoring function survived because it could not be unit-tested
- Customer: the manufacturing engineers on whose machines a silently-wrong build lands with no network, no tools, no IT to ask
- Insight: "add tests" fails when the architecture forbids tests; the process starts with making testing mechanically possible (pure functions pulled into a headless core), then keeps them pure via a known-input harness
- Action (mine): the audit (counts, import-time DOM, innerHTML interpolation of parsed CAD labels - all recorded); defined the headless-core extraction rule; introduced the known-input regression harness run on every change; added the escape-all-parsed-text-before-DOM rule
- Result: a repeatable pre-release check where none could exist before; the injection path and the un-importable module documented and gated by rule [PARTIAL - landing details below]
- Learning: when a practice is missing, ask whether the structure forbids it before blaming discipline; processes for correctness beat heroics at review time

## Follow-Up Bank
1. Where do "zero tests" and "67 alert()" come from? - My own audit of the repo: no test file anywhere, 67 alert() calls counted across the deployed tool folders, analysis functions reading page elements and writing a global results variable - all line-referenced in the audit notes. Counts at audit time, not a CI statistic. [SAFE]
2. Why wasn't this already in place at the company? - The suite was a solo build; company practice never entered the picture. The deeper answer: the tools were browser-first by requirement (they run offline inside one page), and browser-first done naively means page access at import time, which makes any test framework choke before a line of logic runs. The absence was an architectural symptom, not a culture one. [SAFE]
3. What exactly is the process, not the script? - Three rules a person follows: pure logic lives in files that never touch the page at load; a fixed known-input set re-runs on every change and must stay green; no text that came from a parsed customer file enters the page unescaped. The harness is enforcement, the rules are the process. [SAFE]
4. Which functions moved to the headless core? - The four similarity scorers (structure, edge, histogram, shape-description comparisons) were already pure (image pair in, number out) - the extraction was mechanical. That's why I frame the fix as architecture, not rewrite. [SAFE]
5. Does the harness exist in the repo today? - The checked-in snapshot at audit time still had no test files - the harness is the corrective I introduced as the go-forward rule; I tell it that way and never offer to show committed test files from the audited snapshot. [PARTIAL - corrective introduced, snapshot doesn't show it landed]
6. What's the injection line exactly? - Analysis code interpolated a component label parsed from a customer CAD (design) file straight into innerHTML - the browser's "insert page markup" call. If a label contains markup, the browser executes it. Fix: treat every parsed string as untrusted and escape it before display. [SAFE]
7. Alternatives rejected? - Bolting a browser-automation framework on top (runs the whole page headlessly - works, but pays browser setup per test and still can't import the module); and "just add a test file someday" (fails on the import-time DOM). Extraction beat both. Reasoning, not a measured bake-off. [PARTIAL]
8. Who adopted it? - One engineer: me. The value at handoff is that release claims stop depending on my memory. I don't dress a solo habit up as an org rollout; on a team I'd add a reviewable diff for the input set and CI (an automated pipeline that re-runs checks on every saved change). [PARTIAL - honest solo framing]
9. What would you do differently? - Keep the core headless from day one and put the page behind a thin shell, instead of discovering that every correctness function is welded to the browser. The alert() popups were meant as user feedback; they should have been one notification component from the start. [SAFE - reasoning]
