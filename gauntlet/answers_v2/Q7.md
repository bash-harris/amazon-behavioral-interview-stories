## Answer (core, ~440 words)

I failed a subset of the users I built something for. The PCB inspection suite ran on a Flask server, but the manufacturing engineers needed it on factory-floor machines with no internet, no software installs, and limited IT support. So I built a standalone version: one self-contained HTML file that embedded the libraries directly — OpenCV.js as a base64 WebAssembly module (about 8MB), TensorFlow.js (about 3MB), PDF.js (about 1MB), XLSX.js (about 500KB) — so an engineer could just double-click it. My compile script concatenated the HTML, CSS, and JS and base64-embedded the binaries.

My assumption was simple and untested: that the factory-floor machines ran modern browsers. They didn't, all of them. Some ran IE11. IE11 has no WebAssembly support, and OpenCV.js is a WebAssembly module, so on those machines the tool just didn't work — and those were exactly the machines the offline build existed to serve. I'll be honest about the size of that failure: I never took a fleet count. I don't know today whether it was one cell's machine or half the floor, and that missing number was itself part of the same failure — I never went and looked at the environment I was shipping into.

Here's the part I own: it wasn't a tricky bug that slipped through a test. It was an assumption about the deployment environment I never verified. My testing was on modern browsers, which is precisely why it didn't catch it — I had tested the environment I had, not the environment I was shipping into. I could point at the age of the machines or the IT setup, but the honest root cause is that I designed for "browser" in the abstract instead of for the actual machines in front of me.

I couldn't fully fix it. Making the tools work on IE11 would have meant a complete rewrite — my on-the-spot estimate was replacing the WebAssembly-dependent image pipeline with JavaScript fallbacks, which I judged as not worth the cost for an end-of-life browser; if a still-supported browser on the fleet had shown the same gap, I would have paid that cost. So I did the honest version: I added a startup browser-compatibility check that displays a clear error message when the browser can't run the tool, so the engineer got an explicit, understandable "this won't run here" instead of a mystery.

The lasting change is the habit. I now verify the target environment before I build for it — the actual OS and browser on the actual machines, not the assumed one — the same lesson the BOM parser taught me about data: don't trust your assumptions about the environment you're deploying into; go look. Being curious about *why* IE11 failed — the WebAssembly capability gap, not "old browser, shrug" — is what turned a dead end into a guardrail.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why didn't you catch this before you built and distributed it?**
**A:** Because I tested on my own modern browser and never inventoried the floor fleet. The failure was in verification, not in code. I now start by confirming the target environment — OS, browser, and required platform capabilities — before I build for it.

**Q: How many machines were actually affected?**
**A:** **GAP — candidate must fill from recall or concede honestly.** Prepared line: "I never took a fleet count — that missing number was itself part of the failure. I know some machines ran IE11 and the tool didn't work on them; I never quantified it, and I should have." Do not invent a number in the interview.

**Q: How did you find out it was failing?**
**A:** **GAP — candidate must fill from recall.** The source documents only that the assumption was wrong and some machines ran IE11. Prepared line until recall supplies the scene: "The failure surfaced through use, not through a test I designed — which is the point I keep coming back to: my verification never touched the real environment."

**Q: Why not just rewrite it so it runs on IE11?**
**A:** The source of truth: it "couldn't [be made to work] on IE11 without a complete rewrite" (line 431). My on-the-spot reasoning — estimate, not a scoped plan — was that the image pipeline depends on OpenCV.js, a WebAssembly module, so the rewrite meant replacing it with JavaScript fallbacks: effectively rebuilding the tool for an end-of-life browser. The right call was to make the limitation explicit and gate it. Re-open condition, stated in the story: if a still-supported browser on the fleet had the same gap, I'd pay the rewrite cost.

**Q: What exactly does the compatibility check do?**
**A:** What the record supports: it's a browser-compatibility check that displays a clear error message when the tool can't run. Beyond that — the exact wording of the message, the precise detection logic — is candidate recall of code I wrote, not something I can currently point to in documentation; if asked to show it, that's the honest line. *(No "documented minimum browser requirement" is claimed — no such artifact was found.)*

**Q: How is this different from an ordinary bug?**
**A:** A bug is code that doesn't do what I intended. This was code doing exactly what I intended, on an environment I had assumed rather than verified. The deeper failure was the assumption, not the implementation.

**Q: What changed in how you work after this?**
**A:** I verify the deployment environment before building for it — the actual machines, not the assumed one. It's the same discipline the BOM parser taught me about data: don't assume, go look. *(v2: narrowed from the pass-1 "capability check into anything that depends on WebAssembly or WebGL" sweep, which had no demonstrated instances behind it.)*

**Q: Did anyone still get value from the build?**
**A:** Yes. On modern-browser machines the standalone worked as designed — a single file, offline, no installs, ~5s load, double-click to run — and on the IE11 machines users got an explicit error message instead of a mystery. Being honest about the limitation was better than pretending the tool worked everywhere.
