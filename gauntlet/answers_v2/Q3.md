# Q3 — tell me about a time you used genai to solve a business problem and what measurable result it delivered

**Mapped LP(s):** Invent and Simplify (primary — this is how the source story is actually labeled: Invent and Simplify, Think Big, Learn and Be Curious, Customer Obsession); Deliver Results via the concurrent suite delivery, which is a separate documented story (STORY 12) and I'll say so if pressed; touches Customer Obsession.

**Story used:** BGSW PCB Inspector Suite — GPT-4o VLM inspection engine (`AMAZON_INTERVIEW_PREPARATION.md` STORY 8 "Adding an AI Eye to the Inspection"). The documented result figures (manual interpretation about 30 seconds → about 5 seconds per mismatch; roughly 85% correct on component type and mismatch type) appear in STORY 8's Result with no measurement protocol behind them — no eval set, no sample size, no instrumented timing. I present them as documented estimates, not validated accuracy. They belong to the server build; the offline standalone tool the factory floor used does not run the VLM. The conflicting telling in `AMAZON_INTERVIEW_PREP.md` STORY 3 ("92% accuracy on 100 board pairs") is deliberately not used, and its 100-pair F1 methodology cannot be borrowed to dress up the 85%.

## Answer (core, ~500 words)

The business problem was on the manufacturing floor, not in my editor. I built the PCB inspection suite at Bosch: tools that compare a photograph of a board against its CAD layout and highlight every mismatch in red. But the tool could only say *where* the mismatch was. It couldn't say what it *meant*. Every red region became a manual task — zoom in and decide whether it's a wrong-value part, a component rotated 180°, or just a reflection off a solder joint. That took roughly thirty seconds per mismatch, and a typical board flags five to twenty of them. That interpretation step was the bottleneck in verification: slow, and resting entirely on each operator's judgment. I was the only developer on the suite, and my job was to delete that step.

I added a vision-language model as the inspection engine: it reads the flagged region, identifies the component, classifies the mismatch — wrong value, wrong orientation, missing, extra, or false alarm — and returns a confidence. The constraint was business-real: under five seconds per analysis, and accurate enough to be worth the operator's attention.

I chose GPT-4o. I evaluated GPT-4V, which was slower — about eight seconds per request versus three for 4o; Claude 3, whose API was less mature at the time; and Gemini Pro Vision, which was weak on small SMD parts. GPT-4o had the best balance of accuracy, speed, and API availability, and it handles image and text in one request. I rejected training a custom vision model: a bespoke classifier would have been a labeling-and-retraining project on top of the load I was already carrying, per defect type. My engineering went into the pipeline: crop the region from both the layout and the photo, send both with a structured prompt, and parse a JSON reply with `component_type`, `mismatch_type`, `confidence`, and `description`.

My first prompt failed. "Describe what you see and compare it to the expected layout" returned verbose, inconsistent answers — sometimes background, sometimes the part. I rewrote it to force the fixed JSON schema and added examples for the common mismatch types. That's when it became reliable.

Now the result, stated carefully. The documented figures are manual interpretation going from about thirty seconds per mismatch to about five, at roughly 85% correctness on component and mismatch type — and I want to be explicit that those are estimates logged from validation use, not an instrumented study: no labeled eval set, no recorded sample size. Typical API response was about three seconds, inside the five-second budget. The 15% failures were images too poor or components too small to read. Scope: the VLM ran only in the server version, where there is API access; the offline standalone HTML file the factory floor used does not use the VLM feature — no model, no API key. So the honest business-impact claim is: per-mismatch estimates on the server build, board-level arithmetic — ten mismatches takes roughly five minutes of interpretation down to under a minute, which is derived from the documented figures, not separately measured — at about a cent per analysis, and engineers reporting to me that the AI helped them prioritize mismatches on dense boards. Adoption, precisely: all three comparison tools shipped within eight weeks and the *suite* — not the AI specifically — was adopted by 15 engineers across two sites; I never instrumented feature-level usage of the AI analysis itself.

Reflection: I was wrong that the model could read values off small surface-mount parts — the text is too small, and it's much better at type and orientation. And I know what I'd add first: a labeled eval set and feature-level telemetry, so the next version of this number is measured rather than logged.

## Deep follow-ups (likely bar-raiser probes)

**Q: How is this a business result and not just a cool technical demo?**
**A:** The cost was operator time on a required verification step — manual interpretation was the documented bottleneck. At about thirty seconds per mismatch and five to twenty mismatches per board, a ten-mismatch board cost roughly five minutes of interpretation; after, under a minute, at about a cent per analysis. But I'll scope it honestly: that arithmetic is on the server build, the deployed floor tool ran the offline version without the VLM, and I never instrumented how often the AI feature itself was used. The documented business signals are the per-mismatch estimates, the cost arithmetic, and engineers reporting better triage on dense boards. Feature-level telemetry is the first thing I'd add to turn that into a measured floor result.

**Q: 85% sounds low. How was it measured, and why is that acceptable?**
**A:** Measured is too strong a word, and I'd rather say so than defend a number I can't source to a protocol. The ~85% and the 30s→5s are figures logged from validation use — the analyses checked against what the engineers' inspection actually found — not an eval with a defined sample size and ground-truth labeling process. If you want n and a confusion matrix, that's a gap: I'd have built a labeled set of mismatch crops with engineer-confirmed verdicts, and that's what I say I'd do next. What makes 85% acceptable even unquantified is architectural: the model is a first-pass classifier, not the decision. The UI labels it "AI Analysis" with a confidence percentage, the engineer always verifies, and a correct/incorrect feedback button lets errors surface systematically instead of silently. It moves human attention from interpretation to judgment.

**Q: What does this cost at scale, and where would you not use the model?**
**A:** I only send the regions the comparison already flagged, so cost and latency scale with mismatches — five to twenty per board — not with component count. About $0.01 per analysis, so roughly $0.10 for a ten-mismatch board. I would not put a VLM on every component: five hundred components across a thousand boards a day would wreck cost, latency, and auditability, because you can't reproduce a verdict from a hosted model version months later. The deterministic four-signal comparison stays the core. A cost-aware cascade that escalates only the hard cases to the model is a design target I'd want, and I want to be clear it's designed, not built.

**Q: Why GPT-4o rather than a purpose-built vision model you control?**
**A:** I evaluated GPT-4V (about eight seconds per request versus three), Claude 3 (strong visual understanding, but its API was less mature at the time), and Gemini Pro Vision (fast but weaker small-object detection, which matters for SMD parts). GPT-4o had the best balance of accuracy, speed, and API availability, and its single-request image-plus-text handling simplified the integration. Against a custom classifier: labeling data and training per defect type, then retraining whenever a new defect appeared — real ongoing work for a task where an existing general model could be pointed at it after preprocessing. A self-hosted VLM like LLaVA is the alternative I'd weigh if API cost or privacy became the binding constraint — the source raises it only as a future option for a more sensitive environment, not something I evaluated or ran, and it needs a GPU with at least 8GB VRAM the factory floor machines don't have.

**Q: You've told two different things about the standalone version — a BYOK API-key panel, and no VLM at all. Which is it?**
**A:** Both are in my record, and the reconciliation is the key handling, not a contradiction in the tool. I did build a standalone configuration panel for bring-your-own-key usage: the key stays in localStorage, goes straight to the API, and — this is the part that resolves it — with no key configured the VLM analysis is gracefully disabled with a clear message. The standalone build as deployed to the floor shipped with no key, so the VLM feature was off: that's what "the standalone version doesn't use the VLM feature, so no API key is needed" describes. The code path existed; the feature was not live on the floor. I won't tell you an offline AI usage story I can't substantiate — the documented result is the server build, full stop.

**Q: Where did the design ideas come from, inside and outside the company?**
**A:** Outside: the model landscape — GPT-4o, GPT-4V, Claude 3, and Gemini Pro Vision — plus the browser CV stack, OpenCV.js and TensorFlow.js, that already powered the tools. Inside: I sat in on three of the engineers' screen-sharing sessions before writing the first comparison tool, and that's what shaped how mismatches get presented — visual highlighting over a score; the AI analysis was built on top of that established workflow, not designed from fresh observation. I walked the data question through the security team, who approved sending board photos because they contain no trade secrets.

**Q: What happens when the API is down, and what would you do differently?**
**A:** The VLM is an enhancement, not a dependency. If the API is unreachable, the comparison still runs, the visual highlights still show, and the UI says "AI analysis unavailable — check API connection," and the engineer falls back to the manual check. That fallback describes the server experience; the offline standalone file does not use the VLM feature at all. Differently: start with the simple structured prompt instead of the clever one; don't assume a VLM can read values off small SMD parts; and before scaling the AI claim, build the labeled eval set and the feature-level usage telemetry I skipped. The self-hosted question — LLaVA-class, needing ≥8GB VRAM the factory floor doesn't have — is a future consideration, not something I built or benchmarked.
