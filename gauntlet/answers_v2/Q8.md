## Answer (core, ~500 words)

The project I completed on my own was making the PCB inspection suite ship as one double-click file — no Python, no server to run, nothing to install. I built the suite solo: browser tools for reconciling a BOM against the board layout and classifying defects, with a Flask backend that did server-side BOM parsing and served the trained model. The people using the tools are manufacturing engineers on factory-floor machines — restricted network, no software installs, minimal IT support. Every rollout meant installing Python and configuring the server per machine, which turned each deployment into an IT ticket the team couldn't absorb. The delivery problem, not the code, was the blocker between a working tool and a used tool. I was the only engineer on it, so the call was mine alone: kill the running server and ship one file users already know how to open.

I started by auditing what the browser couldn't fetch at runtime. The app code was already client-side. What actually lived on the server was the trained model — a TensorFlow.js topology JSON plus 3.4 MB of binary weight shards the page fetched over HTTP. That had to travel inside the file.

So I wrote `compile_tool.py`. It's 80 lines, checked in with the source. It reads `model.json`, concatenates the weight shards in manifest order — not filesystem order, which is wrong whenever a model ships as multiple shards — base64-encodes the result, and injects both topology and weights into the HTML as JavaScript constants before the closing body tag. The page's loader decodes the constant into buffers at startup and builds the model from them. Base64 costs about 33%, and I could watch it: 3.4 MB of weights become roughly 4.6 MB of text, which is why the finished file is about 4.7 MB and the embedded model is nearly all of it. The script's own success message is my acceptance criterion: "send this single file to your colleagues… just double-click it to run (No server required)."

The other server dependency was state. The tool keeps per-board training labels — good, bad, ignore — and the standalone build persists them in localStorage keyed by inspection file, so sessions survive restarts with nothing behind them. And packaging went from a by-hand, order-dependent assembly that took tens of minutes and broke periodically to one deterministic command that finishes in seconds, timed with a hand stopwatch. I marked builds by editing the file title by hand — "v26 (Hardcoded Model)" — which is technical debt: the git-hash version stamp I'd planned, I never built.

I want to be precise about what this architecture won and what it cost. Won: zero installs on machines where IT approves no binaries, board layouts — trade secrets — that never leave the machine, and a reproducible one-command build. Gave up: no update channel — every fix means re-sending the file — nothing aggregates across machines, and startup pays to decode the embedded weights. The fully-offline end-state, where the generic libraries (TensorFlow.js, XLSX, an OpenCV.js WASM pass) are embedded the same way so the file needs no network at all, was designed — but the checked-in build still pulls those four libraries from a CDN, so I won't quote a single offline load-time or size number I can't show you the file for.

I distributed it by email and USB. The handoff that used to be "install Python, configure the network, file a ticket" became "double-click."

The lesson I actually took is about verification, not engineering. I shipped on qualitative confidence — the same boards run before and after, by hand — and never built the golden-output parity harness I'd designed or measured load times properly, and my notes filled that space with round numbers I could no longer reproduce. My rule now is to never claim a measurement I didn't take. Architecturally: design for standalone from day one. Retrofitting delivery is harder than designing it in.

## Deep follow-ups (likely bar-raiser probes)

**Q: Can you show me the file? What's actually inside it?**
**A:** Yes — `Bosch_Inspector_Standalone.html`, 4,657,494 bytes, title "Bosch PCB Inspector v26 (Hardcoded Model)". Inside: the full app markup/JS, an embedded-model block (`EMBEDDED_MODEL_JSON` + `EMBEDDED_WEIGHTS_BIN`, about 4.6 MB of base64 — the 3.4 MB weight shard plus the topology), localStorage persistence (`pcb_train_*` keys for the per-board good/bad/ignore labels, plus the tour flag), and five CDN script/link tags for the generic libraries. That last part is why I tell the story from this file and not from my notes.

**Q: Your situation says the factory floor has no internet, but this file loads libraries from a public CDN. Which is it?**
**A:** Both, sequentially, and conflating them is exactly the failure my notes contained. What I can produce and stand behind is the single-file, server-free build — no install, no backend, model baked in. The offline-completion pass — embedding TF.js/XLSX/the CV libraries the same way so a disconnected machine works — was the designed end-state; I'm not going to assert its size, load time, or delivery as verified results in an answer when the file I can open doesn't contain it. If you ask "did the fully-embedded build exist?", my honest interview answer is: it's not in the checked-in snapshot or the backups I can search, so I demote it to design and strip its numbers.

**Q: Why one file instead of a zip or an installer?**
**A:** A multi-file deliverable adds a failure mode: the files must stay together, and moving just the HTML breaks the tool. An installer is precisely the thing IT wouldn't approve on those machines. Base64 costs ~33% overhead — visible in the arithmetic, 3.4 MB in, 4.6 MB of text out — and single-artifact delivery is worth it.

**Q: What was the hardest part?**
**A:** Making the model travel correctly. TF.js stores weights as manifest-referenced binary shards; concatenating them in filesystem order is wrong, so the script reads `weightsManifest` and merges in manifest order, then the page's loader had to build the model from the decoded constants instead of a URL. The guard path matters too — if the embedded block is missing, the loader refuses rather than half-working.

**Q: Why Python instead of Webpack or a JS bundler?**
**A:** The job is reading two files, concatenating bytes, encoding base64, and replacing one string — no module graph, no minification, no source maps. It's 80 lines. (My notes said "about 200" — they were wrong; I checked the file.) A bundler's config surface isn't justified for a step that runs once per release.

**Q: How did you know the standalone matched the server version?**
**A:** Qualitatively, on the boards I had — same inputs, same outputs by hand. I designed a golden-output harness (run five boards, dump every score to JSON as the oracle; refactors must stay byte-identical) and never built it. That's the verification debt I'd pay first, and the reason I don't quote parity percentages.

**Q: What happens at 10× — 100 machines, 100 boards a day?**
**A:** Per-user load is the frugality win: it's fully client-side, so 10× users breaks nothing I maintain. The ceilings are organizational: fixes require re-distributing files, and calibration/label data can't aggregate across machines, so there's no fleet learning. A service worker was the middle path I considered — cache the libraries and keep the small file — but workers need HTTPS to register, which the floor machines didn't have configured.

**Q: How did versioning work across builds?**
**A:** Badly, and honestly: I incremented the title string by hand — that's the "v26 (Hardcoded Model)" in the file. Automating a git-hash stamp was on the list and never done; with no update channel, a wrong-version file in someone's hands is undetectable, which is why I count this as the architecture's real cost, not trivia.

**Q: Did anyone disagree with deleting the server?**
**A:** There's no documented stakeholder pushback — it was a solo project and I'd be inventing a scene to claim one. The disagreement that did exist was with my own default assumption that tools ship on servers; the trade-off list in the answer is the argument I had with myself, written down.

**Q: How many engineers used it?**
**A:** I don't have a number and won't quote one. Distribution was email and USB; the handoff became double-click. Adoption counts were never tracked — another item on my verification-debt list, not a stat.
