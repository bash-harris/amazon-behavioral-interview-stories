## Answer (core, ~400 words)

My stakeholders were the manufacturing engineers who used the BOM reconciliation tool I built. Before it existed they verified boards by hand — cross-referencing the SAP-exported BOM against the Altium layout PDF, entry by entry. The baseline they gave me was 20–30 minutes per board; that was their estimate, not a measurement I took.

The first important interaction was a correction, not a request. My parser treated references like `R1||R2` and `R1/R2` as invalid and silently dropped them. A manufacturing engineer told me those notations mean the same physical position can accept either part depending on the board variant — so the system should treat each as a valid match. He had the manufacturing intent and I didn't. I built a variant splitter that normalizes both separators, extracts the individual references, and matches either one. That change came from the customer; I would not have found it from the data alone.

The second interaction was about trust. The engineers were using the tool but didn't fully trust it: when it flagged a mismatch they couldn't see why, and they were hesitant to rely on it for critical decisions. Making the results auditable was my responsibility, and I shipped two things in the server build. A per-component debug route: give it a reference and it returns the raw evidence behind the decision — which pages of the layout PDF that reference appears on, the matched text spans with their position and color classification, and the nearby hyperlinks and DNP keywords the matcher weighed. And a stats dashboard above every reconciliation — schematic component count, BOM entry count, matched, issues flagged — so they could see the shape of a run before drilling into any decision. I kept the diagnostics on a separate route so the main view stayed clean. The intent wasn't to prove the tool right; it was to let them audit the decisions themselves. Both were part of a small Flask service on the plant network — local network only, not the internet.

The result: the audit capability turned into an informal test channel — in the first week the engineers used it to surface two edge cases with unusual component naming, and I fixed both. Parsing a 2000-component BOM took under 200 milliseconds; a full report came back in seconds against their reported 20–30 minute baseline, and the tool caught three real mismatches in week one that manual review had missed. I verified every change against a regression suite of fifteen production BOMs covering each known edge case. The honest scope: one team, one plant, one week of numbers. What changed most was the trust dynamic — once they could see the reasoning, they reported being more willing to rely on the results for production verification.

What I'd do differently: ship the transparency capability from the beginning instead of after their skepticism, and collect representative BOMs from the floor before writing the parser. Both are the same lesson — get the customer's real artifacts in front of me earlier.

## Deep follow-ups (likely bar-raiser probes)

**Q: How did you know what the engineers actually needed versus what you assumed?**
**A:** They told me directly. A manufacturing engineer explained that `R1||R2` and `R1/R2` mean the same position can take either part — I had been dropping those as invalid. And after v1 shipped, the engineers made clear they didn't trust a verdict they couldn't inspect. Both of those drove the design.

**Q: What did you do when their domain knowledge conflicted with your design?**
**A:** I had been silently dropping variant references; the engineer said the system should treat either reference as a valid match for the position. He had the manufacturing intent and I didn't, so I built a variant splitter that normalizes `||` and `/` and matches either reference. That change came from the customer, not from me.

**Q: Why "either reference matches" rather than flagging variant positions for review?**
**A:** Honestly: the either-matches behavior came to me as a stated requirement — the engineer told me what the notation meant and what the system should do, and flagging every variant position for review would have pushed back onto the manual queue the tool existed to clear. I can defend that reasoning, but I should be straight that my record doesn't show a formal comparison of the review-flag alternative. If you're asking whether I benchmarked options, the documented answer is that the customer's stated intent set the design.

**Q: Walk me through what an engineer actually does when they question a mismatch.**
**A:** They question the verdict in the report, and the server's debug route answers with raw evidence for that reference: which pages of the layout PDF it appears on, the actual matched text spans with position and color classification, and the nearby hyperlinks and DNP keywords the matcher considered. They compare that against their own BOM and layout file and tell me where the logic went wrong. One caveat I want to be upfront about: my written story describes a fuller per-component trace page behind a `?debug=true` parameter; what I can stand behind from the code is the debug route and the stats dashboard in the server build — I'd describe the former, not demo it.

**Q: Why a separate route instead of putting everything in the main view?**
**A:** The diagnostic data is for investigation, not routine verification — showing all of it by default is overwhelming for normal use. A separate route kept the main reconciliation view clean while leaving the full evidence one request away for the engineers, who were technical users.

**Q: How did you keep getting feedback after launch?**
**A:** I didn't design it as a feedback channel, but it became one. In the first week the engineers used the debug route to surface two edge cases with unusual component naming, which I fixed. They were effectively testing the parser for me using the tooling I'd built for them.

**Q: Who provisioned the server, and what did the transparency work cost?**
**A:** It was a small Flask service running on the plant network — local network only, not internet-exposed, and the data it showed was the engineers' own BOM and layout content. What I can't give you from my records is the provisioning and security sign-off trail, or a time figure for the debug-and-dashboard work versus what it displaced. I'd need to check rather than guess.

**Q: Was the debug capability part of the offline standalone build?**
**A:** No — it lived in the local server build. The standalone single-file HTML was a separate deployment for factory-floor machines that couldn't run a server or install software at all. That constraint was exactly why the standalone build existed: the debug route and dashboard stayed with the one plant-network server; the no-infrastructure problem got solved differently, in the standalone file.
