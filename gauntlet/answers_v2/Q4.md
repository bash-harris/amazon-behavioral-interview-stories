# Q4 — tell me about a time you failed

**Mapped LP(s):** Earn Trust (primary); Learn and Be Curious; touches Are Right, A Lot.

## Answer (core)

The failure wasn't a crash — it was a rule I shipped on an assumption I never tested, and it made my tool flag correct boards as wrong.

I built the BOM reconciliation tool that compares a board's Bill of Materials against its layout. I wrote a comparison that required the component's pin count in the BOM to equal the number of pads in the layout. I had assumed pin count was a reliable signal that two references pointed at the same part. It isn't. A concrete case: the BOM lists an IC as "U1 (8-pin)," but the layout footprint has 16 pads. That's not an error — footprints are often drawn for multiple package variants, and the extra pads are unused or no-connect. My tool called it a mismatch.

On boards with mixed component types I was generating false positives on parts that were perfectly fine — false-positive reports ran around 12%. And every false pin-count mismatch meant a manufacturing engineer had to hand-verify that component's pin count: the exact work the tool was supposed to remove. The cost wasn't just minutes — it was credibility. A tool that cries wolf stops mattering.

I want to be clear about ownership: this was my wrong assumption, not bad data and not a subtle upstream bug. I built a rule on a signal I had never validated, and I only tested it on the boards I happened to have — none of which had the mixed-component-type cases that broke it.

So I went at the root cause instead of the symptom. I collected twenty BOMs that had pin-count discrepancies and categorized them: footprint larger than the component (almost always legitimate — package variants or no-connects), footprint smaller (a genuine mismatch — the part physically can't fit), and exact match. I changed the rule to follow those semantics instead of literal equality: more pads in the layout is a possible match, flagged for review; fewer pads is a definite mismatch. That's where I hit a second-order problem — a wrong component can still have a *larger* footprint, like a 4-pin resistor network against an 8-pin footprint belonging to something else, and my new rule would have waved it through. So I added a component-type check: a difference within a configurable threshold — default 2:1 — is accepted only when the reference type agrees. And I built a debug view that shows, per component, the BOM pin count, the layout pad count, whether the type matched, the ratio, and the tool's decision, so an engineer can see why it decided and override it.

The result: false-positive reports on boards with mixed component types dropped from about 12% to under 2%. I want to be precise about what that number is, because it's the kind of thing I got wrong here: it comes from the analysis I actually did — the twenty failing BOMs I collected and categorized and a fifteen-BOM regression suite, re-run after the fix — where "false positive" means *my categorization of the flagged mismatch against those files*, not a production rate validated against a labeled ground-truth set. Within that scope: the five suite BOMs with pin-count issues produced correct results, the other ten were unchanged, and no component that previously matched flipped status. The engineers could then trust the report without verifying every pin count by hand.

The lasting lesson: I now treat a signal as a hypothesis until I've watched it fail across diverse samples, and I collect those samples from users before I write the rule. The deeper one is that pin count was never the right signal — reference designator plus footprint name is. And the practical one: the debug view should have existed from day one; it would have shown me the pin-count behavior during development.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why didn't you just ignore pin count entirely?**
**A:** Because it catches genuine mismatches. If the BOM specifies a 16-pin IC and the layout shows an 8-pad footprint, that's a real problem — the component physically won't fit. Ignoring pin count would let those errors ship. The fix was to be smarter about *when* pin count matters, not to drop it.

**Q: If reference designator plus footprint name was the right signal, why did you keep pin count in the rule?**
**A:** Because the two signals answer different questions. Reference designator plus footprint name decides *which part a reference is* — the matching decision. The pin-versus-pad relationship still has to gate *fit* errors: a 16-pin part on an 8-pad footprint is physically impossible, and a matching key alone won't catch that. The type-and-ratio rule was the minimum fix that stopped the false positives while preserving genuine-mismatch detection. Changing the matching key itself was the bigger-scope move — and part of my "what I'd do differently" answer is that with representative data from the start, I'd have gone straight to the better signal instead of patching the weaker one.

**Q: How reliable are the 12%→<2% numbers on boards you hadn't seen?**
**A:** I can't promise generalization, and I won't pretend otherwise. The numbers come from twenty failing BOMs I categorized myself and a fifteen-BOM regression suite — no held-out set, no labeled ground truth. I've called out this exact failure mode in a technical review of a sibling module on the same project: tuning thresholds "on the same boards I was looking at, with no held-out set to measure what it cost." What I'd do now: label about two hundred components as ground truth, plot the precision-recall curve, and pick the operating point from the false-negative/false-positive cost ratio the process engineers give me. That's also why the debug view keeps a human in the loop for borderline cases — until the measurement exists, the tool defers instead of asserting.

**Q: How did you pick the 2:1 threshold, and what's the risk of a heuristic here?**
**A:** I analyzed the twenty failing BOMs and found legitimate footprint variations typically had a pad-to-component ratio of 2:1 or less, so I set the default to 2:1 and made it configurable. Twenty files is a thin base for a ratio rule — that's exactly why the default is an escape hatch, not a verdict: borderline ratios go to the review-flag path or the engineer adjusts the threshold. The residual risk is false negatives: a genuinely wrong component that happens to satisfy the ratio and shares a type letter could pass. The debug view mitigates that — the engineer sees the ratio and type match and can override. The rule is a heuristic, not a proof.

**Q: Why not train a model to classify this instead?**
**A:** I considered it, but I had only about 200 examples of known pin-count mismatches — not enough to train a reliable classifier. Those two hundred are component-level cases; the twenty BOMs I categorized are files, and a file can contain many such cases, so the numbers describe the same dataset at different granularity. Heuristics work when the rules are clear and the edge cases are enumerable. If the cases became more complex, I'd revisit the ML approach.

**Q: How did you verify the fix didn't break the components that were already matching?**
**A:** I ran the full regression suite of fifteen BOMs, five of which had pin-count mismatches. I confirmed three things: the five now produced correct results, the other ten were unchanged, and no component that previously matched correctly changed status. I want to bound that claim: fifteen BOMs is a regression safety net, not production evidence — it verifies the rule change did what I intended on the files I had; it doesn't certify a rate on unseen boards.

**Q: What happens on a board with a 3:1 ratio?**
**A:** With the default it's flagged as a mismatch for review. That's deliberate — the engineer decides whether it's a legitimate footprint variation (and adjusts the threshold) or a genuine mismatch. I put the judgment in the user's hands instead of making an automatic call.

**Q: What was the hardest part?**
**A:** Mid-fix, when my first version of the new rule failed on its own terms. The more-pads-is-acceptable logic created a blind spot: a genuinely wrong component whose footprint was *larger* would now pass. I'd built the improvement on the same habit that caused the original failure — accepting a signal I hadn't stress-tested. Catching it forced the component-type check, and it's why the "signal as hypothesis" lesson stuck.

**Q: How did you find out the rule was producing false positives?**
**A:** Honestly: the documentation of this event starts from the symptom — false mismatch reports on mixed-type boards — and doesn't record the channel through which it surfaced. I won't retrofit a story about who reported it. What I can say is that my first action was to go to the evidence itself: collect the twenty failing BOMs and categorize them, rather than argue from a single repro.

**Q: What would you do differently, concretely?**
**A:** Collect representative files from the manufacturing floor before writing the parser, instead of discovering edge cases reactively. Build the debug/observability view from day one — it would have surfaced the pin-count behavior during development. And the two deeper changes: don't trust a matching signal until I've seen it hold across diverse samples, and check whether a signal is even invariant — and whether it's the *right* one — before building a rule on it.
