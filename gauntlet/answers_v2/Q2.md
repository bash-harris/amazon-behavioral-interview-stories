# Q2 — tell me about a time you used genai to automate or streamline a workflow

**Mapped LP(s):** Invent and Simplify (primary); touches Deliver Results, Frugality, and Learn and Be Curious.

**Story used:** BGSW PCB Inspector Suite, told deliberately as **one inspection workflow, two tools**: (1) the deterministic BOM parser/reconciliation and its `?debug=true` transparency layer (`AMAZON_INTERVIEW_PREPARATION.md` STORY 1 "The BOM Parser That Refused to Break" + STORY 11 "Debug Endpoint for Manufacturing Transparency", plus the post-release pin-count false-positive fix from STORY 10), and (2) the PCB-vs-layout visual comparison tool, which is where the GPT-4o VLM is actually wired (`AMAZON_INTERVIEW_PREPARATION.md` STORY 8 "Adding an AI Eye to the Inspection"). **Boundary disclosure:** no source and no code places a model call inside the BOM tool — the reconciliation has no photo input, and the VLM integration lives in the comparison tool's code (`PCBvsLayoutnew/js/vlm_scanner.js`; zero GPT/OpenAI references in `bom_server.py` / `bom-verification.js`). ## Answer (core)

I built the PCB inspection suite at Bosch, solo. Verifying a populated board had two manual steps inside one workflow. The first: an engineer cross-referenced the SAP-exported BOM spreadsheet against the Altium layout, part by part — the engineers reported 20–30 minutes per board, and it was easy to get wrong. The second: every region the photo-vs-layout comparison tool flagged in red still meant a person inspecting the component — about 30 seconds a mismatch — to decide whether it was a wrong value, a wrong orientation, or just a lighting artifact. I deleted the first step with deterministic parsing and the second with GenAI, and I deliberately kept the two apart. The constraints were the environment: factory-floor machines with restricted network access, non-developer users, and me as the only developer.

The naive parser — a regex like `/^[A-Z]+\d+$/` — worked on about 70% of real BOMs, then production data broke it four separate ways: an `MP_` manufacturing-process prefix; SAP cells exported as hyperlinks, where the extractor had to follow the link to the display text instead of grabbing the URL; variant references like `R1||R2` and `R1/R2` sharing one position, whose matching semantics the manufacturing engineer taught me; and DNP entries — positions intentionally empty, not missing. Each was a production failure before it was a test case, so I grew a 15-BOM regression suite from the failures and reran it after every change. Because engineers don't trust black boxes, I also built a `?debug=true` view — raw BOM text, every preprocessing step, the layout match, and the exact decision tree — plus an aggregate reconciliation dashboard. In week one the engineers used it to surface two naming edge cases.

The GenAI layer lives entirely in the other tool, and the boundary is honest: the visual comparison has images on both sides of the question, while the BOM reconciliation is document-versus-document with no photo — so the model runs only where interpretation is the bottleneck. When the comparison pipeline flagged a region, I cropped it from both the layout and the photo and sent both to GPT-4o with a structured prompt: identify the component type, classify the mismatch — wrong value, orientation, missing, extra, or false alarm — and return JSON I could parse. Before choosing GPT-4o I baked off GPT-4V (about 8 seconds per request versus 3), Claude 3 (less mature API at the time), and Gemini Pro Vision (weaker on small parts); a local LLaVA would have needed 8GB of VRAM the factory machines didn't have. The answer is presented as a suggestion labeled "AI Analysis" with a confidence figure and correct/incorrect feedback marks — so I could spot systematic prompt errors — never as a diagnosis. Cost scales with flagged mismatches (typically 5–20 a board), not with 2,000 components — roughly a cent an analysis — and with no API access the tool degrades gracefully: the highlights still show and the UI says AI analysis unavailable.

The results. Reconciliation returns in seconds what the engineers reported taking 20–30 minutes; a 2,000-component BOM parses in under 200 milliseconds; zero false positives and zero false negatives across the 15-BOM suite, and in its first production week the tool caught three real mismatches manual review had missed. I'll be honest about that suite: production later exposed a false-positive class it hadn't seen — footprints with more pads than the BOM listed, because the extra pads were no-connects or package variants. I root-caused it across 20 failure BOMs and fixed it with a component-type check and a configurable 2:1 threshold; false alarms on mixed-type boards dropped from about 12% to under 2%. On the GenAI side, per-mismatch judgment collapsed from a reported ~30-second inspection to a ~5-second model suggestion the engineer verified.

What I'd do differently: collect representative BOMs and pin-count semantics from the floor *before* writing code — I found every edge case reactively, one production failure at a time; build the debug view from day one; and never let a "zero false positives" claim outrun my own test set, because a regression suite only tests my imagination. The VLM taught me its ceiling too: it reads type and orientation well, not values on tiny surface-mount parts. GenAI belongs where interpretation is the bottleneck; rules should own everything else.

## Deep follow-ups (likely bar-raiser probes)

**Q: How do the two tools relate — does the reconciliation feed the model?**
**A:** It doesn't, and I won't pretend it does. They're two tools on one inspection line, different artifacts. Reconciliation compares a BOM Excel to a layout PDF — structured data, no photo, no model in its code. The comparison tool puts a photograph of the populated board against the layout; only there does a flagged region have images to show a VLM. The workflow is automated end to end because both manual steps are gone, not because one pipeline calls the model.

**Q: Where is the GenAI actually doing work, and why not just send everything to the model?**
**A:** GenAI does the part rules can't: look at a cropped region and say "wrong orientation" versus "lighting artifact," in parseable JSON. The structured matching is deterministic because a parser is cheaper, faster, and explainable. Sending every component to a VLM would be slower and costlier for no gain; I send only the small set the comparison already flagged — typically 5–20 regions a board at about a cent each.

**Q: How did you measure the improvement?**
**A:** With honesty about what's instrumented. The 20–30-minute baseline and the ~30-second per-mismatch inspection were engineer-reported, not a timed study. The reconciliation stats are regression-suite runs (15 production BOMs; zero FP/FN *there*). The ~5 seconds is the API response time from the comparison tool. The pin-count fix's 12%→<2% came from analyzing 20 failure BOMs before and after. If you're asking whether I ran a stopwatch study — no; that's a gap in my measurement discipline, and one of the things I'd do differently.

**Q: What happens when the model is wrong, or the API is down?**
**A:** The model's output is a suggestion labeled "AI Analysis" with a confidence figure; the engineer verifies it — the human was never removed from the loop. I added correct/incorrect feedback marks specifically so systematic prompt errors would surface. If the API is unreachable or no key is configured, the comparison tool still works — visual highlights show, the UI says AI analysis unavailable, and the engineer inspects as before. The reconciliation tool never needed the API at all. The VLM is an enhancement, not a dependency.

**Q: Walk me through the messy-data edge cases — and did anything escape your suite?**
**A:** Parser: MP_ prefix; hyperlink cells (follow to display text, not URL); variants `R1||R2` / `R1/R2` (the manufacturing engineer told me the semantics); DNP as intentionally-empty. Each was a production failure first, then a permanent test case. And yes, something escaped: the 15-BOM suite passed with zero FP/FN, yet production later showed a pin-count false-positive class — footprints legitimately have more pads than a component uses (no-connects, package variants). I categorized 20 failure BOMs, added a component-type check with a configurable 2:1 pad ratio, and false alarms on mixed-type boards dropped from ~12% to under 2%. Lesson: a heuristic can be wrong in both directions, so the debug view shows the raw comparison per component and lets the engineer override the decision.

**Q: Tell me about one of the three mismatches it caught in week one.**
**A:** Straight answer: I know the count and the report's categories — missing, extra, or mismatched — but I can't walk you through each of the three from memory; they live in the tool's production reports, not in my notes. I'd rather say that than dress up the headline. What I can speak to concretely is the class of defect the tool surfaces and the pin-count false-positive fix, because those I analyzed component by component.

**Q: Where did the design ideas come from, inside and outside the company?**
**A:** Externally: the model bake-off (GPT-4V, Claude 3, Gemini Pro Vision, local LLaVA — each rejected for a stated reason) and the browser CV stack. Internally: the manufacturing engineer on variant semantics and later on trusting pin counts less than footprints; the engineers' debug-view findings in week one; and the security team, who approved sending board photos because they contain no trade secrets.

**Q: What would you do differently?**
**A:** Collect floor BOMs and pin-count semantics before writing code — every edge case arrived as a production failure. Build the debug endpoint from day one. Don't claim "zero false positives" from a suite you sized yourself. And design the UI around the VLM's ceiling: strong on component type and orientation, unreliable on tiny SMD values.
