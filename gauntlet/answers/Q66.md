# Q66 — describe a time you simplified a complex process

**Mapped LP(s):** Invent and Simplify.

**Story used:** Tab Scroller — the token-saving AI command pipeline (`EXTENSION_SUMMARY.md` §3, "The 'Token-Saving' Optimization Engine"; `IMPLEMENTATION_GUIDE.md`, "Token Optimization (Phase 1)"; positioning context in `10_project.md`). One telling only: the guide's documented Phase-1 architecture and its own "Expected Performance Gains" table. **Honesty note:** the guide labels those speed/cost figures as *expected* gains, not measured outcomes, so they are presented here as the design's projected impact; the mechanics that produce them (a rule shortcut that never calls the model, a pre-filter that shrinks the tab set, batched parallel extraction, triplet compression) are implemented in `background.js` and are cited as such.

## Answer (core, ~470 words)

The process that needed simplifying was how my browser extension answered a natural-language command. The original path was one-size-fits-all: for *every* command — even "close all youtube tabs" — the extension queried all open tabs, extracted the full text of each page one at a time, and shipped the whole pile to Gemini or Ollama. On a 50-tab window that is roughly 50,000 tokens and about eight seconds per command, at around $0.50 a query, and it does not work at all offline. The process was complex in the worst way: it treated a trivial request and a hard one identically, so the cost and latency were set by the hardest case and paid by every case.

I simplified it into a staged pipeline, and the core idea was to stop paying the model for work that doesn't need a model.

Stage one is a local rule engine. Commands that fit predictable shapes — group/close/bookmark/pin/mute a named site, find duplicates, cluster by domain, find inactive tabs — are matched and executed locally with **zero API calls**. The pattern match runs in under a millisecond, so the most frequent commands get cheap and instant.

Stage two is a smart pre-filter that runs before any extraction. It maps the query against a fixed category ontology (coding, dev, docs, video, social, shopping, news, work, learning) and a keyword score, then keeps only the relevant slice — the guide's example narrows 50 tabs to 8, and caps the output at the top 30% or a minimum of five. The model only ever sees tabs that could matter.

Stage three extracts in parallel batches of ten instead of sequentially, and stage four compresses each page into `[Subject, Predicate, Object]` triplets and sends a minimal prompt listing only the filtered tabs.

The documented impact, framed by the guide's own "Expected Performance Gains" table: simple commands go from about two seconds and 5,000 tokens to roughly 10ms and zero tokens, because they never hit the API; a 50-tab complex command goes from about 50,000 tokens to roughly 3,000 (about a 94% token reduction); extraction drops from about five seconds sequential to about half a second batched; and projected API cost falls from roughly $0.50 to about $0.03 per query. The offline capability is the new one — the rule path handles roughly 70% of queries with the network off. I keep those as projected figures because that's how they're labeled in the guide.

On the "externally aware" half: I evaluated and wired two model backends — Gemini and Ollama — and deliberately put the local rule engine in front of both, which is the privacy and cost win as well as the speed one. And it scales: the pre-filter and the parallel batcher are sized to tab count, the ontology is versioned, and the guide's Phase 2 names embeddings and a WebLLM client as the next offline step.

One trade I'd name honestly: a rule engine only covers patterns it recognizes, and anything it doesn't match falls through to the full AI path, so the rules have to be conservative. The simplification wasn't removing the complex path — it was routing around it whenever the simpler one was provably enough.

## Deep follow-ups (likely bar-raiser probes)

**Q: What exactly was complex before, and what made it simpler?**
**A:** The complexity was that every command took the same expensive path: query all tabs, extract all page text sequentially, send everything to the model. I replaced that with routing — a local rule path for predictable commands, a pre-filter that shrinks the tab set, parallel extraction, and compressed triplets. Same outcomes, far less work per command.

**Q: Are those numbers measured or estimated?**
**A:** The guide labels them "Expected Performance Gains," so I present them as projected, not measured. The mechanics behind them are implemented — the rule engine genuinely makes zero API calls, the pre-filter genuinely reduces the tab set before extraction, and extraction genuinely runs in parallel batches. I won't dress the projected figures as measured results.

**Q: How does the pre-filter decide what's relevant without asking the model?**
**A:** It's deterministic. It matches the query against a category map of domains and against keyword scores on titles and URLs, keeps scoring tabs, then returns the top ~30% capped between five and thirty tabs. No tokens, sub-millisecond, and it fails back to the full tab set if nothing scores.

**Q: Why rule-based shortcuts instead of just using a bigger model?**
**A:** Because most commands don't need one, and using a model for them costs latency, money, and privacy. "Close all youtube tabs" is a pattern match. Reserving the model for genuinely ambiguous commands makes the common case instant and keeps simple commands on the machine.

**Q: How does this scale as the user opens more tabs?**
**A:** The expensive steps are bounded by the filtered set, not the total. The pre-filter caps its output, extraction runs in batches of ten concurrently, and the compressed triplet payload is small. So a 50-tab window doesn't cost what a 5-tab window costs on the AI path — that's the design intent.

**Q: What would you simplify next?**
**A:** The guide's own next steps: replace keyword pre-filtering with local embeddings, add a client-side WebLLM for fully offline semantic work, and implement progressive context disclosure so even the AI path sends only what the current decision needs.
