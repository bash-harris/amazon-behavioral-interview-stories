# Q4 — tell me about a time you failed

**Mapped LP(s):** Earn Trust (primary); Learn and Be Curious; touches Are Right, A Lot.

**Story used:** BGSW PCB Inspector Suite — the pin-count mismatch in BOM reconciliation, `AMAZON_INTERVIEW_PREPARATION.md` STORY 10 "The Pin Count Mismatch Problem." One telling only; the conflicting four-edge-case telling in `AMAZON_INTERVIEW_PREP.md` Story 2 is not used.

## Answer (core, ~440 words)

The failure wasn't a crash — it was a rule I shipped on an assumption I never tested, and it made my tool flag correct boards as wrong.

I built the BOM reconciliation tool that compares a board's Bill of Materials against its layout. I wrote a comparison that treated the component's pin count in the BOM and the number of pads in the layout as something that had to match. I had assumed pin count was a reliable signal that two references pointed at the same part. It isn't. A concrete case: the BOM lists an IC as "U1 (8-pin)," but the layout footprint has 16 pads. That's not an error — footprints are often drawn for multiple package variants, and the extra pads are unused or no-connect. My tool called it a mismatch.

On boards with mixed component types I was generating false positives on parts that were perfectly fine — about a 12% false-positive rate. That number mattered more than it sounds. Every false alarm sent a manufacturing engineer to manually verify a pin-count mismatch, and it taught them not to trust the report. They had started re-checking the tool's output by hand, which was the exact work the tool was supposed to remove. A false alarm costs an operator about thirty seconds, but the real cost was the confidence.

I want to be clear about ownership: this was my wrong assumption, not bad data and not a subtle upstream bug. I built a rule on a signal I had never validated, and I only tested it on the boards I happened to have — none of which had the mixed-component-type cases that broke it.

So I went at the root cause instead of the symptom. I pulled twenty BOMs that had pin-count discrepancies and categorized them: footprint larger than the component (almost always legitimate — package variants or no-connects), footprint smaller (a genuine mismatch — the part physically can't fit), and exact match. I changed the rule to follow those semantics instead of literal equality: more pads in the layout is a possible match, flagged for review; fewer pads is a definite mismatch. I added a component-type check so a difference within a configurable threshold — default 2:1 — is accepted only when the reference type agrees. And I built a debug endpoint that shows, per component, the BOM pin count, the layout pad count, whether the type matched, the ratio, and the tool's decision, so an engineer can see why it decided and override it.

The false-positive rate for boards with mixed component types dropped from about 12% to under 2%. Engineers stopped hand-verifying every pin count and used the debug view when a result looked odd.

The lasting lesson: I now treat a signal as a hypothesis until I've watched it fail across diverse samples, and I collect those samples from users before I write the rule. The deeper one is that pin count was never the right signal — reference designator plus footprint name is. I'd have found both faster with representative data instead of the boards I had.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why didn't you just ignore pin count entirely?** 
**A:** Because it catches genuine mismatches. If the BOM specifies a 16-pin IC and the layout shows an 8-pin footprint, that's a real problem — the component physically won't fit. Ignoring pin count would let those errors ship. The fix was to be smarter about *when* pin count matters, not to drop it.

**Q: How did you pick the 2:1 threshold, and what's the risk of a heuristic here?** 
**A:** I analyzed the twenty failing BOMs and found legitimate footprint variations typically had a pad-to-component ratio of 2:1 or less, so I set the default to 2:1 and made it configurable. The risk is false negatives: a genuinely wrong component that happens to satisfy the ratio and shares a type letter could pass. The debug endpoint mitigates that — the engineer sees the ratio and type match and can override. The rule is a heuristic, not a proof.

**Q: Why not train a model to classify this instead?** 
**A:** I considered it, but I had only about 200 examples of known pin-count mismatches — not enough to train a reliable classifier. Heuristics work when the rules are clear and the edge cases are enumerable. If the cases became more complex, I'd revisit the ML approach.

**Q: How did you verify the fix didn't break the components that were already matching?** 
**A:** I ran the full regression suite of fifteen BOMs, five of which had pin-count mismatches. I confirmed three things: the five now produced correct results, the other ten were unchanged, and no component that previously matched correctly changed status.

**Q: What happens on a board with a 3:1 ratio?** 
**A:** With the default it's flagged as a mismatch for review. That's deliberate — the engineer decides whether it's a legitimate footprint variation (and adjusts the threshold) or a genuine mismatch. I put the judgment in the user's hands instead of making an automatic call.

**Q: What would you do differently, concretely?** 
**A:** Collect representative files from the manufacturing floor before writing the parser, instead of discovering edge cases reactively. I'd also build the debug/observability view from day one — it would have surfaced the pin-count behavior during development. The deeper change: I don't trust a matching signal until I've seen it hold across diverse samples, and I now check whether a signal is even invariant before building a rule on it.
