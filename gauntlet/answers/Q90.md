## Answer (core, ~460 words)

The application was the browser-based PCB inspection suite, and the performance I optimized was ML inference latency inside an interactive tool. Component defect classification had to run entirely in the browser on a factory-floor machine with no server, and the bar was explicit: inference under 100 milliseconds per component image. If a crop couldn't be classified inside that budget, the tool wasn't interactive and the workflow broke.

The instinct in ML is to reach for the most accurate model. I did the opposite and optimized against the budget. I evaluated ResNet, EfficientNet, and Vision Transformers. Vision Transformers were powerful but needed large datasets and significant compute; ResNet was well-understood but surpassed. EfficientNetV2S gave the best trade-off, and the sizing was the performance decision: small is about 21 million parameters, medium about 54 million, large about 119 million. For small 224×224 component crops — features like color, shape, and text — small was sufficient. On my dataset the accuracy difference between small and large was less than 2%, which did not justify the extra parameters, and small trains roughly 3x faster than large. I took the accuracy I could measure and refused to pay latency for the rest.

At inference the cost is the convolutions. For a 224×224 input the forward pass is about 8 billion FLOPs, and on a CPU that lands at about 45ms. On a GPU it would be under 5ms, and in the browser TensorFlow.js runs through WebGL acceleration, which brings it close to GPU performance. The measured result: 45ms per image on CPU, comfortably inside the 100ms target. That is the number I report, because it's the one the pipeline actually produced — the sub-5ms and WebGL figures are the documented performance characteristics of the hardware paths, not a benchmark I re-ran.

The measurement I care about most is that I didn't buy latency with accuracy. I set recall above 90% as the bar and it held: 92% on wrong-value, 96% on wrong-orientation, 98% on missing components. And because the model was small, the pipeline retrained on new data in about 30 minutes on a single GPU, so new defect types didn't stall the inspection workflow.

What I'd do differently: instrument earlier, and look at the whole browser path, not just the model. The model turned out not to be the dominant cost — the source notes that in this pipeline the OpenCV.js library load is the real bottleneck, not the computation. So the next performance work is the load path and the pre-inference stages, not shrinking the model further. I'd also profile before optimizing so every change has a measured before and after rather than a reasoned one.

## Deep follow-ups (likely bar-raiser probes)

**Q: How do you know you optimized anything, versus just picked a smaller model?**
**A:** Because the optimization target was a hard latency budget — under 100ms per component image — and the measured result was 45ms on CPU. The sizing decision is what delivered it: small is ~21M parameters against ~54M/119M for medium/large, and the accuracy difference was under 2%, so the larger models would have spent latency for accuracy I couldn't justify. The number is measured; the reasoning connects the choice to it.

**Q: Are the sub-5ms GPU and WebGL figures measured?**
**A:** No — I present those as the documented performance characteristics of the hardware and runtime paths, not as benchmarks I ran. The measured number is 45ms per image on CPU. I'd want a profile before claiming a WebGL number.

**Q: Why not use the large EfficientNetV2 for more accuracy?**
**A:** Because the accuracy difference between small and large on my dataset was less than 2%, and large has roughly 5–6x the parameters of small and trains about 3x slower. In an interactive browser tool, that's paying latency and compute for a gain I couldn't measure into the bar. If accuracy had been the binding constraint, I'd have revisited it.

**Q: How did you keep from trading accuracy for speed?**
**A:** By setting both targets up front. The latency target was under 100ms; the accuracy target was classification accuracy above 90%. I reported per-class recall — 92% wrong-value, 96% wrong-orientation, 98% missing — so I could show the fast path was still correct, not just fast.

**Q: What breaks at 10x — more components or higher-resolution images?**
**A:** Higher-resolution images are the real risk: the model input is 224×224, so upscaling or tiling means more forward passes, and memory grows. At 10x components the per-image latency is fixed, so it's throughput, not the model. Both point at the same next step: profile the full browser path and offload the pre-inference work.

**Q: What would you optimize next?**
**A:** The load path and the stages around the model. The source explicitly notes that the OpenCV.js library load is the bottleneck in this pipeline, not the computation, so the model is not where the remaining seconds live. After that I'd instrument per-stage latency so each optimization has a measured before and after, and I'd reuse the documented next step of parallelizing the independent comparison signals — the source projects about a 3.5x speedup from Web Workers, which I'd treat as projected until I measured it.
