# Q67 — tell me about a time when you had to implement a direction you didn't agree with

**Mapped LP(s):** Have Backbone; Disagree and Commit (primary); touches Are Right, A Lot and Earn Trust.

**Story used:** `AMAZON_INTERVIEW_PREPARATION.md` STORY 10 ("The Pin Count Mismatch Problem") — the documented direction to keep pin count as a reconciliation signal and fix the false alarms without breaking genuine mismatch detection, which I implemented fully despite believing pin count was the wrong signal. **Distinct re-frame of Q17:** Q17's spine was the disagreement (Have Backbone — bringing 20 BOMs of evidence against the literal rule); this answer's spine is the **implementation/commitment** half (Disagree and Commit — executing the direction I had reservations about, completely, and owning the residual risk). One telling only: STORY 10's numbers (20 BOMs, ~12% → under 2%, 2:1 threshold). `AMAZON_INTERVIEW_PREP.md` Story 2/11's conflicting telling (15% → under 1%, 20 boards, `R1 (Rev A)`) is not used.

## Answer (core, ~440 words)

I want to be precise about what this is, because the honest version matters more than a tidy one.

The direction I had to execute was the pin-count rule in the BOM reconciliation tool: keep pin count as a matching signal, and fix the false alarms without breaking genuine mismatch detection. I did not agree with pin count as the signal. My view was that the better signal is the component reference designator combined with the footprint name — pin count is unreliable because footprints are designed for whole package families, not single parts. But the direction was set: the tool compares pin count, and the requirement was to make that comparison discriminating, not to remove it.

So I did the disagreement half once, properly, with evidence instead of preference. I collected 20 BOMs that had pin-count mismatches and categorized every one into three buckets: footprint larger than the component, footprint smaller, and exact match. The pattern was clean — footprint-larger was almost always a legitimate package variation (extra pads for variants or no-connects), footprint-smaller was always a genuine mismatch because the part physically can't fit, exact match was fine. I stated my position with that data and said plainly that I thought reference designator plus footprint name was the stronger signal.

Then I committed — fully, not a half-version. I kept pin count in the comparison and made it discriminating instead of literal: layout has more pads → flag for review, not a mismatch; layout has fewer pads → definite mismatch. That opened a real hole — a larger footprint on the wrong component type would pass — so I added a component-type check: if the type (R, C, U, and so on) doesn't match, flag it regardless of pin count. For matching types I added a configurable pin-count ratio threshold, defaulted to 2:1 because that's what the 20 test BOMs supported. I built a debug view that shows the raw BOM pin count, the layout pad count, the type match, the ratio, and the tool's decision for every component, so an engineer can verify and override any call. And I documented the residual risk rather than hiding it: a heuristic this shape can produce false negatives, and the debug view is the mitigation. The result: false positives dropped from about 12% to under 2% on boards with mixed component types.

Could I have dragged my feet, built the minimum, and let it fail to prove my point? Yes — and that would have been the wrong answer. Half-committing is worse than the original disagreement.

**FRAMEWORK — if a manager actually hands me a direction I disagree with and overrules me:** I state the counter-argument once, directly and privately, anchored to the specific data and the customer or business risk. If the decision stands, I implement it as if I'd made it, and I don't relitigate. If implementing it surfaces a new material fact the decision-maker couldn't have seen, I raise that once, with evidence, then respect the call. I keep that framework labeled because the record doesn't show me losing that argument — I won't claim a scene that didn't happen.

## Deep follow-ups (likely bar-raiser probes)

**Q: Did a manager actually give you that direction, or was it the tool's existing rule?**
**A:** Honest answer: it was the tool's existing pin-count measurement rule plus the explicit requirement to keep pin count and fix the false alarms — not a manager handing me an approach in a meeting and overruling me. The disagreement and the full implementation are documented and real. The formal "boss disagrees, gets overruled, commits" scene isn't in the record, and I won't manufacture one — that half is labeled as a framework.

**Q: Why did you disagree with pin-count equality in the first place?**
**A:** Because pin count isn't a clean signal. A footprint is designed for a whole package family; an 8-pin SOIC footprint can legitimately host a 4-pin part with four no-connect pads. Literal equality treated normal hardware reality as an error, which is why it generated false alarms on boards with mixed component types. My preferred signal was reference designator combined with footprint name.

**Q: How did you commit without quietly sabotaging the direction?**
**A:** By implementing it at full strength and owning its weakness. I kept pin count in rather than disabling it, made it discriminating (larger → review, smaller → definite mismatch), added a component-type check and a configurable 2:1 ratio threshold, and built the debug override. I also documented out loud that the heuristic can produce false negatives — committing meant owning that the approach isn't perfect, not pretending it is.

**Q: Why keep the threshold configurable instead of hardcoding a value?**
**A:** Because the tool's decision shouldn't be an automatic final word. The 2:1 default came from the 20 test BOMs, but different board designs differ, so the threshold is configurable and the engineer can adjust it. The debug view puts the judgment where the domain expertise is.

**Q: What did the story teach you?**
**A:** That I'd assumed pin count was a reliable matching signal and it isn't; the better signal is reference designator plus footprint name. I also learned to gather more diverse test data up front — the issue only appeared with component types my initial test set didn't cover.

**Q: What if the decision had gone against you and you still disagreed strongly? (FRAMEWORK)**
**A:** State the counter-argument once, directly and privately, tied to specific data and customer/business risk. If the decision stands, implement it as if I'd made it and don't relitigate. If implementation surfaces a new material fact that wasn't visible when the call was made, raise it once with evidence, then respect the call. Half-committing is the worst outcome. That's a framework — the record doesn't show me losing that argument.
