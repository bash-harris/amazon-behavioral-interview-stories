## Answer (core, ~460 words)

I'll walk through the BOM reconciliation feature, because the customer input is what made it work.

The problem: manufacturing engineers verified every board by hand — cross-referencing the SAP-exported Bill of Materials against the Altium layout PDF, entry by entry. That was 20 to 30 minutes per board. I was building the tool that would do it automatically: upload two files, get a report of components missing, extra, or mismatched, in seconds, for users who are manufacturing engineers, not developers.

**Design.** I started with the external pieces rather than writing everything myself: XLSX.js to read the SAP Excel and PDF.js to parse the Altium layout PDF. I deliberately did not map cells by column position, because column positions shift between exports — the only reliable signal is the reference pattern itself (`/^[A-Z]+\d+$/`). That baseline handled roughly 70% of real BOMs. Then production data broke it one edge case at a time, and each fix became one small, isolated normalization stage: strip the `MP_` process prefix; recursively unwrap SAP's hyperlink cells (which XLSX.js hands back as objects, not strings); detect `DNP` so a intentionally-empty position is not reported missing.

The design decision that mattered most came from the customer, not from me. My parser treated variant references like `R1||R2` and `R1/R2` as invalid and silently dropped them. A manufacturing engineer told me what they actually mean: one physical position can accept either part depending on the board variant, so `R1||R2` should match either R1 or R2 — not be discarded. I could see the string; I could not see the manufacturing intent. That is exactly the kind of input you cannot infer from the data, and it reshaped the feature: I built a variant splitter that normalizes both separators, extracts the individual references, and treats each as a valid match target for that position.

**Implementation.** Each fix stayed a small, isolated preprocessing stage, so adding a case could not regress the others, and I backed the whole pipeline with a regression suite that grew to 15 representative production BOMs covering every edge case I had found. The suite runs in about two seconds, so I ran it after every change.

**Measured outcome.** Against those 15 production BOMs — different board variants and SAP export configurations — the parser produced zero false positives and zero false negatives, and a 2,000-component BOM parsed in under 200 milliseconds. The manual cross-reference that took 20 to 30 minutes per board now returns a report in seconds, and in the first week of production use the tool caught three real mismatches that manual review had missed.

What I'd do differently: collect representative BOMs from the floor and interview the engineers before writing the parser, instead of discovering each edge case as a production failure. The variant semantics came from a person — I should have gone to that person first.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why regex over positional parsing — isn't that fragile?**
**A:** Positional parsing is the fragile one here. The BOM is semi-structured: it has rows and columns, but the column positions vary between exports — references are in column A in some BOMs and column C in others. The only consistent signal is the shape of the text itself, so a pattern match is the robust choice. The alternative I considered was a config file of column mappings, and I rejected it because the users are manufacturing engineers, not developers — asking them to maintain mappings is a worse experience than a parser that just works. (`AMAZON_INTERVIEW_PREPARATION.md` STORY 1, lines 119, 143.)

**Q: How did you know the variant behavior was correct and not just convenient?**
**A:** The engineer was the authority on floor semantics — he was right and I changed the code. Then I proved it mechanically with a test matrix: `R1||R2`, `R1/R2`, `R1||R2||R3`, `R1/R2/R3`, and malformed cases like `||R1` and `R1/`. For each I verified the parser extracted the correct individual references and treated each as a valid match target. (STORY 1, lines 89, 131.)

**Q: What happens on a format you have never seen?**
**A:** The default is graceful degradation — anything that doesn't match the standard reference pattern is skipped rather than crashing the tool, and incomplete results beat errors for a non-developer user. But I'm explicit about the limit: a silent skip is data loss, so a later debug view exposed the raw entry and every parsing step so an engineer could flag a new format rather than have it vanish. I stopped at zero false positives / false negatives across 15 BOMs and don't claim I've seen every format. (STORY 1, line 135; STORY 11, line 1049.)

**Q: Does it scale, and what's the complexity?**
**A:** The main loop is O(n) over BOM entries; layout parsing is O(m); reconciliation is a set intersection, so the whole thing is O(n+m) — linear. A 2,000-component BOM parses in under 200 ms, which is effectively instant in the UI. (STORY 1, lines 97, 155.)

**Q: Where did the external ideas come from, concretely?**
**A:** Two external sources and one internal one. Externally, XLSX.js for parsing SAP's Excel export and PDF.js for the Altium layout — reusing libraries I didn't have to write. Internally, the manufacturing engineer who explained the variant semantics. The design that mattered most wasn't a library; it was the person with the floor knowledge, which is why I'd go to the users first next time. (STORY 1, line 87; `AMAZON_INTERVIEW_PREPARATION.md` STORY 4, line 411.)

**Q: What would you do differently?**
**A:** Collect representative BOMs from the manufacturing floor and interview the users before writing the parser. Every edge case here was discovered reactively, as a production failure, when a proactive sample set would have turned the first variant notation into a test case instead of an incident. (STORY 1, line 103.)
