# Q7 — tell me about a time you failed

**Mapped LP(s):** Earn Trust (primary); Learn and Be Curious; touches Deliver Results.

**Story used:** BGSW PCB Inspector Suite — the browser-compatibility failure in the standalone single-file deployment (`AMAZON_INTERVIEW_PREPARATION.md` STORY 4, "The Standalone HTML That Replaced a Server"). One telling only; the conflicting 150MB standalone telling in `AMAZON_INTERVIEW_PREP.md` STORY 7 is not used, and the 25MB distribution-barrier reflection is not blended in.

## Answer (core, ~430 words)

I failed a subset of the users I built something for. The PCB inspection suite ran on a Flask server, but the manufacturing engineers needed it on factory-floor machines with no internet, no software installs, and limited IT support. So I built a standalone version: one self-contained HTML file that embedded the libraries directly — OpenCV.js as a base64 WebAssembly module (about 8MB), TensorFlow.js (about 3MB), PDF.js (about 1MB), XLSX.js (about 500KB) — so an engineer could just double-click it. My compile script concatenated the HTML, CSS, and JS and base64-embedded the binaries.

My assumption was simple and untested: that the factory-floor machines ran modern browsers. They didn't, all of them. Some ran IE11. IE11 has no WebAssembly support, and OpenCV.js is a WebAssembly module, so on those machines the standalone build never loaded at all — not a partial failure, a total one. And those were exactly the machines the offline build existed to serve.

Here's the part I own: it wasn't a tricky bug that slipped through a test. It was an assumption about the deployment environment I never verified. My testing was on modern browsers, which is precisely why it didn't catch it — I had tested the environment I had, not the environment I was shipping into. I could point at the age of the machines or the IT setup, but the honest root cause is that I designed for "browser" in the abstract instead of for the actual fleet in front of me.

I couldn't fully fix it. Making the tools run on IE11 would have meant a complete rewrite — replacing the WebAssembly-dependent image pipeline with JavaScript fallbacks — and that cost wasn't justified for an end-of-life browser. So I did the honest version: I added a browser-compatibility check that runs at startup, detects the missing WebAssembly support, and shows a clear, specific message instead of failing silently, and I documented the minimum browser requirement. That turned a confusing dead end into an actionable one — the engineer knows immediately why it won't run and what's needed.

The lasting change is bigger than the check. I now verify the target environment before I build for it — the actual OS and browser, not the assumed one — and I put a capability check into anything that depends on a platform feature like WebAssembly or WebGL. It's the same lesson the BOM parser taught me about data: don't trust your assumptions about the environment you're deploying into; go look. Being curious about *why* IE11 failed — the WebAssembly capability gap, not "old browser, shrug" — is what turned a dead end into a guardrail.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why didn't you catch this before you built and distributed it?**
**A:** Because I tested on my own modern browser and never inventoried the floor fleet. The failure was in verification, not in code. I now start by confirming the target environment — OS, browser, and required platform capabilities — before I build for it.

**Q: Why not just rewrite it so it runs on IE11?**
**A:** The image pipeline depends on OpenCV.js, which is a WebAssembly module, and IE11 has no WebAssembly. A fallback meant replacing that pipeline with JavaScript implementations — effectively rebuilding the tool — for an end-of-life browser. The right call was to make the requirement explicit and gate it, not to spend weeks on a platform that was on its way out. I'd revisit that if a supported browser on the fleet had the same limitation.

**Q: What exactly does the compatibility check do?**
**A:** It runs at startup, tests for the platform capabilities the tool needs — WebAssembly for OpenCV.js — and if they're missing it shows a clear message naming the requirement instead of a blank page or a cryptic error. I also documented the minimum browser requirement so distribution was honest.

**Q: How is this different from an ordinary bug?**
**A:** A bug is code that doesn't do what I intended. This was code doing exactly what I intended, on an environment I had assumed rather than verified. The deeper failure was the assumption, not the implementation.

**Q: What changed in how you work after this?**
**A:** I verify the deployment environment before building for it, and I design a capability check into anything that depends on a platform feature like WebAssembly or WebGL. It's the same discipline the BOM parser taught me about data: don't assume, go look.

**Q: Did anyone still get value from the build?**
**A:** Yes. On modern-browser machines the standalone worked as designed — a single file, offline, no installs — and the compatibility check made the affected machines an explicit, understandable failure rather than a mystery. Being honest about the limitation was better than pretending the tool worked everywhere.
