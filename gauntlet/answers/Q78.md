# Q78 — tell me about a time you utilized customer feedback to drive improvement

**Mapped LP(s):** Customer Obsession (primary); Earn Trust; Learn and Be Curious.

**Story used:** BGSW PCB Inspector Suite — a chain of feedback loops, each cited to a single telling: **(1)** the engineers' trust/transparency feedback driving the `?debug=true` view and reconciliation dashboard (`AMAZON_INTERVIEW_PREPARATION.md` STORY 11, "Debug Endpoint for Manufacturing Transparency"); **(2)** the manufacturing engineer's variant-semantics correction driving the variant splitter (`AMAZON_INTERVIEW_PREPARATION.md` STORY 1, "The BOM Parser That Refused to Break"); **(3)** the prototype team's "no export" feedback driving export (`AMAZON_INTERVIEW_PREP.md` STORY 8, "Bias for Action — First Working Prototype"). No conflicting numbers are merged. Distinct from Q5 (stakeholder interaction), Q24 (Ownership of the transparency layer), and Q75 (the silent-drop mistake), which use the same events for different spines — here the spine is specific feedback → specific improvement → the trust/usage change.

## Answer (core, ~460 words)

The clearest feedback loop I can point to is the one that turned "we don't trust this tool" into a feature the manufacturing engineers actually relied on.

The product was the BOM reconciliation tool. It worked, but the engineers didn't fully trust it: when it flagged a mismatch, the report showed the verdict and hid the reasoning, so for anything that mattered they fell back to cross-checking by hand — which defeated the point of automating it. That was the feedback, and it was uncomfortable because it wasn't about a missing feature; it was about my tool's credibility.

I didn't ask them to trust it. I made it auditable. I built a `?debug=true` view that shows, per component, the raw BOM entry text, the parsed reference after every preprocessing step, the layout reference it was matched against, the comparison result, and the specific rule that fired — a step-by-step decision tree. I added a reconciliation dashboard with the aggregate picture first — total components, matches, mismatches, reviews, and the component-type distribution — so they could see the shape of a result before drilling into one component. The design rule was simple: if an engineer asks "why did the tool call this a mismatch?", the view has to answer completely, because any missing step just sends them back to me.

That turned the feedback loop two-way. In the first week, the engineers used the new view to surface two edge cases where my heuristic was wrong — both unusual naming conventions — and because the view exposed the intermediate data instead of just the verdict, those were quick to diagnose and fix. Then the behavior changed: once they could see how decisions were made, they were willing to rely on the results for production verification instead of re-checking by hand. That's the improvement I care about most, because trust, not accuracy, was the binding constraint.

The second loop was more direct. I had built the parser to treat variant references like `R1||R2` and `R1/R2` as invalid and silently drop them. A manufacturing engineer told me they actually mean one physical position can accept either part depending on the board variant, and the system should match either. I rewrote the parser — normalize both separators, extract each reference, treat each as a valid match target — and locked it with a regression suite that grew to 15 production BOMs. Against those, the parser reached zero false positives and zero false negatives, and a 2,000-component BOM parsed in under 200 milliseconds. In the first production week it caught three real mismatches that manual review had missed.

I'll add one more, because it shows the same habit early. The first working prototype's users found three gaps within an hour, one being that they couldn't save comparison results — so export became part of the roadmap and shipped. Getting feedback isn't the hard part; treating it as the specification is.

## Deep follow-ups (likely bar-raiser probes)

**Q: Which feedback mattered most, and why?**
**A:** The transparency feedback, because it was about adoption, not features. The tool could have been perfectly accurate and still failed if the engineers wouldn't trust it. Making the reasoning auditable moved them from re-checking by hand to relying on results for production verification — that's the change that made the tool actually get used. (`AMAZON_INTERVIEW_PREPARATION.md` STORY 11, lines 1057–1059.)

**Q: How did you know the improvement worked, and not just that you shipped it?**
**A:** Two signals. A concrete one: in the first week the debug view surfaced two edge cases where my heuristic was wrong, both unusual naming conventions, and they were easy to fix because the view showed the intermediate data. A behavioral one: the engineers stopped re-checking by hand and used the results for production verification. On the parser side, the measurable version was zero false positives and zero false negatives across 15 production BOMs, a 2,000-component parse under 200 ms, and three real mismatches caught in week one. (STORY 11, lines 1057–1059; STORY 1, lines 97, 99.)

**Q: How do you keep gathering feedback after launch?**
**A:** I made the debugging tool a feedback channel rather than just a viewer — the engineers used it to find cases the heuristic got wrong. The same pattern showed up on the AI feature: I added a mechanism for engineers to mark AI analyses correct or incorrect, which surfaced systematic prompt errors I could fix. Feedback only counts if there's a path from the user back into the code. (`AMAZON_INTERVIEW_PREPARATION.md` STORY 8, line 829.)

**Q: What about feedback you can't act on immediately?**
**A:** I prioritize it rather than dropping it. The prototype users found three issues in the first hour — alignment, illumination, and export — and I fixed them in order of impact: alignment first, illumination second, export third as the nice-to-have. Being explicit about the order is part of using the feedback honestly instead of pretending everything is urgent. (`AMAZON_INTERVIEW_PREP.md` STORY 8, line 325.)

**Q: How do you avoid over-fitting to one loud customer?**
**A:** I anchor changes in evidence, not volume. The pin-count and variant corrections were validated with a regression suite of 15 production BOMs and explicit false-positive/false-negative measurements, and the configurable threshold keeps the judgment with the user rather than hard-coding one person's preference. (`AMAZON_INTERVIEW_PREPARATION.md` STORY 10, lines 959–961, 995; STORY 1, line 93.)

**Q: What would you do differently?**
**A:** Build the transparency layer from the beginning instead of as an afterthought, and collect representative BOMs and talk to the engineers before writing the parser. Both are the same lesson: get the customer's real artifacts and feedback in front of me earlier, because in both cases the input that mattered most came from a person, not the data. (STORY 11, line 1063; STORY 1, line 103.)
