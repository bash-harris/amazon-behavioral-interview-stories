## Answer (core, ~450 words)

The deadline I have in mind is the final milestone of the PCB inspection suite: the standalone, offline single-file build. It was the weeks-seven-and-eight work of an eight-week delivery, so everything built before it had to be correct inside one artifact — and it was the last thing standing between the manufacturing engineers and a tool they could actually run.

The temptation at that stage is to ship the build you just made. Compilation took about eight seconds on average — closer to twelve worst case, because OpenCV.js at about 8 MB is the bottleneck — and the file already opened in my browser. Every recompile felt low-risk. So I set a rule: no build went out unless it had passed the regression harness, and I ran the harness after every compilation, not just the last one.

The harness was not a spot check. It pushed the same 15 BOM files and 10 board images through both the server version and the freshly compiled standalone version, and compared the three things that mattered: the reconciliation reports had to match exactly, alignment had to be within one pixel, and the ML classifications had to be identical. Any difference meant a compilation bug — a file inlined out of order, a library embedded wrong, a path not resolved — and those are exactly the failures that only surface when a manufacturing engineer opens the file on the floor, not on my dev machine. If any test failed, that compilation was rejected.

That is why I kept paying the cost while the deadline was close. A failure at that point wasn't just a bug; it was an offline artifact someone had already put on a USB stick. The harness was the only thing that let me say "this build is the same product as the tested server version" rather than "this build opens."

The result: the standalone file, about 25 MB with roughly 12.5 MB of embedded libraries, loaded in about five seconds on a factory machine versus two for the server version, and ran the full suite — BOM parsing, layout comparison, alignment, ML inference, auto-save. The engineers double-clicked it with no Python install, no network setup, and no IT ticket. I distributed it by email and USB.

What I'd do differently is harden the verification itself: I would have added a checksum on the compiled output and a diff mode between two compilations, so a corrupted or silently changed build gets caught by the tool instead of by the harness or by me. The call I'd defend is refusing to treat the final build as exempt from the test — a near deadline was the reason to verify more, not less.

## Deep follow-ups (likely bar-raiser probes)

**Q: What exactly did the harness compare?**
**A:** Three outputs, run through both the server and standalone versions on the same 15 BOM files and 10 board images. The reconciliation reports had to match exactly, the alignment had to be within one pixel, and the ML classifications had to be identical. Any mismatch indicated a bug in the compilation, not noise — so the tests were pass/fail, with no tolerance to argue about.

**Q: How can a compilation fail silently enough that you'd need this?**
**A:** The compiler concatenates HTML, CSS, JS, and libraries, inlines them, base64-encodes binaries, and resolves relative paths. Get the ordering wrong — CSS after the HTML that uses it, business logic before the utility it calls — or miss a file, and the standalone build breaks only when something specific is exercised. On my machine the page might still open; on a factory machine a feature just wouldn't work. The harness exercised the whole tool, not the landing page.

**Q: Why every compile, and not once at the end?**
**A:** Because the artifact was rebuilt repeatedly while I fixed the rest of the suite, and each rebuild could change the inlining order or a path. Running the harness only at the end would let several regressions pile up with no clean point to bisect them. It was cheap relative to a bad offline artifact, so I ran it every time.

**Q: Wasn't that slowing you down right at the deadline?**
**A:** The eight-second build and the harness were a small cost compared with the downside. If a bad build reached an engineer, they had the worst possible debugging environment — no internet, no install tools, restricted IT — so a defect there was far more expensive to resolve than a two-minute delay in my pipeline.

**Q: Where did the "within one pixel" tolerance come from?**
**A:** The comparison pipeline runs on a 10-pixel mismatch threshold, so if alignment drifted by even a pixel or two between builds, the mismatch output could change and the report would no longer be comparable. Reports had to be exact and classifications identical; alignment was the one metric with a tiny numeric tolerance, and I set it at one pixel.

**Q: What was the specific risk you were guarding against?**
**A:** An engineer getting a broken offline build after the server version had passed — with no straightforward way to debug it on the floor, and with me distributing by email and USB, so an untested build could spread. Verifying before submission was the only control I had over that.

**Q: What would you change?**
**A:** Add a checksum to the compiled output and a diff mode between two compilations. Both are named in the source reflection and neither was built; a checksum would catch corruption and the diff would show exactly what changed build-to-build.
