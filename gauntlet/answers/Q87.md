## Answer (core, ~500 words)

The application was my browser extension's AI command layer, and the performance problem was that every command took the most expensive path available.

The pipeline took a natural-language command — "group my coding tabs," "close duplicate YouTube tabs" — queried every open tab, extracted the full text of each page one at a time, and sent the whole pile to Gemini or Ollama. On a 50-tab window that was roughly 50,000 tokens per command, about eight seconds of latency, around $0.50 a query, and no path at all when offline. The defining characteristic was that it was blind to the command: a trivial request and a hard one paid exactly the same cost.

The dive was to measure where the time and the tokens actually went. The instinct was to blame the model, but the measurement said otherwise. The model was fast; I was feeding it everything. Sequential extraction was about five seconds on its own, the payload was enormous, and most commands were simple patterns that never needed a model in the first place. The expensive resource wasn't the inference — it was the work I was doing before inference.

So I optimized in four measured layers. First, a local rule engine in front of both backends: commands with predictable shapes — group, close, bookmark, pin, or mute a named site, find duplicates, cluster by domain, find inactive tabs — are matched and executed on the machine with zero API calls. Simple commands went from about two seconds and 5,000 tokens to roughly 10 milliseconds and zero tokens. Second, a smart pre-filter that runs before any extraction: it maps the query against a fixed category ontology and a keyword score, then keeps only the relevant slice — 50 tabs down to 8 in the guide's own example, capped at the top 30% with a floor of five. It costs no tokens and runs sub-millisecond. Third, parallel extraction in batches of ten instead of sequential: extraction dropped from about five seconds to about half a second, roughly 10x. Fourth, triplet compression — reduce each page to `[subject, predicate, object]` triples and send a minimal prompt listing only the filtered tabs. A 50-tab complex command fell from about 50,000 tokens to roughly 3,000, about a 94% reduction, and from about eight seconds to about three, at roughly $0.03 instead of $0.50.

The Invent-and-Simplify half is that the work is now bounded by the filtered set, not by the total tab count: the pre-filter caps its output, extraction runs concurrently, and the payload stays small. The Deliver Results half is a new capability — with the rule path handling the predictable commands, roughly 70% of queries now work with the network off.

I present those figures as the guide's projected gains, not as numbers I re-benchmarked, because that's how the source labels them. What I'd change is the order I worked in: I optimized before I had an observability view showing tokens and latency per stage. I'd instrument first now, so every change has a measured before and after instead of a designed one.

## Deep follow-ups (likely bar-raiser probes)

**Q: How did you find the real bottleneck?**
**A:** By measuring the path, not the output. The model was the visible cost, but the measurement showed the work in front of it: every command queried all tabs and extracted full page text sequentially, and simple commands that needed no model paid that same cost. Sequential extraction was about five seconds alone.

**Q: Are those before/after numbers measured or estimated?**
**A:** The guide labels them "Expected Performance Gains," so I present them as projected. The mechanisms are implemented — the rule path genuinely makes zero API calls, the pre-filter genuinely shrinks the set before extraction, and extraction genuinely runs in parallel batches. I won't dress projected figures as measured.

**Q: How does the pre-filter decide relevance without calling the model?**
**A:** Deterministically. It matches the query against a fixed category-to-domain map and scores keywords on titles and URLs, keeps the scoring tabs, then returns the top ~30% capped between five and thirty. If nothing scores, it falls back to the full tab set.

**Q: Why a local rule layer instead of just a faster model?**
**A:** Because most commands don't need a model, and using one for them costs latency, money, and privacy. "Close all youtube tabs" is a pattern match. Routing the predictable work locally makes the common case about 10ms and zero tokens, and reserves the model for genuinely ambiguous commands.

**Q: How does this hold up as the user opens more tabs?**
**A:** The expensive steps are bounded by the filtered set, not the total. The pre-filter caps its output, extraction runs in concurrent batches of ten, and the compressed payload stays small — so a 50-tab window doesn't cost what a 5-tab window costs on the AI path.

**Q: What would you optimize next?**
**A:** Instrument first, then extend. I'd add per-stage token and latency telemetry so every change has a measured before and after, then move the pre-filter from keywords to local embeddings and add a client-side WebLLM for fully offline semantic work — the guide's Phase-2 path.
