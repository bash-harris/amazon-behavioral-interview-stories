## Answer (core, ~480 words)

The project I'd call exceptional was making the entire PCB inspection suite run with no server at all — one HTML file an engineer double-clicks, fully offline, on factory-floor machines that had no internet, no permission to install software, and limited IT. What made it exceptional wasn't a single feature; it was the direction. I deleted the server architecture and committed a computer-vision and machine-learning suite to one self-contained document.

The suite had started on a Flask backend, and the easy path was to keep polishing deployment. I argued the opposite: the tool had to run where the engineers actually worked, or it was a demo. That meant every library had to travel inside the file. OpenCV.js is about 8MB, TensorFlow.js about 3MB, PDF.js about 1MB, and XLSX.js about 500KB — roughly 12.5MB that could not come from a CDN. OpenCV.js is the hard one: it's a WebAssembly module that normally fetches a separate `.wasm` file. I embedded the WASM binary as a base64 data URL and rewrote the loader to decode it into an `ArrayBuffer` at runtime, because `WebAssembly.instantiate` accepts a buffer directly — no network. TensorFlow.js inlined cleanly, and I embedded the model weights as a JavaScript constant. Auto-save moved off the server filesystem onto `localStorage`, with a 5MB quota check that warns the user and garbage-collects old inspections. The finished file is about 25MB and loads in roughly five seconds on a factory machine versus two on the server version.

The exceptional part for me is that I didn't let "it opens" stand in for "it's correct." I held the standalone to the same bar as the server version: a regression harness pushed the same 15 BOM files and 10 board images through both and required the reconciliation reports to match exactly, alignment to be within one pixel, and the ML classifications to be identical — and I ran it after every compilation, not just at the end. I also turned the build itself from a manual 30-minute process that broke about one time in five into an 8-second script with zero errors.

It shipped, and it was used. BOM parsing, layout comparison, image alignment, ML inference, and auto-save all worked identically. I distributed it by email and USB, so the engineer's workflow became double-clicking one file — no Python install, no network configuration, no IT ticket. It reached 15 manufacturing engineers across two sites, saving roughly 20 hours a week across the team. A full inspection suite, in people's hands, with zero infrastructure behind it.

Two honest notes. At about 25MB the file ran into 20MB email limits — gzip could have brought it near 15MB — and some machines still ran IE11, which can't run WebAssembly, so I added a compatibility check rather than a rewrite. And architecturally I should have designed for standalone from the start instead of retrofitting it out of a server build.

## Deep follow-ups (likely bar-raiser probes)

**Q: What exactly is "exceptional" here? A standalone HTML file doesn't sound exotic.**
**A:** The output is mundane; the constraints weren't. The product is a computer-vision and ML inspection suite that normally needs a server and a GPU. It runs on machines with no internet and no install rights, from one file, with the entire stack — OpenCV WASM, TensorFlow.js, model weights, PDF and XLSX parsing — embedded. That's the exceptional part: full capability where the environment allowed none.

**Q: How is this different from just packaging an app?**
**A:** Packaging assumes a runtime. Here there was no runtime to assume — no Python, no server, no network. OpenCV.js had to be rewritten to instantiate WebAssembly from a base64 data URL, the model weights had to become a JS constant, and auto-save had to move to a 5MB `localStorage` with quota handling. Every dependency was a design problem, not a bundling step.

**Q: You said you held the standalone to server parity — how?**
**A:** A test harness ran the same 15 BOM files and 10 board images through both the server and the compiled standalone versions and compared outputs: reconciliation reports had to match exactly, alignment had to be within one pixel, and ML classifications had to be identical. I ran it after every compilation, and any failure rejected that build. (STORY 4 follow-up, line 463.)

**Q: What did it cost you, and was it worth it?**
**A:** Roughly 12.5MB of libraries grew to about 25MB after base64 encoding, startup gained about two seconds for the WASM decode, and the file bumped into a 20MB email cap. The payoff was that the tool actually ran and got adopted — 15 engineers across two sites, about 20 hours a week saved. A faster file nobody could open would have been worth nothing.

**Q: Where did the eight-week figure and the adoption numbers come from?**
**A:** The suite was delivered within an eight-week window, with the standalone compilation in the final weeks. Adoption was 15 manufacturing engineers across two sites, roughly 20 hours per week saved. (`AMAZON_INTERVIEW_PREP.md` STORY 12, lines 466, 481–482.)

**Q: What would you do differently?**
**A:** Compress the embedded libraries harder — gzip could take it near 15MB — and design for standalone from day one instead of retrofitting it out of a server build. I'd also have checksummed the compiled output and added a diff mode between builds so corruption is caught by the tool, not by me. Those are process fixes; the direction I'd defend.

**Q: Did you consider alternatives to one big file?**
**A:** Yes. Separate library files break the single-file guarantee — move one and the tool dies, the exact failure mode I was removing. A service worker needs HTTPS to register and carries browser-compatibility risk on those machines. Base64 in one file adds about 33% size but removes every external dependency. (STORY 4 follow-ups, lines 439, 471.)
