# Q3 — tell me about a time you used genai to solve a business problem and what measurable result it delivered

**Mapped LP(s):** Deliver Results (primary); Invent and Simplify; touches Customer Obsession.

**Story used:** BGSW PCB Inspector Suite — GPT-4o VLM inspection engine (`AMAZON_INTERVIEW_PREPARATION.md` STORY 8 "Adding an AI Eye to the Inspection"). Documented measurable result is for the server version: manual mismatch interpretation from about 30 seconds to about 5 seconds per mismatch, at roughly 85% accuracy. The conflicting telling in `AMAZON_INTERVIEW_PREP.md` STORY 3 ("92% accuracy on 100 board pairs") is deliberately not used.

## Answer (core, ~490 words)

The business problem was on the manufacturing floor, not in my editor. I built the PCB inspection suite at Bosch: tools that compare a photograph of a board against its CAD layout and highlight every mismatch in red. But the tool could only say *where* the mismatch was. It couldn't say what it *meant*. Every red region became a manual task — zoom in and decide whether it's a wrong-value part, a component rotated 180°, or just a reflection off a solder joint. That took about thirty seconds per mismatch, and a typical board flags five to twenty of them. That interpretation step was the bottleneck in verification: slow, and resting entirely on each operator's judgment. I was the only developer on the suite, and my job was to delete that step.

I added a vision-language model as the inspection engine: it reads the flagged region, identifies the component, classifies the mismatch — wrong value, wrong orientation, missing, extra, or false alarm — and returns a confidence. The constraint was business-real: under five seconds per analysis, and accurate enough to be worth the operator's attention.

I chose GPT-4o. I evaluated GPT-4V, which was slower — about eight seconds per request versus three for 4o; Claude 3, whose API was less mature at the time; and Gemini Pro Vision, which was weak on small SMD parts. GPT-4o had the best balance of accuracy, speed, and API availability, and it handles image and text in one request. I used it as the "expert eye" rather than training a custom vision model — a bespoke classifier would have been a labeling-and-training project on top of the load I was already carrying, and it would need data for every defect type. My engineering went into the pipeline: crop the region from both the layout and the photo, send both with a structured prompt, and parse a JSON reply with `component_type`, `mismatch_type`, `confidence`, and `description`.

My first prompt failed. "Describe what you see and compare it to the expected layout" returned verbose, inconsistent answers — sometimes background, sometimes the part. I rewrote it to force the fixed JSON schema and added examples for the common mismatch types. That's when it became reliable.

The measured result: on the server version, manual interpretation went from about thirty seconds per mismatch to about five — essentially the API response time — at roughly 85% accuracy on component type and mismatch type. The other 15% were images too poor or components too small to read reliably. On a board with ten mismatches that is roughly five minutes of interpretation down to under a minute — arithmetic from the documented 30s→5s per mismatch and the documented 5–20 mismatches per board, not a separately measured figure — at about a cent per analysis. On deployment I want to be precise: the VLM ran in the server version, where there is API access. The offline standalone HTML file the factory floor used does not use the VLM feature — no model, no API key — so this was a server-side capability, and the deterministic four-signal comparison stayed the core. I did this while delivering the rest of the suite: all three comparison tools shipped within eight weeks and were adopted by 15 engineers across two sites. The engineers told me the AI helped them prioritize which mismatches to investigate first, especially on dense boards.

Reflection: I was wrong that the model could read values off small surface-mount parts — the text is too small, and it's much better at type and orientation. Next time I'd start with the simple structured prompt instead of over-engineering the first one.

## Deep follow-ups (likely bar-raiser probes)

**Q: How is this a business result and not just a cool technical demo?**
**A:** The cost was operator time on a required verification step — manual interpretation was the documented bottleneck in verification. At about thirty seconds per mismatch and five to twenty mismatches per board, a ten-mismatch board cost roughly five minutes of operator interpretation; after, it's under a minute, and each analysis costs about a cent. The engineers used it to triage dense boards first, which is the throughput win: the slowest boards stop being the slowest part of the day.

**Q: 85% sounds low. Why is that acceptable, and how is the result trustworthy?**
**A:** The model is a first-pass classifier, not the decision. The UI labels it "AI Analysis" with a confidence percentage, and the engineer verifies it — the human was always in the loop. It's right on component type and mismatch type about 85% of the time; the other 15% are images too poor or components too small to analyze reliably. It moves human attention from interpretation to judgment, and I added a feedback mechanism so engineers can mark analyses correct or incorrect, which surfaces systematic prompt errors instead of hiding them.

**Q: What does this cost at scale, and where would you not use the model?**
**A:** I only send the regions the comparison already flagged, so cost and latency scale with mismatches — five to twenty per board — not with component count. About $0.01 per analysis, so roughly $0.10 for a ten-mismatch board. I would not put a VLM on every component: five hundred components across a thousand boards a day would wreck cost, latency, and auditability, because you can't reproduce a verdict from a hosted model version months later. The deterministic four-signal comparison stays the core. A cost-aware cascade that escalates only the hard cases to the model is a design target I'd want, and I want to be clear it's designed, not built.

**Q: Why GPT-4o rather than a purpose-built vision model you control?**
**A:** I evaluated GPT-4V (about eight seconds per request versus three), Claude 3 (strong visual understanding, but its API was less mature at the time), and Gemini Pro Vision (fast but weaker small-object detection, which matters for SMD parts). GPT-4o had the best balance of accuracy, speed, and API availability, and it handles image and text in a single request, which simplified the integration. A custom classifier meant labeling data and training per defect type, then retraining whenever a new defect appeared — real work with real maintenance, for a task where reusing an existing "expert eye" was simpler and more general. A self-hosted VLM like LLaVA is the alternative I'd weigh if API cost or privacy became the binding constraint — the source raises it only as a future option for a more sensitive environment, not something I evaluated or ran, and it needs a GPU with at least 8GB VRAM the factory floor machines don't have.

**Q: Where did the design ideas come from, inside and outside the company?**
**A:** Outside: the model landscape — GPT-4o, GPT-4V, Claude 3, and Gemini Pro Vision — plus the browser CV stack, OpenCV.js and TensorFlow.js, that already powered the tools. Inside: I sat in on the engineers' screen-sharing sessions before writing anything so the AI matched how they actually compared boards, and I walked the data question through the security team, who approved sending board photos because they contain no trade secrets.

**Q: What happens when the API is down, and what would you do differently?**
**A:** The VLM is an enhancement, not a dependency. If the API is unreachable, the comparison still runs, the visual highlights still show, and the UI says "AI analysis unavailable — check API connection," and the engineer falls back to the manual check. That fallback describes the server experience; the offline standalone file does not use the VLM feature at all. Differently: start with the simple structured prompt instead of the clever one, and weigh a self-hosted option — LLaVA-class, needing ≥8GB VRAM the factory floor doesn't have — if per-call cost became the constraint. That last part is a future consideration, not something I built or benchmarked.
