## Answer (core, ~450 words)

Straight answer first: I made a data-loss mistake in the BOM reconciliation pipeline, and it stayed invisible until a user caught it. The pipeline reads a SAP-exported BOM spreadsheet, extracts every component reference, and reconciles it against the Altium layout. I built the first version on a strict reference pattern — letters then digits — and I made anything that didn't match that pattern get silently skipped. That default was the mistake.

Here's what it cost. Some boards use variant notation: `R1||R2` means two components share one physical position, and `R1/R2` is the same idea with a different separator. My parser treated those as invalid strings and dropped them, so a position that should have been reconciled simply vanished from the report. That's the worst kind of data-quality bug: the output looks clean, because a report only lists what it parsed. A missing component doesn't announce itself — the reconciliation said "no problem" where the truth was "I never looked at this." A manufacturing engineer found it, not me, and that's the part I own.

I didn't explain it away. The BOM wasn't malformed and the notation wasn't wrong; my parser was wrong, and my silent-skip default was the root cause. So I fixed both the feature and the default. I built a variant splitter that normalizes both `||` and `/`, extracts each individual reference, and treats each one as a valid match target for that position — so `R1||R2` matches either part instead of disappearing. Then I proved it instead of eyeballing it: a test matrix of `R1||R2`, `R1/R2`, `R1||R2||R3`, `R1/R2/R3`, and malformed cases like `||R1` and `R1/`. Every case went into a regression suite that grew to 15 representative BOMs, which I reran after every change so fixing one format couldn't break another.

The result: in testing against 15 production BOMs the parser produced zero false positives and zero false negatives, and a 2,000-component BOM parses in under 200 milliseconds. The manual cross-reference that took 20 to 30 minutes per board now returns a report in seconds, and in the first production week it caught three real mismatches that manual review had missed. The rule I took from it and apply now: never let a pipeline silently discard an input it doesn't understand. Surface it. An incomplete result that looks complete is more dangerous than a failure that announces itself.

What I'd do differently is upstream of the code: collect representative files from the floor before writing the parser, so the first variant notation is a test case instead of a production incident.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why did the parser skip invalid entries instead of failing?**
**A:** Because I designed for graceful degradation — the users are manufacturing engineers, not developers, and I didn't want an unknown format to crash the tool. That instinct was right at the wrong granularity. Skipping one unparseable cell is acceptable; silently dropping a component reference is data loss. The correct behavior is to report what it couldn't parse, not discard it.

**Q: Walk me through the variant fix.**
**A:** Normalize both separators — `||` and `/` — split on whichever is present, extract each individual reference, and treat each as a valid match target for that position. So `R1||R2` matches `R1` or `R2` in the layout. I locked it down with a matrix covering double and triple variants and malformed cases (`||R1`, `R1/`), and ran it after every change.

**Q: How did you prevent the same class of bug from coming back?**
**A:** A regression suite that grew to 15 representative BOMs, rerun after every change; each new production failure became a new case. It runs in about two seconds, so there was no friction in using it constantly. And the rule for new formats is to surface them rather than skip them.

**Q: Is this really a "data pipeline" mistake?**
**A:** Honest answer: no, not in the streaming/warehouse sense. It's a structured-document reconciliation pipeline — SAP Excel plus Altium layout — not an ETL job over event streams. But the failure is the same class: an unhandled input silently dropped, producing a complete-looking but wrong result. The fix — fail loud, test the formats, regression-lock them — is the same, which is why I'm answering with it rather than inventing a pipeline incident.

**Q: How do you know there aren't more silent drops?**
**A:** I don't claim completeness. I stopped when false positives and false negatives both hit zero across 15 production BOMs, and I added a `?debug=true` view that shows the raw BOM text and every parsing step, so an engineer can see exactly what the parser did and flag a format I haven't seen. That view is the safety net for the next unknown format.

**Q: What's the general principle you carry from this?**
**A:** Two. Never normalize an input without understanding its semantics — for example, I don't strip dots, because a dot can be a meaningful sub-component. And never let an input the system doesn't understand disappear; make it visible. Complete-looking output built on silent drops is the most dangerous thing a data path can produce.

**Q: What would you do differently?**
**A:** Collect representative BOMs from the manufacturing floor before writing any code. I found these edge cases reactively, each one a production failure; a proactive sample set would have made the variant notation a test case on day one.
