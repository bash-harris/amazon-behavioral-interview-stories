# Q29 — a time when you had a blocker in your work and how did you resolve that blocker?

**Mapped LP(s):** Bias for Action (primary); Deliver Results.

**Story used:** `AMAZON_INTERVIEW_PREPARATION.md` STORY 4, "The Standalone HTML That Replaced a Server" — specifically the OpenCV.js / WebAssembly loading blocker in the standalone single-file build. One telling only: STORY 4's numbers (OpenCV.js ~8MB, TF.js ~3MB, PDF.js ~1MB, XLSX.js ~0.5MB, ~12.5MB embedded libraries, ~25MB single HTML, ~5s vs 2s load, +~2s for the base64 WASM decode). ## Answer (core, ~450 words)

The clearest blocker was getting OpenCV.js to run inside the standalone single-file build of the PCB inspection suite. It stopped the whole deliverable: the file compiled, the UI loaded, and the image alignment and comparison — which is the actual product — never initialized.

Here is the setup. The tools had to run on factory-floor machines with no internet, no installs, and limited IT support. The original build used a Flask backend, but Python installation, dependency management, and network configuration were beyond what the manufacturing team could handle, so I was compiling everything into one offline HTML file with my `compile_tool.py` script. The suite depended on OpenCV.js for alignment, and OpenCV.js is a WebAssembly module: the loader fetches its `.wasm` binary separately from a file, normally over the network. In the server build that is fine. In a single offline file there is nothing to fetch from. The library would load its JavaScript, then fail to instantiate the WASM module, and the pipeline was dead.

The diagnosis was the loader's transport, not the library. OpenCV.js asks the browser for the `.wasm` file via XMLHttpRequest. Offline, that request has nowhere to go. Shipping a folder of files was not an option either — the whole point was one file the engineers could double-click, because a second file that gets accidentally moved breaks the tool.

I unblocked it by removing the network fetch entirely. I embedded the WASM binary as a base64 data URL inside the HTML, then modified the OpenCV.js loader to decode it at runtime. The key is that `WebAssembly.instantiate()` accepts an ArrayBuffer directly, so once the base64 is decoded there is no fetch, no network, and no separate file. I applied the same approach to TensorFlow.js — inlined the minified bundle and stored the model weights as a JavaScript constant instead of a sidecar file.

That cost about two seconds of initial load, and I took it deliberately: a slower cold start was worth an offline tool that actually worked. I also made sure it was not just "it runs." A test harness pushed the same 15 BOM files and 10 board images through both the server and standalone versions and compared the outputs: reconciliation reports matched, alignment was within a pixel, and classifications were identical.

The result was a roughly 25MB single HTML file — the embedded libraries total about 12.5MB, with OpenCV alone around 8MB — that loads in about 5 seconds on a factory machine versus 2 for the server version. The engineers could open it by double-clicking, with no Python install, no network setup, and no IT ticket. I distributed it by email and USB drive.

What I would do differently: compress the embedded libraries harder. At 25MB it ran into a 20MB email attachment limit, and gzip could have brought it closer to 15MB.

## Deep follow-ups (likely bar-raiser probes)

**Q: What exactly was the blocker?**
**A:** OpenCV.js is a WebAssembly module whose `.wasm` binary is fetched separately at load time. In the single offline HTML file there was nothing to fetch it from, so the module never instantiated and the alignment/comparison pipeline — the core of the tool — would not start.

**Q: How did you diagnose it?**
**A:** I separated the library load from the WASM instantiation and saw the JavaScript load succeed while the WASM step failed. Reading the loader, the `.wasm` is requested via XMLHttpRequest; offline, that request has no target. So the problem was the transport, not the library or my code.

**Q: Why base64 and not separate files, or a service worker?**
**A:** Separate files break the single-file requirement — if one gets moved, the tool dies, which was the exact failure mode I was eliminating. A service worker needs HTTPS to register and adds browser compatibility risk on the factory machines. Base64 adds about 33% encoding overhead but removes every external dependency, which was the right trade here.

**Q: What did the fix cost?**
**A:** About two seconds of initial load for the WASM decode, the ~33% base64 overhead across roughly 12.5MB of libraries, and a final file of about 25MB loading in about 5 seconds on a factory machine versus 2 seconds for the server version.

**Q: How did you verify the standalone build was functionally identical?**
**A:** A test harness ran the same 15 BOM files and 10 board images through the server and standalone versions and compared reconciliation reports, alignment accuracy (within one pixel), and ML classifications. Any difference would have been a compilation bug, so I ran it after each compile.

**Q: When is a blocker yours to solve versus something to escalate?**
**A:** When it stands between the users and the deliverable and I have a real path to it, it is mine. This one was in my own build pipeline, the constraint was immediate, and I could test the fix directly — so escalating would only have added delay.

**Q: What would you do differently?**
**A:** Compress more aggressively. The 25MB file bumped into a 20MB email attachment limit, and gzip on the embedded libraries could have brought it closer to 15MB — a distribution problem I accepted when I did not have to.
