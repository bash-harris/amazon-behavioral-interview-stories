# Q15 — a time when you help your friend or co-worker

**Mapped LP(s):** Earn Trust (primary); Hire and Develop the Best, SDE-1 scope (coaching/enablement — noted honestly, not as formal management).

**Story used:** BGSW PCB Inspector Suite — helping the manufacturing engineers become self-sufficient on the BOM reconciliation tool (`AMAZON_INTERVIEW_PREPARATION.md` STORY 11 "Debug Endpoint for Manufacturing Transparency", plus the shared-UX enablement in STORY 5). The counterpart is a documented stakeholder group — the manufacturing engineers — not a friend or teammate; see the honesty note. Angle differs from Q6, which used the same debug view for stakeholder influence, not for helping/enablement.

## Answer (core, ~400 words)

I'll be precise about the relationship, because it matters here. I built the PCB inspection suite solo — there was no colleague on my team — so the people I helped were the manufacturing engineers who used it. I don't have a mentee I can honestly point to. But the help was real, and it was the kind that sticks: I made them independent of me.

The problem was trust held together by dependency. The BOM reconciliation tool would flag a mismatch, and the engineer couldn't see why. So they either distrusted the result or came to me to explain the tool's reasoning. Either way they couldn't verify it themselves, and I was in the loop for every question. That isn't a tool — it's a ticket queue with my name on it.

So what I built for them was a `?debug=true` view. For every component it shows the raw BOM text, the parsed reference after each preprocessing step — prefix stripping, hyperlink extraction, variant splitting — the matched layout entry, the comparison result, and the exact rule that fired. Plus a reconciliation dashboard with the aggregate stats: totals, matches, mismatches, reviews, and component-type distribution. The principle I set was simple: if an engineer asks "why did the tool decide this," the debug view should answer it completely. If any step were missing, they'd have to ask me — which would defeat the point of building it.

I also lowered the learning cost across the suite. I kept the UX identical on all three tools — same drag-and-drop, same color coding, green match, red mismatch, blue unknown — so an engineer who learned one tool had effectively learned all three. And I added a correct/incorrect control on the AI analysis, so their expertise flowed back into the tool instead of stopping at my desk.

The outcome I care about is that they stopped needing me. In the first week they used the debug view to find two edge cases with unusual naming conventions and reported them; I fixed both. The transparency moved them from hand-verifying every result to relying on the tool for production verification. That's what helping looks like to me — not doing it for someone, but getting them to where they can do it themselves. On the development LP: I didn't manage anyone's career and wouldn't claim to. But the growth I invested in was real.

## Deep follow-ups (likely bar-raiser probes)

**Q: The question says friend or co-worker — was there really one?**
**A:** No teammate or friend is documented — it was a solo project. The people I helped were the manufacturing engineers using the tools. I'd rather tell you that plainly than invent a colleague. The helping behavior is what's documented; the relationship label isn't what I'm claiming.

**Q: How is building a debug view "helping a co-worker" rather than just building a feature?**
**A:** Because the design goal was explicitly to remove me from the loop. The stated principle was that if any step were missing, the engineer would have to ask me, which defeats transparency. The feature's purpose was their independence, not my convenience — that's the difference between helping and being needed.

**Q: Did you actually develop anyone's skills, or just hand them a screen?**
**A:** I won't overclaim it as formal coaching — there were no direct reports. What I did was lower the skill needed to use the tools (identical UX across all three, so learning one covered all three) and raise the engineers' ability to verify the tool's reasoning themselves. That's skill transfer in the practical sense: they could diagnose problems I would otherwise have owned.

**Q: What did you learn from them?**
**A:** They found two edge cases in unusual component naming in the first week using the debug view, and both were real gaps in my logic. That's the return on helping people see your work: their domain knowledge surfaced failures my own testing missed.

**Q: How did you know the help actually landed?**
**A:** Behavior change. They went from hand-verifying every result to relying on the tool for production verification, and they were diagnosing and reporting edge cases instead of asking me what a result meant. Both are visible in the first week.

**Q: What would you do differently?**
**A:** Build the transparency view from day one. It was an afterthought, and the trust gap was predictable — if I'd designed enablement into the product instead of adding it after skepticism, the engineers would have gotten there faster and I'd have caught the edge cases earlier.

**Q: If you had a real junior teammate, how would you coach them?**
**A:** Same principle, applied to code: give them the reasoning, not the answer — walk the decision path, let them reproduce the failure and propose the fix, and review the fix against the evidence. The debug view is the tool version of that; with a person it's pairing on the reproduction. I haven't managed a junior engineer, so I'd treat this as how I'd approach it, not something I've already done at scale.
