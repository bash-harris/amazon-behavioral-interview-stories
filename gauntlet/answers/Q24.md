## Answer (core, ~450 words)

The example I keep coming back to is the transparency layer on the BOM reconciliation tool.

The assigned deliverable was the reconciliation engine itself â€” the code that compares the bill of materials, the CAD layout, and the physical board and prints a verdict for every component. That engine worked. What wasn't in the brief was the part I took on anyway: getting the manufacturing engineers to actually trust it.

They used the tool, but they didn't believe it. When it flagged a mismatch, they couldn't see why â€” the report showed the conclusion and hid the reasoning. So for anything that mattered, they fell back to checking by hand. A verdict nobody trusts has no value, and that was an adoption problem, not a coding task. I decided it was mine to solve.

I started with a debug view behind a `?debug=true` URL parameter, tucked out of the normal UI. For each component it shows the raw BOM entry text, the parsed reference after every preprocessing step â€” `MP_` prefix stripped, hyperlinks extracted, variants split â€” the layout reference found at that position, the comparison result (match, mismatch, or review), and the specific rules that fired. Then a step-by-step decision tree: was the reference valid, was there a matching layout entry, was the pin count acceptable, was the component type correct. I built it on one principle: if an engineer asks "why did it call this a mismatch?", the view has to answer completely â€” because any missing step just sends them back to me, which defeats the point.

Beside it I added a reconciliation dashboard over the same BOM, CAD, and inspection state â€” a live table with side-wise counters for top and bottom, a visible-versus-total count, color-coded status chips, and severity ranking so missing components sort to the top. Clicking a row jumps straight to that component in the main view.

The result showed up in the first week. Using the debug view, the engineers found two edge cases where the heuristic was wrong â€” both unusual component-naming conventions â€” and because it exposed the intermediate data instead of just the verdict, those were quick to diagnose and fix. The bigger outcome was the shift: once they could see how decisions were made, they stopped double-checking and started relying on the tool for production verification.

My honest reflection is that I built it as an afterthought. Next time I would build the transparency layer from the start, because it did not just explain the tool â€” it surfaced real defects and earned the users' confidence. Owning the adoption risk, not just the feature, is what made the tool actually get used.

## Deep follow-ups (likely bar-raiser probes)

**Q: The comparison engine was your job. What exactly did you take on that wasn't?**
**A:** Building the verdict was the brief. Determining whether anyone would trust the verdict, and building the machinery for them to verify it, was not â€” that was adoption work. It came after the core tool shipped, as an afterthought, which is exactly why it sits outside the original responsibility.

**Q: Why hide the debug view behind a URL parameter instead of a normal toggle?**
**A:** Because it is for technical users doing deep investigation, not routine verification. A query parameter keeps the main interface clean. The engineers learned to add `?debug=true` quickly, and I did not want 50-plus columns of per-component detail in the default view where it would distract from the report.

**Q: How did you know the transparency work actually helped?**
**A:** Two signals. First, a concrete one: in the first week the engineers used the debug view to find two edge cases where the heuristic was wrong â€” both unusual component-naming conventions â€” and those were easy to diagnose and fix. Second, the behavioral shift: once they could see how decisions were made, they were willing to rely on the results for production verification instead of re-checking by hand.

**Q: What did the reconciliation dashboard add that the debug view didn't?**
**A:** Scale of review. The debug view answers a question about one component. The dashboard gives the high-level picture first â€” total components, matches, mismatches, reviews, the component-type distribution, side-wise counters, and severity ranking so missing components lead. Then clicking a row drops you into the specific component. Verify the whole board, then drill in.

**Q: What if the debug view itself showed something wrong?**
**A:** It displays the raw output of the parsing pipeline, and it displays it consistently. If the parsing is wrong, the view shows the wrong data â€” but the engineer can compare that raw data against the actual BOM file and see exactly where the parse diverged. That is precisely how the two naming edge cases were found. Hiding the intermediate data would have made those invisible.

**Q: Isn't exposing internal data a risk?**
**A:** It runs on localhost or the local network, not the internet, and it only shows data the manufacturing engineer already has in their BOM and layout files. There is no new exposure â€” it is the same data, arranged so a human can audit the decision.

**Q: What would you do differently?**
**A:** Build the transparency layer from the beginning rather than as an afterthought. It would have surfaced edge cases earlier, and the lesson is that for an automated system, explainability is not a nice-to-have â€” it is what makes the system usable at all.
