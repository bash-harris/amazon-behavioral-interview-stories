## Answer (core, ~450 words)

The challenge I'd point to was a correctness problem in the BOM reconciliation tool that looked like a simple tuning request and kept turning out to be deeper each time I fixed it.

Context: the tool compares a board's Bill of Materials against its design layout and reports components missing, extra, or mismatched. The first version compared pin count literally — if the BOM called a part 8-pin and the layout footprint showed 16 pads, it reported a mismatch. On boards with mixed component types, false-positive reports were running at about 12%. Every false alarm sent a manufacturing engineer to manually verify a part that was perfectly fine, which is the exact work the tool existed to remove.

The surface read is "the tool is too strict, loosen it." That fix would have been wrong, and the real challenge was finding the line between a normal manufacturing variation and a genuine mismatch. So instead of turning a threshold by feel, I went at the data. I pulled 20 BOMs with pin-count discrepancies and categorized every one. The pattern was clean and asymmetric: when the layout had more pads than the component required, it was almost always legitimate — footprints are drawn for a whole package family, and the extra pads are unused or no-connect. When the layout had fewer pads, it was a genuine mismatch, because the part physically can't fit. Same number, opposite meaning depending on direction.

I rewrote the rule to follow that asymmetry: more pads became "flag for review," not a mismatch; fewer pads stayed a definite mismatch. That fixed the 12% — and immediately exposed the next layer. Some components had a genuinely wrong footprint that happened to be larger, so the new rule waved them through. I went back in. The distinguishing fact was component type: a larger footprint is acceptable only if the reference type agrees. So I added a component-type check and a configurable pin-count ratio threshold, defaulted from the data at 2:1, which put the judgment in the engineer's hands instead of hard-coding my own. I also built a debug view that shows, per component, the BOM pin count, the layout pad count, whether the type matched, the ratio, and the tool's decision, so an engineer can see why it decided and override it. And I verified the whole change against a regression suite of 15 BOMs — five with pin-count issues — confirming the fixes worked and that nothing which previously matched had changed.

False-positive reports on mixed-component boards dropped from about 12% to under 2%, and the engineers went back to trusting the report instead of hand-verifying every pin count.

The lesson is about depth: the first failure mode was hiding the second. I had assumed pin count was a reliable signal — it isn't; reference designator plus footprint name is — and I'd have found that boundary faster by collecting diverse BOMs up front instead of discovering edge cases one production file at a time.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why not just ignore pin count entirely?**
**A:** Because it catches genuine mismatches. If the BOM specifies a 16-pin IC and the layout shows an 8-pin footprint, that's a real problem — the component physically won't fit. Ignoring pin count would let those errors through. The fix was to make pin count discriminating, not to drop it.

**Q: How did you pick 2:1, and what's the risk of a heuristic?**
**A:** I set it from the 20 BOMs: legitimate footprint variations typically had a pad-to-component ratio of 2:1 or less. The risk is false negatives — a genuinely wrong component that happens to satisfy the type and ratio rules could pass. The debug view mitigates that: the engineer sees the ratio and the type match and can override. The rule is a heuristic, not a proof.

**Q: Why not train a model to classify this instead?**
**A:** I considered it, but I had only about 200 examples of known pin-count mismatches — not enough for a reliable classifier. Heuristics fit when the rules are clear and the edge cases are enumerable. If the cases got more complex, I'd revisit the ML approach.

**Q: How did you know your fix didn't break components that already matched correctly?**
**A:** I ran the regression suite of 15 BOMs, five with pin-count issues, and checked three things: the five now produced correct results, the other ten were unchanged, and no component that previously matched changed status.

**Q: What happens on a board with a 3:1 ratio?**
**A:** With the default threshold of 2:1, a 3:1 ratio would be flagged as a mismatch. That's deliberate — match, mismatch, and review are three distinct decision states, not degrees of the same one, and a ratio past the threshold is a mismatch, not a review. From there the manufacturing engineer verifies whether it's a legitimate footprint variation (and raises the threshold) or a genuine mismatch (and investigates the component). I put that judgment with the person who knows the board rather than making an automatic accept/reject call.

**Q: What would you do differently?**
**A:** Collect diverse sample BOMs from the floor before writing the comparison rule, instead of discovering edge cases reactively. And I'd treat a matching signal as a hypothesis until I've watched it hold across varied samples — pin count wasn't the right signal; reference designator plus footprint name is.
