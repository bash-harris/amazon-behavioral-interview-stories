# Q72 — tell me about a time you pushed for something

**Mapped LP(s):** Have Backbone; Disagree and Commit (primary); Customer Obsession (primary); Ownership (primary).

**Story used:** BGSW PCB Inspector Suite — the **pin-count measurement pushback and the transparency push** on the BOM reconciliation tool (`AMAZON_INTERVIEW_PREPARATION.md` STORY 10, "The Pin Count Mismatch Problem", with the debug-view behavior expanded in STORY 11, "Debug Endpoint for Manufacturing Transparency"). One telling only: STORY 10's numbers (20 BOMs, ~12% → under 2%, 2:1 threshold). **Distinct re-frame from Q17** (which owns the "implement a direction you disagreed with" commit narrative): here the spine is *advocacy backed by data plus ownership of the fix through to transparency* — what I actually pushed for and saw through. **Counterparty honesty:** the record documents a push against the tool's literal measurement rule and the requirement to fix false alarms without breaking genuine detection — there is no named person in that disagreement, and none is invented.

## Answer (core, ~470 words)

The thing I pushed for was a change to how our BOM reconciliation tool decided whether a part matched — and then for the engineers using it to be able to see why.

The tool compared the pin count in the BOM against the number of pads in the layout footprint, literally. If the BOM called a part an 8-pin and the layout showed 16 pads, it reported a mismatch. On real boards that produced false alarms, and the manufacturing engineers had started manually re-checking every pin-count mismatch — which defeats the point of automating it. I pushed to change the measurement.

I didn't push with an opinion. I pulled 20 BOMs that had pin-count mismatches and categorized every one into three buckets: footprint larger than the component, footprint smaller, and exact match. The pattern was clean — footprint-larger was almost always a legitimate package variation, with extra pads for package variants or no-connects; footprint-smaller was a genuine mismatch because the part physically can't fit; exact match was fine. That turned "pin count is noisy" into a finding with numbers behind it.

What I pushed for specifically: keep pin count in the comparison, because it's the signal that catches a wrong part, but stop treating it as exact equality. Larger footprint → flag for review, not a mismatch; smaller footprint → definite mismatch. That opened a new hole — a larger footprint on the wrong component type — so I pushed again for a component-type check with a configurable ratio threshold, defaulted from the data at 2:1.

Then the part I'm most deliberate about. The engineers didn't just need the rule fixed; they needed to be able to trust it. So I pushed for transparency: a debug view showing the raw BOM entry, the parsed reference after each preprocessing step, the layout reference found, and the rule applied, with the ability to override the tool. That's the piece that changed it from "the computer said so" into something they'd rely on for production verification. In the first week it surfaced two edge cases my heuristic got wrong, both unusual component naming conventions.

The results: false positives dropped from about 12% to under 2% on boards with mixed component types, and the engineers stopped manually verifying every pin-count mismatch. I also ran the full 15-BOM regression suite to confirm the new logic didn't change any component that previously matched correctly, because a fix that breaks the good cases isn't a fix.

Honest boundary: I pushed against the tool's measurement rule and the requirement to fix false alarms without breaking genuine detection — not against a named person. I'm not going to invent a counterparty. What I can stand behind is that I built the case with data, proposed the change, owned the residual risk — a heuristic can still miss a mismatch that happens to satisfy the rules — and followed through to the debug view instead of stopping at "this is broken."

## Deep follow-ups (likely bar-raiser probes)

**Q: What exactly did you push for, and who were you pushing against?**
**A:** I pushed to change how the tool measured a match — from literal pin-count equality to a discriminating rule — and then pushed to make the tool's reasoning transparent. Honest answer on the counterparty: the record shows a push against the tool's existing rule and the requirement to fix false alarms without breaking genuine mismatch detection. There is no named person in the record, and I won't invent one. The push is real; the "who" is the tool's logic, not a colleague.

**Q: How did you build the case before you said anything?**
**A:** With data. I collected 20 BOMs with pin-count mismatches and categorized every one into three types — footprint larger, footprint smaller, exact match. Saying "pin count is unreliable" is a preference; showing that footprint-larger cases are almost always legitimate package variation is a finding the team could act on.

**Q: Why not just remove pin count from the comparison entirely?**
**A:** Because pin count is the signal that catches a wrong part — if the BOM specifies a 16-pin IC and the layout only has an 8-pin footprint, the part physically won't fit. Removing it would let genuine errors through. The right move was to make it smarter about when it matters, not to delete it.

**Q: How did you get the engineers to actually trust the new behavior?**
**A:** Transparency, not just a bug fix. The debug view showed the raw entry, the parsed reference after each step, the layout reference found, and the rule applied, and let them override the tool. They used it immediately, and in the first week it surfaced two edge cases my heuristic got wrong — both unusual naming conventions. Once they could see the reasoning, they relied on the results for production verification.

**Q: How did you make sure the change didn't break genuine detection?**
**A:** I ran the full 15-BOM regression suite, including the 5 boards with pin-count issues, and verified three things: the 5 problem boards now produced correct results, the other 10 still did, and no component that previously matched correctly changed. The residual risk — a heuristic can still miss a mismatch that satisfies the type and ratio rules — I stated explicitly rather than hiding it.

**Q: Where do you draw the line between pushing for something and refusing to let go?**
**A:** Push once, with evidence, on the finding and the customer risk — then commit to whatever the decision is and stop relitigating it. The test for me is whether I have new data or just a preference. With pin count I had a finding, so I pushed; once the rule was set and the residual risk was documented with a configurable threshold and an override, there was nothing left to push — the judgment belonged in the engineer's hands.
