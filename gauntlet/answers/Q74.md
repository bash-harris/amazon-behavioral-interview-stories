# Q74 — describe a time you had to make a decision with incomplete information

**Mapped LP(s):** Bias for Action; Are Right, A Lot.

**Story used:** BGSW PCB Inspector Suite — the **standalone-vs-server decision** (`AMAZON_INTERVIEW_PREPARATION.md` STORY 4, "The Standalone HTML That Replaced a Server"): abandoning the Flask backend and shipping the whole suite as one offline HTML file, made without being able to verify the target environment. One telling only — STORY 4's numbers throughout (OpenCV.js ~8MB / TF.js ~3MB / PDF.js ~1MB / XLSX.js ~0.5MB ≈ 12.5MB embedded; ~25MB single file; ~5s vs ~2s load; 15 BOMs + 10 board images parity harness; +~2s WASM decode). This is the **architecture decision**, deliberately distinct from Q58/Q19/Q36, which use the five-day **prototype scope** telling, and from Q7 (the IE11 failure), Q29 (the WASM blocker), and Q30 (localStorage durability), which used this same project for different angles.

## Answer (core, ~440 words)

The decision I'd point to is killing the Flask server and shipping the entire PCB inspection suite as one offline HTML file — and I made it without being able to check the ground truth.

Here's the information gap. The tools had to run on factory-floor machines with no internet, no software installs, and limited IT support, and the Flask backend required a Python install, dependency management, and network configuration the manufacturing team couldn't do. I could see that. What I couldn't see was whether a browser-only single file could actually carry the whole stack and behave identically. The suite depended on OpenCV.js — about 8MB, and a WebAssembly module — plus TensorFlow.js at about 3MB, PDF.js at about 1MB, and XLSX.js at about 500KB: roughly 12.5MB of libraries. I didn't know whether embedding all of that would work, whether a ~25MB file would load acceptably on those machines, or whether the floor fleet even had browsers capable of running it. I couldn't inventory the fleet, and I had no lab that matched it.

I put three options on the table. Keep the server and push the install-and-network problem onto the engineers and IT — the status quo, and exactly what made the tools unusable for them. Stand up a lighter local server I'd still have to support, which keeps the install and network dependency. Or go standalone: one self-contained HTML file that embeds everything and opens by double-click, with no network and no install.

I chose standalone, but I made it a checkable bet rather than a leap. `compile_tool.py` builds the standalone file from the same source as the server version, and a `STANDALONE_MODE` flag switches only the storage layer — localStorage versus the server filesystem. So I never had to bet the only copy: the server build stayed alive, and I wrote a parity harness that ran the same 15 BOM files and 10 board images through both builds and compared reconciliation reports, alignment (within one pixel), and ML classifications. If the standalone build couldn't match, I had a fallback and I would know before shipping. That's what made it safe to commit with the information I had — the cost of being wrong was bounded by a test I could run myself.

The outcome held. The result was a ~25MB single HTML file that loaded in about 5 seconds on a factory machine versus 2 seconds for the server, with every function identical — BOM parsing, layout comparison, alignment, ML inference, and auto-save. The engineers opened it by double-clicking, with no Python, no network setup, and no IT ticket; I distributed it by email and USB.

What I couldn't know up front I found out later: some floor machines had browsers that couldn't run the WebAssembly the build depends on. I handled that with a capability check instead of pretending it didn't exist — and I'd rather state that limit than claim the call was perfect.

## Deep follow-ups (likely bar-raiser probes)

**Q: What exactly was the incomplete information?**
**A:** Three unknowns. Whether a browser-only file could carry the full stack — OpenCV.js WASM (~8MB), TF.js (~3MB), PDF.js (~1MB), XLSX.js (~0.5MB), about 12.5MB total — and still behave identically; whether a ~25MB file loaded acceptably on factory machines; and whether the fleet's browsers could run it at all. I could not inventory the fleet or test on a matching lab.

**Q: What made this a reversible bet rather than a gamble?**
**A:** I bounded the downside. `compile_tool.py` generates the standalone build from the same source as the server, so the two stay in sync; a `STANDALONE_MODE` flag swaps only the storage layer; and the parity harness (15 BOMs + 10 board images, comparing reports, alignment within one pixel, and classifications) told me whether parity held. The server build remained a fallback, so the worst case was losing a day — not breaking the product.

**Q: Why not keep the server and ask IT to open the network or image the machines?**
**A:** Because the constraint was the users' environment — no internet, no installs, limited IT — and escalating would have stalled the engineers on a dependency I could remove inside my own build. When the path is mine and I can test it, waiting for someone else is the slower, not the safer, choice.

**Q: Was a slower load really acceptable?**
**A:** Yes, deliberately. About 5 seconds on a factory machine versus 2 for the server, in exchange for a tool that runs offline with no install and no network. I noted the ceiling too: at ~25MB the file ran into a 20MB email attachment limit, and gzip on the embedded libraries could have brought it closer to 15MB — that's the optimization I deferred, not a surprise.

**Q: What did you get wrong?**
**A:** I assumed every floor machine ran a modern browser. Some didn't, and the WebAssembly-dependent build failed entirely on those. I could not fix that without a rewrite, so I added a startup capability check that names the missing requirement and documented the minimum browser. I don't dress that up as a win — it's the part of the bet I couldn't de-risk up front.

**Q: How do you decide a bet is safe enough to make?**
**A:** Bound the downside and make it checkable. Here that meant the same source for both builds, a parity test I could run after every compile, and a live fallback. I'll commit under uncertainty when being wrong is cheap, fast to detect, and recoverable — and I'll slow down when it isn't.
