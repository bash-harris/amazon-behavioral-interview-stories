# Q47 — tell me about a time you had to make a design trade-off that prioritized the customer experience over technical convenience

**Mapped LP(s):** Customer Obsession.

**Story used:** BGSW PCB Inspector Suite — the decision to ship the standalone single-file build instead of the Flask server version (`AMAZON_INTERVIEW_PREPARATION.md` STORY 4, "The Standalone HTML That Replaced a Server"). Distinct angle from Q8 (solo completion), Q9 (pride/adoption), Q29 (the WASM blocker), and Q30 (scope beyond responsibility), which all use the same project but different subjects. Here the subject is the trade-off decision itself: the technically convenient server architecture was rejected because the customers could not run it. One telling only — PREPARATION.md STORY 4's numbers (~25MB file, ~12.5MB embedded libraries, OpenCV.js ~8MB, ~5s vs ~2s load, +~2s WASM decode, localStorage 5MB with quota/GC handling). The conflicting `AMAZON_INTERVIEW_PREP.md` STORY 7 telling (150MB file, "2–3 days → 5 min", 3.2GB→1.8GB, float16) is not used.

## Answer (core, ~450 words)

The clearest trade-off was the deployment format of the PCB inspection suite, and I made it by working backwards from the only thing that mattered: the engineers had to be able to run the tool at all.

The original build was a Flask server. On paper that was the technically convenient choice — it launched in about two seconds, libraries loaded from disk, and I had already written it. But my users were manufacturing engineers on factory-floor machines with restricted network access: no internet, no permission to install software, and limited IT support. The Flask server needed Python installed, dependencies managed, and networking configured — all beyond what that team could handle. The "better" architecture was unusable by the people it was built for.

So I traded technical convenience for their experience and compiled the whole suite into a single standalone HTML file. That choice cost me real work and real performance. I had to embed every library — OpenCV.js at about 8 MB, TensorFlow.js about 3 MB, PDF.js about 1 MB, XLSX.js about 500 KB, roughly 12.5 MB total — base64-encode the WebAssembly binary, and modify the OpenCV.js loader to decode it at runtime, which added about two seconds to startup. The finished file is about 25 MB and loads in roughly five seconds on a factory machine versus two for the server version. I took all of that knowingly.

The customer-facing result is what justified it. Instead of an install guide and an IT ticket, the engineer double-clicks one file. No Python, no network configuration, no support request. I handed it out by email and USB drive. The point was that the tool worked where they worked, not where it was convenient for it to run.

I applied the same lens to the parts they would feel. Auto-save had to be dependable, so I used synchronous localStorage and wrapped every write in a quota check — on a QuotaExceededError it warns the user and garbage-collects the oldest results instead of silently failing and losing an inspection. IndexedDB is the more capable store, but it is asynchronous and would have complicated exactly the behavior the engineers depended on. And I was honest about a distribution cost: at 25 MB the file bumped into a 20 MB email limit, and gzip could have brought it to about 15 MB.

What I'd defend is the direction of the decision. I didn't choose the architecture that was easiest to build or fastest to load; I chose the one the customer could actually operate, and I absorbed the size, build complexity, and load-time penalty myself.

## Deep follow-ups (likely bar-raiser probes)

**Q: Wasn't the server version just better technically?**
**A:** By its own metrics, yes — it loaded in about two seconds versus five, and it avoided the embedding gymnastics entirely. That's precisely the trade-off: the technically better artifact was unusable by the customer. I chose the worse-from-my-side option because it was the only one that met them where they were.

**Q: What did the standalone build cost you?**
**A:** Roughly 12.5 MB of embedded libraries grew to about 25 MB once base64-encoding was applied, startup gained about two seconds for the WASM decode, and the file ran into a 20 MB email attachment limit. I accepted all three deliberately, and I'd still gzip the libraries to about 15 MB if I did it again.

**Q: Why not separate files or a service worker instead of one giant file?**
**A:** Separate files break the single-file guarantee — move one and the tool dies, which is the exact failure mode I was removing. A service worker needs HTTPS to register and carries browser-compatibility risk on those machines. Base64 in one file adds size but removes every external dependency.

**Q: You chose localStorage over IndexedDB — isn't that the technically weaker option?**
**A:** For capability, yes: IndexedDB has a much larger quota and supports structured data. But auto-save here is a few KB per inspection, and IndexedDB is asynchronous, which complicates the save logic. The engineers' experience depended on auto-save being simple and reliable, so synchronous localStorage was the right fit, with quota handling so a full store warns and cleans up rather than losing their work.

**Q: How did you know the trade-off was the right one?**
**A:** The outcome was adoption on their terms: engineers used it by double-clicking, with no Python install, no network setup, and no IT ticket, and I distributed it by email and USB. If the format had been wrong, none of that would have happened.

**Q: What's the risk of optimizing this hard for the customer's current constraint?**
**A:** The constraint could change. If the factory floor later got reliable internet, a CDN approach would drop the file from 25 MB to about 5 MB and I'd switch. But the constraint at the time was real, and designing for a future that didn't exist would have left the engineers with a tool they couldn't use.

**Q: Did anything besides the format get shaped by this lens?**
**A:** The auto-save behavior — the quota check and the garbage collection of old results — was the other one. It isn't a technical showpiece, but it's the difference between the tool quietly losing an inspection and telling the engineer what happened.
