# Q34 — tell me about a time where you introduced a new process and why was it not already in place at your company ?

**Mapped LP(s):** Invent and Simplify.

**Story used:** BGSW PCB Inspector Suite — the standalone build process automated by `compile_tool.py` (`AMAZON_INTERVIEW_PREPARATION.md` STORY 15, "Compiling a Full Stack into a Single File"). Deliberately distinct from Q31, which used the same automation as a speed-to-deadline case; here the subject is the **process introduction itself** and why it didn't exist before. One telling only — PREPARATION.md's ~30-min → 8-s compile, ~1-in-5 → 0 error rate, ~200-line Python script, ~25 MB artifact. The conflicting `AMAZON_INTERVIEW_PREP.md` STORY 7 telling (150 MB file, "2–3 days → 5 min") is not used.

## Answer (core, ~460 words)

The process I introduced was a build process — and the more interesting half of the question is why it wasn't there, because it only makes sense against the constraint that created it.

The tools started life as a Flask application. In that world there was no packaging step at all: deploying meant pointing someone at a URL. The standalone format came later, and it came from the customer's environment, not from me. The manufacturing engineers worked on factory-floor machines with no internet, no ability to install software, and limited IT support. A server wasn't available, and neither was a CDN. The only delivery format that survived that environment was one self-contained HTML file the engineer could double-click. That requirement was new, which is exactly why the process didn't exist: nobody had ever needed to produce a single-file build here.

So for a while I produced it by hand. I concatenated the modular source in the right order, inlined the CSS and JavaScript, base64-encoded the libraries, and checked the result. It took about thirty minutes a build and it was wrong roughly one time in five — usually a file inlined in the wrong order or missed entirely, and it wouldn't fail until an engineer opened the file on the floor. That failure mode is what turned it from a chore into a process problem: the artifact was being shipped into an environment I couldn't see.

I wrote `compile_tool.py` to replace it. It's about two hundred lines and does three stages: collect every HTML, CSS, JS, and library file; process each by type (CSS into style tags, JS into script tags in dependency order, binaries base64-encoded); and assemble the document. Two decisions carried most of the value. First, it reads a manifest for ordering instead of trusting the filesystem, because CSS has to be inlined before the HTML that consumes it and utilities before the business logic. Second, it stamps the current git commit hash into the document title, so a file in the field traces back to the build that produced it. The build went from thirty minutes with roughly one failure in five to eight seconds with zero — repeatable enough to trust, cheap enough to run on every change.

I also know why it's not a one-off. Because the script is manifest-driven, adding a fourth comparison tool is a one-line change to the manifest; the existing tools don't move. And the embedding approach was a deliberate choice, not the default — I looked at a real bundler (Webpack) and at serving the libraries from a CDN. Webpack was more machinery than a string-assembly step needed, and a CDN would have cut the file from ~25 MB to roughly 5 MB but required internet the factory floor doesn't have. I picked the boring script because it was the smallest thing that solved the actual constraint, and it was still the right trade after the fact.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why wasn't this process already in place — was it just that nobody had built it?**
**A:** Two reasons, and only one is "nobody got to it." The real reason is that the requirement didn't exist: while the tool was a Flask server, there was nothing to package. Standalone was forced by the factory environment, and when that requirement appeared I shipped the first versions by hand because shipping the tool mattered more than tooling the build. The process lagged the requirement, and the one-in-five failure rate is what finally justified the automation.

**Q: Why not a real build tool like Webpack?**
**A:** The logic is string manipulation — no module bundling, minification, or source maps needed. `compile_tool.py` is about two hundred lines and does exactly what the artifact requires. Webpack would have added config, plugins, and a learning curve for a step that runs once before deployment.

**Q: How do you know the compiled artifact is correct, not just fast?**
**A:** Speed wasn't the only acceptance criterion. A test harness runs the same 15 BOM files and 10 board images through both the server and standalone builds and compares reconciliation reports (must match exactly), alignment (within one pixel), and ML classifications (identical). If any check fails, the compilation is rejected.

**Q: Why embed the libraries instead of loading them from a CDN?**
**A:** A CDN would drop the file from ~25 MB to about 5 MB, but the factory floor has no internet, so the artifact wouldn't run where it's actually used. Base64 embedding is a deliberate trade of file size for offline function. If those machines ever get network access, CDN delivery becomes the better choice.

**Q: Is this process scalable, or does it break when the product grows?**
**A:** It's manifest-driven, so it grows cleanly. Adding a fourth comparison tool means adding its files to the manifest — a one-line change — and the existing tools are untouched. The design assumption is "one core, many views," so the build scales with the number of views, not the amount of duplicated config.

**Q: What would you do differently?**
**A:** Add a checksum on the compiled output so corruption is caught by the tool, and a diff mode that compares two compilations so a silently changed build is visible. I named both in my own reflection; neither got built.
