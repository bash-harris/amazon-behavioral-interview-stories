# Q40 — tell me about a time you made an unorthodox decision

**Mapped LP(s):** Are Right, A Lot; Invent and Simplify; Bias for Action.

**Story used:** BGSW PCB Inspector Suite — choosing a general-purpose vision-language model (GPT-4o) as the inspection engine instead of building the purpose-built classifier the domain expects (`AMAZON_INTERVIEW_PREPARATION.md` STORY 8, "Adding an AI Eye to the Inspection"; same event as `AMAZON_INTERVIEW_PREP.md` STORY 3, "Invent and Simplify — GPT-4o VLM PCB Inspection"). One telling only — STORY 8's numbers (manual interpretation ~30s → ~5s per mismatch; ~85% accuracy on component type and mismatch type; under-5-second constraint). The conflicting PREP.md STORY 3 numbers (92% accuracy, 78% pixel baseline, 100 board pairs, ~2s latency) are deliberately not used. This is a **decision-framed** telling of the same event Q1 (productivity) and Q3 (business result) used; here the subject is the choice itself — why it was unorthodox, the risk, and why it was right.

## Answer (core, ~440 words)

The unorthodox decision was to use a general-purpose vision-language model as the inspection engine instead of building the classifier that industrial inspection says you build.

I was the only engineer on a PCB inspection suite for manufacturing engineers. The comparison pipeline could say *where* a board didn't match its design — it drew a red region — but it couldn't say what the region *meant*. Wrong-value part, rotated part, or just a reflection? Every flag became a manual judgment call, about thirty seconds each, and a typical board threw five to twenty of them. That interpretation step was the bottleneck.

The conventional answer is a purpose-built classifier: label defect crops, train an EfficientNet-class model, own the asset. Template matching is the cheaper cousin. Everyone expects that, and it has real advantages — offline, cheap per inference, fully under your control. I went the other way. I used GPT-4o as the "expert eye": crop the flagged region from the layout and from the photo, send both with a structured prompt, and read back a JSON verdict — component type, mismatch type, confidence, description.

That was unorthodox for three reasons, and each was a real risk. First, it put a cloud model in the loop of a tool built for factory-floor machines whose entire problem was restricted network access — so I confined it to the server build and kept the deterministic comparison as the core for the offline file. Second, the "intelligence" was a black box I didn't train or own, and a wrong verdict on a production tool is expensive. Third, it inverted the build: I wasn't building a model, I was building the preprocessing and the prompt around someone else's.

I treated it as a calculated bet. I evaluated the alternatives before committing — GPT-4V was slower, about eight seconds per request versus three for 4o; Claude 3's API was less mature then; Gemini Pro Vision was weak on the small SMD parts that matter here; and a local LLaVA needed at least 8GB of VRAM the factory machines don't have. I bounded latency by sending only flagged regions, kept the API optional so the tool degraded gracefully offline, and made the output a labeled suggestion with a confidence plus a correct/incorrect feedback loop, so the engineer stayed the decision-maker.

It was right. Manual interpretation dropped from about thirty seconds to about five per mismatch, at roughly 85% accuracy on component type and mismatch type, and the engineers used it to triage dense boards first. The remaining 15% were images too poor or parts too small to read.

The honest reflection: I was wrong that the model could read values off small surface-mount parts — it's context, not OCR — and I'd start with the simple structured prompt instead of the clever one. The decision was right because I measured the risk before I took it, not because I was sure.

## Deep follow-ups (likely bar-raiser probes)

**Q: A trained classifier is offline, cheap per inference, and something you'd own. Why not that?**
**A:** Because it's a labeling-and-training project that has to be re-done for every new defect type, and I was a solo developer already carrying three tools. Reusing an existing "expert eye" let me spend my effort on the preprocessing and the structured prompt instead. It also isn't either/or: the deterministic comparison stays the core, and the VLM is the escalation for flagged regions. A custom classifier is the thing I'd build only if cost or privacy became the binding constraint.

**Q: How do you trust a black-box model in a production tool?**
**A:** I don't ask it to be the decision. The output is labeled "AI Analysis" with a confidence, the engineer confirms or overrides it, and there's a correct/incorrect feedback loop that surfaces systematic prompt errors. If the API is unreachable the comparison still runs, the highlights still show, and the UI says the AI analysis is unavailable — so the model is an enhancement, never a dependency.

**Q: Why GPT-4o specifically?**
**A:** I evaluated GPT-4V (about eight seconds per request versus three for 4o), Claude 3 (strong vision, but its API was less mature at the time), and Gemini Pro Vision (fast, but weaker small-object detection, which matters for SMD parts). GPT-4o had the best balance of accuracy, speed, and API availability, and it handled image and text in one request, which simplified the integration. A local LLaVA was the alternative for cost or privacy, but it needs at least 8GB of VRAM the factory machines don't have.

**Q: 85% sounds low. What did it actually buy you if a human still verifies?**
**A:** It moved the engineer from interpretation to judgment. Manual per-mismatch interpretation was about thirty seconds; reading the structured verdict was about five. On a board with five to twenty flags, that's minutes back, and the engineers said it let them prioritize dense boards. The human was always in the loop — the point was never to replace the judgment, only the time spent figuring out what the red box meant.

**Q: What happens when the API is down or slow?**
**A:** The VLM is an enhancement, not a core requirement. If the API is unreachable, the comparison and the visual highlights still work, the UI reports that AI analysis is unavailable, and the engineer falls back to the manual check. I also kept the model off the offline path entirely — the standalone factory-floor build doesn't use the VLM at all, so the network constraint never became a failure mode.

**Q: Where would you deliberately not use the model?**
**A:** Not on every component — I only send regions the comparison already flagged, so cost and latency scale with mismatches, not with the component count. Not in the offline build, where there's no network by design. And I'd weigh a self-hosted option if per-call cost or data sensitivity became the binding constraint, though that needs GPU hardware the floor machines don't have. A cost-aware cascade that escalates only hard cases to the model is a design target I'd want, and I'd be clear it's designed, not built.
