## Answer (core, ~450 words)

The clearest example is a tool nobody asked me to build: the labeling tool for the PCB defect model.

I was building the inspection suite — the comparison tools and the machine-learning pipeline. The classifier needed training data: cropped images of components, each labeled good, wrong value, wrong orientation, or missing. What existed was a pile of board photographs with no labels attached. My responsibility was the inspection tools. Building a dataset was not on anyone's list. But without labels there is no model, so I treated the data problem as mine.

The obvious path was a spreadsheet: open an image, look at it, type the label in a cell, repeat. At roughly 30 seconds an image, that is hours of error-prone work, and one fat-fingered label quietly poisons the training set. So I built a small Tkinter desktop app instead — an image, a status bar, and nothing else. Press G for good, 1 for wrong value, 2 for wrong orientation, 3 for missing, 4 for other, and the next image loads automatically. I added a skip key, because an image too blurry to call should not enter the dataset with a guessed label; skipped images went to a separate file for later review. The session was resumable, because labeling 2,000 images does not fit in one sitting. Pillow for image display, pandas for CSV, and the CSV columns matched what the training pipeline already expected, so there was no conversion step between labeling and training.

The part I would point to as ownership happened after it worked. A labeling tool is easy; a trustworthy dataset is not. I labeled the entire set twice, a week apart, and compared the results. My agreement with myself was 92%. The 8% were borderline cases, and instead of ignoring them I re-examined each one and chose the label that best described the primary defect. I also plotted learning curves during training, which told me that doubling the set to about 4,000 images would likely buy roughly two points of accuracy, and that beyond that the return flattened. That is the number that decides whether the next labeling push is worth the time — which is a decision I would have been guessing at without the tool and the measured quality figure.

The measured result: per-image labeling went from about 30 seconds to about 3 seconds. The full 2,000-image set took roughly 100 minutes instead of an estimated 10 hours, and it came out in the format the pipeline needed.

What I would do differently is add batch labeling for near-identical images, because many crops were the same component at slightly different angles. I also confirmed that for hundreds of images, keyboard shortcuts beat mouse clicks, even though mouse is more intuitive for a first-time user.

## Deep follow-ups (likely bar-raiser probes)

**Q: Nobody assigned this. Why did you decide it was yours?**
**A:** Because the model was useless without labels and nobody else was closer to the problem. "That's not my job" would have stalled the whole pipeline. The work was unglamorous, which is exactly when ownership matters most.

**Q: Why Tkinter instead of a web-based labeling tool?**
**A:** Tkinter was the simplest thing that met the requirement. A web tool would have meant a local server, file serving, and browser compatibility work. Tkinter is built into Python and runs anywhere Python runs. The trade-off is a less polished UI, but for an internal tool used by one person, polish was not the point.

**Q: How did you make sure the labels were actually good?**
**A:** I labeled the whole dataset twice, a week apart, and compared. Agreement was 92%; the 8% were borderline, and I re-examined each one rather than leaving a coin-flip label in the training set.

**Q: What if an image had two defects at once — wrong value and wrong orientation?**
**A:** The tool allows one label per image, which forces a decision about the primary defect. That is a simplification: a real component can have multiple issues. If the defect was genuinely ambiguous, I used skip and reviewed it later with more care. In practice most defects were clearly one type.

**Q: Why CSV instead of JSON?**
**A:** The labels are flat — one row per image with filename, label, and timestamp — so CSV is simpler to generate and easy to inspect in Excel. JSON would only pay off if the labels were nested.

**Q: What did the learning curves actually tell you?**
**A:** That the 2,000-image set put the model at 94% accuracy, and that roughly doubling to 4,000 images would likely reach about 96%, with the return flattening beyond that. That told me where to stop spending labeling time.

**Q: What would you improve in the tool?**
**A:** Batch labeling for near-identical crops. Many images were the same component at slightly different angles, and a "label all similar" function would have cut the remaining time further.
