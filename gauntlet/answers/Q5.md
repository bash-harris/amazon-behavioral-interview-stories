# Q5 — tell me about a time you directly interacted with a stakeholder for your project or work

**Mapped LP(s):** Customer Obsession (primary); touches Earn Trust and Ownership.

**Story used:** BGSW PCB Inspector Suite — the manufacturing-engineer stakeholder on the BOM reconciliation tool: the engineer-supplied variant semantics (`AMAZON_INTERVIEW_PREPARATION.md` STORY 1) and the debug/verification view (`AMAZON_INTERVIEW_PREPARATION.md` STORY 11 "Debug Endpoint for Manufacturing Transparency"). One stakeholder throughout; each fact sourced to a single telling.

## Answer (core, ~440 words)

My stakeholders were the manufacturing engineers who used the BOM reconciliation tool. Before it existed they verified boards by hand — cross-referencing the SAP BOM against the Altium layout PDF, entry by entry. That was 20–30 minutes per board.

The most important interaction was a correction, not a request. My parser treated references like `R1||R2` and `R1/R2` as invalid and silently dropped them. A manufacturing engineer told me those notations mean the same physical position can accept either part depending on the board variant — so the system should treat each as a valid match. He had the manufacturing intent and I didn't. I rewrote the variant splitter to normalize both separators, extract the individual references, and match either one. That change came from the customer; I would not have found it from the data alone.

The second interaction was about trust. The engineers were using the tool but didn't fully trust it: when it flagged a mismatch they couldn't see why, so they re-verified by hand, which defeated the purpose. I didn't wait to be asked for a fix. I added a debug view, reachable with `?debug=true`, that exposes the raw BOM entry text, the parsed reference after each preprocessing step, the layout reference it was matched against, the comparison result (match, mismatch, or review), the specific rules that fired, and a per-component decision tree. I also added a reconciliation dashboard with aggregate numbers — total components, matches, mismatches, reviews, and the component-type distribution — so they could see the shape of a result before drilling in. The intent wasn't to prove the tool right; it was to let them audit any decision themselves. That view was part of the local server build — a small Flask service I ran for them on the plant network, reachable on localhost, not the internet.

The result: in the first week the debug view was live, the engineers used it to surface two edge cases with unusual component naming, and I fixed both. Reconciliation dropped from 20–30 minutes per board to seconds, and the parser caught three real mismatches in week one that manual review had missed. The bigger change was the trust dynamic — once they could see the reasoning, they were willing to rely on the results for production verification.

What I'd do differently: build the debug view from the beginning instead of after their skepticism, and collect representative BOMs from the floor before writing the parser. Both are the same lesson — get the customer's real artifacts in front of me earlier.

## Deep follow-ups (likely bar-raiser probes)

**Q: How did you know what the engineers actually needed versus what you assumed?**
**A:** They told me directly. A manufacturing engineer explained that `R1||R2` and `R1/R2` mean the same position can take either part — I had been dropping those as invalid. And when the tool's results came back, the engineers made clear they wanted to understand *why* a mismatch was reported, not just that it was. Both of those drove the design.

**Q: What did you do when their domain knowledge conflicted with your design?**
**A:** A manufacturing engineer told me `R1||R2` should match either component at that position. I had been dropping those as invalid. He had the manufacturing intent and I didn't, so I rewrote the variant splitter to normalize `||` and `/` and treat each reference as a valid match. That change came from the customer, not from me.

**Q: Why a `?debug=true` query parameter instead of a UI toggle?**
**A:** The debug view is for investigation, not routine use — it shows 50+ columns of data per component. Hiding it behind a URL parameter kept the main reconciliation view clean while leaving the full trace one edit away. The engineers quickly learned to add `?debug=true`.

**Q: How did you handle the case where they still didn't trust a result?**
**A:** I didn't ask them to trust it — I made it auditable. The view shows the raw entry, every preprocessing step, the matched layout reference, the comparison result, and the rule that fired. If they thought a decision was wrong, they could see exactly where it went wrong and tell me.

**Q: How did you keep getting feedback after launch?**
**A:** The debug view became the feedback channel. In the first week the engineers used it to surface two edge cases with unusual naming, which I fixed. They were effectively testing the parser for me, using the same view I'd built for them.

**Q: Was the debug view part of the offline standalone build?**
**A:** No — it lived in the local server build, the Flask service I ran for them on the plant network. The standalone single-file HTML was a separate deployment for machines with no infrastructure; I don't want to imply the verification trace ran in the offline build when it was the server one.
