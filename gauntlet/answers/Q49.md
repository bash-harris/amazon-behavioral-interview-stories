# Q49 — tell me about a time you went above and beyond for a customer

**Mapped LP(s):** Customer Obsession (primary); Deliver Results.

**Story used:** BGSW PCB Inspector Suite — going past the tool request for the manufacturing engineers. ## Answer (core, ~470 words)

The customer was the manufacturing engineers on the factory floor, and the ask was an automated tool to compare boards. Going above and beyond, for me, meant not stopping when the comparison logic worked — staying until they could actually run it, on their machines, and share it.

First I went to them instead of assuming. Before writing code I sat in on three of their screen-sharing sessions and watched how they compared boards — toggling between images and using Zoom's annotation to circle the areas they cared about. They didn't need a difference score; they needed to see where the problem was. So I designed the tool around color-coded highlighting that matched the workflow they already had.

Then I built a five-day prototype and put it in front of them instead of polishing in private. The engineering lead shared it with the team the same day, and within an hour they had found three real problems: it failed under lighting changes, it couldn't handle boards photographed at different angles, and it couldn't export results. That was the fastest feedback I'd had on anything — six months of scoping had produced nothing, and the prototype produced a roadmap in an hour. I fixed the issues in the order that mattered to them: alignment first, illumination second, export third.

Then the environment. Their machines sat on the factory floor: no internet, no permission to install software, limited IT. The easy build was a Flask server — but it needed Python, dependencies, and network configuration the manufacturing team couldn't handle, so delivering it that way meant it would never run. So I took on work that wasn't the comparison logic anyone had asked for and compiled the whole suite into one standalone HTML file: I embedded roughly 12.5MB of libraries — OpenCV.js about 8MB, TensorFlow.js about 3MB, PDF.js about 1MB, XLSX.js about 500KB — as base64, which grew the file to about 25MB, and I rewrote the OpenCV.js loader to decode the WebAssembly binary from a data URL at runtime, adding about two seconds to startup. I also had to move auto-save off the server filesystem onto localStorage and add quota handling, because the 5MB limit can overflow. The file loads in about five seconds on a factory machine versus two for the server version. I accepted all of it so the engineer's job became double-clicking one file — no install, no network, no IT ticket.

None of that was a feature on the request. It was the difference between a demo and something they could use. I handed the file out by email and USB, and it spread — 15 engineers across two sites, saving roughly 20 hours a week.

What I'd do differently: I'd have treated the locked-down environment as the design driver from the start, before building the server version, because that constraint was known on day one. And I'd compress the embedded libraries harder — at about 25MB the file bumped into a 20MB email cap.

## Deep follow-ups (likely bar-raiser probes)

**Q: What did they actually ask for versus what you delivered?**
**A:** The ask was an automated board-comparison tool. What I delivered was one they could run on locked-down factory machines and share — because a comparison tool that needs Python installed on the factory floor is a comparison tool nobody can use.

**Q: How did you know they needed highlighting and not a difference score?**
**A:** I watched them. In three screen-sharing sessions they toggled between images and used Zoom's annotation to circle concerns. That told me the output had to show *where*, in a form they could point at and discuss — so the color-coded diff regions replaced their manual circling.

**Q: Wasn't the standalone build just your assigned task?**
**A:** The comparison logic was the assigned work. Nobody specified that it had to survive a machine with no internet and no install rights — that came from me watching how the team worked. Rewriting the OpenCV.js loader, embedding the model weights, and handling the localStorage quota were all effort I chose to make the deliverable usable, not work that was handed to me.

**Q: How do you go above and beyond without gold-plating?**
**A:** I anchor the extra effort to a customer cost I can name. The offline build addressed machines with no installs and no network. If I can't name the customer cost, it's scope creep, not above-and-beyond. That's why I left a formal versioning/CI system out — it wouldn't have helped any engineer run the tool.

**Q: How did shipping a rough prototype help the customer?**
**A:** It replaced guessing with their words. After the demo, three priorities — illumination, alignment, export — were things they'd told me, not things I'd assumed. If I'd polished for two weeks first, I'd have built features they didn't need.

**Q: What would you do differently?**
**A:** Treat the deployment environment as the design driver from day one — I built the server version before fully internalizing that the customer could never run it. And compress the embedded libraries more aggressively; at about 25MB the file hit a 20MB email limit, and gzip could have brought it closer to 15MB.
