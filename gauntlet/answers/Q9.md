# Q9 — tell me about a time you were proud of your work

**Mapped LP(s):** Ownership (primary); touches Deliver Results and Think Big.

**Story used:** BGSW PCB Inspector Suite — "Three Tools, One Vision" / "Three Tools in Production": the unified three-tool suite delivered solo and adopted on the manufacturing floor (`AMAZON_INTERVIEW_PREPARATION.md` STORY 5; `AMAZON_INTERVIEW_PREP.md` STORY 12). Distinct angle from Q7 (browser-compat failure) and Q8 (standalone single-file deployment): here the pride is the breadth of ownership and the adoption outcome.

## Answer (core, ~450 words)

I'm proudest of the PCB inspection suite I built at Bosch, because I owned it end to end — and because it stopped being my project and became the way the manufacturing team worked.

The manufacturing process had three separate verification steps, and engineers were doing all three by hand with different software. Schematic vs EBOM: does the bill of materials match the schematic? PCB vs Layout: does the physical board match its design? Good Board vs New Board: does a newly made board match a known-good reference? Each was a different kind of comparison — document-to-document, image-to-document, image-to-image — with different alignment needs and different failure modes.

I was the only engineer on it, so I owned the whole thing. My responsibility was to build all three tools as one suite: reliable per tool, usable by non-technical engineers, and maintainable by a single developer.

The design that made that possible was to share the infrastructure and specialize the logic. All three needed the same skeleton — file upload and validation, image preprocessing, auto-save, report generation, UI components — so I built that once. The comparison engines stayed separate: entity matching for the BOM, homography-based alignment for the PCB-vs-layout images, and a multi-signal pipeline for the board-vs-board compare. I kept the UX identical across all three — same drag-and-drop, same color coding, green for match, red for mismatch, blue for unknown — so learning one tool meant you'd learned all three. When I improved the auto-save, all three tools improved together.

I sequenced the build by dependency, which is where ownership mattered. The Schematic vs EBOM tool had no dependencies, so it went first. I learned OpenCV.js while building the PCB-vs-Layout tool — the second one — and TensorFlow.js while building the Good Board tool — the third. Each tool funded the next one's learning.

The outcome is what I'm proud of. All three tools were delivered within eight weeks. They were adopted by 15 manufacturing engineers across two sites, and the combined time savings was about 20 hours a week across the team. The BOM tool caught three real mismatches in its first production week that manual review had missed. Engineers went from cross-referencing two documents for 20–30 minutes per board to getting a reconciliation report in seconds.

The part I'd point to as ownership is that I didn't stop at "it works." When the engineers didn't trust the BOM results, I built the debug view so they could audit every decision, and that transparency is what made them rely on it for production. That's the shift from delivering a tool to owning the outcome.

If I did it again, I'd build the shared infrastructure before the first tool instead of retrofitting it, and I'd collect sample BOMs from the floor before writing the parser. Both are the same lesson: get the real artifacts and the real users in front of me earlier.

## Deep follow-ups (likely bar-raiser probes)

**Q: What was the hardest part of owning all three tools?**
**A:** Balancing shared infrastructure against specialized logic. Getting the shared skeleton right kept the three tools consistent and maintainable by one developer; the risk was over-abstracting, so I deliberately kept the comparison engines separate instead of forcing one universal comparison engine.

**Q: How did you deliver three tools in eight weeks on your own?**
**A:** I sequenced by dependency. The Schematic vs EBOM tool had no dependencies, so it went first. I learned OpenCV.js while building the PCB-vs-Layout tool and TensorFlow.js while building the Good Board tool — each one funded the next one's learning, and the third built on infrastructure from the first two.

**Q: What's the evidence it actually mattered?**
**A:** 15 engineers across two sites adopted it, the combined time savings was about 20 hours a week, and the BOM tool caught three real mismatches in its first production week that manual review had missed. The debug view moved them from hand-verifying results to relying on them for production.

**Q: How did you make it usable by non-developers?**
**A:** Identical UX across all three tools — same drag-and-drop, same color-coded output, green match, red mismatch, blue unknown — so they learned the workflow once. And the standalone build let them run it as a single file with no server and no install.

**Q: Which of the three was hardest, and why?**
**A:** PCB vs Layout. It had the steepest learning curve — I had to learn OpenCV.js and implement the alignment/parsing side from scratch. The Good Board tool was the most algorithmically complex, but by then it was standing on infrastructure the first two tools had paid for.

**Q: What would you do differently?**
**A:** Build the shared infrastructure first instead of retrofitting it after the first tool, and collect representative BOMs from the floor before writing the parser. Both are the same lesson: get the real artifacts and the real users in front of me before I build.
