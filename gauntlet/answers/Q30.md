## Answer (core, ~450 words)

The work I took on outside my responsibility was the data-safety layer under the standalone build â€” not because it was glamorous, but because nobody had been given it.

Context: I was building the PCB inspection suite, and the tools had to run on factory-floor machines with no internet, no installs, and limited IT support. Converting everything into one offline HTML file was my task. What was not in that brief was a failure mode I noticed while wiring up auto-save. The server version wrote state to the filesystem. The standalone version could not, so it had to use localStorage â€” and localStorage has a hard 5MB cap. When that cap is hit, a write does not get truncated quietly; it throws. My first pass did not handle that, which meant a save could fail and the engineer's work simply would not persist.

Nobody asked me to solve that. The acceptance criterion was "functionality works," and a quota exception does not show up in a demo. But a manufacturing engineer losing a board's inspection state after mapping components by hand is a real cost, and I decided the durability of their work was mine to own.

So I hardened it. I wrapped every localStorage write in a try-catch so a QuotaExceededError could not take down or corrupt a save. On quota, I surfaced a clear warning and pointed the user at clearing old inspection results. And I added a simple garbage collector: when an inspection completes, the tool measures total usage and removes the oldest entries once it crosses 4MB, keeping normal use safely under the 5MB ceiling. I kept the auto-save interface identical between server and standalone modes â€” only the storage implementation differs â€” so the rest of the code did not need to care which way it ran.

I also took on the distribution problem that came with it. Nobody was going to configure a server for these engineers, so I built for the reality they had: one file, distributed by email and USB, double-click to run. That is adoption work, and it sat outside the feature brief, but shipping a tool nobody can run is not shipping.

The result: the standalone build ran with the same functionality as the server version, auto-save included, with the quota path handled instead of ignored. It loaded in about 5 seconds on a factory machine, needed no Python or network or IT ticket, and the engineers could use it the moment they had the file.

My honest reflection is that I got the durability part right and the packaging part less so â€” the file landed around 25MB, close to a 20MB email attachment limit, and gzip compression would have cut it substantially. Owning a tool means owning whether it reaches people and whether it keeps their work, not just whether it compiles.

## Deep follow-ups (likely bar-raiser probes)

**Q: The standalone conversion was your task. What exactly did you take on that wasn't?**
**A:** Two things. First, the durability of the saved data. The conversion brief was "it works offline"; making sure a localStorage write could never silently fail against the 5MB cap was a failure mode nobody had assigned, and it does not show up in a demo. Second, distribution â€” getting the file into the engineers' hands on machines with no installs and limited IT â€” which is adoption work, not feature work.

**Q: Why did the quota issue matter if the cap is only 5MB?**
**A:** Because the failure is silent in effect. The inspector saves alignment config and per-board state keyed to the image and side, and an engineer can spend real time mapping components by hand. A write that throws on quota means that work does not persist, and there is no crash to warn you. For a tool people are supposed to rely on, that is worse than an obvious error.

**Q: How did you handle it specifically?**
**A:** A try-catch around every write so a QuotaExceededError cannot take down or corrupt a save; on quota, a clear warning and a suggestion to clear old inspection results; and a garbage collector that runs when an inspection completes and trims the oldest entries once total usage passes 4MB, keeping normal use under the 5MB ceiling.

**Q: Why 4MB and not just the full 5MB?**
**A:** Headroom. If I waited until 5MB to clean up, the next write â€” or an in-flight inspection â€” could still hit the cap. Trimming at 4MB means the system stays clear of the ceiling during normal use, so the user never sees the quota path in ordinary work.

**Q: Why localStorage at all, and not IndexedDB?**
**A:** IndexedDB has a much larger quota, but it is asynchronous, which complicates auto-save logic and requires callback handling. The data volume here is a few KB per inspection, so 5MB is sufficient and synchronous writes are simpler to reason about. If the data volume grew, IndexedDB would be the next step.

**Q: Isn't distribution really IT's job?**
**A:** In principle, but the constraint was real and immediate: those machines had no internet, no installs, and limited IT support, so a server-based deployment would have stalled the users entirely. I was closer to the problem and had a path â€” one file, email and USB â€” so I took it rather than hand it off and wait.

**Q: What would you do differently?**
**A:** Compress the embedded libraries harder. The ~25MB file bumped against a 20MB email attachment limit, and gzip could have brought it closer to 15MB. I owned getting it to the users, and that packaging detail was part of that ownership.
