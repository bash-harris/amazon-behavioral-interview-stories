# Q84 — tell me about a time you did something that was not your task (like go above and beyond)

**Mapped LP(s):** Ownership (primary); Customer Obsession (touch).

**Story used:** BGSW PCB Inspector Suite — the transparency layer on the BOM reconciliation tool (`AMAZON_INTERVIEW_PREPARATION.md` STORY 11, "Debug Endpoint for Manufacturing Transparency"). **Honest framing, stated up front:** the debug mode itself was assigned — my own prep notes call it my responsibility (STORY 11 Task, line 1045). I am **not** claiming it was outside my role, and I am not going to relabel assigned work as "not my task." This is the *"I exceeded the brief"* telling: the assigned deliverable was a debug view; what went past the literal ask was the reconciliation dashboard, a completeness bar nobody requested, and owning the tool's adoption until the engineers actually relied on it. One telling only: STORY 11.

## Answer (core, ~500 words)

I'll answer this honestly, because the honest version is more useful than the flattering one. The assigned task was a debug mode: expose the BOM reconciliation tool's internal reasoning so the manufacturing engineers could see why it called a component a mismatch. I built that. What went past the literal brief was everything I did after it — and I'd argue that's where the "above and beyond" actually lived.

The problem underneath the task was adoption, not visibility. The engineers used the tool but didn't trust it. When it flagged a mismatch, the report showed the verdict and hid the reasoning, so for anything that mattered they checked by hand. A debug view answers a question about one component; it doesn't tell an engineer whether the whole board is safe. So I built a second thing nobody asked for: a reconciliation dashboard over the same BOM, CAD, and inspection state — a live table with totals, matches, mismatches, and reviews, the component-type distribution, color-coded status chips, and severity ranking so missing components sort to the top. Clicking a row jumps to that component in the debug view. The dashboard lets you verify the whole board first, then drill in; the debug view answers the one-part question.

I also set a bar for myself that was not in the brief. The rule was: if an engineer asks "why did the tool call this a mismatch?", the debug view has to answer completely — the raw entry text, the parsed reference after every preprocessing step, the layout entry it matched, and the exact rule that fired. Any missing step just sends them back to me, which defeats the point of building transparency at all.

Then I owned what the transparency exposed. In the first week, using the debug view, the engineers found two cases where my heuristic was wrong — both unusual component-naming conventions. Those were my tool's mistakes, so I fixed them rather than defending the logic.

The outcome wasn't the feature; it was the behavior change. Once the engineers could see how a decision was made and check it against their own files, they stopped re-checking every result by hand and started relying on the tool for production verification.

My honest reflection is that I built all of this as an afterthought — I'd build the transparency from the start next time, because it didn't just explain the tool, it surfaced two real defects and earned the users' confidence. Going above and beyond for a customer usually isn't a longer feature list. It's removing the reason they don't trust the result.

## Deep follow-ups (likely bar-raiser probes)

**Q: But the debug mode was your task. How is this "something that was not your task"?**
**A:** It was my task — I'm not going to pretend otherwise. The debug mode is in my notes as my responsibility. The parts that weren't: the reconciliation dashboard, the self-imposed rule that the view must answer any "why" completely, and owning adoption until the engineers relied on the result. I'd rather give you the accurate version than stretch a bigger-sounding claim. If you want a case where nothing was assigned, the labeling tool I built for the training dataset is one — the tooling had no owner — but I didn't want to blur this story to make it sound better.

**Q: What does the dashboard give that the debug view doesn't?**
**A:** Scale of review. The debug view answers a question about one component. The dashboard shows the whole board — totals, matches, mismatches, reviews, component-type distribution — with severity ranking so missing components lead. Verify the whole board, then click a row and drill into the specific part.

**Q: How did you know the transparency actually helped?**
**A:** Two signals. Concrete: in the first week the engineers used the debug view to find two heuristic bugs, both unusual naming conventions, and both were quick to diagnose because the view exposed the intermediate data. Behavioral: they stopped re-checking by hand and started relying on the results for production verification.

**Q: Isn't exposing internal data a risk?**
**A:** It runs on localhost or the local network, not the internet, and it only shows data the engineer already has in their BOM and layout files. There's no new exposure — it's the same data, arranged so a human can audit the decision.

**Q: If the debug view itself were wrong, wouldn't that give false confidence?**
**A:** It displays the raw pipeline output consistently, so an engineer can compare that raw data against the actual BOM file and see exactly where the parse diverged — which is precisely how the two naming bugs were found. Hiding the intermediate data is what would create false confidence.

**Q: What would you do differently?**
**A:** Build the transparency from the start instead of as an afterthought. It would have surfaced the edge cases earlier. The lesson is that for an automated system, explainability isn't a nice-to-have — it's what makes the result usable at all.
