# Q21 — tell me about a time when you went out of your comfort zone

**Mapped LP(s):** Learn and Be Curious (primary); touches Invent and Simplify and Deliver Results.

**Story used:** BGSW PCB Inspector Suite — moving from Python/Flask to browser-only computer vision and learning OpenCV.js/TensorFlow.js from scratch (`AMAZON_INTERVIEW_PREP.md` STORY 5, "Learn and Be Curious — Browser-Based Computer Vision"; supported by `AMAZON_INTERVIEW_PREPARATION.md` STORY 12 and STORY 13 for the TPS-from-paper work, and STORY 8 for the later LLM-vision integration). ## Answer (core, ~470 words)

The clearest time I left my comfort zone was moving from Python and a Flask backend to running computer vision entirely in the browser — and doing it with two libraries I'd never used.

I was the only engineer on the PCB inspection tools, and the manufacturing engineers couldn't install desktop software because of IT restrictions. That constraint killed the obvious plan of a Python CV service. If the tool had to run on a locked-down factory machine, it had to run in the browser, which meant OpenCV.js for image processing and TensorFlow.js for inference. I'd never touched either, and this wasn't a toy — I needed feature matching, illumination normalization, and non-rigid warping to all work.

So I bounded the risk. I gave myself one day for a minimal prototype: load two images, convert to grayscale, run Canny edge detection, compute a difference. No pipeline, no abstraction — just enough to learn whether the library could do the core operations at all. It could, and that one day bought me the confidence to build the real thing.

The honest hard parts. OpenCV.js mirrors the C++ API, but the documentation was sparse and most examples I found were C++, so I was translating as I learned — Canny when I needed edges, CLAHE when I hit the lighting problem, ORB features when I needed alignment. TensorFlow.js bit me on tensor layout: it expects a specific tensor shape, and I fed it `[1, 3, 224, 224]` when the model wanted `[1, 224, 224, 3]`. That shape mismatch took about three hours to find. And the worst one — Thin Plate Spline warping had no JavaScript library at all. I read the original Bookstein 1989 paper and implemented the algorithm from scratch, checking my results against the paper's examples. That's the real definition of outside my comfort zone: I didn't just use unfamiliar tools, I implemented an algorithm from the primary literature.

My rule throughout was to learn just enough to build the next feature, then build it, rather than trying to master the whole library up front. I spent a couple of days on the documentation and the minimal prototype, then iterated for about two weeks.

The payoff was concrete: 40ms comparison and 60ms inference, fast enough to be interactive, and browser-based deployment meant no IT approval and immediate adoption. I learned the lesson well enough to repeat it — later I integrated a GPT-4o vision API, another unfamiliar surface, and again I evaluated the alternatives (GPT-4V, Claude 3, Gemini Pro Vision) and let the measured constraints pick.

What I'd do differently: I'd write the tensor-shape assertion first, before any inference code, so the three-hour debug becomes a one-line failure. And I'd start the TPS implementation from a written derivation rather than jumping into code — I spent time re-deriving what the paper had already established.

## Deep follow-ups (likely bar-raiser probes)

**Q: How did you actually learn OpenCV.js — what was your process?**
**A:** Three steps: read the official docs for the API surface, build a minimal prototype to validate the core operations, then build the full pipeline incrementally. I spent about two days on the first two steps, then roughly two weeks iterating on the pipeline. OpenCV.js mirrors the C++ API closely, so general OpenCV knowledge transferred, but much of the documentation and most examples were C++, so I was translating as I went.

**Q: What was the hardest part of TensorFlow.js?**
**A:** The data pipeline. The library expects tensors in a specific layout (NHWC), and the preprocessing — resize, normalize, transpose — has to match exactly what the model was trained on. I fed `[1, 3, 224, 224]` when the model wanted `[1, 224, 224, 3]`, and that took about three hours to isolate. I now check tensor shapes before inference as a rule.

**Q: How did you stay productive while learning unfamiliar libraries?**
**A:** I set a rule: learn just enough to build the next feature, then build it. I didn't try to learn all of OpenCV.js up front — I learned Canny when I needed edges, CLAHE when I needed illumination normalization, and ORB features when I needed alignment. That kept the learning focused and immediately applicable instead of theoretical.

**Q: You implemented TPS from scratch. How did you validate it without a reference implementation?**
**A:** I read the original Bookstein 1989 paper and implemented it step by step, checking intermediate results against the paper's examples. The math is a sum of radial basis functions (r² log r in 2D) centered on control points, plus a linear polynomial term, solving a linear system of size (n+3)×(n+3). Because it has a closed-form solution, I could verify each stage deterministically rather than tuning it.

**Q: What was the risk of failure, and what would you have done if the browser couldn't do it?**
**A:** The real risk was that the browser stack couldn't hit interactive performance on factory hardware, which would have invalidated the whole no-install plan. I managed it by spiking the core operation in one day before committing. Honest gap: the source doesn't record a fallback plan if that spike had failed — I'd have been back to a server deployment the network constraints were already ruling out. What I relied on was bounding the unknown cheaply before building on it.

**Q: What would you tell someone learning browser-based CV for the first time?**
**A:** Start with a minimal prototype — load an image, run one operation, visualize the result. Then add operations incrementally rather than trying to build the full pipeline before understanding the pieces. And profile with the browser devtools, because WebGL acceleration is the difference between usable and not for tensor operations.

**Q: Why is this "outside your comfort zone" rather than just your job?**
**A:** Because the plan I already knew how to build — a Python CV service — was ruled out by the environment, and the replacement required learning an unfamiliar language surface and then implementing a non-rigid alignment algorithm that had no JavaScript library. I was doing primary-literature work, not API calls.
