## Answer (core, ~450 words)

The time I remember being genuinely stuck was about three hours into a TensorFlow.js bug where the model wasn't giving me correct predictions and I couldn't see why.

The setup: the PCB inspection tools had to run in the browser, because the manufacturing engineers couldn't install software on the factory machines under IT restrictions. So I was implementing the computer-vision pipeline in JavaScript with OpenCV.js and TensorFlow.js — neither of which I had used before. I'd loaded a pre-trained EfficientNetV2S defect classifier and wired up the preprocessing: resize to 224×224, normalize. When I ran inference, it didn't produce what I expected, and there was no obvious next step. I had to decide where to look.

What I did was stop changing code and treat it as a data-plumbing problem. I stripped the pipeline down to a minimal input and inspected the tensor right before it entered the model, then compared it against the shape the model actually expected. TensorFlow.js is explicit about tensor layout, and the model wanted NHWC — batch, height, width, channels. My preprocessing was producing the values in a different order: `[1, 3, 224, 224]` instead of `[1, 224, 224, 3]`. Same data, wrong arrangement, so the model was receiving the wrong thing. Seeing the produced shape next to the expected one made it obvious; the fix was to make the preprocessing emit the layout the model was trained on. Finding it was the hard part — the change itself was small.

The lesson wasn't really about TensorFlow. It was a method for when you don't know where to look: don't hunt at random — find the boundary where the data has to be a known shape and check it there. I now check tensor shapes before inference as a reflex, and I'd assert the shape up front so a mismatch surfaces immediately instead of costing three hours.

The shape debug was part of a rule I still use: learn just enough to build the next feature, then build it. I didn't try to master all of TensorFlow.js up front — I learned its data pipeline exactly where it bit me, at the preprocessing boundary, and moved on. The same approach carried me through the other unfamiliar library in that pipeline: the OpenCV.js documentation was sparse and many examples were written in C++ rather than JavaScript, so learning the pipeline was genuinely non-trivial. The payoff was worth it — inference ran at roughly 60 ms per image through WebGL on a standard laptop, fast enough to ship the ML feature client-side, with no server for the factory floor to configure.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why did the wrong tensor shape happen at all?**
**A:** Because TensorFlow.js is explicit about tensor format, and the preprocessing steps — resize and normalize — had to produce exactly the layout the model was trained on. Mine produced the values in the wrong order for that model. It's an easy thing to get wrong when the library is new to you; the discipline is to verify the format instead of assuming.

**Q: What exactly is the difference between those two shapes?**
**A:** They're two orderings of the same four dimensions — batch, height, width, channels. TensorFlow.js wanted NHWC, `[1, 224, 224, 3]`; my preprocessing built the data as `[1, 3, 224, 224]`. Same numbers, wrong arrangement, so every value reached the model in the wrong position.

**Q: How did you isolate it rather than guessing?**
**A:** I reduced it to a minimal input and inspected the tensor right before the model call, then compared it against the layout the model expected. Seeing `[1, 3, 224, 224]` next to `[1, 224, 224, 3]` made it obvious. The method is to find the boundary where the data must be a known shape and check it there, instead of changing code at random.

**Q: Why not use a wrapper or a reference implementation?**
**A:** A wrapper would have hidden the exact fault I needed to understand. The mismatch was in how my preprocessing fed the model, so a reference wouldn't have fixed my pipeline. Understanding the data format was the point, and it's knowledge I keep.

**Q: How do you prevent this class of bug now?**
**A:** I check the tensor shape before inference, so a mismatch shows up immediately instead of costing hours of hunting. More generally, when a result is wrong and the cause isn't obvious, I locate the boundary where the data contract is defined and verify the data there.

**Q: What was the outcome for the product?**
**A:** In-browser inference worked at roughly 60 ms per image via WebGL, which made the client-side ML feature viable on the factory machines — no server needed. That mattered because the factory floor had no way to install or host one.
