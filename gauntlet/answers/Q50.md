## Answer (core, ~490 words)

The time I genuinely didn't know what to do next was when I had to implement Thin Plate Spline warping and there was no JavaScript implementation I could use. I knew *what* I needed — a non-rigid correction on top of the global alignment — but I had no idea how to build it in the browser.

Here's the setup. I was aligning photographs of PCBs to their CAD layouts. Homography corrected the global perspective, but boards go through a reflow oven and warp, and that warp isn't uniform — the center bows differently than the edges. A global transform cannot fix a local bow, by definition. The only way the comparison could be meaningful was a non-rigid stage. I searched for a JavaScript TPS library and found none. So the problem changed from "call the right function" to "derive and implement the algorithm," which is a completely different kind of stuck.

Before I wrote anything, I narrowed the choice. Elastic deformation needs material properties that don't have a clear physical meaning for a PCB. B-spline transforms need a control-grid resolution, another hyperparameter I'd have to guess. TPS minimizes bending energy and is deterministic given the control points, so it gave me a target I could verify rather than tune. That mattered, because with no reference implementation I needed a way to know I was right.

The way out was the primary source. I read the original Thin Plate Spline paper — Bookstein, 1989 — because the secondary explanations skipped the actual math. I implemented it step by step and, crucially, checked intermediate results against the examples in the paper rather than only judging the final image. That was the whole method: with no library to test against, the paper's own examples became my test. I wired it in after the homography stage and selected control points by template matching known features — board corners, fiducials, component pads — rejecting any match whose similarity fell below a threshold, because a single bad control point pulls the whole warp the wrong way.

Then I proved it rather than stopping at "it ran." The manufacturing engineers reported the tool now correctly identified component mismatches on warped boards that had previously triggered false alarms, and the alignment became consistent enough that the comparison's 10-pixel mismatch threshold was finally reliable. The pipeline handled boards photographed up to 30 degrees off-perpendicular and up to 3mm of visible warp — and I was honest with myself about the boundary: very severely warped boards, above about 5mm, still defeat it, and steep angles past roughly 45 degrees break feature matching outright, so a more physically based model would be needed for those.

What that taught me is a rule I've kept: learn just enough to build the next feature, then build it. I didn't try to master the whole computer-vision stack up front — I learned Canny when I needed edges, CLAHE when I needed illumination normalization, SURF when I needed feature matching, and TPS when I needed non-rigid warping. A smaller version of the same pattern bit me with TensorFlow.js: I fed the model a `[1, 3, 224, 224]` tensor when it wanted `[1, 224, 224, 3]`, and that took about three hours to isolate. I now check tensor shapes before inference as a reflex.

My honest reflection: I'd start simpler and add complexity incrementally — I spent time implementing full SURF feature matching before discovering that board-outline contour detection was sufficient for most boards — and I'd have questioned my assumption that TPS was the final answer, since severe warping still defeats it.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why not just use an existing library or a simpler method?**
**A:** There was no JavaScript TPS library — I searched for one. And "simpler" wasn't actually simpler here: elastic deformation needs material properties that have no clear meaning for a PCB, and B-splines add a control-grid resolution I'd have to guess. TPS is deterministic given the control points and minimizes bending energy, which gave me something I could verify when I had no reference implementation to test against.

**Q: How did you validate an implementation when nothing existed to compare it to?**
**A:** Against the paper itself. Bookstein's 1989 paper includes worked examples, so I checked intermediate results stage by stage against those rather than only eyeballing the final warped image. Combined with template matching for control points and rejecting low-similarity matches, that kept a wrong control point from silently pulling the warp.

**Q: Explain what TPS actually does, simply.**
**A:** It fits a smooth deformation field that passes through a set of control points while minimizing a "bending energy" measure, so the warp is exact at the points and smooth everywhere between them. In practice: I supply correspondences — this point in the photo should land on this point in the layout — and TPS turns them into a warp that corrects the local board distortion a single global transform can't represent.

**Q: How did you decide the problem was worth this depth rather than a workaround?**
**A:** Because the comparison runs on a fixed mismatch threshold; if alignment is off, every result downstream is noise. The warping was real and visible in the images, and the requirement was concrete, so the depth was tied to whether the tool could work at all — not to polish. If a simpler fix had met the threshold, I'd have taken it, and I deliberately compared the alternatives before committing.

**Q: How did you keep from being stuck for days without a path?**
**A:** I changed the question. Once no library existed, "find the function" had no answer, so the tractable version was "pick the method with a verifiable ground truth, then build it against that ground truth." The paper's examples gave me checkpoints, so I always had a next test even when I didn't have a next answer. And the rule I use generally is to learn just enough to build the next feature, then build it.

**Q: What did the result actually prove?**
**A:** That the non-rigid stage was real, not cosmetic. The engineers told me the tool was correctly catching mismatches on warped boards that had previously set off false alarms, and alignment got consistent enough for the 10-pixel comparison threshold to be trustworthy. I also know its edge — severe warp beyond about 5mm and angles past roughly 45 degrees still fail, and I'd say so rather than imply it's universal.

**Q: What would you do differently?**
**A:** Start simpler and add complexity incrementally. I spent time implementing full SURF feature matching before discovering board-outline contour detection was sufficient for most boards — SURF is more general but costlier and harder to debug. And I'd have questioned my assumption that TPS was the final solution, since severely warped boards still defeat it. For the TensorFlow.js shape mismatch (I fed `[1, 3, 224, 224]` when the model wanted `[1, 224, 224, 3]`, about three hours to isolate), I'd assert the tensor shape up front so that failure is one line instead of three hours.
