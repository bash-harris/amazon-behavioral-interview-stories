## Answer (core, ~470 words)

The feedback came five days into the first prototype of the board-comparison tool.

There had been a six-month backlog to build an automated PCB comparison tool, and it kept stalling because it was "too complex" to scope. I stopped scoping and built a working prototype: a single monolithic HTML file, inline JavaScript, a basic pixel-level comparison. It worked under ideal conditions and was rough everywhere else. I demoed it to my engineering lead on day five, he shared it with the team immediately, and within an hour they came back with three critical issues: the pixel comparison failed under illumination changes, there was no image alignment so boards had to be photographed at exactly the same angle, and there was no export so results couldn't be saved.

I accepted all three and implemented them in priority order — which was not the order they were listed. Alignment first, because without it every comparison on a real photo was untrustworthy. Illumination second, because it was the most frequent complaint. Export third, because it was valuable but didn't block inspection.

Here is what actually changed. For alignment, the fix was two-stage: a homography to correct global perspective, then a non-rigid Thin Plate Spline warp to correct the local board flex that a global transform can't. That alignment pipeline took average misalignment from 15–20 pixels to 2–3. For illumination, I applied CLAHE — contrast-limited adaptive histogram equalization — to both images before comparison, so lighting variation stopped registering as a difference and the tool stopped keying on shadows. Those fixes went into shared modules, so all three tools inherited them; when I improved a shared component, every tool benefited automatically. For export, I added PNG/PDF output so engineers could save and share a comparison.

Then the part that matters as much as the fixes: proving they landed. I didn't declare victory because it demoed well. I validated the alignment on 20 board images with ground-truth markers — average offset 2.1 pixels, standard deviation 0.8 — and had the manufacturing engineers overlay the aligned photo on the layout to eyeball the pads, which catches a good number hiding a subtly wrong warp. I kept a fixed regression set and re-ran it after each change, so a fix for one issue couldn't silently break another. And the behavioral signal: engineers reported the tool now caught mismatches on warped boards that previously triggered false alarms. It went production-ready in two weeks — five days to the prototype, nine days of refinement.

Two changes outlasted the tool. First, I now build observability in from the start: the debug view on the later BOM tool was an afterthought, and building it from the beginning would have surfaced edge cases sooner. Second, I applied the same collect-the-failures-then-analyze-the-patterns discipline to the Good Board tool's illumination, rotation, and scale problems instead of fixing symptoms one at a time.

The review cost me an hour of pride and bought a two-week roadmap that was actually right. What I implemented wasn't an apology — it was three fixes and a measured check on each.

## Deep follow-ups (likely bar-raiser probes)

**Q: How did you decide the priority order?**
**A:** Impact and frequency. Alignment gated everything — without it, every comparison on a real photo was untrustworthy, so nothing else mattered until it worked. Illumination was the most frequent complaint. Export was valuable but didn't block inspection, so it went last. The team set the problems; I owned the sequencing.

**Q: How did you know the fixes actually worked, rather than just that you shipped them?**
**A:** Three signals. Quantitatively, the alignment was validated on 20 board images with ground-truth markers — average offset 2.1 pixels, standard deviation 0.8. Qualitatively, the manufacturing engineers overlaid the aligned photo on the layout and spot-checked that pads lined up, which caught cases where the metric looked fine but the warp was subtly wrong. Behaviorally, they reported the tool now caught mismatches on warped boards that used to trigger false alarms. I also re-ran a fixed regression set after each change so a fix for one issue couldn't break another.

**Q: The alignment fix was the hardest one. What did it actually take?**
**A:** Two stages of math instead of one. A homography corrects global perspective — board tilt, the photo not being perfectly perpendicular — but it can't correct local deformation, and boards flex non-uniformly in the reflow oven. So I added a Thin Plate Spline warp on top, which fits a smooth warp through control points at board corners, fiducials, and component pads, rejecting any match below a template-similarity threshold. That combination took average misalignment from 15–20 pixels to 2–3.

**Q: What did the illumination fix change, concretely?**
**A:** I applied CLAHE to both images before comparison. The pixel comparison was flagging lighting variation and shadow edges as differences. Normalizing local contrast first meant illumination stopped registering as a defect and the tool could actually see the meaningful differences — like a wrong-value component with slightly different markings. I put it in shared preprocessing, so all three tools got it, not just the comparison tool.

**Q: Wasn't this just the team's list? How is that your work?**
**A:** The team set the problems; I owned the solution and the proof. I chose the priority order by dependency, chose the methods — homography plus TPS, CLAHE, client-side export — and then had to show each one landed, which is where the 2.1-pixel validation and the regression set came from. Anyone can accept a critique; the job is converting it into changes that survive contact with real boards.

**Q: What changed in how you work afterwards?**
**A:** Two things. I build observability in from the start now, because the debug view on the later BOM tool was an afterthought and building it earlier would have surfaced edge cases sooner. And I apply the same collect-failures-and-analyze-patterns discipline to the next tool instead of fixing symptoms one at a time — that's what I did with the Good Board tool's illumination, rotation, and scale problems. I also ask for the specific failing case rather than a general verdict, because a case is reproducible and a verdict isn't.
