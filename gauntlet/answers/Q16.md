## Answer (core, ~500 words)

Going beyond surface-level analysis means refusing to stop at the first explanation that fits. My clearest example is the BOM parser in the PCB inspection suite.

The tool reconciled a Bill of Materials exported from SAP against a PCB layout and reported missing, extra, or mismatched components. My first parser was the obvious one: read the Excel file with XLSX.js and pull each reference out with a regex like `/^[A-Z]+\d+$/`. It worked for roughly 70% of real BOMs. Then production files arrived and it broke — and "broke" is where the dive starts, because the surface symptom and the root cause were different things.

The first failure looked total: the report said every component was missing. The shallow read is "the file didn't parse." I didn't accept that. I added logging to print the raw cell values and saw every reference coming back as "MP_R1" instead of "R1" — a manufacturing process code prefixed onto the reference. The fix wasn't a blind strip. I audited the pattern across thousands of entries, found `MP_` was consistently a two-to-three-letter process code always followed by a standard reference, and stripped only `/^[A-Z]{2,3}_/`. I also questioned the opposite risk: could I be deleting a legitimate prefix like "TP" for test points? That's why I keyed the rule on the suffix pattern, not just "anything with an underscore."

Second: cells that looked empty. SAP exports some cells as hyperlinks, and XLSX.js returns an object, not a string. My test data had none, so I stopped trusting my test data. I wrote a recursive extractor that walks the cell: plain string first, else the `v` value, else the `l` link's display text.

Third: `R1||R2` — one physical position, two possible parts depending on board variant. I had silently dropped these as invalid. The real question wasn't "is this a valid string," it was "what does the manufacturing line mean by it." Once I understood it as a valid match target, I split both `||` and `/` and tested the matrix — `R1||R2`, `R1/R2`, `R1||R2||R3`, and malformed cases like `||R1`.

Fourth, the subtlest: `DNP_R3` — Do Not Populate. My parser treated it as a required component and reported it missing, which was technically true and semantically wrong. DNP means the position should be empty. I detected it case-insensitively and marked the position intentionally empty.

What made this a dive rather than four patches was the audit around it: a suite of 15 representative production BOMs, one per edge case, grown every time production found a new one, and re-run after every change. The result was zero false positives and zero false negatives across those 15 BOMs, and a 2,000-component BOM parsed in under 200 milliseconds. In the first week it caught three real mismatches manual review had missed — against a manual cross-reference that took 20 to 30 minutes per board.

The lesson: surface analysis tells you *what* broke, not *why*. I'd assumed the references were the data; the real work was understanding the conventions underneath them.

## Deep follow-ups (likely bar-raiser probes)

**Q: Walk me through how you discovered the MP_ issue.**
**A:** The first real BOM run showed every component as missing. I initially thought the parser wasn't reading the file at all. I added logging to print raw cell values and saw that every reference was prefixed with "MP_," like "MP_R1" instead of "R1," while the layout correctly showed "R1." The mismatch was entirely a BOM naming convention, not a parsing failure — which is precisely the difference between the symptom and the cause.

**Q: Why regex rather than structured or positional parsing?**
**A:** The BOM is semi-structured: it has rows and columns, but column positions vary between exports. Some put references in column A, others in column C. The only reliable signal is the text pattern itself, since a component reference always looks like letters followed by numbers. A positional mapping would need configuration per BOM variant, which defeats the point of automation for non-developer users.

**Q: You mentioned a recursive cell extractor. Walk through the recursion.**
**A:** XLSX.js returns cell values in different types. A plain string is direct. A formula result might be numeric. A hyperlink is an object where the display text lives inside the link, not the raw value. Some cells are null. My extractor takes any cell object and returns a clean string: if it's a string, return it; if it has a `v` property, recursively extract `v`; if it has an `l` property, extract the link's display text. Checking properties in priority order let it handle nested structures I hadn't anticipated.

**Q: Why not just ignore DNP entries, and how did you know it was a false positive?**
**A:** The report said "missing: DNP_R3," which is technically correct but semantically wrong, because DNP means the position *should* be empty. Treating DNP as a required component created false "missing" alerts. The fix was to detect DNP case-insensitively and mark the position as intentionally empty rather than required. That's the kind of false positive that erodes trust in an inspection tool, so it mattered.

**Q: How did you know the prefix-strip rule wouldn't damage legitimate prefixes?**
**A:** I audited the pattern instead of assuming it. `MP_` was consistently a manufacturing process code always followed by a standard reference pattern. Legitimate prefixes like "TP" for test points have a different suffix pattern. My operating rule became: never normalize without understanding the semantics. If a case appears where I don't understand the convention, I leave it alone and flag it rather than guess.

**Q: What would you do differently, and what surprised you?**
**A:** I discovered the edge cases reactively, each one causing a production failure; I'd collect sample BOMs from the manufacturing floor before writing code next time. What surprised me was DNP proximity: I'd assumed DNP was simple — just skip it — but its interaction with variant references was a subtle logic puzzle that required understanding manufacturing intent, not just matching text.
