## Answer (core, ~470 words)

The problem I saw was that the defect classifier I needed to train had no usable data, and the obvious way to fix that was going to be slow and error-prone.

Context: I was building the ML defect classifier for the PCB inspection suite — take a cropped image of a component and label it good, wrong value, wrong orientation, or missing. The classifier is only as good as its training set, and the images I had were unlabeled: boards with known good and defective components, but no link between an image and its label. The default path was a spreadsheet — open an image, look at it, type the label, repeat. At roughly 30 seconds an image across about 2,000 images, that's close to 10 hours of work, and a single mis-typed label quietly degrades the training set the engineers would have to trust.

So instead of accepting the spreadsheet, I looked at where the bottleneck actually was: the labeling interface, not the labels. That's the problem I decided to solve. I built a small Tkinter desktop app: one component image at a time, keyboard shortcuts — G for good, 1 through 4 for the defect types — and the next image loads automatically. I kept the UI deliberately bare, because any extra complexity would slow the person labeling. Pillow handled image display and pandas handled the CSV.

The part I'd call invention was in how I chose the pieces and who I asked. I did not build a web-based labeler. I looked at what a browser tool would cost — a local server, file serving, browser-compatibility work — and what it would buy, which was nothing for a tool I ran on my own machine; Tkinter ships with Python and needed only Pillow. I drew the format from both sides: the output was a flat CSV — inspectable, one row per image — partly because that's a file the manufacturing engineers already lived in, and the CSV columns matched exactly what the TensorFlow.js training pipeline already consumed, so there was no conversion step. That last point is the durable part: the schema is the interface, so the same labeling workflow and format scale to the next dataset without rework. I also considered where the tool would grow — a multi-label version would change the pipeline's loss function and output layer, which told me the single-label CSV was the right simple boundary for now.

Two details I added because the data mattered more than the demo: a skip key for images too blurry or ambiguous to call, which sent them to a separate file rather than forcing a guessed label into the set; and a resumable session, because labeling 2,000 images spans more than one sitting.

The result: per-image labeling dropped from about 30 seconds to about 3, so the full ~2,000-image set took roughly 100 minutes instead of an estimated 10 hours, in the format the pipeline consumed directly. That dataset is what the classifier was trained on, and the classifier is what gave the manufacturing engineers an automated defect check.

What I'd do differently: add batch labeling for near-identical crops. Many were the same component at a slightly different angle, and a "label all similar" function would have cut the remaining time.

## Deep follow-ups (likely bar-raiser probes)

**Q: Who is the customer here? It sounds like you built this for yourself.**
**A:** The end customers were the manufacturing engineers who needed the defect classifier — the labeling step was the bottleneck between them and a model they could rely on. I designed the tool around the person doing the labeling, but the reason it had to be fast and correct is that an error-prone dataset trains an unreliable model for the floor. That's the line from the tool to the customer.

**Q: Why Tkinter instead of a web-based labeling tool?**
**A:** It was the simplest thing that met the requirement. A web tool would have meant a local server, file serving, and browser-compatibility work. Tkinter ships with Python, needed only Pillow, and runs anywhere Python runs. The trade-off is a plainer UI, but for an internal tool polished chrome wasn't the point.

**Q: Where did the ideas for the design actually come from?**
**A:** Two places. Externally, I weighed the coding options — a web labeler against the built-in Tkinter/Pillow/pandas stack — and picked on the constraint, not familiarity. Internally, I shaped the output around the people downstream: CSV because a flat sheet is what the manufacturing engineers already work in, and the columns were matched to the training pipeline so no conversion step would exist.

**Q: How did you handle an image that could be both "wrong value" and "wrong orientation"?**
**A:** The tool allows one label per image, which forces a decision about the primary defect — that's what training needs. If the defect was genuinely ambiguous, I used the skip key and deferred it rather than forcing a coin-flip label into the set. In practice most defects were cleanly one type.

**Q: What did the tooling actually save, in numbers?**
**A:** About 30 seconds per image down to about 3, so the ~2,000-image set took roughly 100 minutes instead of an estimated 10 hours — and it came out in the format the pipeline expected, removing a conversion step.

**Q: Why CSV and not JSON?**
**A:** CSV is simpler to generate and easier to inspect — it opens in Excel, which the team already lived in. The labels are flat (one row per image: filename, label, timestamp), so nested JSON would have added structure with no benefit.

**Q: What would you do differently?**
**A:** Add batch labeling for near-identical crops. Many were the same component at a slightly different angle, and grouping them would have cut the remaining time and shown how much of the set was near-duplicate content rather than new information.
