# Q2 — tell me about a time you used genai to automate or streamline a workflow

**Mapped LP(s):** Invent and Simplify (primary); touches Deliver Results and Frugality.

**Story used:** BGSW PCB Inspector Suite — the BOM parser/reconciliation and the transparency debug endpoint (`AMAZON_INTERVIEW_PREPARATION.md` STORY 1 "The BOM Parser That Refused to Break" + STORY 11 "Debug Endpoint for Manufacturing Transparency"), with the GPT-4o VLM as the GenAI interpretation layer (`AMAZON_INTERVIEW_PREPARATION.md` STORY 8). This is a synthesis across the same BGSW suite, anchored on the documented BOM workflow outcome rather than Q1's per-mismatch productivity story. Tab Scroller is not used.

## Answer (core, ~480 words)

I built the PCB inspection tools at Bosch. Before them, verifying a board's Bill of Materials was a manual chore: an engineer took the SAP-exported BOM spreadsheet and cross-referenced it, part by part, against the Altium layout — 20 to 30 minutes per board, and easy to get wrong. Even after we automated the first pass, every flagged mismatch still meant a person zooming in to decide what the discrepancy actually was. Those were two manual steps I wanted to delete, so I used deterministic parsing plus GenAI to automate the workflow end to end.

My task was to let a non-developer upload a BOM and a layout and get a trustworthy reconciliation report in seconds. The constraint was the environment: factory-floor machines with restricted network access, and I was the only developer.

The naive parser — a regex like `/^[A-Z]+\d+$/` — worked on about 70% of real BOMs, then production data broke it. Four edge cases, each fixed at the root, not the symptom. Some references carried an `MP_` manufacturing-process prefix. Some SAP cells were hyperlinks, so the parser had to follow the link to the display text instead of grabbing the URL. Some positions were variants — `R1||R2` or `R1/R2` — which the manufacturing engineer pointed out should match either part, so I built a variant splitter that normalizes both separators. And DNP entries marked positions that were intentionally empty, not missing. I built a 15-BOM test suite and reran it after every change. Then the GenAI layer: when reconciliation flagged a suspicious component, I cropped that region from the layout and the photo and sent both to GPT-4o with a structured prompt, asking it to identify the component type and classify the mismatch — wrong value, orientation, missing, extra, or false alarm — and return JSON I could parse. I evaluated GPT-4V (about 8 seconds per request versus 3), Claude 3, and Gemini Pro Vision before choosing GPT-4o; a local LLaVA would have needed 8GB of VRAM the factory machines didn't have. To keep it honest, I also built a `?debug=true` view showing the raw BOM text, every preprocessing step, the layout match, and the exact decision tree, plus a reconciliation dashboard of aggregate stats.

In testing against 15 production BOMs the reconciliation produced zero false positives and zero false negatives, and a 2,000-component BOM parses in under 200 milliseconds. The workflow that took 20–30 minutes of manual cross-referencing now returns a report in seconds; in its first week it caught three real mismatches manual review had missed. The GenAI layer cut a per-mismatch interpretation from about 30 seconds to about 5, at roughly 85% accuracy, and the debug view earned trust — engineers used it to surface two more naming edge cases in week one.

What I'd do differently: collect representative BOMs from the floor before writing code instead of finding edge cases reactively, and build the debug endpoint from day one. The VLM also taught me its ceiling: it reads type and orientation well, but not values on tiny surface-mount parts.

## Deep follow-ups (likely bar-raiser probes)

**Q: Where is the GenAI actually doing work, and why not just send everything to the model?**
**A:** The structured part — matching references between the BOM and the layout — is deterministic. A parser is cheaper, faster, and explainable, so I kept the model out of it. GenAI does the part rules can't: look at a flagged region and say "wrong orientation" versus "lighting artifact" in natural language. Sending every component to a VLM would be slower and costlier for no gain; I only send the small set the reconciliation already flagged.

**Q: How do you know the workflow actually improved rather than just adding automation on top?**
**A:** Numbers, not vibes. The manual cross-reference was 20–30 minutes per board; the report now comes back in seconds. In testing across 15 production BOMs the reconciliation produced zero false positives and zero false negatives, a 2,000-component BOM parsed in under 200 milliseconds, and in the first production week the tool caught three real mismatches manual review had missed. On the GenAI side, interpreting a flagged mismatch dropped from about 30 seconds to about 5, at roughly 85% accuracy.

**Q: What happens when the model is wrong, or the API is down?**
**A:** The output is presented as a suggestion, labeled "AI Analysis" with a confidence percentage, and the engineer verifies it. I added a feedback mechanism to mark analyses correct or incorrect, which surfaced systematic prompt errors. If the API is unreachable or no key is configured, the reconciliation still runs and the visual highlights still show; the UI says AI analysis unavailable. The VLM is an enhancement, not a dependency.

**Q: Walk me through the messy-data edge cases.**
**A:** MP_ prefix; hyperlink cells (follow to the display text, not the URL); variants like `R1||R2` and `R1/R2` (split, normalize, match either part — the manufacturing engineer flagged this); and DNP positions that are intentionally empty, not missing. Each was root-caused and added to the 15-BOM regression suite, and the debug view shows the raw text and every step so a new format is easy to diagnose.

**Q: Where did the design ideas come from, inside and outside the company?**
**A:** Externally I evaluated GPT-4V, Claude 3, Gemini Pro Vision, and a self-hosted LLaVA before settling on GPT-4o, and built on OpenCV.js and TensorFlow.js. Internally, a manufacturing engineer told me how the `R1||R2` variant notation should be interpreted; the engineers' use of the debug view surfaced two more edge cases in week one; and I walked the image-data question through the security team, who approved sending board photos because they contain no trade secrets.

**Q: What would you do differently?**
**A:** Collect representative BOMs from the floor before writing any code — I found the edge cases reactively, each one a production failure. Build the debug endpoint from the start; it would have caught them during development. And respect the VLM's ceiling: strong on component type and orientation, weak on reading values from small SMD parts, so I'd design the UI around that.
