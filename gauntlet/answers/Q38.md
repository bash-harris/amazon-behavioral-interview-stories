# Q38 — tell me about a project where you chose the ui/middle layer/database/etc

**Mapped LP(s):** Are Right, A Lot; Invent and Simplify.

**Story used:** BGSW PCB Inspector Suite — the decision to make the suite browser-only with embedded libraries and a single-file distribution, plus the storage-layer choice of localStorage over IndexedDB (`AMAZON_INTERVIEW_PREPARATION.md` STORY 4, "The Standalone HTML That Replaced a Server"; supported by STORY 5 for the browser-CV middle layer and the "why the browser at all" trade-off in `BAR_RAISER_TECHNICAL_PREP.md`). One telling only: STORY 4's ~12.5 MB libraries, ~25 MB file, ~5 s vs ~2 s, base64 WASM, and 5 MB localStorage. The 150 MB / $500-per-month tellings in `AMAZON_INTERVIEW_PREP.md` are not used. Distinct from Q21 (learning the unfamiliar stack) and Q29 (a deployment blocker): the subject here is the choice among options and why it was right.

## Answer (core, ~470 words)

I'll give you the stack decision on the PCB inspection suite, because it was a real choice between options and it drove everything else.

The obvious build was a Flask backend with a browser front end — Python for the BOM parsing and image processing, a web page on top. That's the default for this kind of tool, and it's where I started. But the users were manufacturing engineers on factory-floor machines with restricted network access: no internet, no installs, limited IT. A Flask server meant Python, dependencies, and network configuration those engineers couldn't support, and a desktop app meant an install IT wouldn't approve. Those two options were ruled out by the environment, not by preference.

The middle layer I chose instead was browser-only: OpenCV.js for image processing and alignment, TensorFlow.js for inference, PDF.js and XLSX.js for the document parsing. I evaluated each against the native desktop alternative on the one axis that mattered — could it run with no install and no network on a locked-down machine? The browser libraries could. Then, to remove the last server dependency, I embedded all of them in the HTML as base64, including the OpenCV.js WebAssembly binary as a data URL instead of a fetched `.wasm` file, so the whole suite was a single file. That's a deliberate simplicity trade: base64 adds about 33% overhead, but one file eliminates the failure mode where someone moves the HTML and the tool breaks because the companion files didn't come with it.

The database layer was its own choice. Auto-save needed persistence, and the realistic options were localStorage and IndexedDB. I chose localStorage: it's synchronous, so the auto-save path is simple to reason about; the data is only a few kilobytes per inspection; and its 5 MB quota is plenty at that volume. IndexedDB has a much larger quota and handles structured data, but it's asynchronous, which complicates the save path for a benefit I didn't need yet. I added a quota check and a small garbage-collection pass that drops the oldest entries past about 4 MB, and I said I'd switch to IndexedDB if the data volume grew.

The outcome: a ~25 MB single HTML file that loads in about 5 seconds on a factory machine versus 2 seconds server-backed, with identical functionality. Engineers double-click it — no Python, no network, no IT ticket. I was right about the stack and wrong about one assumption: I assumed every machine had a modern browser, and some had IE11, which can't run WebAssembly. I added a clear compatibility check rather than pretending it worked, and named the real cost of the choice — no central audit log or shared calibration data, because everything is local. If I did it again, I'd compress the embedded libraries; gzip could take the file toward 15 MB.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why not just run a local server on each machine?**
**A:** That is the deployment problem, not a solution to it: Python, dependencies, and network configuration on a machine the engineers don't administer and IT won't support. The browser already existed on the machine; I built on it.

**Q: Why base64 embedding instead of separate files or a service worker?**
**A:** Single-file distribution removes the failure mode of a moved HTML missing its companions. A service worker would need HTTPS and has browser-compatibility issues; base64 is browser-agnostic. The cost is ~33% size overhead, which I accepted.

**Q: localStorage versus IndexedDB — defend the choice.**
**A:** Data volume per inspection was a few KB, so 5 MB was sufficient; localStorage is synchronous, which keeps the save path simple; IndexedDB is asynchronous and structured but I didn't need the capacity yet. I added quota handling and committed to switching if the data grew.

**Q: How did you verify the standalone build behaved like the server version?**
**A:** A test harness ran the same 15 BOM files and 10 board images through both and compared outputs — the reconciliation reports, alignment within a pixel, and identical classifications.

**Q: What did the browser-only choice cost you?**
**A:** No central audit log or shared calibration corpus across machines, an 8 MB WASM cold start, a single-machine performance ceiling, and no way to push a fix except re-distributing the file. I'd name those costs rather than pretend the choice was free.

**Q: What would you do differently?**
**A:** Compress the embedded libraries more aggressively — gzip could take the file toward 15 MB — and add the browser-compatibility check from the start instead of after encountering IE11.
