# Q95 — a time when you took a big risk and it failed

**Mapped LP(s):** Learn and Be Curious; Earn Trust; Bias for Action.

**Story used:** BGSW PCB Inspector Suite — the **single-file, base64-embedded standalone build and its 25MB distribution failure** (`AMAZON_INTERVIEW_PREPARATION.md` STORY 4, "The Standalone HTML That Replaced a Server": Result line 423, Reflection line 429). Single telling only. **Distinct from Q7** (which owns the IE11/WebAssembly compatibility miss as "a time you failed") and **Q88** (negative feedback that was my fault): here the failed bet is the *size/distribution assumption* of the embedding approach, not the browser-capability miss — the IE11 event is deliberately not retold or blended. The conflicting 150MB standalone telling in `AMAZON_INTERVIEW_PREP.md` STORY 7 is also excluded.

## Answer (core, ~430 words)

The risk I'll give you is one where I made the bet, it half-failed, and the failure was in an assumption I never checked.

The setup: the PCB inspection tools had to run on factory-floor machines with no internet, no installs, and limited IT. That killed the server plan. So I made a calculated bet — build the whole thing as one self-contained HTML file, with every library embedded directly as base64 so there'd be no CDN, no separate files, nothing to break: OpenCV.js at about 8MB as a base64 WebAssembly module, TensorFlow.js about 3MB, PDF.js about 1MB, XLSX.js about 500KB — roughly 12.5MB of libraries total. A single file you double-click. I moved fast on it because it unblocked the users, and the upside was real: no installs, no server, no IT ticket.

Here's how it failed. Base64 encoding inflates a payload by about a third, so ~12.5MB of libraries became a standalone file of roughly 25MB. It worked — on a modern browser it loaded in about 5 seconds versus 2 for the server version, and everything functioned. But the distribution channel I'd picked broke. I was sending it to satellite engineers by email, and some email systems cap attachments at 20MB. The file exceeded that. So the very thing that made it *easy* to distribute — one file — was also the thing that made it *hard* to distribute at that size. I'd verified the file worked; I had not verified the channel could carry it. That's on me, and it's the same class of mistake as assuming the target environment instead of checking it.

What I did about it was bounded and honest. I distributed by USB drive as well as email, and I documented the file size and the minimum browser requirement so nobody hit a mystery. What I did *not* do — and I'll say it plainly — is fix the size. I identified the fix in reflection: compressing the embedded libraries more aggressively could have brought the file down to about 15MB, under the common limit. That was a projection I never implemented, so I don't claim it as a result.

What I learned: a calculated risk includes the delivery constraint, not just the artifact. I now verify the channel the same way I verify the target — attachment limits, storage quotas, the actual pipe — before I build around it. The bet was still worth making, because it's what put the tool on the locked-down machines. The miss was not checking the pipe first.

## Deep follow-ups (likely bar-raiser probes)

**Q: Was this really a failure, or just a trade-off?**
**A:** It was a partial failure of a specific bet. The bet was that one embedded HTML file would be an easy distribution channel; the file worked but at ~25MB it exceeded the 20MB attachment limits some email systems use — so the channel I planned on partly failed. The tool succeeded; the distribution assumption didn't.

**Q: Why did base64 make it so big?**
**A:** Base64 encoding inflates a binary payload by about a third. I was embedding roughly 12.5MB of libraries — OpenCV.js ~8MB, TensorFlow.js ~3MB, PDF.js ~1MB, XLSX.js ~500KB — and that became a ~25MB single file. The convenience of one file added about 33% overhead on top of the already-large libraries.

**Q: Why not just use a CDN or separate files?**
**A:** A CDN needs internet, which the factory floor machines don't have. Separate files reintroduce the failure mode where someone moves the HTML without its dependencies and the tool breaks. The single file eliminated that, which is why I took the size hit. It was a deliberate trade — I just didn't verify the size against the delivery channel.

**Q: The fix was to compress to ~15MB — why didn't you ship it?**
**A:** Because I identified it in reflection, after distribution, and it was a projection rather than a measured result. I'm not going to present something I didn't implement as if I did. What I did implement was the USB fallback and the documented requirement; the compression improvement is what I'd do next.

**Q: How is this different from the browser-compatibility failure on the same build?**
**A:** Different assumption, different failure. That one was a capability assumption — that the fleet ran modern browsers with WebAssembly. This one was a distribution assumption — that email could carry the file. Both trace to the same root habit of not verifying one of the deployment constraints, which is why the lesson generalizes to verifying the channel as well as the environment.

**Q: What would you do differently at the start?**
**A:** Check the delivery constraints before choosing the packaging — attachment limits, storage quotas, throughput. The risk calculation should include the pipe, not just the artifact. And I'd test the compressed build earlier, so size was a measured input to the architecture rather than an after-the-fact finding.
