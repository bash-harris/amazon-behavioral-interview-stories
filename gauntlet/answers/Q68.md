## Answer (core, ~450 words)

The process I introduced was a release process, not just a build script — and the reason it wasn't already in place is that the thing it governs didn't exist before.

The tools started life as a Flask application. In that world there was no artifact at all: deploying meant pointing an engineer at a URL, and the code was whatever was on the server. There was nothing to package, nothing to stamp, and nothing to hand across a network boundary — so there was no release discipline to miss. The standalone format changed that. It came from the customer environment, not from me: the manufacturing engineers worked on factory-floor machines with no internet, no installs, and limited IT, so the only format that survived was one self-contained HTML file they could double-click. That created, for the first time, a **distributed artifact** — and no process around it.

For a while I produced it by hand: concatenate the modules in the right order, inline the CSS and JS, base64-encode the libraries, verify the result. About thirty minutes per build, wrong roughly one time in five. The worst part is where it failed: a file inlined out of order or dropped entirely wouldn't break the build, it would break when an engineer opened the file on the floor — an environment I couldn't see. That's the real reason no process existed: the manual step worked often enough to hide the gap, until the failure rate made the artifact untrustworthy.

`compile_tool.py` is what I introduced — about two hundred lines, three stages: collect every HTML, CSS, JS, and library file; process each by type (CSS into style tags, JS into script tags, binaries base64-encoded); assemble the document. Three decisions were the actual process. First, a **manifest defines ordering** instead of trusting the filesystem, because CSS has to be inlined before the HTML that consumes it and utilities before business logic — ordering was the dominant failure mode, so I made it explicit data rather than a convention I had to remember. Second, the script **stamps the current git commit hash into the HTML title**, so a file in the field traces back to the exact build that produced it — that is the release-control part, and it's why an artifact that leaves the building is now auditable. Third, the compiled output is **gated by a test**: I open it, run the workflow, and compare its behavior against the server version using the suite of 15 BOMs. If it doesn't match, the compilation is rejected.

The result: compilation dropped from thirty minutes with roughly one failure in five to eight seconds with zero, and every standalone in the field is identifiable. It also scales — a fourth comparison tool is a one-line change to the manifest, with the existing tools untouched, because the design assumption is "one core, many views." I evaluated Webpack and CDN delivery and rejected both: Webpack is more machinery than a string-assembly step needs, and a CDN would cut the ~25 MB file to about 5 MB but need internet the factory floor doesn't have.

Why not already in place, honestly: the requirement was new, the manual process was tolerable until its failure rate became unacceptable, and on a solo project nobody owned release tooling. I built it when the pain became measurable. If I did it again I'd add a checksum and a diff mode so a silently changed build is caught.

## Deep follow-ups (likely bar-raiser probes)

**Q: Why wasn't this process already in place — was it just that nobody had built it?**
**A:** Two reasons, and only one is "nobody got to it." The real reason is that the requirement didn't exist: while the tool was a Flask server there was no artifact — you pointed at a URL. The standalone format was forced by the factory environment, and when that requirement appeared I shipped the first versions by hand because shipping the tool mattered more than tooling the build. The process lagged the requirement, and the one-in-five failure rate is what finally justified it.

**Q: What makes this a "process" and not just a script?**
**A:** Three things beyond automation: a manifest that defines ordering so correctness doesn't depend on the filesystem, a git commit hash embedded in the HTML title so a distributed file is traceable to its build, and a test gate against the server version so a bad compile can't ship. The script is the mechanism; the ordering rule, the stamp, and the gate are the process.

**Q: Why not a real build tool like Webpack?**
**A:** The logic is string manipulation — no module bundling, minification, or source maps needed. `compile_tool.py` is about two hundred lines and does exactly what the artifact requires. Webpack would have added config, plugins, and a learning curve for a step that runs once before deployment.

**Q: How do you know the compiled artifact is correct, not just fast?**
**A:** Speed wasn't the only acceptance criterion. I open the compiled HTML, run the workflow, and compare its behavior against the server version using the suite of 15 BOMs. If any check fails, the compilation is rejected. Correctness for the 15 representative BOMs is the release bar.

**Q: Why embed the libraries instead of loading them from a CDN?**
**A:** A CDN would drop the file from ~25 MB to about 5 MB, but the factory floor has no internet, so the artifact wouldn't run where it's actually used. Base64 embedding is a deliberate trade of file size for offline function. If those machines ever get network access, CDN delivery becomes the better choice.

**Q: Is this process scalable, or does it break when the product grows?**
**A:** It's manifest-driven, so it grows cleanly. Adding a fourth comparison tool means adding its files to the manifest — a one-line change — and the existing tools are untouched. The design assumption is "one core, many views," so the build scales with the number of views, not the amount of duplicated config.

**Q: What would you do differently?**
**A:** Add a checksum on the compiled output so corruption is caught by the tool, and a diff mode that compares two compilations so a silently changed build is visible. I named both in my own reflection; neither got built.
