# Q88 — a time where you got negative feedback and it was your fault

**Mapped LP(s):** Earn Trust (primary); Learn and Be Curious.

## Answer (core, ~450 words)

The negative feedback I earned was on my first BOM reconciliation tool, and it was entirely my fault — I shipped a matching rule built on an assumption I never tested. It made the tool flag correct boards as wrong.

The tool compares a board's Bill of Materials against its layout. I wrote a comparison that treated the component's pin count in the BOM and the number of pads in the layout as something that had to match. I had assumed pin count was a reliable signal that two references pointed at the same part. It isn't. A concrete case: the BOM lists an IC as "U1 (8-pin)," but the layout footprint has 16 pads. That's not an error — footprints are often drawn for multiple package variants, and the extra pads are unused or no-connect. My tool called it a mismatch. On boards with mixed component types I was generating false positives on parts that were perfectly fine — about a 12% false-positive rate.

The feedback came straight from the manufacturing engineers using it: they told me the report was flagging parts that were good. That is the worst feedback you can get on a QA tool, because every false alarm sends an engineer to hand-verify a pin count that was never wrong, and it taught them not to trust the report. They had started re-checking the tool's output by hand — the exact work the tool was supposed to remove. They were right, and I had no defense: this was my wrong assumption, not bad data and not a subtle upstream bug. I built a rule on a signal I had never validated, and I had only tested it on the boards I happened to have, none of which had the mixed-component-type cases that broke it.

So I owned it and went at the root cause. I pulled twenty BOMs that had pin-count discrepancies and categorized them: footprint larger than the component (almost always legitimate — package variants or no-connects), footprint smaller (a genuine mismatch — the part physically can't fit), and exact match. I changed the rule to follow those semantics instead of literal equality: more pads in the layout is a possible match, flagged for review; fewer pads is a definite mismatch. I added a component-type check so a difference within a configurable threshold — default 2:1 — is accepted only when the reference type agrees. And I built a debug endpoint that shows, per component, the BOM pin count, the layout pad count, whether the type matched, the ratio, and the tool's decision, so an engineer can see why it decided and override it.

The false-positive rate for boards with mixed component types dropped from about 12% to under 2%. Engineers stopped hand-verifying every pin count. The lasting lesson: I now treat a signal as a hypothesis until I've watched it fail across diverse samples, and I collect those samples from users before I write the rule. The deeper one is that pin count was never the right signal — reference designator plus footprint name is. You repair trust with a mistake like that by admitting it plainly and then shipping the fix and the transparency to prove it.

## Deep follow-ups (likely bar-raiser probes)

**Q: Was the feedback really "your fault," or was it bad test data?**
**A:** It was my fault. The data was fine — real footprints legitimately have more pads than the component populates. I wrote a rule on an unvalidated assumption and tested it only on the boards I had. That's a decision I made, so it's on me. I say that plainly rather than pointing at the input files.

**Q: How did you keep from getting defensive when they told you it was flagging good parts?**
**A:** There was nothing to defend — they were describing exactly the failure the tool was designed to prevent, and the false positives were reproducible. Defending the rule would have meant defending an assumption I already knew I hadn't tested. I asked for the failing cases instead.

**Q: Why didn't you just ignore pin count entirely?**
**A:** Because it catches genuine mismatches. If the BOM specifies a 16-pin IC and the layout shows an 8-pin footprint, that's real — the component physically won't fit. The fix was to be smarter about *when* pin count matters, not to drop it.

**Q: How did you pick the 2:1 threshold, and what's the risk?**
**A:** I analyzed the twenty failing BOMs and found legitimate footprint variations typically had a pad-to-component ratio of 2:1 or less, so I set the default to 2:1 and made it configurable. The risk is false negatives: a genuinely wrong component that happens to satisfy the ratio and shares a type letter could pass. The debug endpoint mitigates that — the engineer sees the ratio and type match and can override. It's a heuristic, not a proof.

**Q: What did you change about how you work?**
**A:** Two things. I collect representative files from the people who own the data before I write the rule, instead of discovering edge cases reactively. And I build the observability view from day one — the debug endpoint was the thing that let the engineers verify the tool on their own terms, and building it earlier would have surfaced the pin-count behavior during development.

**Q: What would you do differently, concretely?**
**A:** Same answer I gave on the failure: gather diverse samples from the floor before coding, and treat a matching signal as unproven until I've seen it hold across samples. If I'd done that, the mixed-component-type boards would have been in my first test set and the false positives would never have shipped.
