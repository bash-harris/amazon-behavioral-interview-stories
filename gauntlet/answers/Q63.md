# Q63 — describe a time you used data to make a recommendation, which requires you to explain your financial reasoning without necessarily building a valuation model on the spot

**Mapped LP(s):** Are Right, A Lot; Dive Deep; Customer Obsession.

**Story used:** BGSW PCB Inspector Suite — the recommendation of which AI engine to use for mismatch interpretation: the hosted GPT-4o VLM vs a purpose-trained custom classifier. Both data sets come from one document, `AMAZON_INTERVIEW_PREPARATION.md`: STORY 8 (VLM: ~85% on component/mismatch type, ~3 s per call, ~$0.01 per analysis; models benchmarked: GPT-4V ~8 s, Claude 3, Gemini Pro Vision) and STORY 3 (custom EfficientNetV2S classifier: 94% on 500 held-out images, 45 ms CPU inference, ~30-minute retrain, ~2,000 labeled images). **Honesty note, stated in the answer:** the domain is engineering QA, not finance; the "financial reasoning" here is a cost-benefit on operator time and per-call cost, not a valuation model.

## Answer (core, ~470 words)

Up front: the domain here is engineering QA, not finance, so I can't hand you a DCF — but the reasoning the question is really testing is the same one: gather the numbers, compare the options on cost and benefit, and put a recommendation behind it. I'll give you the recommendation I actually made and the trade-offs that decided it.

The problem first, because the problem sets the cost function. Our board-inspection tool flagged mismatches but couldn't say what they meant, so a manufacturing engineer had to zoom in and interpret each one — about thirty seconds each, and five to twenty of them per board. Two realistic ways to automate that step: train my own custom classifier, or use a hosted vision-language model.

So I gathered data on both, measured on the axes that actually decide the question — accuracy, latency, cost per unit, and maintenance burden. The custom model was the EfficientNetV2S classifier I had already trained for defect classification: 94% accuracy on a held-out set of 500 images, 45 milliseconds per inference on CPU, retrained in about 30 minutes — but it was built on roughly 2,000 labeled images, needed the two-phase training tuning, and would need a fresh labeled set and a retrain for every new defect type. The hosted model, GPT-4o, came in at about 85% on component and mismatch type, roughly three seconds per call, and about a cent per analysis — with no training data at all. Before committing I benchmarked the alternatives: GPT-4V was slower at about eight seconds, Claude 3's API was less mature at the time, and Gemini Pro Vision was weaker on small surface-mount parts.

The recommendation came from matching the tool to the job, not from which model was "best." For per-component pass/fail on the hot path, the classifier wins outright: lower latency, lower unit cost, and a verdict you can reproduce from a versioned model. But the actual task here was interpreting five to twenty flagged regions per board, with a human verifying the result and no labeled dataset for every defect type. There, the VLM won the cost-benefit: a cent per analysis — about ten cents for a ten-mismatch board — measured against the engineer's thirty seconds per region and the avoided labeling-and-training project.

So I recommended GPT-4o for the interpretation step, kept the deterministic four-signal comparison as the core, and refused to put the VLM on every component. The trade-offs I flagged with the recommendation: API cost, latency, and availability, plus the fact that you can't reproduce a hosted model's verdict six months later the way you can a versioned classifier — so the VLM output is labeled a suggestion with a confidence, not a diagnosis, and the tool degrades gracefully without it. If volume or privacy changed, the calculus flips, and I'd say so — that's the point of arguing from a cost model rather than a preference.

## Deep follow-ups (likely bar-raiser probes)

**Q: This isn't a finance question — why is it a fair answer?**
**A:** Because the question is really about reasoning from data to a recommendation under cost, and being honest about what you can and can't model. I can't build a valuation model for a QA tool, and I'd rather say that than fake one. What I can do is put a cost per analysis against the cost of the operator time it removes, and let that decide the recommendation — which is the same discipline a finance recommendation uses.

**Q: Give me the financial reasoning in one line.**
**A:** About one cent per analysis, so roughly ten cents for a ten-mismatch board, measured against roughly thirty seconds of engineer time per mismatch and the avoided labeling-and-training cost of a bespoke classifier. The recommendation went to whichever side of that ratio was cheaper for the task shape.

**Q: Your classifier scored 94% and the VLM only ~85% — didn't the classifier win?**
**A:** Different jobs. The classifier is trained for per-component pass/fail and wins there on accuracy, latency, cost, and auditability. The VLM's job was interpreting a small number of flagged regions with no labeled dataset per defect type, where ~85% as a human-verified first pass beat a labeling project. I'd choose the classifier for the hot path and did.

**Q: How did you decide not to put the model on every component?**
**A:** Cost, latency, and reproducibility. Per-component inference at board scale multiplies the cost and latency, and an audit trail matters in QA — you need to reproduce a verdict months later from the input, the model version, and the policy version. A hosted model behind a version you don't control doesn't give you that. So the deterministic comparison stays the core; the VLM stays on the uncertain, low-volume step.

**Q: What data would flip your recommendation?**
**A:** A labeled set per defect class would make retraining the classifier the better call, because it restores determinism and removes per-call cost. Higher volume, tighter cost pressure, or stricter data-privacy requirements all push the same way. The recommendation is a function of those inputs, not a fixed preference.

**Q: What's the risk you accepted and how did you bound it?**
**A:** The 15% of cases where image quality or component size defeats the model, and the API dependency itself. I bounded both by treating the output as a suggestion with a confidence that the engineer verifies, adding a correct/incorrect feedback loop to surface systematic errors, and keeping the tool fully functional when the API is unreachable. The VLM is an enhancement, not a dependency.
