# Q1 — tell me about a time you used genai to improve personal or team productivity

**Mapped LP(s):** Invent and Simplify (primary); touches Deliver Results and Learn and Be Curious.

**Story used:** BGSW PCB Inspector Suite — GPT-4o VLM inspection engine (`AMAZON_INTERVIEW_PREPARATION.md` STORY 8 "Adding an AI Eye to the Inspection"; same event as STORY 3 in `AMAZON_INTERVIEW_PREP.md`). Documented outcome: reduced manual inspection time from 30 seconds to about 5 seconds per mismatch.

## Answer (core, ~300–500 words)

Honestly, the biggest GenAI win wasn't flashy — it deleted a manual interpretation step from someone else's day. I built the PCB inspection suite at Bosch: browser tools that align a photo of a board to its CAD layout and flag components that don't match. The comparison pipeline was good at saying *where* a mismatch was — it highlighted regions in red — but it couldn't say *what* the mismatch meant. Is that a wrong-value resistor, a part rotated 180°, or just a reflection? The manufacturing engineer had to zoom in and decide, region by region. That manual step was the bottleneck.

So my task was to add an AI that could look at the flagged region and describe it: identify the component, classify the mismatch (wrong value, wrong orientation, missing, extra, or false alarm), and give a confidence. It had to come back in under five seconds, and it had to work in both the server build and the standalone build that runs offline.

I evaluated a few vision-language models before committing. GPT-4V was slow — about eight seconds per request versus three for GPT-4o. Claude 3 had strong visual understanding but a less mature API at the time. Gemini Pro Vision was fast but weaker at small-object detection, which matters because these are SMD parts. I chose GPT-4o and used it as the "expert eye," keeping my own effort on the preprocessing: crop the mismatch region from both the layout and the photo, send both to the model with a structured prompt, and parse a JSON reply with `component_type`, `mismatch_type`, `confidence`, and `description`.

The first prompt was a mistake. I wrote "describe what you see and compare it to the expected layout," and got verbose, inconsistent answers — sometimes about the background, sometimes the part. I rewrote it to force a fixed JSON schema and added examples for common mismatch types. That's when it became reliable.

The productivity change was direct. Manually inspecting a flagged mismatch took about thirty seconds; reading the model's structured verdict took about five. The engineers told me it helped them prioritize which mismatches to look at first, especially on dense boards — and I gave them a way to mark an analysis right or wrong so I could keep improving the prompt. One design choice mattered: the AI is an enhancement, not a dependency. If the API is unreachable, the four-signal comparison still runs offline and the engineer just does the manual check.

Reflection: my wrong assumption was that the model could read component values off the board. On small SMD parts the text is too small or blurry — it's much better at type and orientation. I also should have started with the simple structured prompt instead of the clever one. If I did it again I'd look harder at a self-hosted model like LLaVA to cut the per-call cost, but the factory machines don't have the GPU memory for it.

## Deep follow-ups (likely bar-raiser probes)

**Q: How do you know this improved productivity rather than just adding automation on top?**
**A:** The manual step was the whole cost. Every red region meant the engineer zoomed in and made a judgment call — about thirty seconds each. After, the model returned a labeled verdict in roughly five seconds and the engineer confirmed or corrected it. On a board with five to twenty flagged mismatches that's minutes back per board, and the engineers said it let them triage the dense boards first. The human still verifies, so it's assist-not-replace; the gain is that the engineer spends time on judgment instead of interpretation.

**Q: Why GPT-4o and not another model?**
**A:** I evaluated GPT-4V, Claude 3, and Gemini Pro Vision. GPT-4V was slower (about 8s vs 3s), Claude 3's API was less mature then, and Gemini Pro was weaker on small SMD parts. GPT-4o handled image and text in a single request, which simplified the integration. I also looked at a local model like LLaVA to avoid API cost, but it needs at least 8GB of VRAM and the factory machines don't have it, so I kept the API with the 4-signal pipeline as the offline fallback.

**Q: How did you handle the AI being wrong?**
**A:** It's presented as a suggestion, not a diagnosis. The UI labels it "AI Analysis" with a confidence percentage, and the engineer is expected to verify it. I added a feedback mechanism where they can mark analyses correct or incorrect, which surfaced systematic prompt errors. The AI analysis correctly identified the component type and mismatch type in about 85% of cases; the remaining 15% were images too poor in quality or components too small to analyze reliably.

**Q: Where did the design ideas come from, inside and outside the company?**
**A:** Outside: the model landscape — GPT-4o, GPT-4V, Claude 3, Gemini Pro Vision, plus a local option LLaVA — and the browser CV stack, OpenCV.js and TensorFlow.js, that already powered the tools. Inside: I sat in on the engineers' screen-sharing sessions before writing anything so the tool matched how they actually compared boards; the engineers' feedback that the AI helped them prioritize shaped the UI; and I walked the data-privacy question through the security team, who approved sending board photos to the API because they contain no trade secrets.

**Q: What happens when the API is down or slow?**
**A:** The VLM is an enhancement, not a core requirement. If the API is unreachable the comparison tool still works — it shows the visual highlights without the AI description, and the UI says "AI analysis unavailable — check API connection." I limited the region of interest to 512×512 and cached results for identical image pairs to keep latency down. Rate limits were a non-issue at five to twenty mismatches per board.

**Q: What would you do differently?**
**A:** Two things. I'd start with the simple structured prompt and iterate up, instead of over-engineering the first one — I lost time converging on it. And I'd design for cost and control from day one by evaluating a self-hosted VLM, since per-call API cost is non-trivial at scale, though that needs GPU hardware the factory floor doesn't have.
