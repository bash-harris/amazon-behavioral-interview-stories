# Q31 — tell me about a time when you had to finish a project quickly to meet a deadline

**Mapped LP(s):** Bias for Action (primary); Deliver Results.

**Story used:** BGSW PCB Inspector Suite — the standalone single-file build and the compiler that produced it (`AMAZON_INTERVIEW_PREPARATION.md` STORY 15 "Compiling a Full Stack into a Single File", with the artifact facts from STORY 4 "The Standalone HTML That Replaced a Server"). This is deliberately a different speed case from Q26 (the eight-week three-tool delivery) and from the five-day prototype (Q13/Q18/Q19): here the subject is the **build turnaround** — a 30-minute, error-prone manual packaging step replaced by an 8-second automated one so the final milestone could land inside the delivery window. STORY 15 was used only in passing in Q8 (for the solo/Think-Big angle), so it is the least-used documented speed case. One telling only: PREPARATION.md's ~25MB standalone and ~30-min→8s compile. The conflicting `AMAZON_INTERVIEW_PREP.md` STORY 7 telling (150MB file, "2–3 days → 5 min") is not used.

## Answer (core, ~450 words)

The deadline was the standalone build of the PCB inspection suite. The whole suite was on an eight-week delivery window, and the offline, single-file build was the last milestone — that was the weeks-seven-and-eight work. The threat to the date wasn't code; it was packaging. Turning the modular source into one self-contained HTML file was manual. I concatenated the files by hand, inlined the CSS and JavaScript, base64-encoded the libraries, and checked the result. That took about thirty minutes per build, and it broke roughly one time in five — usually because I inlined a file in the wrong order or missed one, and the standalone file would fail in ways that only showed up when a manufacturing engineer opened it.

That turnaround was the schedule risk. I was rebuilding the standalone file repeatedly as I fixed things across the suite, so thirty minutes a build at a one-in-five failure rate was both eating the calendar and shipping defects into the artifact.

So I stopped compiling by hand and wrote the compiler. `compile_tool.py` is about two hundred lines and does three things: collect every HTML, CSS, JS, and library file; process each by type — CSS into `<style>`, JS into `<script>` in dependency order, binaries base64-encoded; and assemble the final document. Two details mattered. Ordering: CSS has to be inlined before the HTML that uses it, and utility JavaScript before the business logic that calls it, so the script reads a manifest order rather than the filesystem's. And traceability: it stamps the current git commit hash into the HTML title, so I could tell which build a file in the field came from.

The result was a build that takes eight seconds and doesn't fail on ordering. The manual step was about thirty minutes with roughly one failure in five; the automated step is eight seconds with zero. The artifact it produces is unchanged — the same roughly 25MB single HTML, with libraries totaling about 12.5MB (OpenCV.js alone around 8MB), loading in about five seconds on a factory machine versus two on the server version, running the whole suite offline.

What I'd do differently is add a checksum on the compiled output and a diff mode between two compilations, so a corrupted or silently changed build gets caught by the tool instead of by me. The call I'd defend is deciding that a thirty-minute manual step repeated under a deadline was a schedule problem worth an hour of automation — the compiler paid for itself on the second build.

## Deep follow-ups (likely bar-raiser probes)

**Q: Was there a real deadline, or did you decide it was urgent?**
**A:** The eight-week delivery window is documented, and the standalone compilation was the weeks-seven-and-eight milestone. The compiler wasn't an external demand — I decided the manual turnaround was a risk worth removing to protect that date. I'll say that plainly rather than dress it as an imposed deadline.

**Q: Why not use a real build tool like Webpack?**
**A:** The logic is string manipulation — no module bundling, minification, or source maps needed. `compile_tool.py` is about two hundred lines and does exactly what the artifact requires. Webpack would add config, plugins, and a learning curve for a step that runs once before deployment.

**Q: Walk me through what the eight-second build actually does.**
**A:** Three stages: collect source files; process each by type (inline CSS in `<style>`, inline JS in `<script>` in dependency order, base64-encode the binary libraries, modify the OpenCV.js WASM loader to decode at runtime); then assemble the final HTML. It reads files from a manifest that defines the order, not the filesystem's natural order, which is what removed the ordering failures.

**Q: What's the worst case, and what did automation cost you?**
**A:** The bottleneck is reading and base64-encoding OpenCV.js at about 8MB; total build is about eight seconds on average and about twelve seconds worst case on a slow disk. The cost is trust in the automation — I no longer eyeball each inlining, which is exactly why I'd add a checksum and a diff mode.

**Q: How do you know the compiled artifact is correct and not just fast?**
**A:** A test harness runs the same 15 BOM files and 10 board images through both the server and standalone builds and compares reconciliation reports (must match exactly), alignment (within one pixel), and ML classifications (identical). Both Q8 and Q29 use that same harness, so the numbers are consistent across answers.

**Q: What would you do differently?**
**A:** Add checksums to verify the compiled output caught corruption, and a diff mode that compares two compilations to show what changed. I named both in the source reflection; neither was built.
