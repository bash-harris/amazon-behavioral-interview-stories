## Answer (core, ~470 words)

The project I'd point to is Tab Scroller, a Manifest V3 Chrome extension I built around a problem I was living with. I routinely keep a few hundred tabs open between work, interview prep, and paper reading, and the browser stops being usable — nothing is findable, and there's no way to resume a research session a day later. Chrome doesn't let an extension modify the native tab bar, so the whole thing had to live as an injected overlay. That constraint set the architecture.

I deliberately scoped it bigger than a tab manager. The goal was an AI research workspace: control your tabs in plain English, then turn a messy session into something reusable.

The hard part wasn't the UI — it was making the AI cheap and private. My first instinct was to send every command to a model, and that's wasteful; "close all the YouTube tabs" doesn't need an LLM. So I built a token-saving pipeline. Simple commands are matched by local rules and never touch the network. For everything else, a pre-filter narrows the tab set by domain category and keyword score before any extraction happens, extraction runs in parallel batches — ten tabs in about 523 ms — and page content is compressed into [Subject, Predicate, Object] triplets before it reaches the model. The model became the last hop, not the first. I supported two backends on purpose: cloud Gemini for quality, and local Ollama so privacy-sensitive users can keep everything on-machine. That range of inputs — two external model ecosystems, plus reading where the category was heading, from tab utilities toward AI workspaces — is what shaped the design. I also kept the extension framework-free, vanilla JS and CSS, rather than pulling in a UI framework that would slow the injected bar down.

Snoozing was the reliability problem worth solving. A dismissed tab has to return even if the browser restarts, so I used `chrome.alarms` on a one-minute tick and `chrome.storage.local` holding `{url, title, wakeTime}`; when the alarm passes the wake time it reopens the tab as an inactive background tab. I wrote it against a PRD and shipped it in three iterations — the alarm/storage engine, the message handler, then the context-menu UI — verifying each before moving on.

The result is a working extension where simple commands resolve locally in under 10 ms with zero API calls, deep extraction stays under a second, and a session can be condensed into a Markdown research brief with source-referenced Q&A and evidence capture. It's the second tool I've delivered this way — before it I shipped the Bosch PCB inspection suite solo — and the pattern I keep reusing is starting from the hardest constraint and letting it pick the architecture.

Honest reflection: I shipped the AI action layer without the guardrails I'd want. A wrong model call can close your tabs, and the fix — a confidence gate, transactional undo, and telemetry — is written up in my upgrade plan but not in the build. That's the piece I'd do first next time.

## Deep follow-ups (likely bar-raiser probes)

**Q: What was the hardest technical decision?**
**A:** Making the model the last hop instead of the first. The trade-off is more local logic to maintain, but it buys latency, cost, and privacy — and it's the reason simple commands can run offline.

**Q: Why support two models instead of one?**
**A:** Because the two serve different users. Gemini gives better reasoning for hard commands; Ollama lets someone who won't send tab data to a cloud still use the feature. I abstracted the call so the backend is a setting, not a rewrite.

**Q: How does snoozing survive a browser restart?**
**A:** State lives in `chrome.storage.local`, and `chrome.alarms` re-arms when the browser comes back, so the one-minute tick resumes and the tab still wakes. The tab is removed only after the storage write is confirmed.

**Q: What's the biggest weakness in the build?**
**A:** The AI action layer has no guardrails. A wrong model call can close tabs, and I don't have a confidence gate or undo in the shipped code — I have the design (a confidence score with auto/confirm/clarify thresholds and transactional undo) written up, but not implemented.

**Q: How would you extend it next?**
**A:** Implement the Canonical Command Plan: score confidence deterministically, auto-execute above 0.75, ask for confirmation from 0.4–0.74, and clarify below 0.4; make destructive actions undoable; and add telemetry for intent latency and failure rates.

**Q: What did you learn?**
**A:** Start from the constraint, not the feature list. The offline-friendly, rule-first design came from asking what the browser and the user's data actually require, not from what was easy to build.
